GitHub Copilot Quickstart

Install it, orient yourself, and make one useful change

Welcome. This is a practical setup session, not a feature tour. In the next 18 minutes we will get GitHub Copilot running in the standalone app, VS Code, and the terminal. Then we will use one repository to learn two habits that matter immediately: give Copilot precise context and verify every change. The next presenter will take you deeper into the Copilot app, so today we will stop after installation and a first safe session.

Before You Install

  • A GitHub account with Copilot Free or an assigned paid plan
  • Git and a small repository you are allowed to change
  • The latest Visual Studio Code
  • For managed accounts, ask your administrator to enable both the Copilot app and Copilot CLI policies
  • For the npm CLI route only: Node.js 22 or later

Quick check: Can you sign in at github.com and open the repository you will use?

Access is the most common setup blocker. A successful GitHub sign-in does not guarantee that an organization has assigned a Copilot seat or enabled every surface. The Copilot app and Copilot CLI have separate organization policies. Use a disposable sample repository if attendees do not have a safe project. Never make the first experiment in a production working tree with uncommitted work.
Install 1 of 3

GitHub Copilot App

  1. Open github.com/features/ai/github-app
  2. Download and run the installer for your platform
  3. Select Sign in to GitHub and complete authentication
  4. Add one local folder or clone one repository
  5. Start an Interactive session, then open Changes to review its diff

Stop there: installation and orientation only. The next presenter will explore app workflows in depth.

Budget two minutes. Show the download page, authentication, and the project picker. Point out Sessions and Changes, but resist opening My work, Automations, canvases, or parallel agent workflows. For a quick smoke test, use: "Suggest one small, low-risk improvement in this repository. Do not edit yet." This confirms that the app can read the project without consuming the next presenter's content.
Install 2 of 3

GitHub Copilot in VS Code

  1. Open Extensions with Ctrl+Shift+X or Cmd+Shift+X
  2. Search for GitHub Copilot by GitHub and select Install
  3. Select the Copilot icon and Sign in to GitHub
  4. Authorize the browser prompt, then return to VS Code
  5. Open Copilot Chat and confirm you can select Ask, Plan, or Agent

Verify: ask, "What language and test framework does this repository use?"

Budget two minutes. Current VS Code releases may already include the extension, so many attendees only need to sign in. Verify the publisher is GitHub. Explain the three modes in one sentence each: Ask explains without changing files, Plan proposes an approach before implementation, and Agent can edit files and run tools. We will use Ask first because it is the safest way to confirm context.
Install 3 of 3

GitHub Copilot CLI

# Windows
winget install GitHub.Copilot

# macOS or Linux
brew install --cask copilot-cli

# Any platform with Node.js 22+
npm install -g @github/copilot

# Verify and launch
copilot --version
copilot

On first launch, trust only a folder you recognize. Use /login if authentication is required.

Budget three minutes. Demonstrate one native package route rather than typing all three. The old gh copilot extension is retired; the current standalone command is copilot. Launch it from the sample repository, discuss the folder trust prompt, and sign in if needed. Trust means the repository may influence the session and the tools it requests, so do not approve an unfamiliar directory automatically.

One Copilot, Three Work Surfaces

SurfaceReach for it when...Start safely with...
VS CodeYou are already reading or editing codeAsk about selected code or an open file
CLIThe workflow starts with commands, logs, tests, or GitInspect first; approve tools deliberately
Copilot appYou want a dedicated workspace for agent sessionsInteractive mode and a low-risk task

Rule of thumb: choose the surface closest to the evidence you need.

Do not frame these as competing products. The task should determine the surface. Editor context is strongest when the developer is looking at code. The terminal is natural when the evidence is command output or repository state. The app provides a dedicated agent workspace, which the next presenter will cover. The developer remains responsible for scope, permissions, and the final diff in every surface.

2. the behavior this file owns, and

Do not edit anything yet.
  • In VS Code, select code or attach the relevant files
  • In the CLI, reference a file with @path/to/file
Budget three minutes. Run this in Ask mode in VS Code. The practical lesson is that good context is selected, not dumped. Name the evidence that should constrain the answer and specify that no edit is wanted yet. Ask one follow-up such as, "Which test proves that?" If Copilot cannot cite the repository evidence, do not move to implementation.
Demo 2

Tip: Plan, Change, Verify

Plan a small improvement to the validation error message.
Keep behavior unchanged except for the message.

Before editing:
- name the files you expect to touch,
- identify the smallest relevant test.

After editing:
- run that test,
- summarize the diff and any remaining risk.

Review sequence: plan → permissions → diff → test output → your judgment

Budget four minutes. Run this from Copilot CLI in standard or plan mode. Use a real low-risk issue from the sample repository, not a fabricated production change. Pause when Copilot requests permission and explain why the command is or is not appropriate. At the end, inspect git diff yourself and compare it with Copilot's summary. A confident summary is not verification; test output and human review are.

Four Habits for Day One

Scope it

Ask for one bounded outcome and state what must not change.

Ground it

Attach the files, errors, tests, or documentation that matter.

Inspect it

Review requested permissions, commands, and every diff.

Prove it

Run the smallest useful check, then broaden validation when risk warrants it.

Never paste secrets, tokens, customer data, or content your organization forbids.

These four habits transfer across all three surfaces. Scope prevents the agent from solving a larger problem than intended. Grounding reduces guesses. Inspection keeps authority with the developer. Proof turns a plausible answer into evidence. Remind attendees that organizational data-handling rules still apply even when the tool is approved.

Your First-Day Checklist

  • Sign in and verify access in the app, VS Code, and CLI
  • Use one safe repository across all three surfaces
  • Ask Copilot to explain a file and cite the evidence it used
  • Make one bounded change with an explicit verification step
  • Review the diff yourself before you keep or share it
