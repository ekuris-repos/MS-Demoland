Advanced Software Engineering with GitHub Copilot

Agentic workflows, best practices, and emerging capabilities

This session treats Copilot as part of a software delivery system, not just a code generator. We will follow one change from issue to pull request, assign clear responsibilities to people and agents, and examine where parallel work helps or creates risk. The goal is a workflow your engineering teams can apply with confidence.

Our End-to-End Scenario

Add organization-level audit export to a mature, security-sensitive service.

  • The issue defines user outcomes, constraints, and acceptance criteria
  • The repository contains multiple services, shared libraries, and deployment policy
  • The change requires implementation, tests, documentation, security review, and a pull request
  • A human engineer owns architecture, evidence, approval, and integration
A realistic scenario gives every practice a purpose. Audit export sounds contained, but it crosses authorization, data handling, performance, documentation, and deployment boundaries. That makes it useful for testing whether an agentic workflow can preserve engineering intent instead of merely producing plausible code.

Part 1

From AI-Assisted Coding to an Agentic SDLC

We begin by changing the unit of work. Suggestions help with the line in front of us. An agentic workflow coordinates a bounded engineering outcome across planning, editing, validation, and review. That broader scope creates leverage, but it also makes responsibility and evidence more important.

Three Levels of Assistance

ModeTypical scopeDeveloper role
SuggestionComplete or transform nearby codeDirect every edit
AgentComplete a bounded task using toolsSet constraints and validate
Agentic workflowCoordinate multiple engineering responsibilitiesDesign the system and approve outcomes
These modes are complementary. A developer may use completions while shaping an API, ask an agent to implement one bounded change, and use a larger workflow to coordinate tests and review. The level of autonomy should follow task clarity, repository maturity, and the cost of a wrong decision.

The Agentic Delivery Loop

graph LR
  A[Issue] --> B[Plan]
  B --> C[Implement]
  C --> D[Test]
  D --> E[Review]
  E --> F[Pull request]
  F --> G{Human approval}
  G -->|Revise| B
  G -->|Approve| H[Integrate]
The loop matters more than any single model response. Each stage creates an artifact that the next stage can inspect: a plan, a diff, test evidence, review findings, and finally a pull request. Human approval is not ceremonial. It is the point where evidence is weighed against architecture, risk, and business intent.

Start With an Executable Specification

Intent

User outcome, non-goals, and affected system boundary.

Evidence

Acceptance criteria, required tests, and observable behavior.

Agents amplify ambiguity as efficiently as they amplify clarity. A good issue says what must become true and what must remain unchanged. For our audit export, that includes who may export, which records are included, how sensitive fields are handled, and which tests prove the contract.

Human Responsibility Does Not Move

ResponsibilityAgent contributionHuman accountability
ArchitectureSurface options and dependenciesSelect boundaries and tradeoffs
CorrectnessGenerate and run checksJudge whether evidence is sufficient
SecurityIdentify patterns and findingsAccept risk and approve controls
IntegrationPrepare a reviewable pull requestApprove and merge
Delegation moves work, not accountability. The agent can search broadly, propose alternatives, and produce evidence. The engineer still understands the system's obligations and decides whether the result belongs in production. That distinction should be explicit in policy and visible in the workflow.

Choose Autonomy by Risk

Task shapeRecommended autonomyCheckpoint
Local, reversible, well testedImplement and validateDiff review
Cross-module with clear contractPlan, then implementPlan and PR review
Security, data, or architecture changeResearch and proposeHuman decision before editing
Autonomy is a design variable. Reversible work with strong automated checks can move quickly. A permission model or data-retention change deserves an earlier checkpoint because tests cannot decide the policy for us. Use the cost of error and quality of feedback to set the boundary.
Part 2

Engineering Repository Context for Reliable Agent Behavior

Reliable behavior starts before the prompt. The repository should explain how work is done, which boundaries matter, and what must pass before a change is complete. This turns institutional knowledge into context that both people and agents can use.

Context Has Layers

graph TD
  A[Organization policy] --> B[Repository instructions]
  B --> C[Path-specific instructions]
  C --> D[Task specification]
  D --> E[Current code and tests]
  E --> F[Tool output]
A prompt is only one layer of context. Stable rules belong close to the code so they do not depend on a developer remembering to paste them. The task adds change-specific intent, while the current code and tool output provide the evidence needed to act safely.

Context Has a Sweet Spot

More context is not automatically better. The goal is enough relevant evidence to act without burying the task.

Context starvation
Relevant and sufficient
Context overload
Too little
Missing constraints force assumptions and repeated discovery.
Sweet spot
Task, applicable rules, current code, and decisive evidence.
Too much
Stale history and irrelevant detail compete with the real signal.
Context starvation occurs when the agent lacks the requirements, constraints, code, or evidence needed to decide safely. It then has to guess or spend time rediscovering the task. Context overload is the opposite failure: a large session contains stale plans, abandoned approaches, unrelated output, and repeated discussion that compete for attention. The green center is not a fixed token count. It is the smallest set of current, relevant, authoritative information that supports the next decision.

Context Poisoning Reinforces a False Premise

graph LR
  A[Early reasoning mistake] --> B[Work continues from it]
  B --> C[Mistake is repeated in plans and output]
  C --> D[Agent treats it as important context]
  D --> E[Later answers preserve the false premise]

Reset the context boundary

Start a new session when changing tasks, abandoning an approach, or debugging faulty AI reasoning. Bring forward only the verified facts, current objective, and relevant evidence.

Context poisoning does not mean the model was retrained by the conversation. It means a plausible mistake entered the active context and subsequent work repeatedly treated it as true. Repetition, recency, and dependencies built on that mistake can make it look like an important established premise. Continuing to argue with the mistake in the same session may add even more references to it. When the task changes, an approach is abandoned, or AI-generated logic itself needs debugging, start a clean session. State the corrected objective and provide verified evidence without carrying forward the faulty reasoning trail.

Make Reliable Context a Repository Property

Shared instructions

Keep architecture boundaries, dependency policy, and required checks at the repository root.

Local instructions

Place service, test, and documentation conventions near the files where they apply.

Task context

Provide the current objective, acceptance criteria, constraints, and authoritative decisions.

Evidence of done

Require build, test, lint, security, compatibility, and risk results with the change.

Stable context should not depend on developers remembering what to paste into every conversation. Put shared rules at the repository root and specialized guidance near the relevant code. Keep task-specific intent in the issue or plan, then require verifiable evidence before the work is considered complete. This structure supplies the green-zone context while reducing both starvation and irrelevant conversational history.
Part 3

Custom Agents as Reusable Engineering Roles

Repository instructions define the environment. Custom agents define reusable roles within it. A useful role has a narrow purpose, appropriate tools, a clear output contract, and an explicit point where its responsibility ends.

Specialize Around Responsibilities

AgentPrimary outputShould not own
PlannerChange plan and dependency mapProduction edits
ImplementerFocused code changeFinal approval
TesterRisk-based tests and resultsChanging requirements
ReviewerPrioritized findingsDefending the implementation
DocumenterAccurate user and operator guidanceInventing behavior
Role separation reduces self-confirmation. The implementer is naturally biased toward the path it chose. A tester or reviewer with a different mandate can challenge assumptions and inspect failure modes. The human remains responsible for resolving disagreement and ensuring the roles cover the actual risk.

The Custom Agent Contract

  • Purpose: the engineering responsibility this role performs
  • Scope: files, systems, and decisions it may touch
  • Inputs: required issue, plan, diff, or evidence
  • Tools: only the capabilities needed for the role
  • Output: a predictable artifact another role can consume
  • Stop conditions: ambiguity, risk, or failure that requires escalation
Treat an agent definition like an internal API. Vague inputs and outputs force every caller to reinterpret the role. A strong contract makes handoffs inspectable and gives the agent permission to stop when the task crosses a boundary it should not decide.

Scope Tools and MCP Access Deliberately

RoleLikely accessRestrict by default
PlannerRead, search, issue contextWrite and deployment
ImplementerEdit, build, focused testsProduction systems
Security reviewerRead, scan results, policy sourcesSilent remediation
DocumenterRead behavior, edit docs, link checksApplication changes
Tool access is part of the control design. MCP can connect an agent to valuable systems, but access should follow the role's purpose and data classification. A planning agent rarely needs deployment credentials, and a reviewer should not quietly rewrite the code it is evaluating.

Choose Models by Workload

Optimize capability

Use deeper reasoning for architecture, ambiguous failures, and cross-system review.

Optimize efficiency

Use faster models for classification, formatting, focused edits, and routine checks.

A role does not automatically require the largest model. Match the model to ambiguity, context size, and consequence. Teams should evaluate quality and cost on their own tasks, because model labels alone do not tell us which option produces the least rework.

When Custom Agents Add Value

SignalSpecializeKeep one general agent
Workflow repeats across teamsYesNo
Distinct tools or permissions applyYesNo
Independent review is valuableYesNo
Small, local, low-risk taskNoYes
Roles merely rephrase one anotherNoYes
Specialization has overhead: definitions, handoffs, context, and reconciliation. Add a role when it creates a meaningful boundary or reusable capability. If five agents all read the same prompt and produce similar prose, we have multiplied activity without improving the engineering decision.
Part 4

Sub-Agent Orchestration and Parallel Engineering Work

This is where agentic workflows become more sophisticated. We will decompose the audit export into responsibilities, isolate context, run truly independent work in parallel, and control the points where outputs must converge.

Decompose by Dependency, Not File Count

  • Find the decisions that other work depends on
  • Separate research from changes that mutate the repository
  • Group tightly coupled edits under one owner
  • Identify outputs that can be validated independently
  • Define the integration order before parallel work begins
Splitting ten files among ten agents is not decomposition. If those files share an API decision, parallel editing creates churn. Start with the dependency graph: authorization and export format may need agreement first, while test discovery and documentation impact analysis can proceed independently.

Orchestration Pattern for the Scenario

graph TD
  A[Human owner] --> B[Planner]
  B --> C[Implementation task]
  B --> D[Test strategy]
  B --> E[Security analysis]
  B --> F[Documentation impact]
  C --> G[Consolidator]
  D --> G
  E --> G
  F --> G
  G --> H[Human review]
The planner produces shared boundaries, then specialized roles work from that contract. The consolidator does not simply concatenate outputs. It checks for contradictions, missing evidence, and assumptions that changed during implementation. The human reviews the integrated result and decides what moves forward.

Build a Task Graph

TaskDepends onCan run with
Confirm API and authorizationIssue and repository contextExisting-test discovery
Implement export endpointAPI decisionDocumentation draft
Add integration testsAPI decision and test strategySecurity review
Consolidate and validateAll change-producing tasksNone
A task graph makes parallelism explicit instead of optimistic. Work may run together only when it does not depend on an unsettled output or modify the same contract. This is the simplest way to answer DocuSign's question about parallel sub-agents without creating conflicting changes.

Parallelize Independent Work

Good candidates

Repository research, test discovery, threat analysis, docs impact, and independent review.

Poor candidates

Competing API designs, overlapping edits, sequential migrations, and shared generated artifacts.

Parallelism should reduce elapsed time without increasing reconciliation cost. Read-only analysis is often a strong first candidate because agents cannot collide in the working tree. Parallel implementation is more valuable when ownership boundaries and interfaces are already stable.

Isolate Context on Purpose

  • Give each sub-agent only the task, constraints, and artifacts it needs
  • Preserve a shared source of truth for decisions and acceptance criteria
  • Avoid passing unverified conclusions as established facts
  • Return concise findings with file references and confidence
  • Keep sensitive data outside contexts that do not require it
Context isolation improves focus and can reduce cost, but it must not create separate realities. Every role should inherit the same approved decisions and acceptance criteria. Findings should distinguish observed evidence from inference so the next role knows what it can safely trust.

Use Structured Handoffs

Outcome: What was completed
Decisions: Choices made and why
Changes: Files or contracts affected
Evidence: Commands, tests, and results
Risks: Known gaps or uncertainty
Next: Required dependent work
A handoff is an engineering artifact, not a status message. This structure gives the next agent or reviewer enough information to continue without replaying the entire session. It also exposes weak work quickly: if there is no evidence or the decisions are unclear, the task is not ready to hand off.

Manage Conflicting Outputs

graph LR
  A[Collect outputs] --> B{Same contract?}
  B -->|No| C[Human decision]
  B -->|Yes| D{Evidence agrees?}
  D -->|No| E[Targeted validation]
  D -->|Yes| F[Integrate]
  C --> G[Update shared decision]
  E --> G
  G --> F
Conflicts are useful signals. Two agents may have discovered an ambiguous requirement or inconsistent repository behavior. Do not resolve disagreement by majority vote. Identify the contested contract, run the smallest discriminating check, and bring policy or architecture decisions back to the human owner.

Control Shared-State Risk

RiskControlIntegration rule
Overlapping editsAssign ownership by boundaryOne change owner
Stale assumptionsVersion the plan and decisionsRebase context before work
Generated-file collisionsGenerate once after source mergeSingle final command
Test interferenceUse isolated environmentsRun full validation after combine
Most parallel failures are shared-state failures. Boundaries, versioned decisions, and isolated environments are more important than clever prompting. Even when each task passes independently, the consolidated branch still needs full validation because interaction defects only appear after the pieces meet.

The Orchestrator's Definition of Done

  • Every delegated task has a completed or explicitly deferred outcome
  • Conflicting decisions are resolved against evidence or human judgment
  • Combined changes satisfy repository instructions and acceptance criteria
  • Integration checks run on the consolidated result
  • The final summary preserves risks, provenance, and review needs
The orchestrator owns coherence, not merely completion. Five green subtasks can still produce one broken change if they implement different assumptions. The final artifact must tell the reviewer what changed, how it was verified, where uncertainty remains, and which human decisions shaped the result.
Part 5

Agent-Assisted Implementation and Multi-Perspective Review

Now we move from the plan into a proposed code change. The core pattern is separation: implementation creates the change, tests challenge behavior, reviewers inspect different risk dimensions, and a human consolidates the evidence before approval.

Issue to Proposed Change

sequenceDiagram
  participant H as Human
  participant P as Planner
  participant I as Implementer
  participant T as Tester
  H->>P: Issue and constraints
  P-->>H: Plan and decisions
  H->>I: Approved plan
  I-->>T: Diff and assumptions
  T-->>H: Results and gaps
The human checkpoint after planning is important for a cross-cutting change. Once the plan is approved, the implementer works within a defined boundary and exposes assumptions to the tester. The tester evaluates the behavior rather than inheriting the implementer's confidence.

Keep Implementation Focused

  • Confirm the controlling code path before editing
  • Make the smallest change that satisfies the approved contract
  • Preserve unrelated behavior and public APIs
  • Validate after each meaningful change
  • Report assumptions, tradeoffs, and evidence with the diff
Agentic does not mean broad. Small, validated steps produce better evidence and make review easier. If implementation discovers that the approved plan does not match the code, the right action is to stop and update the decision, not improvise a larger architecture change.

Separate Testing From Implementation

PerspectiveQuestionEvidence
AcceptanceDoes the feature meet the issue?Behavioral tests
RegressionWhat existing behavior could break?Focused and suite results
FailureHow does it behave under invalid input or dependency failure?Negative tests
OperationalCan we observe and support it?Logs, metrics, and runbook checks
Tests generated alongside implementation often mirror the same assumptions. A separate testing role can begin from acceptance criteria and risk, then look for what the implementation did not anticipate. Independence matters most at boundaries such as authorization, retries, and data filtering.

Review Through Four Lenses

Security

Can the change expose data or expand access?

Examine authorization, tenant boundaries, input handling, secrets, and auditability.

Correctness

Does every path honor the intended contract?

Examine requirements, edge cases, state changes, errors, and regression behavior.

Performance

Will the design remain efficient at production scale?

Examine query patterns, memory, concurrency, latency, limits, and failure recovery.

Maintainability

Can the owning team understand and evolve it safely?

Examine complexity, cohesion, duplication, tests, documentation, and ownership.

One generic “review this code” prompt tends to produce a shallow mixture of concerns. Security asks whether the export crosses an authorization or tenant boundary. Correctness traces expected and failure paths against the contract. Performance tests assumptions about data volume and concurrency. Maintainability considers whether the owning team can support and change the implementation without creating fragile coupling. Separate findings make each risk easier to evaluate and resolve.

Consolidate Findings Before Approval

PriorityMeaningRequired response
BlockingCorrectness, security, or contract failureFix and revalidate
ImportantMaterial maintainability or operational riskFix or document decision
AdvisoryOptional improvement with limited riskConsider separately
ConflictReviewers disagree on a requirement or tradeoffHuman adjudication
Consolidation removes duplicates, tests findings against the actual diff, and makes disagreement visible. A human should not receive four unranked reports and be expected to infer the decision. The result should state which issues block approval, which tradeoffs were accepted, and what evidence changed.
Part 6

Asynchronous Development, Guardrails, and Safe Integration

Longer-running tasks can continue asynchronously while engineers focus elsewhere. That changes the interaction model, but not the integration standard. Isolated environments, automated checks, protected branches, and human review create the boundary between delegated work and trusted production code.

Bounded Work Is an Engineering Requirement

Developers should send ambiguous work back for clarification before assigning it to an agent.

Project management defines

The outcome, priority, acceptance criteria, non-goals, dependencies, and business constraints.

Engineering validates

The system boundary, architecture constraints, repository context, required evidence, risks, and escalation path.

Push back when: scope is open-ended, success is subjective, dependencies are unresolved, or the task requires an unmade product or architecture decision.

Successful AI coding begins with work that is ready for engineering, not merely work that has been named. Developers have to push back constructively when a request lacks boundaries or asks the agent to make a product decision by inference. That pushback is not resistance to delivery. It protects delivery by turning intent into acceptance criteria, non-goals, constraints, and evidence. Once project management defines the desired outcome, engineering can validate that the task fits a coherent system boundary and can return as a reviewable pull request. If those conditions are missing, clarify the work before increasing autonomy.

Isolation Is a Safety Control

graph LR
  A[Issue] --> B[Isolated environment]
  B --> C[Agent changes]
  C --> D[Build and tests]
  D --> E[Pull request]
  E --> F[Protected branch]
  F --> G[Human approval]
Isolation limits blast radius and makes the work reproducible. The agent should operate with the minimum credentials and network access needed for the task. Nothing about successful execution in that environment grants permission to bypass the protected integration path.

Required Validation Gates

GatePurposeFailure response
Build and type checkStructural validityRepair before review
Focused and regression testsBehavioral evidenceInvestigate and rerun
Lint and formattingRepository consistencyApply approved tooling
Security and dependency checksKnown risk detectionResolve or formally accept
PR policy checksGovernance and ownershipBlock integration
Automated checks are evidence, not approval. They catch known classes of failure and enforce repeatable policy. The pull request should make failures visible, and the workflow should never weaken a gate merely to complete an agent task successfully.

Safe Integration Requires Independent Authority

  • Agents propose changes through normal branches and pull requests
  • Branch protection requires checks and appropriate reviewers
  • CODEOWNERS routes sensitive areas to accountable teams
  • Secrets and production deployment permissions remain restricted
  • A human with authority approves the final integration decision
The same actor should not write, validate, approve, and deploy a sensitive change without independent control. Existing software supply-chain practices remain relevant. Agent identity and activity should be auditable, but the most important boundary is still who has authority to integrate and release.

What's New, Emerging Capabilities, and Roadmap

This section summarizes customer-relevant GitHub Copilot updates current as of August 12, 2026. The releases show Copilot expanding from individual assistance into a portable, governed agent platform across the editor, terminal, GitHub, and enterprise management surfaces. Preview capabilities and directional themes are labeled separately from generally available features.

Agent Plugins 1.0: Build Once, Use Across Tools

Generally available in VS Code, Copilot CLI, the Copilot SDK, and the Copilot app.

Portable specialization

One installable package can carry skills and MCP server configuration across compatible agent clients.

Copilot-specific agents, commands, rules, and hooks remain available through a namespaced package.

Enterprise governance

Managed settings can install or block plugins and control approved marketplaces across supported Copilot surfaces.

MCP allowlists add control over the servers a plugin may introduce.

Agent Plugins 1.0 addresses a practical scaling problem: teams no longer need a separate package for every agent client. A platform team can combine a deployment skill with its MCP integration, publish it once, and make it available across supported tools. Business and Enterprise customers can govern plugin installation and marketplaces through existing managed settings, while MCP allowlists control the connected servers.

Cloud Agent and CLI: Broader Delegation

Research before code

Copilot cloud agent can research a repository, propose a plan, iterate on a branch, and open a pull request when the change is ready.

Reasoning controls

Customers can select supported models and reasoning levels for cloud-agent tasks, balancing depth against token consumption.

CLI plan and automation

Copilot CLI supports interactive planning, programmatic prompts, GitHub operations, custom agents, skills, hooks, and MCP tools.

Sandboxed parallel work

Local and cloud CLI sandboxes are in public preview. Cloud sessions can preserve state and run multiple isolated tasks in parallel.

Delegation now spans GitHub and the terminal. Cloud agent supports repository research and planning before a pull request, while model and reasoning controls let teams match effort to task complexity. Copilot CLI adds plan mode, programmatic execution, customization, and GitHub operations. Local and cloud sandboxes are public preview capabilities; cloud sandboxes are especially relevant to parallel work because each task can run in an isolated, persistent environment.

Review, Governance, and Visibility Are Expanding

Review effort levels

Lite and Balanced are generally available, with organization defaults and per-review selection based on risk.

Agentic remediation

Reviews can use full project context. Passing suggestions to cloud agent for a remediation pull request is in public preview.

MCP allowlists

Enterprise managed settings can allow or deny MCP servers across VS Code, Copilot CLI, and the Copilot app.

Agent-level metrics

The usage metrics API can report job starts and sessions by recognized agent app for adoption comparisons.

The enterprise story is growing alongside agent capability. Review effort levels are generally available, so routine and sensitive changes can receive different analysis depth. Agentic review gathers broader project context, and delegated remediation is in public preview. MCP allowlists provide a fail-closed governance control for connected servers. Agent-level usage metrics help leaders compare adoption across Copilot and partner agents instead of treating all activity as one bucket.

Roadmap Direction: Managed Agentic Delivery

Portable specialization

Agents, skills, hooks, and MCP integrations move consistently across developer surfaces.

Concurrent execution

Isolated cloud work makes multiple delegated tasks practical without sharing local state.

Directional view: these themes reflect current releases and previews, not commitments to unannounced features or delivery dates.

The direction visible across these releases is a managed agentic delivery platform. Specialization is becoming portable, execution is moving into isolated and concurrent environments, context is becoming richer and more persistent, and enterprise controls are becoming more granular and measurable. This is the roadmap signal customers can use for planning. It does not imply a commitment to any unannounced feature or date, and preview capabilities should still be evaluated against current limitations.
Part 8

Best Practices, Recommendations, and Q&A

We will close by turning the patterns into an adoption sequence and a scorecard. The objective is controlled learning: start where the workflow is valuable and measurable, then increase specialization and parallelism only when the evidence supports it.

A Practical Adoption Scorecard

MeasureQuestionWatch for
QualityDid escaped defects or security findings change?Faster output with weaker outcomes
Cycle timeDid issue-to-approved-PR time improve?Local speed with integration delay
ReworkHow often were plans or changes substantially redone?Ambiguous context or poor boundaries
Review burdenDid human review time and finding quality change?More generated noise
AdoptionWhich high-value workflows repeat successfully?Usage without durable value
Begin with one or two high-value workflows, establish reliable repository context, and assign narrow responsibilities. Parallelize only independent work and retain human review. These measures tell us whether the system improves delivery as a whole instead of merely increasing the volume of generated activity.
