Part 1

What Is GitHub Copilot?

Let's start at the beginning. What exactly is GitHub Copilot?

Your AI Pair Programmer

  • GitHub Copilot is an AI-powered code assistant that lives inside your editor
  • Powered by a catalog of large language models from OpenAI, Anthropic, Google, and more; available choices depend on your plan and policy
  • Suggests whole lines, entire functions, tests, documentation, and even terminal commands
  • Works in VS Code, JetBrains IDEs, Neovim, Visual Studio, and github.com
Think of GitHub Copilot as an AI pair programmer in the tools you already use. It can suggest code, explain a function, and help you build tests. A catalog of models from providers such as OpenAI, Anthropic, and Google supports different tasks. Your actual choices depend on the plan, organization policy, and feature you're using; some accounts use Auto rather than a list of individual chat models. We'll explore that picker later. Copilot also works in editors such as Visual Studio, JetBrains IDEs, and Neovim, and on github.com, but they don't all expose the same features. We'll stay with VS Code so you can practice one coherent workflow.

How Copilot Works

  • Context gathering - Copilot reads your open file, neighboring tabs, comments, and function signatures
  • Model inference - Sends relevant context to the applicable model service; chat and inline suggestions have separate model choices
  • Suggestion delivery - Returns completions as grey "ghost text" in your editor, or full answers in chat
  • Know your data policy - Business and Enterprise data is not used to train models; retention and processing depend on the feature, model, and policy
graph LR

  B --> C[Applicable Model Service]
  C --> D[Suggestion Returned]
  D --> E{Accept?}
  E -->|Tab| F[Code Inserted]
  E -->|Esc| A
Copilot first gathers relevant context, such as nearby code, comments, and related files. It then requests a suggestion from the applicable model service. The model you choose for chat is separate from the model used for inline suggestions. Models can run on GitHub's or a provider's infrastructure, so we shouldn't picture every request going to one identical backend. The response appears as ghost text or a chat answer. For project questions, Copilot can search and read relevant files; that doesn't mean the entire project is included in every request. Here's the important privacy distinction: business data is not used to train models, but that is not the same as a universal promise of zero retention. Processing, caching, and retention can vary by feature and model. Before sending work code, check your organization's policy and GitHub's current model-hosting documentation.

Part 3

Inline Completions

Now we're getting to the good stuff. Inline completions are the feature most developers encounter first, and for many people, it's the moment Copilot goes from "interesting" to "I can't code without this." Let's see how it works.

Ghost Text - Your New Superpower

  • As you type, Copilot shows grey "ghost text" - predicted completions inline
  • Press Tab to accept the full suggestion
  • Press Ctrl+→ to accept word-by-word
  • Press Esc or keep typing to dismiss and get a new suggestion
  • Browse alternatives with the suggestion toolbar; shortcuts depend on your platform and keybindings
  • Next Edit Suggestions predict related edits: press Tab to navigate to a suggestion, then Tab again to accept
Ghost text and hotkeys
Ghost text is a proposed completion, not a change you have to accept. Tab accepts the suggestion, and Escape dismisses it. On the default Windows or Linux keymap, Ctrl+Right accepts a portion, which is useful when only the beginning is right. On macOS, use Command+Right; customized bindings can differ. The suggestion toolbar lets you inspect alternatives without memorizing platform-specific shortcuts. Next Edit Suggestions work from your editing activity and may propose a related change somewhere else, even if you haven't just accepted ghost text. If the suggestion is away from your cursor, Tab navigates to it and a second Tab accepts it. Look at the proposed change before that second press. Updating a function parameter and its callers is a useful example, but you still need to check every changed call site.

Getting Better Suggestions

  • Write a comment first - describe the function in plain English, then let Copilot generate it
  • Meaningful names - calculateShippingCost gives better results than doStuff
  • Open related files - Copilot uses neighboring tabs as context
  • Type signatures and JSDoc - the more structure you give, the better the completions
Ghost text completing from a comment
Now, the quality of suggestions depends a lot on the context you give Copilot. Here are four techniques that make a real difference. First, write a comment before you write the code. Describe what the function should do in plain English, press Enter, and watch Copilot generate the implementation. This "comment-first" approach is one of the most effective patterns. Second, use meaningful names. A function called "calculateShippingCost" gives Copilot much better signals than one called "doStuff." Your variable names and function names are essentially prompts. Third, open related files in neighboring tabs. Copilot looks at your other open tabs for context, so if you're writing a function that calls an API, having the API definition open in another tab helps a lot. And fourth, add type signatures, JSDoc comments, or any other structural hints. The more structure you provide, the better the completions will be.
Part 4

Copilot Chat

Next up is Copilot Chat - the conversational interface. A lot of developers use inline completions every day but haven't explored Chat yet, so even if you've been using Copilot for a while, this part might be new to you.

Conversational AI in Your Editor

  • Open Copilot Chat with Ctrl+Alt+I (Windows/Linux default), or use the Chat menu
  • Ask questions in natural language: "How do I read a file in Node?"
  • Copilot responds with explanations, code snippets, and follow-up suggestions
  • Add important context explicitly: a selected function, relevant file, error, or test output
  • Use inline chat (Ctrl+I) for quick edits right in the editor
  • Use controls beside the chat input to choose the session target, agent, model, and permissions; available choices vary
The Chat view gives you a conversation beside your code. Ctrl+Alt+I opens it on the default Windows or Linux keymap; macOS uses Control+Command+I. Near the input you'll find controls for the session target, agent, model, and permissions. You don't need to understand every target today. Start with the supported Copilot setup your account provides, and choose Ask when you want a read-only explanation. For a focused editor change, select code and open inline chat with Ctrl+I, or Command+I on macOS. Context helps in both places, but automatic discovery isn't a guarantee. Try Add Context or type # to browse supported context items, attach the relevant file, and include the actual error or test output. That is more reliable than assuming every open tab is part of every chat request. The panel screenshot is an earlier layout, so use the current input controls rather than copying its exact positions.

Choosing Your Model

  • Use the model selector beside the chat input; Auto is a useful beginner starting point
  • Available provider families include OpenAI, Anthropic, and Google; the catalog changes
  • Each model has different strengths: speed, reasoning depth, context window size, and cost
  • AI credit usage depends on model and input, output, and cached tokens; inspect pricing details in the picker
  • Model choices depend on your plan, organization policy, and session target; some accounts offer Auto only
You don't need to memorize a list of model names to get started. Auto can choose an available model for you, and it respects the choices your plan and organization allow. If your account offers specific models, use the picker beside the chat input to compare their capabilities and pricing. A lighter model can suit a short question, while a reasoning model may help with a harder investigation. Cost isn't a flat number per message: input, output, and cached tokens all matter, and an agent task may make several model calls. The picker exposes cost details; the status dashboard helps you monitor actual usage. Some accounts offer Auto only, so a shorter menu isn't necessarily a setup problem. Chat model selection is separate from inline suggestions. Useful Chat Commands

  • /explain - Explain selected code in plain language
  • /fix - Suggest a fix for problems in the selection or file
  • /tests - Generate unit tests for the selected code
  • /doc - Generate documentation comments in editor inline chat
  • Ask a project question naturally; attach important files with Add Context or supported # context items
Chat interface
Short commands can save typing, but their availability depends on the chat surface, session target, and enabled features. Type a slash to see what your current session supports. The explain, fix, and tests commands are useful shortcuts; documentation comments with /doc belong in editor inline chat. You can also ask in plain language. For example, ask where the database connection is configured and attach the relevant configuration file if you know it. Copilot can search and read project files to gather context, but an index doesn't place the entire repository into every request or guarantee the answer is right. Check the files it cites. Older tutorials may use the workspace chat participant; chat participants are deprecated and aren't supported by the current Copilot harness, so we don't depend on them here.

Chat Modes: Ask, Plan & Agent

  • Ask: questions, explanations, and brainstorming without changing your code
  • Plan: research the task and propose a step-by-step plan; review it before separately choosing implementation
  • Agent: implement multi-step changes and use available tools to validate them; inspect diffs and tool requests
  • Choose the agent and permissions beside the chat input; defaults and available controls vary
  • Vision: supported models can analyze attached images; availability depends on your setup
Choose Ask when you want to understand code without changing it. Don't assume it's already selected; defaults can change. Plan is for researching the task and identifying an approach, risks, and verification steps before implementation. Read the plan and resolve assumptions, then explicitly choose whether to implement it. Selecting Plan alone isn't approval to change files. Agent can edit files, run available tools, and iterate on errors, so define a bounded outcome and how to verify it. Start with the normal manual-permission workflow and review requests before allowing commands or external actions. That doesn't mean every file edit requires a prompt: inspect the diff and run relevant tests too. Allow all isn't a prerequisite for using agents. Image attachments can help with visual questions when the selected model supports them. A fresh screenshot of the current controls is still pending.

Chat Layouts and Separate Conversations

  • Keep Chat beside your code, or use New Chat (+) → New Chat Editor for more space
  • Start a new conversation for an unrelated question; moving a conversation doesn't automatically create a new one
  • Separate conversations are not separate working copies: agents using the same folder can change the same files
  • For now, complete and review one implementation task at a time
  • Parallel implementation, worktrees, and integration belong in a later agent workflow
A chat editor is a layout choice, not a way to isolate files. Use New Chat Editor from the new-chat menu if you want a larger conversation area, or keep the side bar open beside your code. Starting a new conversation can keep unrelated questions from mixing their context, but two agents using the same folder can still edit the same files. More parallel work also means more model usage and more results to integrate and verify. For this first session, finish one small implementation, inspect the diff, and test it before starting another. Later we can explore independent tasks and worktree isolation with proper integration checks.
Part 5

Configuring Your Workspace

Now let's talk about configuration. This is especially relevant if you're working on a team and want to standardize how Copilot behaves across everyone's environment.

Key Copilot Settings

  • github.copilot.enable - Toggle inline suggestions per language: {"python": true, "markdown": false}
  • editor.inlineSuggest.enabled - Master switch for inline ghost text
  • github.copilot.chat.localeOverride - Specify a preferred locale for supported chat responses
  • Use Workspace Settings (.vscode/settings.json) to share project defaults, not enforce organization policy
// .vscode/settings.json
{
  "github.copilot.enable": {
    "*": true,
    "plaintext": false,
    "markdown": false
  }
}
Open Settings with Ctrl+Comma on Windows or Linux, or Command+Comma on macOS, and search for Copilot. The per-language enable setting controls inline suggestions, not all AI access. The editor's inline-suggestion switch is useful for controlling ghost text, and localeOverride specifies a locale for supported chat responses. A shared .vscode/settings.json file gives contributors project defaults when they open that workspace. It isn't an administrative enforcement mechanism, and an editable setting isn't a guarantee of identical behavior across every session target. Use organization policy for managed controls. The existing settings screenshot is illustrative; verify names in the current Settings editor rather than assuming every pictured control is unchanged.

Custom Instructions

  • Create a .github/copilot-instructions.md file in your repo
  • Provides shared guidance for supported chat and agent requests, not inline suggestions
  • Describe conventions: "Use TypeScript strict mode", "Prefer async/await over callbacks"
  • Instructions guide the model; tests, linters, and review check whether the result follows them
A repository instruction file saves you from repeating project conventions in every supported chat or agent request. Put concise guidance in .github/copilot-instructions.md, such as the language version, naming conventions, and test command. This is shared model guidance, not a policy engine. It doesn't apply to inline suggestions, and it doesn't guarantee that every generated change follows every rule. Check which instructions your session includes, inspect the result, and use your project's tests and linters to enforce important requirements. Copilot in Action

Alright, it's demo time! Let's switch over to VS Code and see Copilot in action. We're going to write a real function from scratch, then use Chat to improve it.

Demo: Writing a Function with Copilot

  • Create a new file utils.js
  • Describe a simplified, unquoted CSV subset: first row is headers; trim values; reject quotes and uneven rows
  • Watch Copilot generate the full function
  • Review before accepting with Tab; this is not a general CSV parser
// Simplified CSV: headers first; trim values; no quoted fields.
function parseCSV(csvString) {
  if (typeof csvString !== 'string' || !csvString.trim())
    throw new TypeError('Expected nonempty CSV text');
  if (csvString.includes('"')) throw new Error('Quoted fields unsupported');
  const [first, ...rows] = csvString.trim().split(/\r?\n/);
  const headers = first.split(',').map(h => h.trim());
  if (headers.some(h => !h) || new Set(headers).size !== headers.length)
    throw new Error('Headers must be nonempty and unique');
  return rows.map(line => {
    const values = line.split(',').map(v => v.trim());
    if (values.length !== headers.length) throw new Error('Uneven row');
    return Object.fromEntries(headers.map((h, i) => [h, values[i]]));
  });
}
Let's make the requirement small enough to inspect. We want a teaching example with headers on the first row, trimmed values, and no quoted fields. Real CSV can contain quoted commas and newlines, so a simple split-based function isn't a general parser. Ask Copilot for this restricted behavior, then compare the suggestion with the requirement before accepting it. The sample rejects quotes, missing or duplicate headers, and uneven rows rather than silently pretending to support them. Your generated code may differ because model output isn't deterministic. That isn't evidence that either version is correct. Next we'll ask for focused tests that demonstrate the supported behavior and reject unsupported input.

Demo: Using Chat to Refactor

  • Select the function → open inline chat (Ctrl+I)
  • Ask: "Review this restricted parser; preserve its no-quoted-fields contract and explain any proposed fixes"
  • Review the diff - Copilot shows additions in green, removals in red
  • Keep or discard changes after reviewing the diff; labels vary by surface
  • Ask for tests of normal input, CRLF, uneven rows, and rejected quoted fields; run them with the existing test setup
Select parseCSV and open inline chat. Ask for a review that preserves the restricted input contract instead of inviting an undefined parser rewrite. Read the proposed diff and its explanation before keeping any changes. Then ask for tests using the project's existing test setup. Include a normal two-column row, CRLF line endings, a missing value, duplicate headers, and a quoted comma that this function must reject. Read the expected results yourself; generated tests can agree with a generated bug. Run the tests and inspect the actual output rather than stopping at test generation. If they fail, investigate the requirement and implementation before changing an assertion. We don't need to install a new framework just for this example. For production CSV requirements, choose a maintained parser and evaluate it separately.

Tips for Getting the Most from Copilot

  • Be specific - "Write a Python function that validates an email address using regex" beats "write code"
  • Iterate - Review a suggestion, then refine it with follow-up prompts
  • Review everything - AI suggestions are starting points, not final answers
  • Use context - Open related files, add comments, use meaningful names
  • Learn your keybindings - Tab and Esc; Windows/Linux defaults include Ctrl+→, Ctrl+I, and Ctrl+Alt+I
Specific requirements make the result easier to evaluate. Instead of asking for code in general, describe the input, expected output, constraints, and a test that would prove the behavior. Iterate, but review a suggestion before accepting it. Copilot can produce bugs, outdated APIs, or code that doesn't match your standards. Give it meaningful names and comments, and attach important files or failures when chatting. Then run the relevant checks yourself or inspect the agent's real test output. Shortcuts help you stay in flow, but use the bindings for your operating system and editor configuration. If a shortcut doesn't work, the menu or suggestion toolbar is a better next step than assuming your Copilot setup is broken.
