Copilot Primitives - Prompts, Instructions, Skills, Hooks, and Agents

Guide agent behavior with reusable context, then automate critical checks at lifecycle events

Hey everyone! Welcome to "Copilot Primitives: Prompts, Instructions, Skills, Hooks, and Agents." If you've taken "The Copilot Awakens," you already know how to use Copilot Chat and inline suggestions. Today we're going one level deeper: we're going to shape agent sessions in VS Code using files that live in the repository. Our four building blocks are prompts, instructions, skills, and hooks, with a brief orientation to custom agents near the end. One distinction matters from the start: prompt files run in Local harness sessions, while our hook examples target the Copilot harness. For reusable tasks in Copilot, we'll use skills. Hooks are still a Preview feature in VS Code. No customization experience needed. Let's get into it.

Part 1

The Building Blocks

Let's start with the big picture. Before we go deep on any one primitive, let's see all four side by side so you understand how they relate to each other.

Four Building Blocks

Prompts

.prompt.md files capture reusable tasks that you invoke in Local chat sessions.

Instructions

Markdown files provide repository-wide or conditional guidance to the agent.

Skills

SKILL.md folders package workflows, scripts, examples, and resources.

Hooks

.json configurations run commands at defined agent lifecycle events.

Here are the four building blocks side by side. A prompt says, "Here is a task I want to run." Instructions say, "Here is how we work in this repository." A skill says, "Here is a complete workflow and the material you may need to carry it out." All three are written for the model to interpret, so they guide behavior but do not guarantee it. Hooks are different. A hook says, "When this lifecycle event happens, run this command." Its invocation does not depend on the model remembering the check, but the command can still fail. Before choosing a file, check the Session Target: prompt files require Local, while today's hooks use Copilot. Switching models does not change harness compatibility. In Copilot, a manually invoked skill can serve the reusable-task role. This is our course framework, not the complete list of everything VS Code can customize.

Let's make this concrete by looking at the file tree. At the top of the .github folder, copilot-instructions.md holds repository-wide guidance. Reusable Local prompt files go under prompts, conditional instructions go under instructions, and each skill gets its own folder under skills. Hooks live under hooks, where a JSON file connects an event to a command or script. Sharing a repository does not make every file usable in every harness: Copilot does not load dot-prompt-dot-md files. Select your Session Target, then open Open Customizations to see what that harness discovers. Prefer its native locations, especially when sharing files across clients. Also notice that a skill is a folder, not just one Markdown file. That folder can carry examples, templates, schemas, and scripts alongside SKILL.md.
Part 2

Prompt Files

Let's start with prompt files, the simplest of our four primitives. Select Local as the Session Target for this section. Copilot harness sessions use skills for reusable workflows instead; creating a prompt file in a Copilot session does not make it runnable there.

What Is a Prompt File?

  • A Markdown file with the .prompt.md extension
  • Captures a reusable task - like a saved chat message you can run again and again
  • Can include variables, file references, and output format instructions
  • In a Local session, type / and select it from the prompt picker
  • Committed under .github/prompts/ → shared with teammates using Local
graph LR
  A[Invoke prompt] --> B[Resolve variables]
  B --> C[Attach context]
  C --> D[Run selected agent]
Think about the last really good prompt you wrote. Maybe it took a few tries before the output was exactly what you wanted. A prompt file lets you save that work instead of reconstructing it next week. In a Local session, VS Code fills in variables like your current selection, attaches referenced context, and runs the built-in or custom agent named in the prompt. The key word here is invoke. Nothing happens until someone chooses to run it. That makes prompt files useful for generating tests, drafting documentation, or reviewing an API. Commit the file under .github/prompts, and teammates can use it in Local sessions. For the Copilot harness, package that reusable task as a skill instead.

Anatomy of a Prompt File

---
agent: agent
description: Generate a unit test for the selected function
---

Write a comprehensive unit test for the function in the
current selection.

**Requirements:**
- Use the project's existing test framework
- Cover happy path, edge cases, and error conditions
- Follow the repository's test naming conventions

**Context:**
- Selected code: ${selection}
Let's walk through this Local prompt file from top to bottom. Between the triple dashes is YAML frontmatter. The agent field tells VS Code which agent should handle the request. Current built-in choices include Ask, Agent, and Plan, and you can name a custom agent as well. We're using Agent because generating a unit test may require creating or editing a file. The description helps you recognize the prompt in the slash-command picker. Below the frontmatter is the task in Markdown. Highlight a function before running it: selection supplies that highlighted code. For a known supporting file, you can add a Markdown link or a file reference with a path relative to the prompt file. We leave test naming to the repository instructions rather than introduce a conflicting convention here.

Running & Sharing Prompts

  • Select Local as the Session Target, then type /
  • Select your prompt file; VS Code resolves its variables and runs it
  • Use Chat: Run Prompt or the editor play button as alternatives
  • Prompts in .github/prompts/ are shared with teammates using Local
  • Build a prompt library - curated, tested prompts for common tasks

Part 3

Instruction Files

Now let's shift from tasks you choose to run to guidance that can come along automatically. Prompt files answer, "What should the agent do right now?" Instruction files answer, "How do we expect work to be done in this repository?" That distinction is going to matter throughout this section.

What Are Instruction Files?

  • Markdown guidance that VS Code can include automatically with chat requests
  • Two flavors:
    • .github/copilot-instructions.md - repository-wide guidance for chat
    • .instructions.md files - conditional guidance selected by pattern or task relevance
  • Useful for coding standards, architecture decisions, and project conventions
  • They guide generated responses; they do not control inline suggestions or guarantee compliance
Instruction files are where you teach the agent about your coding standards, architecture decisions, and project conventions. The repository-wide file at .github/copilot-instructions.md supplies project guidance in Copilot sessions; Local also discovers it when instruction-file support is enabled. More focused dot-instructions-dot-md files can join when a pattern matches work on a file, when their description is relevant, or when you attach them yourself. Instructions guide the model rather than guarantee compliance, and they do not control inline suggestions. Other formats depend on the harness: AGENTS.md is cross-agent, while CLAUDE.md support is not universal. Local supports compatible CLAUDE.md files. Check the selected harness before assuming a format applies.

Repo-Wide: copilot-instructions.md

# Copilot Instructions

## Language & Framework
- Always use TypeScript with strict mode enabled
- Prefer async/await over raw Promises or callbacks
- Use functional components with hooks (no class components)

## Testing
- Write tests using Vitest, not Jest
- Every public function must have at least one test

## Style
- Use single quotes for strings
- Maximum line length: 100 characters
- Prefer named exports over default exports
Here's a repository-wide instruction file. It lives at one predictable path: .github/copilot-instructions.md. In this example, we're telling the agent which language patterns to prefer, which test framework to use, and how we want code formatted. Notice that every rule is short and concrete. "Use Vitest, not Jest" is much easier to apply than a vague instruction like "write good tests." My advice is to start small. Pay attention to the corrections your team keeps making to generated output, and add the recurring ones here. Because this is Markdown in the repository, the team can review and evolve it through pull requests. And if a rule absolutely must be enforced, don't rely on prose alone. Back it with a formatter, test, policy tool, or hook.

Scoped: .instructions.md Files

---
applyTo: "**/*.test.ts"
---

# Testing Instructions

- Use `describe` / `it` blocks (not `test`)
- Mock external services with `vi.mock()`
- Assert with `expect().toBe()` - never use `assert`
- Name test cases: "should <expected behavior> when <condition>"
  • The optional applyTo glob associates guidance with matching files
  • A description can help the agent select instructions for a relevant task
  • Perfect for language-specific, framework-specific, or folder-specific rules
Now suppose your testing rules are too specific to load for every task. That's where a scoped instruction file helps. The applyTo field is a glob pattern, and this one associates the guidance with TypeScript test files the agent creates or modifies. It is not simply a rule for whichever editor tab happens to be active. You can also add a description so the model recognizes relevance to a testing task. When this file applies, it combines with your repository and organization guidance rather than replacing them. Check the request context or agent debug evidence to confirm the expected instructions were included; matching a filename is not proof of compliance. Don't depend on a particular ordering, because that ordering is not guaranteed.
Part 4

Skills

We've covered reusable requests and reusable guidance. Now let's package a reusable capability. Agent Skills let you put a workflow, its instructions, and any supporting material into one portable folder. In current VS Code, skills are generally available, and they can be selected by the agent or invoked directly from the slash-command menu. Let's see what makes them different from instructions.

What Is a Skill?

  • A folder containing a required SKILL.md and optional supporting resources
  • Packages instructions, scripts, examples, templates, and reference material
  • Can load progressively when relevant or explicitly invoked
  • Can be invoked manually from chat with /skill-name
  • Portable across supporting tools, including VS Code and Copilot CLI
Here's the easiest way to separate a skill from an instruction file. Instructions tell the agent how your team works. A skill gives the agent a capability it can pick up for a particular task. A skill folder can carry scripts, examples, templates, and reference material alongside SKILL.md. VS Code starts by exposing only the skill's name and description. If the agent selects it, it reads the instructions and pulls in supporting resources as needed. Discovery does not guarantee selection for every relevant request. By default, you can also invoke it from the slash-command menu, although frontmatter can limit either entry point. In Copilot, that manual invocation gives us a reusable task without a Local-only prompt file.

Anatomy of a SKILL.md

---
name: azure-deploy
description: >
  Use this skill when deploying services to Azure
  Container Apps. Covers Bicep templates, azd
  configuration, and managed identity setup.
---

# Azure Deployment Skill

## Prerequisites
- Azure CLI installed and authenticated
- Supported Azure Developer CLI (azd) installed and authenticated

## Deployment Steps
1. Run `azd init` to scaffold the project
2. Configure `azure.yaml` with service definitions
3. Run `azd up` to provision and deploy

## Bicep Patterns
- Always use managed identity (no connection strings)
- Tag all resources with `environment` and `team`
- Use Key Vault references for secrets

## Resources
- Read `references/container-apps.md` for platform constraints
- Run `scripts/validate-bicep.ps1` before deployment

Illustrative skill structure, not a complete deployment recipe. No Azure deployment is needed for this course.

Let's open up a skill and look at its anatomy. Every skill gets its own directory containing SKILL.md. The name must match the folder name, using lowercase letters, numbers, and hyphens. The description tells the agent when the skill is relevant. Below it is the workflow, followed by relative paths to supporting material. This Azure example illustrates that structure, not a complete deployment recipe. You do not need to deploy anything today, and azd up can provision real resources with costs. The named reference and validation script are examples you would supply with the skill. In a real workflow, verify the current tool prerequisites and authenticate azd itself rather than assume an Azure CLI login covers it. Keep detailed platform constraints in supporting files and make script prerequisites and failure messages clear.

How Skills Load

Discover

VS Code exposes each skill's name and description so the agent can find relevant capabilities.

Load

The agent reads SKILL.md when it selects the skill or the user invokes it with /.

Execute

The agent follows the workflow and reads or runs supporting resources only as needed.

This three-step flow is what makes skills practical at scale. First, discovery exposes lightweight metadata, not the whole folder. Second, when the agent selects the skill or you invoke it with a slash command, it reads SKILL.md. Third, it follows the workflow and opens the supporting resources it needs. Seeing a skill in Open Customizations proves discovery, not execution. Try a harmless task and inspect the session evidence to confirm it was loaded. To make a reusable Copilot task manual-only, set disable-model-invocation to true in the skill's frontmatter and invoke its slash command yourself. That is the supported alternative to a Local prompt file, not a promise that every prompt-specific agent, model, or tools setting carries over. The workflow is still interpreted by the model; lifecycle-triggered commands are where hooks enter the picture.
Part 5

Agent Hooks

Alright, this is where the execution model changes. Everything we've covered so far gives the model context and asks it to make a good decision. A hook does not ask the model to remember an action. In the Copilot harness, a configured hook is invoked when its agent-session event occurs, so it can support formatting, validation, audit trails, and policy checks. The VS Code hooks experience is currently in Preview. Before configuring one, select Copilot as the Session Target. The older Local harness uses a separate hook format, so its settings and examples are not instructions for a new Copilot hook.

What Is an Agent Hook?

  • A command that runs at a defined point in an agent session lifecycle
  • Shared repository hooks live in .github/hooks/*.json at the repository root
  • Receives structured event data as JSON through standard input
  • Can return a JSON object on standard output; its effect depends on the event
  • Runs executable code in the hook runtime, so review commands and limit access
So what is a hook, mechanically? It's a connection between an agent lifecycle event and a command. In the Copilot harness, event data arrives as JSON on standard input, and the command can return a JSON object on standard output. What that output means depends on the event; some events ignore it, while others can add context or affect a tool decision. Shared repository hooks live in .github/hooks at the repository root. Because hooks run executable commands in the runtime environment, review the configuration and scripts, validate their inputs, and give them only the access they need.

Hook Lifecycle Events

EventWhen it runsTypical use
sessionStartA session starts or resumesAdd project context
userPromptSubmittedA prompt is submittedObserve the request
preToolUseBefore a tool callInspect or decide on an action
postToolUseAfter a tool callValidate a result or add context
preCompactBefore context compactionSave information
subagentStartA subagent startsObserve delegated work
subagentStopA subagent finishesCapture completion data
agentStopThe agent is about to finish its turnCheck whether it should finish
sessionEndThe session terminatesClean up or record an event
The Copilot harness currently supports these nine lifecycle events. sessionStart and sessionEnd mark the session boundary, while agentStop runs as the agent is about to finish its turn. The subagent events let you observe delegated work, and userPromptSubmitted fires when a request is submitted. preCompact happens before context compaction. The two events you'll probably reach for first are preToolUse and postToolUse. The first can inspect a tool call or provide a documented decision; the second can validate a completed result or add context. Choose the narrowest event that fits, and remember that event names, payloads, and output behavior belong to the Copilot format, not the older Local format.

Anatomy of a Workspace Hook

{
  "version": 1,
  "hooks": {
    "postToolUse": [
      {
        "type": "command",
        "command": "node .github/hooks/audit-tool-use.mjs",
        "cwd": ".",
        "timeoutSec": 10
      }
    ]
  }
}
  • Each event can run one or more command hooks
  • Commands can define a working directory, environment values, and timeoutSec
  • Use the documented cross-platform command or platform-specific shell fields
  • This example requires Node.js and the referenced script on the execution host
Let's read this Copilot hook configuration together. The version field identifies the Copilot format, and lowercase postToolUse runs after a tool call. The command launches a Node script, so Node.js and that script must exist on the host where the runtime executes, including a remote host or container. This slide shows the configuration, not the script implementation. The cwd field sets the working directory, and timeoutSec limits command duration. You can also provide environment values or documented bash or PowerShell command fields. Before relying on it, test with a non-sensitive fixture, then a harmless Copilot session, and confirm the expected sanitized result. A hook appearing in the editor is not proof that its command ran.

Hook Execution Flow

graph LR
  A[Configured event] --> B[JSON on stdin]
  B --> C[Hook command]
  C --> D[Optional JSON on stdout]
  D --> E[Event-specific behavior]
  C --> F[Failure or timeout]
  F --> G[Handling varies by event]
Here's what happens when a configured event fires. The Copilot harness sends event data as JSON on standard input, and a command hook can return one JSON object on standard output. Treat stdout as a protocol channel, so keep diagnostic text separate. The meaning of the output and the effect of an error or timeout vary by event; a hook invocation does not guarantee that its command succeeds or that it blocks the agent. To configure Copilot hooks, select Copilot as the Session Target, then open Hooks in Agent Customizations, or enter /hooks in chat. If something fails, check the agent debug logs and provider diagnostics. Chat: Configure Hooks and the GitHub Copilot Chat Hooks output channel are for the older Local harness, whose hook format is separate.

Hooks Are Executable Automation

Do

  • Review hook code before trusting a repository
  • Validate every field received from standard input
  • Use least privilege and short timeouts
  • Log only sanitized metadata

Avoid

  • Passing untrusted input directly to a shell
  • Printing prompts, source code, secrets, or tokens
  • Running broad commands after every tool call
  • Assuming a hook is sandboxed
Let's slow down here, because hooks deserve a stronger security posture than the Markdown files we just covered. Hook configuration and scripts are executable code, so review them before use and do not assume they are sandboxed. Validate the JSON payload before using it, and never interpolate an untrusted value into a shell command. Keep scripts small, limit filesystem and network access, and use short timeouts. Be especially careful with logging. Prompts and tool payloads can contain source code, customer data, or secrets, so log only the minimum sanitized metadata you need. Before you trust a repository and enable its hooks, inspect the configuration and the scripts it invokes.

When to Use What

Repeat a request?

Prompt file in Local
In Copilot, use a manually invoked skill.

Guide behavior?

Instruction file
Provide standards and contextual rules.

Package a workflow?

Agent Skill
Bundle steps, scripts, and resources.

Automate at an event?

Agent hook
Invoke code at a lifecycle event.

If you remember one decision slide from this course, make it this one. Are you repeating the same request? In Local, save a prompt file. In Copilot, use a manually invoked skill for that reusable task. Does the agent need your standards or project context? Put that guidance in instructions. Are you packaging a workflow with scripts, templates, or references? Build a skill. Do you want code invoked at a lifecycle event without relying on the model to request it? Use a hook with the selected harness's format. Prompts request, instructions guide, skills equip, and hooks automate. A hook doesn't replace your linter, tests, permissions, or policy engine. Its invocation is tied to the event, but its command can fail and its effect depends on the event.

How They Work Together

graph LR
  A[Invoke skill in Copilot] --> B[Instructions guide output]
  B --> C[Skill supplies workflow]
  C --> D[Agent workflow]
  D --> E[Configured hook event]
  E --> F[Hook command invoked]
  F --> G[Event-specific handling]

Copilot composition: invoke a skill, apply instructions, run configured hooks. Prompt files remain a Local option.

Let's compose a workflow in one supported harness: Copilot. A developer manually invokes an API skill with a request to create an endpoint. Repository instructions supply the team's TypeScript and Express conventions, while the skill supplies the workflow and supporting resources. This is a conceptual view of the roles, not a strict ordering of context loading. As the agent works, configured Copilot lifecycle events invoke their hook commands. A postToolUse hook might audit a completed tool call, but its output cannot undo that action. The command can also fail. If you want to start with a dot-prompt-dot-md file instead, that is a Local workflow and needs Local-compatible hooks; it cannot start this Copilot session. We can combine the roles without pretending the harness formats are interchangeable.

These Four Are Not the Whole Platform

NeedCustomizationWhat it adds
Specialized roleCustom agentPersona, tools, model, handoffs, and subagents
External systemMCP serverTools and data from APIs, databases, or services
Packaged distributionAgent pluginInstallable bundle of customizations
Before we wrap up, I want to place these four building blocks back into the larger platform. This course is not claiming that Copilot has only four customization options. If you need a specialized role with its own tools, model, handoffs, or subagents, that's a custom agent. If the agent needs to reach an external API, database, or service, that's where MCP fits. If you want to distribute a ready-made bundle of customizations, look at agent plugins. Hooks don't replace any of those options. They add deterministic lifecycle automation alongside them. So think of today's four as a practical beginner framework, not the edge of the platform.
Summary

Wrap-Up & Next Steps

We're in the home stretch. Let's recap the key points and talk about where to go from here.

Key Takeaways

  • Prompt files (.prompt.md) capture reusable tasks invoked in Local
  • Instruction files provide repository-wide or conditional guidance for chat
  • Agent Skills (SKILL.md) package workflows and can be manually invoked in Copilot
  • Agent hooks (.json) run commands at defined lifecycle events
  • Prompts, instructions, and skills guide the model; hooks provide deterministic automation
  • All four can be versioned with the repository and reviewed by the team
Let's bring it all together. Prompt files save tasks for Local sessions. In Copilot, a manually invoked skill can fill that reusable-task role. Instructions provide standards and context. Skills package workflows and load supporting material as needed. Hooks run commands at lifecycle events. The important distinction is between model guidance and event-triggered execution, not a guarantee of enforcement. Keep files in locations supported by the selected harness, verify what actually loads or runs, and review changes through the repository. Because hooks execute code, keep them small and trustworthy. They remain Preview in VS Code and can be restricted by runtime settings or organization policy.
