Copilot Primitives - Prompts, Instructions, Skills, Hooks, and Agents

Guide agent behavior with reusable context, then enforce critical steps with deterministic automation

Hey everyone! Welcome to "Prompts, Instructions, Skills, and Hooks." If you've taken "The Copilot Awakens," you already know how to use Copilot Chat and inline suggestions. Today we're going one level deeper: we're going to shape how local agent sessions behave in VS Code using files that live right in the repository. We'll start with prompts, instructions, and skills, which give the model better context. Then we'll cross an important line into hooks, which run commands at specific lifecycle events whether the model remembers to run them or not. Hooks are still a Preview feature in VS Code, so everything you see today targets the current workspace-hook experience. No customization experience needed. Let's get into it.

Part 1

The Building Blocks

Let's start with the big picture. Before we go deep on any one primitive, let's see all four side by side so you understand how they relate to each other.

Four Building Blocks

Prompts

.prompt.md files capture reusable tasks that you invoke from chat.

Instructions

Markdown files provide repository-wide or conditional guidance to the agent.

Skills

SKILL.md folders package workflows, scripts, examples, and resources.

Hooks

.json configurations run commands at defined agent lifecycle events.

Here are the four building blocks side by side. A prompt says, "Here is a task I want to run." Instructions say, "Here is how we work in this repository." A skill says, "Here is a complete workflow and the material you may need to carry it out." All three are written for the model to interpret, so they guide behavior but do not guarantee it. Hooks are different. A hook says, "When this lifecycle event happens, run this command." That makes hooks the right choice when a check or action cannot depend on the model remembering it. Notice one other difference on the slide: prompts, instructions, and skills are Markdown-based, while hook configuration is JSON and usually points to executable code. And remember, this is our course framework, not the complete list of everything VS Code can customize.

Where They Live in Your Repo

my-project/
├── .github/
│   ├── copilot-instructions.md    ← repo-wide instructions
│   ├── prompts/
│   │   ├── generate-api-test.prompt.md
│   │   └── explain-error.prompt.md
│   ├── instructions/
│   │   ├── typescript.instructions.md
│   │   └── testing.instructions.md
│   ├── skills/
│   │   └── azure-deploy/
│   │       └── SKILL.md
│   └── hooks/
│       ├── quality-checks.json
│       └── audit-tool-use.mjs
└── src/
Let's make this concrete by looking at the file tree. At the top of the .github folder, copilot-instructions.md holds repository-wide guidance. Reusable prompts go under prompts, conditional instructions go under instructions, and each skill gets its own folder under skills. Hooks live under hooks, where a JSON file connects an event to a command or script. These are the default workspace locations VS Code looks in. You can configure additional locations, and VS Code supports some compatible locations from other tools, but dropping a correctly named file anywhere in the repository is not enough. VS Code still has to discover it. Also notice that a skill is a folder, not just one Markdown file. That folder can carry examples, templates, schemas, and scripts alongside SKILL.md.
Part 2

Prompt Files

Let's start with prompt files - the simplest and most approachable of the four primitives. If your team is new to Copilot customization, this is the perfect place to begin.

What Is a Prompt File?

  • A Markdown file with the .prompt.md extension
  • Captures a reusable task - like a saved chat message you can run again and again
  • Can include variables, file references, and output format instructions
  • Shows up in the chat prompt picker - type / and select it
  • Committed to your repo → shared with your entire team automatically
graph LR
  A[Invoke prompt] --> B[Resolve variables]
  B --> C[Attach context]
  C --> D[Run selected agent]
Think about the last really good prompt you wrote. Maybe it took a few tries before the output was exactly what you wanted. A prompt file lets you save that work instead of reconstructing it next week. When you invoke the file, VS Code fills in variables like your current selection, attaches any context you've referenced, and runs the built-in or custom agent named in the prompt. The key word here is invoke. Nothing happens until someone chooses to run it. That makes prompt files a great fit for repeatable tasks such as generating tests, drafting documentation, or reviewing an API. Commit the file under .github/prompts, and the rest of the team gets the same reusable task when they open the repository.

Anatomy of a Prompt File

---
agent: agent
description: Generate a unit test for the selected function
---

Write a comprehensive unit test for the function in the
current selection.

**Requirements:**
- Use the project's existing test framework
- Cover happy path, edge cases, and error conditions
- Follow the naming convention: `test_<function>_<scenario>`

**Context:**
- Test file: #file:${file}
- Selected code: ${selection}
Let's walk through this file from top to bottom. Between the triple dashes is YAML frontmatter. The agent field tells VS Code which agent should handle the request. Current built-in choices include Ask, Agent, and Plan, and you can name a custom agent as well. We're using Agent here because generating a unit test may require creating or editing a file. The description is what helps you recognize this prompt in the slash-command picker. You can also choose a model or restrict tools in frontmatter, but you don't have to. Below that is the actual prompt in Markdown. At runtime, the file variable becomes the current file, and selection becomes whatever code you've highlighted. So when you run this prompt, you're not just saying "write a test." You're handing the agent the exact code and context it needs.

Running & Sharing Prompts

  • In chat, type / to open the prompt picker
  • Select your prompt file; VS Code resolves its variables and runs it
  • Use Chat: Run Prompt or the editor play button as alternatives
  • Prompts committed to .github/prompts/ are available to every team member
  • Build a prompt library - curated, tested prompts for common tasks
Prompt picker in chat
Once the prompt is saved, how do you run it? The quickest path is to open Chat and type a forward slash. Your prompt files appear in the same menu as user-invocable skills. Select the prompt, add any extra details after the command if you need them, and run it. You can also use Chat: Run Prompt from the Command Palette or select the play button while the prompt file is open. Here's the team benefit: when these files are committed under .github/prompts, everyone works from the same task definition. Treat that prompt library like code. Keep each prompt focused, review changes in pull requests, and update it when the project or the available tools change.
Part 3

Instruction Files

Now let's shift from tasks you choose to run to guidance that can come along automatically. Prompt files answer, "What should the agent do right now?" Instruction files answer, "How do we expect work to be done in this repository?" That distinction is going to matter throughout this section.

What Are Instruction Files?

  • Markdown guidance that VS Code can include automatically with chat requests
  • Two flavors:
    • .github/copilot-instructions.md - repository-wide guidance for chat
    • .instructions.md files - conditional guidance selected by pattern or task relevance
  • Useful for coding standards, architecture decisions, and project conventions
  • They guide generated responses; they do not control inline suggestions or guarantee compliance
Instruction files are where you teach the agent about your coding standards, architecture decisions, and project conventions. The repository-wide file at .github/copilot-instructions.md comes into workspace chat requests automatically. More focused dot-instructions-dot-md files can join the request when a file pattern matches, when their description is relevant to the task, or when you attach them yourself. There are two boundaries to remember. First, instructions guide the model; they do not guarantee that every rule will be followed perfectly. Second, these chat instructions do not control the inline suggestions that appear while you type. VS Code can also read formats such as AGENTS.md and compatible CLAUDE.md files, and your organization may contribute another layer of instructions.

Repo-Wide: copilot-instructions.md

# Copilot Instructions

## Language & Framework
- Always use TypeScript with strict mode enabled
- Prefer async/await over raw Promises or callbacks
- Use functional components with hooks (no class components)

## Testing
- Write tests using Vitest, not Jest
- Every public function must have at least one test

## Style
- Use single quotes for strings
- Maximum line length: 100 characters
- Prefer named exports over default exports
Here's a repository-wide instruction file. It lives at one predictable path: .github/copilot-instructions.md. In this example, we're telling the agent which language patterns to prefer, which test framework to use, and how we want code formatted. Notice that every rule is short and concrete. "Use Vitest, not Jest" is much easier to apply than a vague instruction like "write good tests." My advice is to start small. Pay attention to the corrections your team keeps making to generated output, and add the recurring ones here. Because this is Markdown in the repository, the team can review and evolve it through pull requests. And if a rule absolutely must be enforced, don't rely on prose alone. Back it with a formatter, test, policy tool, or hook.

Scoped: .instructions.md Files

---
applyTo: "**/*.test.ts"
---

# Testing Instructions

- Use `describe` / `it` blocks (not `test`)
- Mock external services with `vi.mock()`
- Assert with `expect().toBe()` - never use `assert`
- Name test cases: "should <expected behavior> when <condition>"
  • The optional applyTo glob associates guidance with matching files
  • A description can help the agent select instructions for a relevant task
  • Perfect for language-specific, framework-specific, or folder-specific rules
Now suppose your testing rules are too specific to load for every task. That's where a scoped instruction file helps. The applyTo field is a glob pattern, and this one associates the guidance with TypeScript test files. One subtle point: this is not just about whichever editor tab happens to be active. VS Code considers the files in the request context and the files the agent is working with. You can also add a description so the model recognizes that the instructions are relevant to a testing task. When this file applies, it combines with your repository and organization guidance rather than replacing them. Just don't build a workflow that depends on a particular ordering, because that ordering is not guaranteed.
Part 4

Skills

We've covered reusable requests and reusable guidance. Now let's package a reusable capability. Agent Skills let you put a workflow, its instructions, and any supporting material into one portable folder. In current VS Code, skills are generally available, and they can be selected by the agent or invoked directly from the slash-command menu. Let's see what makes them different from instructions.

What Is a Skill?

  • A folder containing a required SKILL.md and optional supporting resources
  • Packages instructions, scripts, examples, templates, and reference material
  • Loaded progressively when the task matches its description
  • Can be invoked manually from chat with /skill-name
  • Portable across supporting tools, including VS Code and Copilot CLI
Here's the easiest way to separate a skill from an instruction file. Instructions tell the agent how your team works. A skill gives the agent a capability it can pick up for a particular task. And that capability can include much more than prose. A skill folder can carry scripts, examples, templates, and reference material alongside SKILL.md. VS Code starts by exposing only the skill's name and description. If the skill matches the task, it loads the instructions and then pulls in supporting resources as needed. That keeps an Azure deployment manual out of context while you're fixing a React component. By default, the model can select a skill and you can invoke it from the slash-command menu, although frontmatter can limit either entry point.

Anatomy of a SKILL.md

---
name: azure-deploy
description: >
  Use this skill when deploying services to Azure
  Container Apps. Covers Bicep templates, azd
  configuration, and managed identity setup.
---

# Azure Deployment Skill

## Prerequisites
- Azure CLI installed and authenticated
- azd CLI version 1.5+

## Deployment Steps
1. Run `azd init` to scaffold the project
2. Configure `azure.yaml` with service definitions
3. Run `azd up` to provision and deploy

## Bicep Patterns
- Always use managed identity (no connection strings)
- Tag all resources with `environment` and `team`
- Use Key Vault references for secrets

## Resources
- Read `references/container-apps.md` for platform constraints
- Run `scripts/validate-bicep.ps1` before deployment
Let's open up a skill and look at its anatomy. Every skill gets its own directory, and that directory must contain SKILL.md. The name in frontmatter has to match the folder name exactly, using lowercase letters, numbers, and hyphens. The description is doing important work: it's the signal that tells the agent when this skill is relevant. Below the frontmatter is the workflow itself. This example gives the agent prerequisites, deployment steps, and Bicep conventions, then points to a reference file and a validation script using relative paths. Keep SKILL.md focused on the main path through the task. If you have pages of platform constraints or many examples, move those into supporting files so the agent can load them only when needed. And when a skill includes scripts, make their prerequisites, boundaries, and failure messages clear.

How Skills Load

Discover

VS Code exposes each skill's name and description so the agent can find relevant capabilities.

Load

The agent reads SKILL.md when the task matches or the user invokes the skill with /.

Execute

The agent follows the workflow and reads or runs supporting resources only as needed.

This three-step flow is what makes skills practical at scale. First, discovery: VS Code shows the agent lightweight metadata, not the whole skill folder. Second, loading: if the description matches the task, or if you invoke the skill yourself with a slash command, the agent reads SKILL.md. Third, execution: the agent follows the workflow and opens the examples, templates, schemas, or scripts it needs along the way. That makes skills a strong fit for procedures like scaffolding a service, deploying an application, running a migration, or debugging a known class of failures. Just remember that the workflow is still interpreted by the model. If a command must run at a guaranteed point in the lifecycle, that's where hooks enter the picture.
Part 5

Agent Hooks

Alright, this is where the execution model changes. Everything we've covered so far gives the model context and asks it to make a good decision. A hook does not ask the model to remember an action. It runs code when a specific event happens in the agent session. That's why hooks are useful for things like formatting, validation, audit trails, and policy checks. One important caveat before we go further: hooks are currently a Preview feature in VS Code. They depend on the chat.hooks.enabled setting, and your organization may restrict them through policy.

What Is an Agent Hook?

  • A command that runs at a defined point in an agent session lifecycle
  • Configured for a workspace in .github/hooks/*.json
  • Receives structured event data as JSON through standard input
  • Can report an outcome through standard output or its exit status
  • Runs with the permissions of the VS Code process and current user
So what is a hook, mechanically? It's a connection between an agent lifecycle event and a shell command. When the event fires, VS Code sends a JSON payload to the command through standard input and waits for a result. Depending on the event, that result can simply record what happened, add context, or influence whether an operation continues. In this course, we're using workspace hook files under .github/hooks. And here's the security point I want you to hear early: the command runs with your local user permissions. A hook is executable automation, not harmless metadata, so review it with the same care you would give a build script or a GitHub Actions workflow.

Hook Lifecycle Events

EventWhen it runsTypical use
SessionStartA session beginsAdd project context
UserPromptSubmitA prompt is submittedRecord request metadata
PreToolUseBefore a tool callValidate or gate an action
PostToolUseAfter a tool callFormat, test, or audit
PreCompactBefore context compactionPreserve required context
SubagentStartA subagent beginsTrack delegated work
SubagentStopA subagent completesCapture completion data
StopThe agent session stopsRun final checks
VS Code gives us eight lifecycle events, and this table groups them by where they happen. SessionStart and Stop sit at the outer boundary of the session. SubagentStart and SubagentStop let you observe delegated work. UserPromptSubmit fires when a person sends a request. PreCompact gives you a chance to preserve required context before VS Code condenses the conversation. The two events you'll probably reach for first are PreToolUse and PostToolUse. PreToolUse can inspect or gate an action before it happens. PostToolUse can run a formatter, test, or audit step after a tool finishes. Choose the narrowest event that fits. If you only need to format edited files, don't attach a broad formatter to every event in the session.

Anatomy of a Workspace Hook

{
  "hooks": {
    "PostToolUse": [
      {
        "type": "command",
        "command": "node .github/hooks/audit-tool-use.mjs",
        "cwd": ".",
        "timeout": 10
      }
    ]
  }
}
  • Each event can run one or more command hooks
  • Commands can define a working directory, environment values, and timeout
  • OS-specific overrides are available when one command is not portable
Let's read this hook configuration together. Under hooks, we choose the PostToolUse event, which means the command runs after a tool call completes. The type says this is a command hook. The command launches a small Node script in our .github/hooks folder. The cwd field sets the working directory, and the ten-second timeout keeps a stuck script from blocking the agent forever. You can also provide environment values or operating-system-specific overrides. Whenever possible, use a runtime that works across your team's environments. If Windows, macOS, and Linux genuinely need different commands, make those differences visible in the configuration rather than hiding them inside a fragile shell expression.

Hook Execution Flow

graph LR
  A[Lifecycle event] --> B[JSON on stdin]
  B --> C[Hook command]
  C --> D{Outcome}
  D -->|Success| E[Agent continues]
  D -->|Control result| F[Agent responds]
  D -->|Timeout or failure| G[Diagnostic]
Here's what happens when that event fires. First, VS Code turns the event data into JSON and sends it to the hook command through standard input. The script reads and validates that payload, does a small, bounded piece of work, and returns an outcome. Some events can use structured output or exit behavior to influence what the agent does next. One practical rule: treat standard output like a protocol channel. If the hook is returning JSON, don't mix random debug messages into the same stream. Send diagnostics to standard error or to a deliberately sanitized log. To configure hooks, use Chat: Configure Hooks or type slash-hooks in chat. If something fails, open the GitHub Copilot Chat Hooks output channel or the agent debug log to see what actually ran.

Hooks Are Executable Policy

Do

  • Review hook code before trusting a repository
  • Validate every field received from standard input
  • Use least privilege and short timeouts
  • Log only sanitized metadata

Avoid

  • Passing untrusted input directly to a shell
  • Printing prompts, source code, secrets, or tokens
  • Running broad commands after every tool call
  • Assuming a hook is sandboxed
Let's slow down here, because hooks deserve a stronger security posture than the Markdown files we just covered. A hook runs with your user permissions. That means a malicious or careless script could read files, modify the workspace, access credentials available to your process, or send data over the network. Always validate the JSON payload before you use it, and never paste an untrusted value directly into a shell command. Keep hook scripts small enough to review, give them short timeouts, and return useful failure messages. Be especially careful with logging. Prompts and tool payloads can contain source code, customer data, or secrets, so log only the minimum sanitized metadata you need. Before you trust a repository and enable its hooks, inspect the hook configuration and the scripts it invokes.

When to Use What

Repeat a request?

Prompt file
Invoke a focused task on demand.

Guide behavior?

Instruction file
Provide standards and contextual rules.

Package a workflow?

Agent Skill
Bundle steps, scripts, and resources.

Guarantee an action?

Agent hook
Run code at a lifecycle event.

If you remember one decision slide from this course, make it this one. Are you repeating the same request? Save it as a prompt file and run it when you need it. Does the agent need to understand your standards or project context? Put that guidance in instructions. Are you packaging a multi-step workflow with scripts, templates, or reference material? Build a skill. Does a command have to run at a particular lifecycle event whether the model thinks of it or not? Use a hook. Listen to the verbs: prompts request, instructions guide, skills equip, and hooks enforce. A hook doesn't replace your linter, test framework, or policy engine. It gives that deterministic tool a reliable place in the agent lifecycle.

How They Work Together

graph LR
  A[Prompt starts task] --> B[Instructions guide output]
  B --> C[Skill supplies workflow]
  C --> D[Agent uses tools]
  D --> E[Hook runs check]
  E --> F[Agent handles result]

Prompts request. Instructions guide. Skills equip. Hooks enforce.

Let's put all four pieces into one story. A developer invokes a prompt that says, "Create an API endpoint." That prompt starts the task. Repository instructions tell the agent to use TypeScript, async and await, and the team's Express patterns. An API skill gives it the approved workflow, working examples, and a validation script. The agent edits the files and calls the tools it needs. Then a PostToolUse hook runs the formatter or audit check after the relevant operation, and the agent responds to that deterministic result. That's the whole architecture in one sentence: prompts request, instructions guide, skills equip, and hooks enforce. The first three improve the model's decisions. The hook connects those decisions to code that definitely runs.

These Four Are Not the Whole Platform

NeedCustomizationWhat it adds
Specialized roleCustom agentPersona, tools, model, handoffs, and subagents
External systemMCP serverTools and data from APIs, databases, or services
Packaged distributionAgent pluginInstallable bundle of customizations
Before we wrap up, I want to place these four building blocks back into the larger platform. This course is not claiming that Copilot has only four customization options. If you need a specialized role with its own tools, model, handoffs, or subagents, that's a custom agent. If the agent needs to reach an external API, database, or service, that's where MCP fits. If you want to distribute a ready-made bundle of customizations, look at agent plugins. Hooks don't replace any of those options. They add deterministic lifecycle automation alongside them. So think of today's four as a practical beginner framework, not the edge of the platform.
Summary

Wrap-Up & Next Steps

We're in the home stretch. Let's recap the key points and talk about where to go from here.

Key Takeaways

  • Prompt files (.prompt.md) capture reusable tasks that people invoke on demand
  • Instruction files provide repository-wide or conditional guidance for chat
  • Agent Skills (SKILL.md) package workflows, scripts, and supporting resources
  • Agent hooks (.json) run commands at defined lifecycle events
  • Prompts, instructions, and skills guide the model; hooks provide deterministic automation
  • All four can be versioned with the repository and reviewed by the team
Let's bring it all together. Prompt files save a task that someone chooses to start. Instruction files give the agent standards and context for the work in front of it. Agent Skills package a reusable workflow and load supporting material only when it's needed. Hooks run executable commands when lifecycle events occur. The most important distinction is the line between guidance and enforcement. Prompts, instructions, and skills improve what the model decides to do. Hooks connect the agent loop to deterministic automation. Keep all four in supported discovery locations and review them through the repository. And because hooks execute code, keep them especially small, focused, and trustworthy. Remember that hooks are still Preview and may be unavailable if settings or organization policy disable them.
