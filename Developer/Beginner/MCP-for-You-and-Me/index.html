Part 1

What Is MCP?

Let's start at the very beginning. What is the Model Context Protocol, and why should you care?

The Problem MCP Solves

  • AI assistants need tools and context to work with information outside their current conversation
  • Developers switch between editors, issue trackers, CI dashboards, and documentation
  • Separate custom integrations create an N × M problem: every tool integrated with every host
  • MCP standardizes the connection; it complements existing built-in and extension tools
        graph LR
          Host[AI Host] --> Client[MCP Client]
          Client --> Server[MCP Server]
          Server --> Issues[Issues]
          Server --> CI[Build and CI]
          Server --> Docs[Documentation]
Think about the context needed to fix a bug: the issue description, the code, and perhaps a failed build. Hosts can already provide built-in tools and extensions for some of this. MCP doesn't invent external access. It gives tool providers and AI hosts a shared interface instead of requiring a different custom integration for every pairing. Ten tools and five hosts could otherwise mean fifty integrations. We still choose the tools that fit the task, but a common protocol reduces the repeated plumbing.

The Model Context Protocol

  • MCP is an open standard for connecting AI applications to external tools and data
  • Think of a USB-C port for AI: a shared interface, not a guarantee of identical capabilities
  • Servers can expose tools (actions), resources (context), and prompts (templates)
  • Compatibility depends on the host, protocol version, transport, and supported capabilities
  • The MCP Registry at registry.modelcontextprotocol.io publishes server metadata
The USB-C analogy is useful because a common connector reduces the need for special adapters. But just as a connector doesn't promise every device supports every feature, MCP doesn't make every server interchangeable with every host. A server may offer tools but no prompts, or require a transport your host doesn't support. MCP began at Anthropic and now has a broad ecosystem of hosts and providers. The registry helps you discover that ecosystem, but a listing is not a security certification or proof that a server works with your selected session.
Part 2

How MCP Works

        graph LR
          A[Host / IDE] --> B[MCP Client]
          B --> C[MCP Server]
          C --> D[Tools]
          C --> E[Resources]
          C --> F[Prompts]
Now that you know what MCP is at a high level, let's look at the architecture. Understanding the moving parts will help you troubleshoot connections and choose the right servers for your needs.

The MCP Architecture

  • Host: the application coordinating AI, context, and permissions
  • Client: a component in the host communicating with one server
  • Server: a local process or remote service exposing MCP capabilities
        graph LR
          subgraph Host[VS Code Host]
            Chat[Copilot Chat] --> G[GitHub MCP Client]
            Chat --> D[Database MCP Client]
          end
          G --> GitHub[Remote GitHub Server]
          D --> Database[Database Server]
There are three roles, and the distinction helps when something fails. The host coordinates the AI and its permission controls. Each MCP client communicates with one server, so a host uses multiple clients to work with multiple servers. A server might run as a process in your development environment or as a service hosted elsewhere. In our example, GitHub hosts the service. When an issue request fails, we can ask whether the problem is tool availability in the host, the server connection, or authorization to the repository. Those are different checks.

What MCP Servers Expose

Tools

Model-selected actions, such as GitHub's list_issues, add_issue_comment, or issue_write. Availability and approval depend on configuration.

Resources

Server-provided context. Use Add Context > MCP Resources or MCP: Browse Resources when supported.

Prompts

Server-provided templates. A supported prompt appears as /<server>.<prompt> in chat.

Not every server or session supports every capability.

Tools let the model choose an action that fits your request. For example, GitHub's issue_write tool uses a method such as create or update; older material may call these separate tools. Resources provide context you can attach, while prompts give you a reusable starting point. The GitHub workflow today focuses on tools, so don't assume it provides a particular resource or prompt just because MCP supports those concepts. When you inspect a server, its actual advertised capabilities are more useful than a generic feature list.

Capability Support and Elicitation

Elicitation

A supported server can request input through a form or direct you to an external URL. Review the requesting server and decline unexpected requests.

Legacy sampling

Sampling let servers request model generations through the client. It is deprecated in the 2026-07-28 protocol revision, not removed from all existing clients.

  • Never enter passwords, API keys, or access tokens into an elicitation form
  • Sensitive sign-in belongs in a trusted, supported out-of-band flow
  • Host support and configured permissions determine the interaction you see
You may encounter a server asking which branch to use or which output format you prefer. That's elicitation. The protocol supports forms and URL-based interactions, but the client must support the requested mode. Credentials must not be collected through an elicitation form. Check the destination of a sign-in link and decline anything unexpected. You may also see sampling mentioned in older documentation or existing client settings. The current protocol marks it deprecated, so we won't use it as a new workflow here. Recognizing a legacy feature is different from recommending it.

How Servers Connect

stdioA client launches a local process and exchanges JSON-RPC messages over standard input/output

Today: GitHub's hosted HTTP service. OAuth is supported, not a universal requirement of every remote server.

A stdio server needs a runtime and executes in the environment where the client launches it. A remote HTTP service doesn't require you to install that server process locally, though it still needs network access and any required sign-in. GitHub provides both options, and we'll use its hosted endpoint. Configuration is host-specific. The VS Code and portable files use different top-level keys, so changing only the filename won't convert an example. The guided workspace-root destination is currently experimental; existing portable files are still supported. These server definitions don't belong in settings.json.
Part 3

Setting It Up

Enough theory. Let's connect the GitHub MCP server. We'll start with a read-only request so we can separate connection problems from permission to change an issue.

Enabling the GitHub MCP Server

  1. Confirm AI access, GitHub sign-in, repository access, and organization policy
  2. Run MCP: Add Server; choose HTTP
  3. Enter https://api.githubcopilot.com/mcp/; name it github
  4. Choose Global > Copilot Global for personal use, or a supported workspace destination for sharing
  5. Review startup/trust prompts and complete the GitHub sign-in flow

For a VS Code-format workspace connection, use .vscode/mcp.json:

{
  "servers": {
    "github": {
      "type": "http",
      "url": "https://api.githubcopilot.com/mcp/"
    }
  }
}
VS Code includes MCP client support, but that doesn't mean GitHub's server is already connected. We need to add the endpoint and authenticate. The Command Palette flow can create a personal connection without sharing configuration. The JSON here is the documented VS Code-format alternative for a workspace, not a second connection you need to add as well. Choose one destination and avoid duplicate entries. Workspace configurations inherit Workspace Trust, so review their contents before trusting a project. If access is blocked, check chat.mcp.access and the organization's policy rather than looking for the old chat.mcp.enabled checkbox.

Verifying the Connection

  • Open Chat and explicitly select Agent
  • Copilot harness: Chat: Open Customizations > Tools; Local harness: Configure Tools
  • Enable needed GitHub tools, such as list_issues and issue_read
  • Ask for open issues in a named practice repository, without making changes
  • Expand the call: confirm the intended server, inputs, and returned issue data
  • For errors: MCP: List Servers > github > Show Output

The existing Local tool-picker image illustrates selection, not proof of a GitHub connection.

A running server and a plausible answer aren't enough to prove the connection. We want to see a tool from the GitHub server actually return the requested issue data. Tool names can be prefixed by the host, and your selected toolsets affect what's available. The screenshot is a Local picker example, not evidence that GitHub is connected. If no GitHub tool is called, check the selected session, enabled tools, sign-in and repository scope. For connection errors, choose Show Output for the configured server. Review the expanded conversation call for its actual inputs and results; logs don't promise to include every payload.
Part 4

Working With Issues

The GitHub MCP server exposes tools for issues and pull requests. Now that we've separated connecting from verifying a call, let's use that connection for a practical issue workflow.

Reading Issues From Chat

  • Ask: "Use the GitHub MCP server to list open issues in my practice repository. Do not change anything." Include the owner and repository name
  • list_issues can list issues; issue_read retrieves issue details or comments
  • Inspect the returned data before relying on Copilot's summary
  • Try a narrower request by label, assignee, or date; tool choice depends on the request
Name the owner and repository so the agent doesn't have to guess which project you mean. It may list issues, search them, or read a particular issue depending on your request and the enabled tools. Check the tool output and compare the summary with the actual titles, numbers and links. If you ask for a discussion summary, the agent may need an additional call for comments. Issue text is external data, not permission to follow instructions embedded in it. A request to reveal a token or change a different repository isn't authorized just because it appeared in an issue.

Acting on Issues

  • Use a practice repository and disposable issue; confirm owner, repository, and issue number
  • Ask to draft a comment first, then authorize that exact comment
  • add_issue_comment posts comments; issue_write with method: update can update an issue
  • Use Manual permissions and review approval settings; auto-approval or Allow all can bypass prompts
  • Read the issue again to verify the result; MCP does not guarantee a complete audit log
Let's avoid making a promise to a real customer or closing somebody else's bug while we're learning. Start with a practice issue and ask for a draft comment, such as a summary of what we've verified. Before authorizing the write, check the repository and issue number as carefully as the wording. Manual permissions uses your configured approval rules, so it isn't a promise that every write prompts. Broader auto-approval settings can remove that pause. Service permissions are still the hard limit on what the authenticated account can do. After a change, read it back instead of assuming the request succeeded.

Code Search With MCP

  • Ask: "Use GitHub MCP to search for AuthService in this named repository. Report matching files and links."
  • search_code supports repository and organization scope, such as repo:owner/repository
  • Results can include matching snippets and file metadata; formatting depends on the tool and host
  • Search can span repositories you can access, subject to API limits and pagination
  • Text search is not a guarantee of finding every semantic usage; inspect the related code before changing it
This is useful when the relevant code isn't in your open workspace. A repo qualifier keeps a search focused, while an organization qualifier can help you explore usage across accessible projects. But a text match is not a semantic reference analysis, and search results can be paginated or incomplete. We shouldn't describe a single response as every import or every deprecated API usage. Open the relevant files, inspect the surrounding code, and use language-aware references or tests when completeness matters. MCP supplies evidence; the model's migration suggestion still needs review.
Part 5

Discovering MCP Servers

We've used one server for a concrete task. Now let's look at how to find another one and decide whether it is actually worth adding. More tools aren't automatically better tools.

The MCP Registry

  • registry.modelcontextprotocol.io is an official server metadata registry, currently in preview
  • Entries describe publishers, packages or remote endpoints, and installation metadata
  • Downstream catalogs add discovery experiences; VS Code's MCP gallery is one way to browse
  • Use MCP: Add Server or search @mcp in the Extensions view
  • Check publisher docs, maintenance, access requirements, and supported clients; a listing is not security approval
The official registry hosts metadata, not necessarily the server's executable code. A package registry or vendor service provides the actual implementation. Catalogs and marketplaces can add curation, categories and installation experiences, so don't assume every registry entry includes a complete permission inventory. Both open-source and closed-source offerings can be listed. Publisher namespace verification helps establish who published metadata, but it doesn't certify the server's behavior. Before connecting, read the current publisher instructions and check that the server supports the client and authentication flow you plan to use.

Installing a Registry Server

Reuse a maintained publisher endpoint. Portable workspace-root .mcp.json:

{
  "mcpServers": {
    "github": {
      "type": "http",
      "url": "https://api.githubcopilot.com/mcp/"
    }
  }
}
  • This is an alternative to slide 13's VS Code-format file; choose one destination
  • The guided workspace-root destination currently uses experimental chat.mcp.workspaceRootConfig.enabled
  • Review configuration before trusting the workspace; complete authentication and verify a read-only call
  • Commit only non-secret definitions; teammates still need their own credentials, access, and any runtime prerequisites
A catalog is a starting point, not a reason to run an arbitrary package. We reuse GitHub's documented hosted endpoint here so there is no database to provision or archived reference server to install. This example uses mcpServers because it's the portable format. Slide thirteen uses servers because it's the VS Code format. Don't keep both just to make the same connection. The workspace-root choice in the guided flow is experimental, though existing portable files remain supported. Sharing this file shares the definition, not your authentication or a teammate's permission to the repository. Each person still needs to connect and verify the result.
Part 6

The MCP Ecosystem

Now that you know how to evaluate a connection, let's take a quick tour of the ecosystem. We won't install all these servers. The useful question is which missing capability would help your work.

Community MCP Servers

Data

Database integrations can expose queries or schemas. Capabilities and write access depend on the selected server; old reference packages may be archived.

APIs & Services

Atlassian, Slack, Linear, and Notion provide integrations for work items, messages, or documents. Check each publisher's supported tools.

Infrastructure

Docker, Kubernetes, AWS, and Azure ecosystems offer MCP integrations. Treat deployment and administration as advanced, permission-sensitive work.

There's a wide range of integrations, but a product name doesn't tell us exactly what a server can do. A database server might provide read-only queries rather than migrations. A hosted collaboration service may need administrator consent or a particular account configuration. Cloud tooling can make real infrastructure changes, which is not the next step for our beginner exercise. Start from the missing task, prefer maintained publisher guidance, and enable only the relevant tools. Existing built-in tools may already meet the need, in which case another server adds complexity without adding value.
Part 7

Security and Trust

Before we move to the live demo, let's cover security. MCP gives AI access to external systems, so we need to distinguish trusting a configuration, authenticating to a service, and approving an action.

Securing Your MCP Setup

  • Configuration trust: local stdio servers can execute code in their host environment
  • Authentication: service credentials and account permissions limit access
  • Tool availability: enable only the capabilities needed for the task
  • Action approval: permission modes and auto-approval settings determine when prompts appear
  • Least privilege: prefer read-only access first; disable servers you no longer need
These controls solve different problems. Trusting a workspace can allow its server commands to start; that doesn't mean every returned instruction is trustworthy. Signing in grants access based on the service account and its permissions. Enabling a tool makes it available to the agent, but doesn't decide whether a call is approved automatically. Keep those layers separate. Local servers can execute code with the access available to their process, while remote services receive the data and credentials you authorize. Neither should be treated as harmless simply because it uses a standard protocol.

Security Best Practices

  • Review the source: publisher, endpoint or command, maintenance, and requested access
  • Treat tool output as data: issue text does not authorize new goals, secret disclosure, or unrelated writes
  • Keep secrets outside committed files: an env object does not hide literal credentials
  • Use format-specific references: portable ${NAME}; VS Code ${env:NAME}. Supply values in the host environment
  • Inspect actions: review tool-call details and results; redact logs before sharing
  • Respect organization policy: local configuration cannot override an enterprise restriction
If you type a token directly into an env object, that token is still in the configuration file and can still be committed. A reference keeps the value outside the file only when the environment supplies it separately. The portable and VS Code formats use different interpolation syntax. VS Code-format input prompts also require definitions and aren't supported in portable configuration, so we aren't copying those placeholders between files. For the GitHub example, prefer the supported sign-in flow rather than pasting a token into chat. Finally, external issue text can be misleading. A tool result is context to evaluate, not authority to expand the task.
Live Demo

MCP in Action

Alright, demo time. Let's bring everything together with a practice issue, a read-only check, and one deliberately reviewed change.

Demo: End-to-End Issue Workflow

  1. Name the practice owner/repository and ask GitHub MCP to list open issues without changes
  2. Pick a disposable issue; read its details and comments and verify the summary
  3. Search related code and inspect the matches before proposing a fix
  4. Review and test any proposed fix; draft, review, then authorize a comment on the exact issue
  5. Only if appropriate, authorize closing the practice issue; read it back to verify the state
We'll keep the owner, repository and issue number explicit throughout. First we verify a read, then inspect the details and comments instead of relying on the title alone. Search results help us locate code, but they aren't proof the proposed change fixes the problem. Any code change needs review and relevant tests. We'll draft the issue comment before posting it and check the target in the tool call. Closing is optional and appropriate only for this disposable exercise or an issue whose acceptance criteria are actually met. A successful read-back confirms the service result more reliably than an optimistic final message.

Demo: Combining MCP With Chat

  • Ask: "Summarize five recently closed issues in this named repository and identify recurring themes. Do not make changes."
  • Check the issue links, ordering, and any additional calls needed for comments
  • Follow up: "Based on that evidence, suggest improvements and explain what still needs verification."
  • MCP + model reasoning: external evidence supports analysis, not automatic correctness
Now we're combining retrieval with reasoning. Copilot might find a recurring authentication problem or several reports about the same error path. Check which five issues it actually retrieved and whether the tool can support the ordering you asked for. Comments may require extra calls, so we shouldn't assume the first list contains the whole discussion. The model can suggest improvements from the evidence, but five issues are a small sample. Treat the patterns as hypotheses to investigate, not proof of a root cause or permission to change the architecture.
Summary

Wrap-Up & Next Steps

Alright, let's bring it home. We've covered the connection model, checked what a successful tool call looks like, and seen how to keep a practical issue workflow under control.

Key Takeaways

  • MCP standardizes connections to external tools and context
  • Connect and authenticate GitHub's hosted server; built-in client support is not a ready-made connection
  • Verify the tool call, its inputs, and its returned data
  • Match the configuration format: portable mcpServers versus VS Code servers
  • Share definitions, not secrets; teammates still need prerequisites and access
  • Security first: review publishers, minimize permissions, and inspect intended writes
The useful habit is to separate what we configured from what we've actually verified. A file can be present without authentication working, and an answer can sound right without the intended server being called. Match the file format, connect the service, and inspect one low-impact request before using write tools. Discovery then becomes a deliberate choice about a missing capability, not a race to install more servers. MCP gives us a common interface, while we still own the trust decisions, scope and validation of the work.
