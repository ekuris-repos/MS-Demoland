Part 1

The Multi-Repo Reality

Let's start with the foundational question: why do enterprises work across so many repositories, and why does this matter for AI tooling?

Why Enterprises Have Many Repos

  • Team autonomy: Each team owns its repos, codebases, and release cycles
  • Microservices architecture: Teams may choose separate repos for independently deployed services
  • Shared libraries: Common utilities, SDKs, and design systems live in dedicated repos
  • Infrastructure as code: Terraform modules, Bicep templates, and Helm charts in separate repos
  • Compliance boundaries: Some requirements call for different access controls or repository separation
  • Acquisitions and growth: New repos arrive through mergers, acquisitions, and organic expansion
        graph LR
          Frontend[Frontend Repo] --> Shared[Shared Contracts]
          Backend[Backend Repo] --> Shared
          Infra[Infra Repo] --> Shared
          Mobile[Mobile Repo] --> Shared
          Shared --> Delivery[Release Coordination]
Many enterprises operate numerous repositories because ownership, release cycles, and access boundaries differ. Repo-per-service is a choice, not a requirement of microservices. Shared libraries often need separate versioning, while infrastructure teams may maintain their own deployment templates. Compliance can require different controls, but it does not always require physical separation. Our starting point is simply that important contracts often cross repository boundaries, so the agent needs a deliberate way to retrieve and validate them.

Monorepo vs. Polyrepo Tradeoffs

Monorepo

Advantages: Atomic commits across components. Unified CI/CD. Single source of truth for dependencies.

Challenges: Tooling complexity at scale. Broad blast radius on changes. Access control granularity is harder.

Polyrepo

Advantages: Team autonomy. Clear ownership. Independent release cycles. Fine-grained access control.

Challenges: Cross-repo changes require coordination. Dependency drift. AI context is fragmented.

Before we go further, it is worth acknowledging the monorepo versus polyrepo debate. Monorepos give you atomic cross-component commits and a shared dependency graph, but they require tooling and ownership discipline at scale. Polyrepos give teams independence, but cross-cutting changes become coordination exercises. We focus on that second scenario. A monorepo reduces repository boundaries; it does not put the entire codebase into every model request. Search and selective retrieval are still necessary.
Part 2

Copilot's Context Model

        graph LR
          Request[User Request] --> Search[Search Available Sources]
          Search --> Read[Read Relevant Files]
          Read --> Context[Selected Context]
          Context --> Answer[Proposed Answer]
Now let's examine how Copilot finds relevant code. An index helps it discover material; tools then retrieve selected files or snippets. The resulting context is useful but incomplete, so we still check whether the source and version match the task.

How Copilot Understands a Single Repo

  • Editor context: Selected text and relevant files can inform a request
  • Semantic indexing: Helps retrieve relevant code, not load the entire repo into context
  • Custom instructions: .github/copilot-instructions.md guides behavior at the repo level
  • Search and symbol tools: Find files, definitions, imports, and usages when available
  • Conversation history: Earlier messages and tool results shape ongoing responses
Copilot combines the context you provide with information it retrieves. In an agent session, semantic search, text search, file reading, and symbol tools can uncover related code beyond the current editor. Repository instructions provide conventions, while conversation history carries forward earlier decisions. Availability depends on the surface, selected tools, permissions, and exclusions. None of this guarantees that every relevant file was found, so explicitly reference critical interface contracts.

The Cross-Repo Context Gap

  • Do not assume another repository's code is already in the current request
  • Shared library APIs, interface contracts, and data models need explicit retrieval
  • Cross-repo breaking changes require source/version checks and integration tests
  • Repository files are not automatically inherited by other repositories
  • Missing context leads to inconsistent suggestions, duplicated code, and integration errors
        graph LR
          App[Frontend Repo] --> Agent[Agent Request]
          Contract[API Repo Contract] -. Explicit Retrieval .-> Agent
          Agent --> Check[Verify Contract Version]
          Check --> Change[Proposed Client Change]
When Service A calls an API defined in Service B, a plausible guess is not enough. We need the actual interface, error shapes, and versioning policy. Consider an illustrative React frontend and Express API in separate repositories. Retrieving the API contract can improve a client change, but a repository link alone is not proof that the agent successfully read it. Ask for the source path and ref, then run compatibility checks. This archived deck does not certify a particular demo repository or hands-on environment.

Repository Indexing Deep Dive

  • Automatic indexing: Repository context can trigger semantic indexing for Copilot
  • Selected retrieval: Search returns relevant snippets, not complete repository knowledge
  • Exclusions: Binary files and excluded workspace files are not part of the semantic index
  • Beyond the workspace: VS Code documents #githubRepo and #githubTextSearch for scoped GitHub searches
  • Surface-specific UX: Use documented context controls; this refresh does not verify @github across clients
Repository indexes make relevant code easier to discover, but an index is not a shared organizational brain. In VS Code, #codebase searches workspace context, while documented GitHub repository and text-search tools can look beyond the workspace when available and authorized. GitHub.com has its own context selection. We have not verified the older @github recipe across both surfaces, so do not depend on it. Check index status, permissions, exclusions, and returned sources when a search misses an important contract. An ignored file that is explicitly opened or selected can still enter editor context.
Part 3

Org-Level Custom Instructions

One of the simplest ways to improve cross-repo consistency is shared guidance. Let's separate organization settings from files copied into each repository, because those are different mechanisms with different update paths.

Custom Instructions Strategy

  • Repo-level: .github/copilot-instructions.md in each repository
  • Org-level: Organization owners configure instructions in organization settings, not the special .github repository
  • Supported org surfaces: Current GitHub docs list Chat, code review, and cloud agent on GitHub.com; do not assume IDE inheritance
  • CCPR template: A local Central Code Prompt Repository pattern copies standard files when repos are created
  • Maintenance: Template changes need a separate sync/review process for existing repos
  • Enforcement: Instructions guide behavior; CI, rulesets, and human review enforce standards
At the repo level, the instructions file captures conventions and project details. Organization instructions are entered through organization settings; putting a file in the organization's special .github repository does not establish this inheritance. Current GitHub documentation lists supported GitHub.com surfaces, so we do not promise that an IDE receives those settings. A CCPR is our name for a reusable template pattern, not a separate GitHub product. It gives new repositories a reviewed starting point, but copies do not automatically receive later template edits. Assign an owner to synchronize changes through pull requests, and keep enforcement in deterministic checks and review gates.

CCPR-Based Instructions Example

# Template copy: .github/copilot-instructions.md
# Update existing repositories through reviewed sync PRs.

## Language and framework standards
- Use TypeScript for backend services.
- Follow our REST naming: /api/v{n}/{resource}.

## Error handling and security
- Return structured errors with correlation IDs.
- Never hardcode credentials or secrets.
- Require authentication for API endpoints by default.

## Cross-service communication
- Reference versioned OpenAPI contracts in docs/api/.
- Test consumer compatibility before changing a contract.
Here is an illustrative repository instructions file copied from a shared template. It describes cross-cutting conventions but belongs to this repository after creation. Its contract reference should identify a real, accessible source rather than assume that all agents already know another repo. We can review template updates centrally, then propose sync pull requests to existing repositories. Organization settings remain a separate source of guidance on supported surfaces. We are not claiming that a particular demo application already contains this file.

Scaling Instructions with Prompt Files

  • Prompt files (.prompt.md) define reusable tasks invoked as slash commands
  • Workspace scope: Keep team prompts in .github/prompts and review changes through PRs
  • User scope: VS Code profile prompts can be available across your workspaces
  • Team distribution: Templates seed new repos; a reviewed sync process updates existing copies
  • Use cases: Generate endpoints, write tests, and plan contract migrations
  • Combine explicit task prompts with automatically applied custom instructions
Prompt files give us repeatable task requests, while custom instructions provide standing guidance. Workspace prompts are useful for shared conventions because the team can version and review them. User-profile prompts solve a different problem: personal reuse across workspaces. A CCPR template is one distribution option, not the only supported scope or a live update channel. For team-wide rollout, decide how you will propose updates, handle repo-specific exceptions, and detect drift before copying the same file everywhere.

Instructions tell the agent how we prefer to work. Source context tells it what our system actually does. Let's distinguish repository search from a curated Space, and keep permissions and source versions visible in both.

Copilot Spaces and Repository Search

MechanismPurposeBoundary to check
Repository semantic indexFind relevant code snippetsSource scope, exclusions, index state
Explicit cross-repo searchRetrieve a named repo or org sourceAvailable tools and repository access
Copilot SpacesCurate code, docs, issues, and other contextSpace sharing and underlying source access
MCP toolsFetch data or perform permitted actionsHost policy, tool scope, credentials, ref

Spaces replaced Copilot knowledge bases on November 1, 2025. Current docs allow Spaces with any Copilot license, including Free, subject to access and policy.

These mechanisms complement one another rather than form a strict documentation-versus-code split. Indexes help retrieve relevant code; a Space curates reusable context that can include code and documentation from several sources. GitHub-based sources in Spaces stay synchronized as they change. That does not grant access to sources a viewer cannot otherwise read. MCP tools can add authenticated retrieval and actions. We are replacing the older ambiguous Enterprise-only search framing, not promising that every indexed repository is automatically searched or placed into every response.

Curating Effective Cross-Repo Context

  • Architecture Decision Records: Explain why teams chose particular patterns
  • API contracts: Identify source repo, path, version/ref, and compatibility policy
  • Shared library guides: Document supported APIs and consumer examples
  • Runbooks: Keep operational procedures owned and current
  • Spaces: Curate relevant code and docs without bypassing source permissions
  • Validation: Check retrieved sources and run tests; context is not proof of correctness
Architecture decisions give us the reasoning behind an interface. Versioned contracts give us the exact boundary a consumer must respect. Put both within reach through scoped search or a curated Space, and keep ownership clear. GitHub sources can synchronize automatically, but that does not make an obsolete design decision or incomplete contract correct. For a migration, record which ref you used and validate consumer behavior. That creates reproducible evidence instead of relying on the model's confidence.
Part 5

MCP Servers as Cross-Repo Bridges

When we need an authenticated lookup or action beyond the current workspace, an MCP server can expose that capability as a tool. Let's focus on retrieval boundaries and provenance before considering custom implementation.

MCP for Cross-Repo Context

  • GitHub MCP Server: Official tools for repositories, files, issues, and pull requests
  • Remote option: GitHub hosts a server; use supported authentication and organizational policies
  • Custom tools: Retrieve contracts or schemas only when built-in tools are insufficient
  • Freshness: Invocation can fetch current data; verify branch/ref, caching, and returned source
  • Access: Read and write capabilities depend on enabled tools and scoped credentials
        graph LR
          Agent[Agent] --> Tool[Authorized MCP Tool]
          Tool --> Repo[Selected Repo and Ref]
          Repo --> Result[Content and Provenance]
          Result --> Agent
The official GitHub MCP server already exposes many repository operations, so start there before building a custom bridge. A compatible client can use the GitHub-hosted server rather than require a local deployment. Scope credentials and enabled tools to the task. MCP itself does not guarantee fresh data: a tool may return cached content, a different branch, or an access error. Ask which source and ref were read, and handle missing data explicitly. For coordinated edits, reproducible contract versions can matter more than always selecting the latest default branch.

Example: Cross-Repo API Spec Tool

Design sketch, not executable SDK code. No package/API version, repository path, or runtime is certified here.

TOOL get-api-spec(service, contractRef):
  require service is in the approved repository allowlist
  resolve repository and contract path from trusted configuration
  require read-only credentials for that repository
  fetch the file at contractRef
  if request fails or result is not a readable text file:
    return an explicit error, not a guessed contract
  return text plus repository, path, and resolved commit

CLIENT:
  cite the returned contract and commit
  validate the consumer change with compatibility tests
This is a design sketch, not runnable MCP or Octokit code. We have not selected an SDK version, verified a particular OpenAPI file, or tested server registration and transport. A real implementation must validate the repository, ref, response type, encoding, and error path before exposing content. The important cross-repo pattern is a narrow read-only tool that returns provenance alongside the contract. Prefer the official GitHub tools if they already satisfy that requirement. Do not copy this pseudocode into a project expecting it to register a working server.
Part 6

Copilot Cloud Agent Across Repos

The cloud agent, called the coding agent in older material, performs delegated work on GitHub. Its target-repository write boundary is different from the broader read context a configured tool might provide. That distinction shapes our coordination patterns.

Cloud Agent Fundamentals

  • Start a task through a supported entry point, such as assigning an eligible issue
  • The agent works in an ephemeral development environment and proposes reviewable changes
  • It can read context, plan changes, write code, and run tests; verify the reported results
  • Environment setup: .github/workflows/copilot-setup-steps.yml, with a copilot-setup-steps job on the default branch
  • Behavior guidance: Repository custom instructions are separate from setup steps
  • Write scope: One target repository per run; broader MCP read context needs configuration
A cloud-agent task has a target repository. It can propose changes there, but current documentation does not support one run making changes across several repositories. You may configure broader context access through MCP without expanding that write boundary. Setup steps are a special Actions workflow, not a natural-language instructions file, and the required job must be on the default branch. The agent's test output is evidence to inspect, not a replacement for required checks or human review.

Multi-Repo Patterns with the Cloud Agent

  • Parallel issues: Create linked tasks and explicitly assign/start the agent for each target repo
  • Dependency chain: Validate the upstream contract before migrating consumers
  • Template issues: Embed versioned contracts, acceptance criteria, and repository-specific context
  • Reference linking: Include accessible source links; verify successful retrieval or embed essential details
  • Coordinated PRs: Track and review each PR; merges across repositories are not atomic
Separate cloud tasks can still form a coherent multi-repo workflow. Use parallel tasks for independent changes, and dependency ordering when the consumer needs an upstream contract. Make retrieval explicit: a link to a private repo is not proof that the agent can read it. Embed essential contract details or configure authorized access, then ask for the source used. Track the resulting PRs together, but plan for partial completion and staggered merges. There is no single atomic commit across these repositories.

Local Parallelism: Sessions and Worktrees

  • Independent task: Start a new session; another chat may share the same session's files
  • Delegated subtask: Native subagents use separate conversation context and return results
  • File isolation: Use a distinct worktree/window per editing task; moving Chat into an editor is not isolation
# PowerShell; run from the parent of both existing repos.
# Prerequisite: neither repo already has a migration branch.
git -C .\api-repo worktree add -b migration ..\api-migration
git -C .\frontend-repo worktree add -b migration ..\frontend-migration
code -n .\api-migration
code -n .\frontend-migration

Worktrees separate checkout files, not ports, databases, external services, or all Git metadata. Review and merge per repo.

Local sessions, subagents, and worktrees solve different problems. A fresh conversation does not automatically isolate files, and a subagent's separate context does not guarantee a separate checkout. The commands illustrate creating a new migration branch in each existing repository and opening separate editor windows. They were checked against the documented command syntax, not executed here. Worktrees share repository metadata, and parallel tasks can still collide through runtime resources or external services. You remain responsible for task scope, integration checks, and merge order. Use the session controls supported by your installed VS Code version; the older Open in Editor click sequence is not verified by this refresh.

GitHub Actions as Agent Triggers

  • Use repository_dispatch or other supported events to trigger workflows in target repos
  • A coordinator discovers consumers and creates linked issues with versioned migration context
  • Start explicitly: Assign/start the cloud agent through a supported entry point; issue creation alone is insufficient
  • Separate credentials: App installation tokens can support permitted issue/dispatch operations; the current agent tasks API requires user-to-server tokens
  • Check eligibility, preview API requirements, bounded concurrency, duplicate prevention, and review gates
Consider a library release that requires consumer changes. An Actions workflow can discover affected repos and create issues containing the contract ref, breaking-change summary, and acceptance criteria. Something must then start the agent: explicit assignment, a supported task entry point, or a separately configured eligible automation. Do not assume newly created issues are automatically picked up. Authentication is also operation-specific. The current agent tasks API is in preview and does not accept GitHub App installation tokens, even though such tokens can be useful for other permitted coordinator operations. Keep issue creation and agent initiation as separate, observable steps.
Part 7

Multi-Agent Orchestration

Now let's explore patterns for coordinating multiple agents working across repositories simultaneously. Native subagents help within a session; a cross-repo rollout still needs clear ownership, dependency checks, and a completion rule.

Orchestration Patterns

One Cloud Task Per Repo

Assign/start an independent task per target repo. Link issues and PRs, then coordinate validation and reviews. Native local subagents are a different form of delegation, not extra cloud write scopes.

Coordinator Pattern

A workflow or application creates and sequences tasks, observes results, and starts downstream work after upstream validation. This is a coordination design you build; native automations do not make cross-repo merges atomic.

The one-task-per-repo pattern is a good starting point when changes are independent. A coordinator becomes useful when consumers depend on an upstream change or when you need controlled rollout batches. Native VS Code subagents can divide research and other scoped work, but do not erase the cloud agent's repository boundary. Likewise, platform automations can reduce custom scheduling code without solving compatibility or partial failure for you. Choose the simplest mechanism that preserves a clear source, owner, and review gate for each change.

Fan-Out Pattern

  • Trigger: A validated core change or release starts the coordinator
  • Discovery: Identify affected downstream repositories and eligible tasks
  • Distribution: Create linked issues with contracts, refs, and acceptance criteria
  • Execution: Explicitly assign/start each agent with bounded concurrency
  • Aggregation: Track task/PR links, failures, retries, and compatibility results
  • Completion: Humans review and merge in the planned order; handle partial rollout
Fan-out is useful for platform-wide updates, but unchecked fan-out can amplify a mistake. Discover consumers from a maintained manifest or dependency source, create a stable identifier for each migration task, and avoid duplicate issues on retry. Start the agent explicitly and limit concurrent tasks. A completed agent session is not the same as a compatible merged change, so the tracker should distinguish proposed, validated, reviewed, and deployed states. Stop downstream rollout when integration checks fail and retain a recovery plan for repos already updated.

Dependency Management Across Repos

  • Dependabot: Automate supported dependency updates, including configured private registries
  • Breaking change detection: Use type checking and consumer/provider contract tests
  • Shared dependency graph: Maintain a manifest of internal package consumers
  • Agent-assisted updates: Start a scoped migration task when a version bump needs code changes
  • Version policies: Check supported package ranges and compatibility in CI
Dependency management is where cross-repo challenges become tangible. Dependabot can work with private packages when registry access is configured, so internal dependencies are not automatically a manual-only problem. Simple version bumps may need no agent. Breaking changes need a migration guide and behavioral evidence, such as Pact contract tests alongside type and integration checks. An OpenAPI document describes an interface, but validating a schema alone does not prove that every consumer remains compatible. Track which contract and package versions each repo supports.

Code Consistency Across Repos

  • Shared ESLint / linter configs: Publish org-wide linting rules as a package
  • Template repositories: Seed standard structure, CI, and Copilot configuration; sync later updates separately
  • Shared prompt libraries: Reusable .prompt.md files for common coding tasks
  • Automated audits: Periodic workflows check configuration drift and policy compliance
  • Review and enforcement: Bots suggest; required checks, rulesets, and approved reviews gate merges
Consistency requires proactive defaults and reactive checks. Shared linter packages and templates give new projects a good starting point, while reviewed sync updates keep existing projects aligned. Prompt libraries can reuse a well-crafted request, but they do not enforce its outcome. Automated audits can detect missing files or old configurations; deterministic checks and required reviews decide whether a change is acceptable. Keep room for documented repository-specific exceptions rather than blindly copying the same setup everywhere.

Migration Strategies with Agents

  • Large-scale migrations: Framework upgrades, language version bumps, API contract changes
  • Agent-assisted approach: Write a migration guide and scoped acceptance criteria
  • Batch processing: Validate low-risk repos before expanding rollout
  • Compatibility and rollback: Plan dependency order, version windows, and recovery from partial rollout
  • Progress tracking: Use GitHub Projects or a tracking issue across related PRs
A framework upgrade across many services is a compelling use case, but the migration guide must cover renamed APIs, configuration changes, and repository exceptions. Start with low-risk, well-tested consumers before scaling out. Some migrations genuinely depend on an upstream PR, so record the ordering instead of pretending all PRs are independent. Backward-compatible interfaces and expand/contract changes can create a rollback window while both versions coexist. Track validation, merge, and deployment separately, because reverting one repository may not restore a compatible whole system.
Part 8

Governance & Permissions

With agents operating across repos, governance becomes critical. Let's discuss access controls, audit trails, and policies that keep multi-agent workflows safe and compliant.

Agent Access Controls

  • Initiator authorization: Starting a cloud task requires eligible access and enabled policies
  • Agent credentials: Restricted target-repository and branch scope, not the initiator's full permissions
  • Coordinator identity: Scope GitHub App installations and tokens to each required operation
  • MCP credentials: Separately authorize context tools; prefer read-only contract access
  • Merge controls: Keep required checks and independent human review on agent PRs
Authorization to start a task is different from the credentials the task receives. The cloud agent does not simply inherit every permission of the triggering person or application. Its repository, branch, and action restrictions remain important controls. A coordinator has its own credentials, and an MCP server may have yet another access boundary. Do not treat those identities as interchangeable. Review enabled policies and required approvals, including restrictions on the initiating user's approval, before designing an unattended fan-out.

Audit Trails & Compliance

  • Session logs: Inspect agent execution, reported checks, and source references
  • Git / PR history: Review agent attribution, signed commits, diffs, and human approvals
  • Organization audit events: Use documented event types, not an assumption that every tool action is logged
  • Evidence mapping: Connect initiating task, target repo/ref, session, PR, checks, and deployment
  • Compliance export: Verify exact events, retention, access, and export behavior before promising coverage
Traceability comes from several evidence sources, not one universal audit stream. GitHub documents signed cloud-agent commits, attribution, session logs, and audit events. This refresh has not verified an exhaustive event mapping or retention policy, so we cannot claim that every tool call, issue update, or branch operation appears in the organization audit log. Link session evidence to PR history and required checks, then verify the event types your compliance report actually needs. Conversation content and execution details should not be assumed to have identical logging or retention.

Policy Guardrails for Multi-Repo Agents

  • Copilot policies: Check enabled features, repository eligibility, and permitted tools
  • Repository rulesets: Control branch/tag/push behavior and review bypass grants
  • Required checks: Enforce validation before merge; account for workflow approval gates on agent PRs
  • CODEOWNERS: Route reviews; configure required owner approval separately and account for draft PRs
  • Bounded automation: Limit concurrency, prevent duplicates, monitor failures, and provide a stop control
Policies are only useful when they govern the operation you are actually performing. Check repository eligibility and feature policy before starting tasks, then apply rulesets and required checks to the resulting changes. CODEOWNERS routes requests but does not by itself require approval, and draft PRs do not automatically request owner reviews. Agent PR workflows may also require approval before running, depending on configuration. Finally, bound the fan-out in your own coordinator; an API rate limit is not a complete safety policy or a reliable stop mechanism.

The Evolving Landscape

The Departing badge remains because this is an archived course, not an active product roadmap. Let's summarize verified changes and distinguish them from capabilities we still must not assume.

What Is Changing

  • Shared context: Copilot Spaces replaced knowledge bases on November 1, 2025
  • Integrations: GitHub App-based Copilot Extensions sunset November 10, 2025; use supported MCP integrations
  • Not retired: Ordinary GitHub Apps and client-side VS Code extensions are separate
  • Local coordination: VS Code 1.109 added parallel subagents and unified session management in February 2026
  • Automation: Agentic Workflows was announced in preview February 13, 2026; check current support before adopting
These are dated changes, not predictions. Knowledge bases and GitHub App-based Copilot Extensions are retired paths, so we should not recommend them as current defaults. The Extensions sunset does not apply to ordinary GitHub Apps or client-side VS Code extensions. Native subagents and session management already exist, and Agentic Workflows provides a declarative automation option in preview. We verified these sources on October 27, 2026; that verification date is not a release date for every capability. Preserve useful coordination patterns while replacing obsolete mechanisms.

What to Watch For

  • Current write boundary: One target repository per cloud-agent run, not atomic multi-repo edits
  • Native local delegation: Subagents isolate conversation context; verify checkout and tool boundaries separately
  • Agentic Workflows: Markdown-defined Actions automation is documented in public preview, not merely an unannounced idea
  • Copilot automations: Current docs describe eligible private/internal repo triggers; release date and tenant availability are not established here
  • Adoption check: Recheck policies, auth, preview status, and integration evidence before replacing a coordinator
The useful question is not whether agents will eventually coordinate perfectly. It is which boundary our chosen tool solves today. Native subagents help divide work, while cloud tasks still have one target repository. Agentic Workflows can define repository automation in Markdown, but that does not create transactional merges across repositories. Current docs also describe cloud-agent automations; we have not established their initial release date or availability in your tenant. Detailed setup belongs in a dedicated follow-up. For this course, keep the rollout and review model explicit instead of relying on speculative roadmap features.

Practical Recommendations Today

  • Separate guidance mechanisms: Organization settings, repo files, and template copies have different scopes
  • Curate context: Use accessible contracts, scoped search, and Spaces with source/ref checks
  • Use supported MCP tools: Prefer narrow read access before building custom server code
  • Prototype one bounded fan-out: Start tasks explicitly and track partial failures
  • Establish governance early: Permissions, required checks, human reviews, and evidence retention
  • Recheck official docs: Product support and preview APIs change; this course remains archived
Start with a clearly owned repository baseline and organization settings on supported surfaces. Keep architecture docs and contracts current, and use Spaces or scoped search when shared context is useful. Prefer existing GitHub MCP capabilities before introducing a custom server to maintain. Then prototype a bounded workflow with explicit task initiation, compatibility checks, and a recovery path. Establish access and evidence requirements before scaling. The practical outcome is a safer coordination pattern, not a claim that this archived deck is a turnkey production implementation.
Summary

Wrap-Up & Key Takeaways

Let's summarize the key points from today's session.

Key Takeaways

  • Cross-repo work needs explicit source retrieval, version checks, and compatibility evidence
  • Org settings guide supported surfaces; repository files and template copies need their own maintenance
  • Indexes retrieve, Spaces curate, and MCP tools expose authorized data/actions
  • Native local sessions/subagents and per-repo cloud tasks solve different coordination problems
  • Sequence dependent changes; review each PR and plan for partial rollout
  • Keep least privilege, human approval, and evidence boundaries visible as capabilities evolve
Cross-repo coordination begins with the right source and version, not an assumption that the agent knows everything. Guidance and context are different: instructions describe conventions, while retrieved contracts and code describe the system. Spaces and MCP can both provide code and documentation, with different curation and action boundaries. Native subagents are useful, but they do not remove cloud write-scope limits or the need for integration testing. Keep your changes reviewable, sequence dependencies honestly, and collect evidence from the appropriate logs and PR checks rather than promise universal audit coverage.
