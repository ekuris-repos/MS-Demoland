Part 1

ChatOps Fundamentals

Let's start at the beginning. What is ChatOps, and which parts of your development workflow would benefit from staying connected to the team conversation?

What Is ChatOps?

  • Conversation-driven operations: connect chat with development tools and actions
  • Bring selected repository events, issue actions, and agent tasks into team discussions
  • Reduce context switching while retaining links to authoritative GitHub records
  • Channel history supports collaboration; it is not a complete compliance audit log
  • GitHub's Hubot helped popularize chat bots; deterministic commands and AI agents coexist
        graph LR
          Chat[Team Chat] -->|commands| App[GitHub App]
          App -->|scoped requests| GitHub[GitHub Platform]
          GitHub -->|events| App
          App -->|notifications| Chat
          Chat -->|optional delegation| Agent[Copilot Agent]
          Agent -->|reviewable artifacts| GitHub
ChatOps connects the conversation with the work, rather than making someone relay every update by hand. A subscription might post a workflow result, an issue command might change a status, and an agent might investigate a failure. Those are different kinds of interaction with different permission boundaries. Hubot is a useful historical example, but AI does not replace every scripted bot. Keep the GitHub issue, workflow run, or pull request as the authoritative record, and use chat to connect the people involved.

Why ChatOps Matters

Without the Integration

  • Manually relay PR updates
  • Recreate issue context from chat
  • Switch tools to discover a failed run
  • Repeat a task description elsewhere

With a Supported Integration

  • Subscribe to selected repository events
  • Create or update issues from chat
  • Open linked workflow evidence
  • Delegate an agent task for human review
The benefit is less relaying and more shared context. If a conversation identifies a bug, we can create an issue while the details are fresh. If a workflow fails, a notification can bring the relevant people to the run. An agent may help investigate, but we still inspect the evidence and review its changes. We are reducing unnecessary switching, not promising that every development action happens safely inside chat or that every interaction is visible to the whole team.
Part 2

GitHub in Microsoft Teams

Let's look at the GitHub integration in Teams. The app supports notifications and commands, and eligible users can also start Copilot agent sessions. We will keep those capabilities separate so setup and permissions make sense.

Setting Up GitHub in Teams

  • Follow the official GitHub integration installation flow and add the GitHub app
  • Use @GitHub to connect your GitHub account and see @GitHub help
  • Teams workspace app approval and GitHub organization/repository authorization are separate
  • Agent work additionally needs a paid Copilot plan and enabled cloud sandboxes/policies
  • Current docs label agent features public preview; exact tenant setup remains unverified
Start from the official GitHub installation guide rather than searching for a separate app called GitHub Copilot. After adding GitHub, mention @GitHub and follow the account connection prompts. A Teams administrator controls workspace app approval; a GitHub organization owner may separately control repository installation and Copilot policy. Those are not interchangeable roles. Ordinary notifications do not imply that agent work is enabled. Current docs require a paid Copilot plan and enabled cloud sandboxes for agent sessions. Teams in Action: Delegate, Then Review

You:    @GitHub Investigate the login redirect failure in
        contoso/web-app. Explain the likely cause before changing code.

You:    @GitHub Create a pull request to fix the redirect loop
        and add a regression test. repo=contoso/web-app branch=main

Result: Inspect the linked artifact, diff, tests, and checks on GitHub.
You:    @GitHub Keep the existing callback URL validation.
        Revise the proposed fix in this thread.
We begin with an investigation, then explicitly ask for a bounded change. The repository and branch parameters identify where the proposed work belongs. They do not prove that the agent ran the right tests or that the change is safe. Open the linked artifact, inspect the diff, and confirm the actual check results. Follow-up messages can steer the work, but remember that the agent uses conversation context. Keep unrelated sensitive material out of the thread. GitHub Integrations in Slack

Many development teams collaborate in Slack, where the GitHub app provides subscriptions, issue actions, and optional agent sessions. The existing image is an illustration, not evidence that the current Slack interface looks exactly like this. We still need a tenant check and current media review.

Setting Up GitHub for Slack

  • Install the GitHub app from the Slack Marketplace, with workspace approval if required
  • Connect your GitHub account from the app's welcome message or /github signin
  • Invite the app to the intended channel with /invite @github
  • Authorize the GitHub app for the repositories you intend to use
  • Optional agent sessions need an eligible paid Copilot plan and enabled policies/cloud sandboxes
Slack workspace installation and GitHub repository access are two separate setup steps. After installation, connect your GitHub account and invite the app to the channel where you need it. Start with help and a narrow repository subscription. The optional Copilot capability is part of the GitHub app, but it does not turn every slash command into AI. Agent sessions have additional plan and policy requirements, and an app upgrade may request new permissions. We have verified the documentation, not the setup in your workspace.

GitHub for Slack Capabilities

  • Commands: /github help, subscriptions, and issue lifecycle actions
  • Notifications: selected repository events and workflow start/completion updates
  • Issue cards: documented comment, edit, close, and reopen actions
  • Workflow controls: supported deployment approvals and reruns, subject to permissions
  • Optional agent work: mention @GitHub to delegate and steer a task
Use slash commands for deterministic operations and @GitHub for an optional agent request. The ordinary app supports issue-card actions and documented workflow approvals and reruns. Deployment approval is not the same as approving a pull request review. We are not promising PR approve or merge buttons, because that exact native UI was not verified. Notifications are often threaded, with some state changes also posted to the channel. Individual live job-progress updates were retired in March 2025, so expect workflow-level visibility rather than a continuous per-job feed.

Key GitHub for Slack Commands

/github help
/github subscribe contoso/web-app pulls issues deployments
/github subscribe contoso/web-app workflows
/github unsubscribe contoso/web-app deployments
/github close https://github.com/contoso/web-app/issues/203
  • Feature names are space separated
  • subscribe and unsubscribe change channel notifications
  • close takes an issue link and changes issue state; verify the target first
  • Examples use fictional repositories; do not paste mutating commands into a live channel casually
Start with help so the installed app can show its available commands. For subscriptions, list feature names with spaces, not commas. The workflows feature adds workflow-level notifications and supported controls. Unsubscribing from deployments removes that notification category, not the repository's deployment configuration. The close example uses a full issue URL and closes an issue, not an arbitrary pull request. Confirm the repository, issue, permissions, and channel audience before issuing it. These are documented examples; we have not executed them in Slack.

Before we extend anything, separate the host from the integration mechanism. A supported GitHub App can still call GitHub APIs and receive webhooks. A compatible AI client can use approved MCP tools. Those are distinct paths. An MCP server installed in your IDE does not automatically become available inside Teams or Slack.

Copilot Extensions: Retired Model, Current Choices

  • Retired November 10, 2025: server-side Copilot Extensions built as GitHub Apps, including private extensions
  • Do not build the former agent endpoint or install its retired Marketplace extension category
  • Still supported: standard GitHub Apps and client-side VS Code extensions
  • MCP provides tools/context in supported AI clients; it is an architectural replacement, not a renamed endpoint
  • Check each client's support, server trust, permissions, and organizational policy

Official sunset notice · Current MCP guidance

This archived course previously taught server-side Copilot Extensions as a current workflow. GitHub disabled that model on November 10, 2025, including private versions. That does not retire ordinary GitHub Apps or every extension you can mention in VS Code. For AI tool integration, MCP is the current documented direction in compatible clients, but it uses a different architecture. We will not turn this chat-focused session into an MCP server-building tutorial, or assume feature parity across IDEs, github.com, mobile, Teams, and Slack.

Common ChatOps Workflows

Let's apply those boundaries to everyday work. We will distinguish an existing app control, a reviewed agent task, and a genuinely custom operation instead of treating all three as interchangeable chat magic.

  • Custom dispatch: a bot can call the workflow API after authenticating and authorizing the requester

Issue & PR Management from Chat

Deterministic App Features

  • Create an issue from the discussion
  • Use documented issue lifecycle actions
  • Subscribe to PR and review events
  • Follow authorized link previews

Reviewed Agent Work

  • Investigate a repository-scoped problem
  • Ask for a plan before implementation
  • Delegate a bounded proposed change
  • Inspect the resulting PR, tests, and checks
An issue created from a conversation can preserve the context that would otherwise be lost. That is useful even without AI. An agent task is different: you are delegating reasoning and possibly changes, so inspect its artifacts. Do not equate an agent summary with an approved review or a passing test run. Follow the actual GitHub links. We are not claiming a universal native merge button inside chat; repository rules and required human approvals still apply.

Investigate with Explicit Repository Context

  • Name the repository and the question you need answered
  • Ask for source paths and evidence, then verify the linked content
  • Keep an investigation read-only until you explicitly authorize a change
  • Do not assume automatic org-wide code, wiki, or cross-repository search

contoso/api. Do not change files. Cite the relevant paths
and explain which evidence supports your answer.

A scoped question is easier to evaluate than a request to search everything. Name the repository, explain what you are trying to understand, and ask for evidence. We have removed invented file paths, line numbers, benchmark improvements, and test counts from the sample responses. Those details looked authoritative without proving anything. If the integration cannot reach the necessary context, use an authorized GitHub or IDE workflow rather than assuming chat has unrestricted access to every repository or wiki.
Part 6

Building Custom Integrations

Custom code is justified when the supported app does not meet a real need. Let's look at the building blocks and their boundaries without pretending a short endpoint example is a production-ready bot.

Webhooks & GitHub Apps

  • Webhooks deliver selected GitHub events to your receiver via HTTP POST
  • GitHub Apps use scoped installation or user authority to read data and take actions
  • Validate webhook signatures, check event/action, acknowledge promptly, and deduplicate deliveries
  • For Teams messages, prefer supported Workflows or proactive bot messaging over legacy connector setup
  • Choose Slack's supported messaging transport separately; treat webhook URLs and bot credentials as secrets

Webhook best practices · Teams transport guidance

A webhook is an event delivery, not permission to execute any requested action. Validate the signature against the raw payload, check the event type and action, then queue processing so you can acknowledge promptly. Track the delivery identifier to avoid duplicate effects. A GitHub App supplies scoped API authority, which may be an installation identity rather than a person. For Teams, Microsoft's guidance points new webhook messaging toward Workflows or supported bots as legacy connectors are being retired. Workflows also need ownership continuity, so assign appropriate co-owners. We are not asserting a retirement deadline or teaching tenant-specific setup here.

A Safe Custom Action Boundary

  1. Authenticate the chat request and identify the requester
  2. Authorize the specific repository, operation, and allowed ref
  3. Validate input and preserve required human approvals
  4. Execute with a short-lived, minimally scoped app token
  5. Record a correlation ID and link to the actual GitHub result

GitHub event receivers separately validate webhook signatures and deduplicate deliveries. This is a design checklist, not runnable bot code.

Suppose someone asks a bot to deploy a branch. Being present in the channel is not sufficient authority. The bot must establish who asked, whether that person can request the action, which repository and ref are allowed, and which approvals still apply. Use a scoped token and report the real outcome, including a failure or pending state. We have replaced the old Copilot Extension endpoint example because that service was retired. The security boundary still matters for an ordinary GitHub App, regardless of whether an AI model helped interpret the request.
Part 7

Security & Permissions

Bringing GitHub into chat creates another place where data and authority meet. Let's be precise about who acts, what context leaves the conversation, and which records actually prove an operation happened.

Securing Chat Integrations

  • Identity: direct-message agent actions use linked personal authority; shared-context artifacts can use the app identity
  • Authorization: starting agent changes requires repository write access and applicable policies
  • Context: the agent can capture the entire thread and store context in generated artifacts
  • Privacy: Business/Enterprise data is not used to train AI models; this is not zero retention or a residency guarantee
  • Evidence: correlate supported audit events, workflow records, artifact history, and integration logs
A linked identity does not mean every artifact is attributed to the person who typed the prompt. Current documentation distinguishes personal authority in direct messages from app-attributed artifacts in shared contexts. Only users with the required write access can initiate changes, although other participants can contribute context. The agent can capture the entire thread, and that context can persist in generated artifacts. A direct message can limit the conversation supplied, but it is not a no-retention guarantee. GitHub's Business and Enterprise no-model-training commitment is narrower than that. Audit logs also cover defined event types, not every query or bot interaction, so combine the right records and verify your retention requirements.

Enterprise Best Practices

Governance

  • Approve workspace apps and GitHub policies separately
  • Review thread membership before sharing repository context
  • Secure app keys and use constrained, short-lived tokens
  • Preserve repository rules, human reviews, and deployment gates

Adoption

  • Start with narrow subscriptions and read-only investigations
  • Enable bounded write tasks only with explicit authorization
  • Train teams to verify artifacts and distinguish app commands
  • Recheck preview status, tenant UX, and supported transports
Start with the smallest set of repositories and operations that meets the team's need. A private channel is not a substitute for repository authorization, and it may contain participants who should not receive private code context. Review both the conversation audience and the data that an artifact could retain. Shared-context agent PRs may require an additional approval under applicable repository rulesets. Keep those rules intact rather than designing the bot around them. Review GitHub, chat-platform, and custom-backend data handling separately. Tenant setup, preview behavior, and current screenshots still require authorized verification before a live rollout.
Summary

Wrap-Up & Next Steps

Let's bring the choices together. We want less friction between a conversation and the work, without hiding which tool acted, which authority it used, or which evidence a reviewer still needs.

Key Takeaways

  • Separate notifications, commands, agent sessions, and custom actions
  • Use the supported GitHub apps; delegate agent tasks with @GitHub
  • Server-side Copilot Extensions are retired; standard Apps and supported MCP clients are distinct choices
  • Check acting identity, repository authority, thread context, and human approval
  • Verify actual artifacts and logs; do not assume zero retention or universal audit coverage
  • This course remains archived; media and authorized tenant verification are unfinished
The durable lesson is not a particular bot command. It is choosing the smallest supported interaction and checking its authority and evidence. Use native subscriptions and issue controls where they fit, delegate a bounded agent task when useful, and build custom integration code only when needed. The retired server-side Extension model should not be revived as a shortcut. Keep required reviews, validate outputs against GitHub, and check where conversation context persists.
