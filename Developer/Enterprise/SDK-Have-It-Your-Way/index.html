Build outside the editor with Copilot's agent runtime, custom tools, event streaming, and explicit enterprise controls

Part 1

Why Build Outside the Editor?

Sometimes the right interface for an agent is a service, a workflow, or a product screen rather than an editor. The useful question is not whether we can add a chat box. It is which task needs an agent that can call well-defined tools on a user's behalf.

Use Cases for Standalone Copilot Apps

Customer-facing backends

  • Product assistants with scoped business tools
  • Web or mobile UIs calling your controlled API
  • Authenticated support and workflow services

Internal tooling

  • Slack or Teams bots backed by your service
  • Developer CLI utilities
  • Knowledge retrieval and workflow automation
        graph LR
          App[Backend Application] --> SDK[SDK Client]
          SDK -->|JSON-RPC| Runtime[Copilot CLI Runtime]
          Runtime --> Model[Model Provider]
          Runtime --> Handler[Application Tool Handler]
          Handler --> Services[Authorized Business Services]
The SDK gives our backend access to the agent runtime behind Copilot CLI. The runtime can plan and request tools, while our handlers connect it to business systems. A web or mobile UI calls this backend; we do not put server credentials or a CLI runtime inside the browser or mobile client. Platform connectors, product authentication, and authorization still need their own implementation.

Why the SDK Instead of Raw API Calls?

  • Agent runtime: Planning, tool invocation, and conversation orchestration
  • Sessions: Conversation state and configurable context management
  • Events: Observe message deltas, tool execution, errors, and idle state
  • Authentication: Copilot credentials or a configured custom provider
  • Model choice: Copilot-hosted models or supported BYOK providers
  • Your responsibility: Authorization, permissions, timeouts, retries, and transport pressure
A raw model API leaves you to implement the agent loop. Here the Copilot runtime handles that loop, and the SDK exposes it programmatically. This does not make the SDK a generic GitHub Models API client. Copilot-hosted access follows Copilot identity, plan, billing, and organization policy. BYOK uses your provider's authentication and billing instead. We also should not mistake event delivery for automatic HTTP backpressure or a complete application retry policy.
Part 2

SDK Architecture

The process boundary matters when we deploy. Our Node process hosts the SDK and business handlers, while a Copilot runtime manages sessions and model interactions. Let's make those responsibilities explicit before writing code.

Core Components

  • CopilotClient: Connects to and manages the runtime
  • Copilot CLI runtime: Agent loop and provider interaction over JSON-RPC
  • Session: Conversation identity, configuration, and events
  • Tool: Name, parameter schema, and application handler
  • send(): Returns a promise for a message ID, not a stream
  • sendAndWait(): Waits for completion and returns an assistant event or undefined
In today's Node SDK the runtime is bundled, so a separate CLI installation is not normally required. The client can manage its lifecycle or connect to an explicitly configured runtime. Streaming arrives through session event subscriptions. It is not an async iterable returned by send. When we use sendAndWait, the text is in response.data.content if an assistant event was returned, not the entire response object.

Message Flow

  1. Authenticate the application or requesting user
  2. Create a session with explicit model and tool scope
  3. Register event handlers before sending a prompt
  4. The runtime calls the provider and may request a tool
  5. Your handler validates and authorizes the operation
  6. Observe completion, then retain or clean up the session deliberately
Automatic orchestration means the runtime can pass a tool result back to the model. It does not mean the model can authorize an order cancellation. Our service makes that decision before changing business state. We will start with no tools at all, then add a single read-only demonstration tool so that the capability boundary stays visible.

Part 4

Building Your First App

Let's begin with a complete one-shot program. It uses no business tools, refuses to fall back to another logged-in identity, and stops its client when the work finishes.

Creating the CopilotClient

Complete main.mjs (scroll code); run node main.mjs after slide 11 setup.

import { CopilotClient } from "@github/copilot-sdk";
const gitHubToken = process.env.COPILOT_GITHUB_TOKEN;
if (!gitHubToken) throw new Error("Set COPILOT_GITHUB_TOKEN");
const client = new CopilotClient({
  mode: "empty", gitHubToken, useLoggedInUser: false,
});
let session;
try {
  session = await client.createSession({
    model: "auto", availableTools: [],
  });
  const response = await session.sendAndWait(
    { prompt: "Explain what a pure function is." }, 60_000
  );
  console.log(response?.data.content ?? "No assistant message");
} finally {
  try {
    if (session) {
      try { await session.abort(); }
      finally {
        try { await session.disconnect(); }
        finally { await client.deleteSession(session.id); }
      }
    }
  } finally { await client.stop(); }
}
The option is gitHubToken with a capital H in SDK 1.0.27. Older versions used githubToken, and token is not the correct option for either baseline. Empty mode disables ambient CLI capabilities, and our session allowlist exposes no tools. The object prompt form also avoids the old sample's string-argument incompatibility. Cleanup attempts abort, disconnect, deletion, and client shutdown even if an earlier operation fails. A long-running service also needs monitoring and retries if cleanup itself fails.

Integrating with Express

Complete server.mjs (scroll code); run node server.mjs. Single-user loopback demo only, not a public authenticated API.

import express from "express";
import { CopilotClient } from "@github/copilot-sdk";
const gitHubToken = process.env.COPILOT_GITHUB_TOKEN;
if (!gitHubToken) throw new Error("Set COPILOT_GITHUB_TOKEN");
const client = new CopilotClient({ mode: "empty", gitHubToken,
  useLoggedInUser: false });
await client.start();
const app = express();
app.use(express.json({ limit: "4kb" }));
const validMessage = m => typeof m === "string" &&
  m.trim().length > 0 && m.length <= 2000;
async function release(session) {
  if (!session) return;
  try { await session.abort(); }
  finally {
    try { await session.disconnect(); }
    finally { await client.deleteSession(session.id); }
  }
}
app.post("/chat", async (req, res) => {
  if (!validMessage(req.body?.message))
    return res.status(400).json({ error: "Invalid message" });
  let session;
  try {
    session = await client.createSession({ model: "auto", availableTools: [] });
    const r = await session.sendAndWait({ prompt: req.body.message }, 60_000);
    res.json({ reply: r?.data.content ?? "" });
  } catch {
    res.status(502).json({ error: "Assistant request failed" });
  } finally { await release(session).catch(() => console.error("Cleanup failed")); }
});
const server = app.listen(3000, "127.0.0.1");
process.once("SIGINT", () => server.close(async () => { await client.stop(); }));
This endpoint intentionally creates and removes a one-shot session, so it does not return a misleading session ID for follow-up requests. It bounds request size, validates the message, sets a turn timeout, and returns assistant text rather than the raw event. Cleanup aborts any unfinished turn, disconnects the handle, and removes retained state. Binding to loopback limits this teaching example; it does not implement web authentication, per-user quotas, graceful production shutdown, or a durable cleanup retry queue. Those are prerequisites before exposing it beyond a trusted local machine.
Part 5

Streaming & Tool Integration

We now have a working one-shot endpoint. Streaming changes how we deliver the response, while tools change what the agent can do. Neither change should silently broaden the identity or permissions of our service.

Streaming Responses

Route fragment: insert into slide 15's server.mjs before app.listen. Reuses app, client, validMessage, and release.

app.post("/chat/stream", async (req, res) => {
  if (!validMessage(req.body?.message))
    return res.status(400).json({ error: "Invalid message" });
  let session, unsubscribe;
  const stop = () => { session?.abort().catch(() => {}); };
  try {
    session = await client.createSession({
      model: "auto", availableTools: [], streaming: true,
    });
    res.set({ "Content-Type": "text/event-stream",
      "Cache-Control": "no-cache" });
    res.flushHeaders();
    res.on("close", stop);
    unsubscribe = session.on("assistant.message_delta", event => {
      if (res.destroyed) return;
      const frame = JSON.stringify({ content: event.data.deltaContent });
      if (!res.write(`data: ${frame}\n\n`)) {
        stop();
        res.destroy();
      }
    });
    await session.sendAndWait({ prompt: req.body.message }, 60_000);
    if (!res.destroyed) res.end("data: [DONE]\n\n");
  } catch {
    if (!res.destroyed) {
      if (!res.headersSent) res.status(502).json({ error: "Assistant failed" });
      else res.end('event: error\ndata: {"error":"Assistant failed"}\n\n');
    }
  } finally {
    res.off("close", stop);
    unsubscribe?.();
    await release(session).catch(() => console.error("Cleanup failed"));
  }
});
We enable streaming and subscribe before sending so early deltas are not missed. sendAndWait gives us a bounded completion wait while callbacks forward text. A rejected turn becomes an error response, not a success marker. A closed connection aborts work. This small demo disconnects a slow consumer when the response buffer fills; it does not implement a resumable queue or guarantee transparent backpressure. A production transport needs an explicit bounded buffering policy, proxy timeouts, authentication, and rate limits. Finally removes listeners and releases the session on both success and failure.

Defining and Registering Tools

Complete tools.mjs, imported by slide 21. Read-only fixture data, not a real order service.

import { defineTool } from "@github/copilot-sdk";
const orders = new Map([
  ["ORD-1234", { status: "shipped", cancellable: false }],
]);
export const lookupOrder = defineTool("lookup_order", {
  description: "Read a demonstration order's status; cannot cancel orders",
  parameters: {
    type: "object",
    properties: { orderId: { type: "string" } },
    required: ["orderId"], additionalProperties: false,
  },
  skipPermission: true,
  handler: async ({ orderId }) => {
    if (typeof orderId !== "string" || !/^ORD-\d{4}$/.test(orderId))
      throw new Error("Invalid order ID");
    const order = orders.get(orderId);
    return order ? { orderId, ...order } : { error: "Order not found" };
  },
});

Only this fixed read-only fixture bypasses prompting. Real order APIs must enforce caller ownership and permissions inside the handler.

A schema cannot look up an order by itself. The handler supplies that implementation. This module has real executable fixture logic, and the next program explicitly registers it. We allow this one fixture to run without a prompt because it can only read a hard-coded demonstration map. Do not copy that permission choice onto a database or cancellation tool. For a real service, resolve the caller from authenticated server state and verify order ownership before reading or mutating anything. A model-provided order ID is never proof of access.
Part 6

Multi-Turn Conversations

The next question is how a follow-up stays in the same conversation. Session context helps the model understand what we mean, but our backend still decides who may resume that session and how long it should exist.

Context Management

Runtime responsibilities

  • Conversation events and tool results
  • Context management and configurable compaction
  • Session configuration through systemMessage

Application responsibilities

  • Bind session IDs to authenticated owners
  • Authorize before resumeSession()
  • Serialize turns; limit idle time and retention
  • Plan storage and routing across replicas
Context windows are finite, so preserved session history is not a guarantee that every earlier token remains in the next model prompt. Compaction settings change that behavior. Use the documented systemMessage configuration for application instructions, but keep business policy enforcement in code. For HTTP continuity, map an authenticated principal to an owned session before resuming it. Guessing a session ID must not grant access. Disconnect releases the current handle; deleting a session removes retained conversation state. Horizontal scaling also requires a deliberate storage and routing design.

Multi-Turn in Practice

Complete conversation.mjs; requires slide 18's tools.mjs. Run node conversation.mjs.

import { CopilotClient } from "@github/copilot-sdk";
import { lookupOrder } from "./tools.mjs";
const gitHubToken = process.env.COPILOT_GITHUB_TOKEN;
if (!gitHubToken) throw new Error("Set COPILOT_GITHUB_TOKEN");
const client = new CopilotClient({
  mode: "empty", gitHubToken, useLoggedInUser: false,
});
let session;
try {
  session = await client.createSession({
    model: "auto", tools: [lookupOrder],
    availableTools: ["custom:lookup_order"],
    systemMessage: { mode: "append",
      content: "Use lookup_order for status. This demo cannot cancel orders." },
  });
  for (const prompt of [
    "Use lookup_order to get the status of ORD-1234.",
    "Can you cancel it?",
    "Which order were we discussing?",
  ]) {
    const r = await session.sendAndWait({ prompt }, 60_000);
    console.log(r?.data.content ?? "No assistant message");
  }
} finally {
  try {
    if (session) {
      try { await session.abort(); }
      finally {
        try { await session.disconnect(); }
        finally { await client.deleteSession(session.id); }
      }
    }
  } finally { await client.stop(); }
}
All three turns use the same session, so the model can resolve the follow-up from context. Model wording and tool selection are not deterministic, which is why the prompt requests a lookup rather than guaranteeing a particular trace. Cancellation is not available in the tool allowlist, and the fixture reports that this shipped order is not cancellable. The system message helps explain the limit; the absence of a mutation handler actually enforces it. This is a local conversation, not an implementation of authenticated session persistence across HTTP requests.
Part 7

Bring Your Own Model

The official SDK documentation calls custom-provider mode BYOK, or Bring Your Own Key. Some Azure samples call the scenario BYOM. The important distinction is that our provider configuration changes authentication, billing, model availability, and compliance decisions. It does not turn those decisions into automatic guarantees.

BYOK: Azure Credential Refresh

Complete azure.mjs, using slide 11 packages. Set FOUNDRY_RESOURCE_URL, MODEL_DEPLOYMENT, and AZURE_TOKEN_CREDENTIALS first.

import { CopilotClient } from "@github/copilot-sdk";
import { DefaultAzureCredential } from "@azure/identity";
const resource = process.env.FOUNDRY_RESOURCE_URL;
const model = process.env.MODEL_DEPLOYMENT;
if (!resource || !model || !process.env.AZURE_TOKEN_CREDENTIALS)
  throw new Error("Set resource URL, deployment and credential type");
const endpoint = new URL(resource);
if (endpoint.protocol !== "https:" || endpoint.pathname !== "/")
  throw new Error("Use an HTTPS resource origin, without an API path");
const credential = new DefaultAzureCredential({
  requiredEnvVars: ["AZURE_TOKEN_CREDENTIALS"],
});
const client = new CopilotClient({ mode: "empty", useLoggedInUser: false });
let session;
try {
  session = await client.createSession({
    model, availableTools: [],
    provider: {
      type: "openai", baseUrl: `${endpoint.origin}/openai/v1/`,
      wireApi: "responses",
      bearerTokenProvider: async () => {
        const token = await credential.getToken("https://ai.azure.com/.default");
        if (!token?.token) throw new Error("No Azure bearer token");
        return token.token;
      },
    },
  });
  const r = await session.sendAndWait({ prompt: "What is 2 + 2?" }, 60_000);
  console.log(r?.data.content ?? "No assistant message");
} finally {
  try {
    if (session) {
      try { await session.abort(); }
      finally {
        try { await session.disconnect(); }
        finally { await client.deleteSession(session.id); }
      }
    }
  } finally { await client.stop(); }
}

Use an existing Responses-capable deployment. Local: AZURE_TOKEN_CREDENTIALS=AzureCliCredential and an authenticated Azure CLI. Azure: ManagedIdentityCredential, assigned identity and model-inference RBAC. Run node azure.mjs.

The environment values name a real HTTPS resource origin and an existing deployment, not a model that the code provisions for us. For example, the resource URL has the form https://your-resource.openai.azure.com, without a path. Choose a deployment that supports the Responses API and assign the relevant inference role, such as Cognitive Services OpenAI User for Azure OpenAI. Locally, sign into the intended tenant and subscription before using AzureCliCredential. In Azure, select ManagedIdentityCredential and set AZURE_CLIENT_ID for a user-assigned identity when needed. These are environment variable values; set them using your shell or hosting configuration. The SDK requests a fresh bearer token through our callback, while Azure Identity handles caching and renewal. A static bearerToken string would not renew automatically. This follows the official SDK managed-identity guide's OpenAI-compatible endpoint and scope; verify the audience and endpoint for your chosen service. No GitHub token, deployment, regional quota, or live inference result is assumed here.

Copilot-Hosted Models vs. BYOK

Copilot-hosted

  • Copilot identity, plan, and organization policy
  • No Azure subscription needed for model access
  • Discover allowed models with listModels()
  • Check current Copilot usage and billing terms

Custom provider / BYOK

  • Provider credential, quota, and billing
  • No GitHub authentication required for model access
  • Check tool and wire-API compatibility
  • Evaluate deployment type and data handling

Azure resource location alone does not guarantee inference locality. Global, Data Zone, and geography-based deployment types have different processing boundaries.

Copilot-hosted models are not the separate GitHub Models API product. Provider choice should follow actual access, cost, data processing, and operational requirements, not a blanket rule for an entire industry. Azure Global deployments may process requests outside the resource region. Data stored at rest, inference processing, application logs, and tool data each need their own assessment. Custom provider access can use reserved capacity or supported custom deployments, but those are provider capabilities to verify, not automatic features of our SDK configuration.

Monitoring & Observability

Constructor-option fragment for the current SDK. Merge into your existing constructor; do not create an extra client. Requires an approved OTLP HTTP collector.

telemetry: {
  otlpEndpoint: "http://127.0.0.1:4318",
  captureContent: false,
}
  • Opt in: SDK runtime OpenTelemetry export and W3C trace context
  • Instrument your app: HTTP spans and propagation into the SDK need application setup
  • Measure: Latency, tool outcomes, errors, and available usage events
  • Verify: Follow a request to its session and tool spans in the configured backend

Creating an Application Insights resource is not the same as instrumenting an Express process. Part 9

Security Considerations

The most important boundary is between what the model suggests and what our service is allowed to execute. Authentication identifies the caller. Authorization and runtime permissions determine which data and actions that caller can actually reach.

Authentication & Token Management

Copilot credentials

  • Explicit OAuth user identity for local examples
  • Use per-session identity for shared user services
  • GitHub App installation tokens need organization enablement and Copilot Requests permission
  • Renew short-lived credentials before expiry

Azure provider identity

  • Managed identity with least-privilege model RBAC
  • Explicit credential selection in each environment
  • bearerTokenProvider for renewable tokens
  • Static bearer strings do not auto-refresh

Store secrets in an approved store such as Key Vault. Secure environment injection is supported; never commit or log tokens.

Secret storage and delivery to a process are separate concerns. Key Vault can supply a credential that is securely injected at runtime; environment variables are not categorically forbidden by the SDK. Our local examples use an explicitly supplied user token and disable ambient discovery. A shared service must not accidentally charge every user's work to that local identity. Installation tokens are a separate service-to-service path with organization requirements and a one-hour lifetime, not a drop-in replacement for any user token. Follow the versioned server authentication guidance for renewal, policy, and billing attribution. Azure managed identity avoids a stored provider key, but the access tokens it obtains still expire.

Security Best Practices

  • Runtime baseline: mode: "empty" and explicit tool allowlists for shared servers
  • Authorization: Verify caller, tenant, session, and resource ownership in server code
  • Tool permissions: Use permission decisions and pre-tool hooks; schemas are not access control
  • Business actions: Enforce policy and approval before mutations; make retries idempotent
  • Untrusted content: Treat prompts and tool output as data, not authorization
  • Operations: Bound requests, concurrency, storage, network access, and spending
  • Audit: Redacted metadata, restricted access, and explicit retention
System instructions help guide behavior but cannot enforce access to an order or stop an overprivileged handler from changing it. Our fixture has only a read operation; production tools need server-side ownership checks and permission handling appropriate to their effects. Current shared-server guidance recommends empty mode to avoid inheriting ambient CLI tools and workspace capabilities. Hooks can intercept tool use, and MCP can reuse approved integrations, but neither removes the need to authorize the underlying action. Avoid recording entire prompts and tool outputs by default, since those may contain customer data or secrets.
Summary

Wrap-Up & Next Steps

We now have the pieces of a small agent-backed service, together with a clearer list of what has not been solved by a code sample. Let's separate the reusable SDK patterns from the decisions that still need your organization's verification.

Key Takeaways

  • The SDK controls the Copilot CLI agent runtime, not a generic direct model API
  • Pin versions and distinguish current SDK examples from older samples
  • Use session events for streaming and real handlers for custom tools
  • Conversation context does not replace session ownership or business authorization
  • Custom providers change identity, billing, and data-processing obligations
  • Credential renewal and deployment type require explicit choices
  • Telemetry, permissions, and runtime lifecycle are production work, not automatic template guarantees
The value of the SDK is that we can build on a production-tested agent runtime without writing the orchestration ourselves. The quality of our service still depends on the boundaries around that runtime. We used one pinned API baseline, separated complete programs from fragments, kept a read-only tool genuinely read-only, and chose explicit credential behavior. Before shipping, verify identity isolation, provider compatibility, storage, telemetry, transport behavior, and your organization's approval requirements.
