Copilot Billing - From PRUs to Usage-Based Billing

Prepare your team for GitHub AI Credits, budget guardrails, and lower-cost workflows that keep Copilot productive without surprise spend

Part 1

Why GitHub Changed Billing

The right way to explain the transition is to start with why GitHub made it in the first place. If your team only hears, "billing changed," they will assume it is a pure finance story. It is not. It is a product shape story, because Copilot has become much more agentic, multi-step, and compute-intensive than it was when PRUs were introduced.

Why Move Away From PRUs?

  • Copilot has evolved from a quick in-editor assistant into an agentic platform that can work across whole repositories
  • A short chat question and a long autonomous coding session should not cost the same
  • PRUs masked real differences in compute intensity, model choice, and session length
  • Usage-based billing aligns price to actual token consumption and the model used
  • GitHub positions the change as a way to improve long-term reliability and reduce the need for blunt gating
The official blog is explicit about the motivation. Copilot is not the same product it was a year earlier. Agentic usage is becoming the default, and that means longer runs, more tool use, more context, and higher inference cost. PRUs were too coarse for that reality. Usage-based billing moves the system closer to actual cost drivers: tokens and model selection. For your organization, that means the economics now reward disciplined task shaping instead of treating all advanced usage as equivalent.

PRUs vs. AI Credits

Dimension PRUs Usage-Based Billing
Billing unit Premium request units GitHub AI Credits
Primary cost signal Request count with multipliers Input, output, and cached tokens by model
Best fit Simple request metering Mixed workloads from quick chat to long agent runs
Admin control Limited allowance management Pooled credits, budgets, alerts, and hard stops
After allowance is exhausted Fallback could apply in some cases Usage is charged or blocked based on budget policy
Under PRUs, we counted requests with model multipliers. Under usage-based billing, we account for credits, tokens, and model rates. That change gives us more precise controls, but it also asks engineers to understand scope, output length, and model choice. We should compare the cost of a completed, verified task, not just the price of one request.

What Stays the Same, What Changes

Stays the Same

  • Base seat prices do not change
  • Code completions stay included
  • Next Edit Suggestions stay included
  • Teams still manage model access through policy

Changes

  • Usage is priced from token consumption and model rates
  • Budgets can be set at enterprise, org, cost center, and user levels
  • No automatic fallback to a cheaper model when budget is exhausted
  • Code review's agentic capabilities can also consume hosted GitHub Actions minutes
We are not turning every Copilot interaction into an extra charge. Completions remain included, and the base prices of the existing plans did not change at migration. Variable spend is now more visible and configurable. For code review, model interactions consume credits, while hosted runners used for agentic context gathering and tool use can also consume Actions minutes. Self-hosted runners do not consume Actions minutes, and a limited review can still run when agentic capabilities are unavailable.

Migration Timing and Transitional Details

  • June 1, 2026: monthly Copilot plans moved to usage-based billing
  • Copilot Pro and Pro+ annual subscribers stay on request-based billing until expiry, then move to Copilot Free unless they convert to a monthly paid plan earlier
  • The June-August 2026 Business and Enterprise included-usage promotion has ended
  • The Billing Preview app was retired August 4, 2026; use current billing settings and the AI usage page
  • For adoption or policy recalibration, confirm current allowances and agree on paid usage before expanding access
The June transition is now history, not a future deadline. Existing annual Pro and Pro+ subscriptions remain an exception: they keep premium-request billing until expiry, then move to Copilot Free unless converted to a monthly paid plan earlier. Check the actual account rather than assuming every individual subscription migrated together. For organizations, the launch promotion has ended and the preview app has retired. We now use current AI usage reporting to establish a baseline and refine policy.
Part 2

How Usage-Based Billing Works

Now that we know why the model changed, we can talk about mechanics. This section gives the mental model your teams need in order to reason about spend before they open the bill page. The key terms are AI Credits, tokens, model rates, and included allowances.

What Is a GitHub AI Credit?

  • GitHub AI Credits are the new billing unit for Copilot usage
  • 1 AI credit = $0.01 USD
  • Each interaction consumes input, output, and sometimes cached tokens
  • The total token usage is converted into AI Credits using the published rate for the model used
  • A fast lightweight task may cost a fraction of a credit; a long agent run over many files costs more because it does more work
One AI credit equals one cent. That gives us a common unit for engineering decisions and finance discussions. The model's input, output, cached-input and any cache-write rates determine the conversion. Those rates differ, so a token count alone is not a bill. We need the token mix and the actual model rate, then we can compare the cost of useful outcomes.

What Is Billed and What Is Not?

Surface Uses AI Credits? Operational note
Copilot Chat Yes Scope and model choice matter immediately
Copilot CLI Yes Long transcripts and agentic loops can add up quickly
Copilot cloud agent Yes Multi-step agent sessions are high-value and high-consumption
Copilot code review Yes Agentic capabilities can also use hosted Actions minutes
Code completions No Still included in paid plans
Next Edit Suggestions No Still included in paid plans
If completions or Next Edit Suggestions can accomplish the work, they avoid consuming AI credits on a paid plan. Chat, CLI, cloud agent, and code review are metered; Spaces, Spark, and third-party coding agents can also consume credits. We should use these capabilities when they create value, not avoid them. For reviews, check who pays: the member entitlement is the default for licensed members, but an organization can choose repository-organization billing with paid usage enabled. Hosted Actions minutes for agentic capabilities are a separate meter.

How Spend Accumulates

graph LR
  A[Prompt or agent task] --> B{User budget available?}
  B -->|No| C[Request blocked]
  B -->|Yes| D{Included usage available?}
  D -->|Yes| E[Serve from included credits]
  D -->|No| F{Paid usage and limits permit?}
  F -->|No| C
  F -->|Yes| G[Serve as metered usage]
  E --> H[Tokens priced by model]
  G --> H
Guardrails can stop a request before more model work is served. First, the applicable user budget must permit it. Then available included usage or an authorized paid-usage path determines how the work is funded. This is a simplified flow; cost-center included-usage caps can create a paid path or block a group before the enterprise pool is empty. Once work is served, actual token types and model rates determine its credit consumption. Budget checks and token accounting are different parts of the system.

The Four Spend Levers You Control

Scope

Narrow prompts, smaller selections, and fewer irrelevant files reduce input tokens immediately.

Surface

Use completions or Next Edit Suggestions when they can solve the task instead of starting a billed chat or agent session.

Model

Lower-cost, faster models are enough for simple edits. Save deeper reasoning models for real complexity.

Session Length

Start fresh for unrelated tasks. Compact continuing work, and preserve useful cached context instead of resetting reflexively.

These four levers help us investigate a spend spike without assuming that heavy usage is wasteful. Was context broader than necessary? Did the task need an agent? Was the model appropriate? Did a continuing session carry irrelevant history? These are hypotheses to check against usage and outcomes. Cached context can be inexpensive, so restarting a useful session is not automatically a saving.
Part 3

Admin Controls and Governance

Now we move from mechanics to governance. GitHub added much better controls for organizations and enterprises, but controls only help if you use them in a deliberate policy structure. This section gives you the operating model, not just the feature list.

Pooled Credits Change the Economics

  • Each Business or Enterprise seat adds monthly included AI Credits to a shared pool
  • A company with 100 Business seats gets 190,000 pooled credits, not 100 isolated buckets
  • Power users can consume more when they are creating disproportionate value
  • By default, lighter users offset power-user consumption without manual transfers
  • Optional cost-center included-usage controls cap a group's draw to credits funded by its own licenses
  • Adding licenses mid-cycle increases the pool immediately; removing licenses reduces the pool at the next billing cycle
Pooling recognizes that useful AI usage is unevenly distributed. A staff engineer doing multi-repo remediation may need more than someone asking occasional questions. If chargeback boundaries require isolation, included-usage controls can limit a cost center to the credits its licenses fund. GitHub calculates that cap; you choose whether reaching it blocks the group or allows paid usage, subject to policy. That control is different from a cost-center budget for additional metered charges. Included credits expire each month, so unused capacity is not a savings account.

Budget Control Scopes

ControlWhat it limitsEnforcement
User-level budgetOne person's included + metered creditsAlways a hard stop; $0 blocks immediately
Cost-center budgetGroup's additional metered chargesEnable stop-usage option for a hard stop
Organization budgetAdditional charges for seats billed to that orgCannot override enterprise restrictions
Enterprise budgetTotal additional metered charges, not seat feesEnable stop-usage option for a hard stop

Per-user precedence: individual override > cost-center per-user default > universal default.

The scopes do not all measure the same thing. User-level budgets count credits from the pool and paid usage, and always stop the user at the limit. The most specific per-user setting wins: individual, then cost-center per-user, then universal. A cost-center per-user default is not the same as the team's aggregate metered budget. Enterprise, organization and aggregate cost-center budgets generally govern additional charges after the shared pool runs out; included-usage controls are separate. Seat fees remain outside an enterprise metered budget. For example, 100 Business seats cost $1,900 a month; a $500 additional-usage ceiling makes the combined ceiling $2,400, not $500.

What Happens When the Pool Runs Out?

Additional Usage Allowed

Work can continue at published rates while applicable budgets and account limits permit. Paid usage is enabled by default for organizations and enterprises.

Additional Usage Blocked

Disable AI credits paid usage in AI Controls to block further credit-consuming work when included usage runs out.

Important: user-level limits always stop that user, even with pool headroom. For aggregate budgets, enable Stop usage when budget limit is reached to enforce a ceiling. No automatic cheaper-model fallback applies.

We should never assume additional spending is off until someone enables it. Organizations and enterprises allow paid usage by default, so a no-overage policy requires an explicit change. An alert-only aggregate budget sends a notification but does not stop charges. User-level limits are different: they always stop that person, even while the pool has capacity. Account-level additional-usage caps can also interrupt work. Credit-consuming features have no automatic cheaper-model fallback, but included completions are not an AI-credit charge.

A Sane Starting Policy

Layer Starting point Why
Enterprise Agree paid-usage policy and an authorized ceiling Observe with alerts only inside an approved spending envelope
Organization Track spend and confirm code-review billing owner Separate member entitlements from organization-paid review usage
Cost center Choose included cap, per-user default, or metered budget Match chargeback and fairness controls to the phase of usage
User Set a justified default; allow reviewed exceptions Always-hard caps should protect access without blocking valuable work
Start by agreeing how much additional spend is authorized and who can approve an exception. If finance requires no overage, disable paid usage. If additional spend is approved, make sure the relevant aggregate limits stop usage rather than just send alerts. Within that envelope, observe productive workflows before tightening individual limits. For reviews, the organization-billing option requires paid usage, and organizations can restrict requests from externally licensed users. Governance should protect the organization without treating every power user as a problem.

What to Review Every Week

  • Total AI Credits consumed vs. included pool remaining
  • Top users, teams, and cost centers by spend
  • Model mix: fast help vs. deep reasoning vs. agentic usage
  • Code-review billing attribution and hosted Actions minutes for agentic capabilities
  • Budget alerts, blocked users, and unexpected workflow spikes
Make this an engineering operations ritual, not just a finance report. In enterprise settings, open Billing & licensing, then AI usage; filter by user, model, organization or cost center and export when needed. Compare credits with accepted changes, tests and time saved. A reliability campaign may justify a spike, while repeated failed runs may need coaching. Check the code-review billing owner and hosted runner usage separately. Save a consistent set of filters so the weekly comparisons answer the same questions.
Part 4

Developer Habits That Lower Spend

This is the part most developers care about. They do not want a lecture about billing. They want to know how to keep using Copilot effectively without becoming the reason the budget review gets tense. The answer is not to stop using AI. The answer is to choose the right surface, the right model, and the right context size for the job.

Choose the Cheapest Surface That Still Solves the Task

Need Lower-cost default Why it helps
One line, one block, one file Autocomplete or Next Edit Suggestions These remain included and avoid chat overhead
Question about a specific function Inline chat on a selection Selection scopes the question; actual context and model determine cost
Typical coding or explanation task Copilot Chat with explicit file references You keep scope tighter than a broad repo scan
Large, multi-step autonomous work Cloud agent or CLI agent Evaluate total task cost and value, not a fixed surface ranking
Chat feels universal, but it does not have to be the first move. If completions can draft the change, they avoid consuming credits. For a local question, a selection can help focus inline chat. That is a useful default, not a promise of the lowest bill: inline chat may include other workspace context, and model rates matter too. Use an agent when autonomy improves the whole task, then verify the result rather than judging by surface alone.

Example: Use Inline Chat on a Single Function

function calculateInvoiceTotal(lines, taxRate, discountPct) {
  const subtotal = lines.reduce((sum, line) => sum + line.qty * line.price, 0);
  const discount = subtotal * discountPct;
  return subtotal - discount + subtotal * taxRate;
}
  • Select only the function you want to change
  • State the contract: Discount is a fraction from 0 to 1; reject other values. Tax applies after discount. Round the final total to cents. Change only this function.
  • Avoid broad prompts like @workspace fix invoice math for a local issue
  • Start narrow, verify the fix, then widen scope only if needed
Select the function so we can state the intended behavior precisely. For a $100 subtotal, a ten-percent discount and ten-percent tax should produce $99, not the current $100. Reject discounts outside zero to one and test fractional-cent cases. This is a simplified example, not a production currency library. Inline chat can include other files, and a file already in an editing session may route to Ask in Chat with existing history. Selection is a scope hint, not an isolation boundary or a guaranteed token count.

  • Let autocomplete or Next Edit Suggestions expand each block

  • Use billed chat only if the implementation or edge cases become genuinely tricky
This is one of the highest-leverage spend habits because it moves work from a metered surface to an included surface. The comments do the architectural thinking in plain English, and completions draft the mechanical code. For a huge percentage of CRUD, parsing, mapping, and validation tasks, that is enough. Developers still get acceleration, but the organization does not pay chat or agent costs for work that completions can handle well.

Use Auto for the Default Path

  • Auto combines availability and task complexity to route work efficiently
  • Efficiency: prioritize cost for straightforward tasks
  • Balance: weigh cost, quality, and latency for everyday work
  • Intelligence: prioritize quality for complex work
  • Tiers bias routing over the same supported model set; plan and admin policies still apply
  • Paid plans receive a 10% discount on eligible Auto model usage
Defaulting to Auto removes a routine model-selection decision, but we can still express a tradeoff. Balance is a useful everyday choice, Efficiency favors cost, and Intelligence favors quality. The tiers use the same available model set; even Intelligence can route a simple question to a smaller model. Tiers are available in supported surfaces such as VS Code, Copilot CLI and the GitHub Copilot app; availability differs across clients. Paid-plan Auto usage in Chat, CLI, the app and cloud agent receives the regular ten-percent model-cost discount. It is not a fixed per-task price or a guarantee of the cheapest possible run.

Override Auto Only When the Task Justifies It

Task shape Best fit Reason
Quick syntax, repetitive edits, tiny utilities Fast help / lightweight models Low latency and lower cost are enough
Normal coding, summaries, documentation General-purpose models Good balance of quality, speed, and cost
Complex debugging, refactors, architecture Deep reasoning models The task needs stronger reasoning across more context
Autonomous multi-step implementation Agentic coding models The workflow benefits from planning, tools, and iteration
Choose by task, not vendor preference. A powerful model can be appropriate for ambiguous debugging, but it is not automatically safer for a routine edit. Use these categories as decision aids, then check actual outcomes and pricing. Set the model and reasoning level deliberately at the beginning of a session where possible. Switching models or reasoning settings mid-session can invalidate useful cached context, so escalation has a context cost as well as a different token rate.

Keep Prompts Concise and Batch Related Asks

Wasteful Pattern

Five follow-up messages for one task: "make it blue," "darker," "add padding," "fix the border," "one more thing."

Efficient Pattern

One prompt with all changes, desired output format, and acceptance criteria in a single round-trip.

  • Remove filler, repetition, and narrative backstory that does not help the model solve the task
  • Ask for a constrained output such as a checklist, diff summary, or five bullets max
  • Include success criteria once instead of re-explaining them across multiple messages
GitHub's efficiency guidance emphasizes a clear task, relevant context and a stopping condition. Batching related asks can prevent avoidable follow-ups, but do not remove information the model needs just to make the prompt shorter. A few extra acceptance criteria can save a whole failed run. Keep independent work separate, constrain unnecessary output, and include the test or other check that will tell us the task is done.

Reset or Compact Long Sessions

In Copilot

Start a new chat for unrelated work. For a continuing task, compact useful history rather than discard decisions.

In Copilot CLI

Use /context to inspect context usage and /compact to summarize a continuing conversation.

/compact Focus on the accepted API changes, remaining test failures, and files already modified.

Client-specific: this command with focus instructions is supported in Copilot CLI. Supported IDEs also offer compaction controls; do not assume identical commands everywhere.

A new problem deserves a fresh conversation, but a long continuing task benefits from a useful summary. In Copilot CLI, slash context helps us see where the space is going, and slash compact can preserve accepted decisions and remaining work. Automatic compaction also helps long sessions continue. Compaction uses a model to summarize history, so it is not free work or a substitute for checking important requirements. Cached input is often cheaper than fresh input; compare the context you preserve with the cost of rebuilding it.

Preserve Useful Context, Cut Rework

  • Preserve the cache. Avoid needless model, reasoning, and tool-configuration changes during a task
  • Keep instructions useful. A concise project map can prevent repeated exploration
  • Bound work with checks. Tests and clear stopping conditions reduce retries and scope drift
  • Measure accepted outcomes. Less text is not a saving if it causes another failed run
GitHub's official efficiency guidance adds an important counterweight to shorter prompts: preserve useful cached context. Repeated context may be billed at a lower cached-input rate; cache-write and long-context rates depend on the model. Caches also expire, so an old session may require rebuilding. Clear instructions and deterministic checks can save more than trimming a few words. Copilot CLI also has optional public-preview session credit limits, linked in the resources. They are soft limits, can slightly overshoot while a response finishes, and do not replace monthly admin budgets.
Part 5

Rollout and Real Scenarios

We now have the concepts and the habits. The last step is turning them into rollout guidance that a real organization can use. These scenario slides help explain when cheaper patterns are enough and when higher-cost AI workflows are absolutely justified.

Scenario: Same Bug, Cheaper Workflow

Approach What happens Likely spend pattern
Expensive default Open a broad chat, describe the bug vaguely, let the model explore multiple files, then refine through several follow-ups Higher input tokens, more round-trips, higher chance of rework
Efficient default Select the function, use inline chat for the bug, or write a comment scaffold and accept completions for the fix Can reduce irrelevant context; measure cost and verify correctness
We are not asking developers to stop using AI. We are choosing a bounded starting point for a known local issue. A broad exploration can be justified if we do not know the cause, but it is unnecessary when we already have a failing function and a clear test. Compare the completed fix, actual credit usage and test results. A narrowly scoped attempt is not cheaper if it misses the real bug and forces repeated rework.

Scenario: When Higher Spend Is the Right Call

Good Use of Higher-Cost AI

  • Multi-file refactor with tests
  • Architecture trade-off analysis
  • Repo-wide remediation campaign
  • Agentic workflow with clear acceptance criteria

Poor Use of Higher-Cost AI

  • Single-function bug fix
  • Simple boilerplate the editor can complete
  • Repeated formatting or rename tasks
  • Vague prompts that force unnecessary exploration
A spend-aware culture should not become a fear culture. There are absolutely situations where deeper reasoning models, chat, CLI, or cloud agent are worth every credit. The key test is leverage. If the workflow replaces meaningful human effort, lowers risk, or accelerates a multi-step task that would otherwise be slow and error-prone, higher spend can be excellent value. The anti-pattern is using that same power for tiny jobs that cheaper surfaces solve just as well.

A Practical 30-Day Rollout Plan

Window What to do
Week 0 Confirm current allowances, open AI usage, and agree paid-usage policy plus enforced spending limits with finance
Week 1 Publish Auto tier guidance, included completion options, and client-specific context/compaction practices
Week 2 Choose cost-center included caps or metered budgets where justified; start weekly usage and outcome reviews
Week 3 Identify expensive but low-value patterns and coach teams on better workflows
Week 4 Adjust budgets, document proven practices, and decide where user-level caps are actually needed
This plan works for a new rollout or a reset of existing governance; it is not tied to the first month after June's migration. Before the pilot, agree whether paid usage is permitted and which limits must stop work. Then communicate, observe, coach and refine inside that approved envelope. A firm financial ceiling and an evidence-based learning period can coexist. Include an exception owner so an incident response team is not stranded by a limit nobody can change.

Team Policy Checklist

  • Default to Auto unless there is a clear reason to override it
  • Prefer completions and Next Edit Suggestions for drafting and local edits
  • Use inline chat on a selection before escalating to broad chat or agentic workflows
  • Start fresh for unrelated work; compact continuing work and preserve useful cached context
  • Batch related asks and ask for concise outputs
  • Confirm code-review billing ownership and hosted Actions usage for agentic capabilities
  • Verify paid-usage policy, hard-stop settings, and weekly cost per accepted outcome
Keep the team policy short enough to use during real work. The core message is to match capability to the task, preserve useful context, and verify the outcome. Pair developer habits with an explicit administrative spending envelope and a known path for exceptions. As weekly evidence accumulates, record which workflows justify higher spend rather than treating every large session as a failure.
Summary

Wrap-Up and Next Steps

We have covered the official shift, the pricing model, the governance controls, and the developer behaviors that matter most. Let us close with the takeaways you want people to remember after the meeting ends and the links they will actually need when they go implement this.

Key Takeaways

  • Organizational and migrated monthly plans use tokens, models, and AI Credits; unexpired annual Pro/Pro+ plans are an exception
  • Seat prices stay the same, but variable usage becomes much more visible and controllable
  • For enterprises, pooling and budgets are the two biggest governance improvements
  • Code completions and Next Edit Suggestions remain your best low-cost drafting surfaces
  • Scoped prompts, useful compaction, and cache-aware sessions can reduce waste; verify actual outcomes
  • Auto model selection should be the default for most teams
  • The right goal is not minimal usage. The right goal is high-value usage
Optimization is not about avoiding advanced features. It is about matching the feature, model and scope to the value of the task, within an explicitly approved spending envelope. Remember the exceptions: some annual individual plans still use requests, user budgets can stop work before the pool runs out, and aggregate budgets need enforcement enabled to act as a ceiling. Good teams will still spend credits; they will use evidence to decide where those credits are worthwhile.
