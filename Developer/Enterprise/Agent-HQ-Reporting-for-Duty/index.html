Part 1

What Is Agent Coordination?

Before we dive into specific surfaces and tools, let's establish a shared understanding of what agent coordination actually means in the context of enterprise development.

The Multi-Surface Reality

  • Teams work across IDEs, browsers, terminals, chat platforms, and CI/CD systems
  • Agent coordination connects task assignment, execution, review, and integration
  • Repository guidance supplies context where the chosen feature supports it
  • Pass explicit scope and results between tasks; do not assume shared memory or identical permissions
  • Every handoff needs an owner and evidence of completion
        graph LR
          Task[Scoped task] --> Session[Agent session]
          Guide[Repository guidance] --> Session
          Session --> Evidence[Changes and test results]
          Evidence --> Review[Human review]
          Review --> Next[Next scoped task]
Think about how your team works today. Developers write code in VS Code, review pull requests on GitHub, run commands in the terminal, and discuss decisions in Slack or Teams. Coordination makes those entry points contribute to one accountable workflow. That does not mean every surface automatically shares a conversation or loads the same instructions. A useful handoff says what changed, what was tested, what remains uncertain, and who owns the next decision. We will keep coming back to that contract.

Agent Surfaces at a Glance

VS Code

Work interactively beside code, tests, and the debugger. File and tool access depend on workspace boundaries, harness, permissions, and policy.

GitHub.com

Ask repository questions, start cloud tasks, track sessions, and request PR review. The collaboration surface for asynchronous work.

Copilot CLI

A standalone terminal agent that can inspect files, make changes, and use tools. Review its permissions before delegating work.

Slack

The GitHub app can turn a discussion into a cloud-agent task. Repository access, identity, and conversation context need explicit care.

Each surface has distinct strengths. VS Code is a good fit when you want to inspect a change alongside your tests and debugger. GitHub is useful when the task can continue without your editor being open. The standalone CLI brings agentic work to a terminal-first workflow, rather than only explaining commands. Slack connects a discussion to an implementation task, but it is not an unrestricted gateway to organizational knowledge. Choose the surface for the task and its trust boundary, not just for convenience.
Part 2

Agent Mode in VS Code

Let's start with the surface most developers interact with daily: VS Code. Agent mode represents a significant evolution in how Copilot operates within the editor.

Choose the Least Autonomous Workflow

Suggestions & Focused Edits

Use inline suggestions or inline chat when the change is local and you want to stay close to the code.

Ask Questions

Use chat to understand code and compare approaches without delegating an implementation task.

Plan First

Ask for a plan before edits, or select Plan where available. Agree scope, acceptance criteria, and constraints.

Delegate Execution

Use an agent to find relevant files, make changes, run checks, and iterate. You still verify the result.

These are workflow choices, not four mutually exclusive modes. Chat is also the surface where you direct an agent. If you only need an explanation, there is no reason to grant a task broad execution authority. For a larger change, first agree what success means, then let an agent work within that scope. A dedicated planning option depends on the selected harness and client. The enterprise decision is how much autonomy the task needs and how you will verify the result.

Agent Mode: How It Works

  • Agent loop: gather context, act with tools, inspect results, and adjust
  • Tools: file operations, search, terminal commands, and approved MCP integrations
  • Recovery: an agent can respond to failing tests; success is not guaranteed
  • Permissions: tool and terminal approval depend on settings, harness, and enterprise policy
  • Edit review: inspect the diff before integration; sensitive-file rules can require edit approval
  • Boundaries: review workspace trust, file access, and tool scope before execution
An agent can choose searches and tests without asking you to prescribe each step. That autonomy makes the boundary important. Reviewing a diff after an edit is different from approving a command before it runs; do not treat them as the same safeguard. Tool permissions and sensitive-file protections depend on your configuration and harness. Keep approvals narrowly scoped, inspect proposed commands, and check the resulting changes. An agent saying that tests passed is a starting point for examining evidence, not a substitute for it.

Model Selection in Agent Workflows

  • Available models depend on the surface, plan, and organization policies
  • Compare task fit: reasoning quality, latency, context needs, and tool support
  • Check the live supported-model catalog; availability and retirement dates change
  • Enterprise AI-credit cost depends on the model and input, output, and cached tokens
  • Set budgets and stop conditions before multiplying concurrent sessions
  • Start with the approved default; switch when a measured task requirement justifies it

Supported models · Enterprise billing

We do not need to memorize a model list that can change before our next rollout. Start with the models your organization permits on this surface, then evaluate them against representative tasks. Current enterprise AI credits reflect model and token consumption, not a universal fixed price per message. A long session with large context can cost more than a short question even when both use the same model. Parallel agents can reduce elapsed time, but they also multiply usage and review demand. Decide what evidence would justify the additional cost.
Part 3

Copilot Across Surfaces

Now let's look beyond VS Code at the other surfaces where Copilot agents operate, starting with GitHub.com.

Copilot on GitHub.com

  • Chat: ask repository questions and explore implementation approaches
  • Cloud tasks: delegate scoped work from supported agents and issue entry points
  • PR summaries: draft descriptions; verify intent and completeness
  • Code review: request feedback separately from requesting code changes
  • Search: use repository context; web capabilities depend on availability and policy
  • Access: repository permissions and policies apply, but outputs still require review
GitHub brings questions, delegated work, and review into familiar repository workflows. A PR summary helps describe a change, while code review looks for problems in it; neither proves correctness. Repository permissions constrain access, but they do not eliminate risks such as inappropriate context sharing or prompt injection. Check what context a task can access and inspect what it produces. We will use the agents surface to track work rather than assuming that a mention anywhere invokes the same capability.

Copilot in the CLI

  • Use the standalone GitHub Copilot CLI, launched with copilot
  • It can inspect local code, edit files, run commands, and use configured tools
  • Ask for explanations or delegate scoped implementation and debugging tasks
  • Review directory trust, tool permissions, and proposed actions before granting access
  • Availability depends on your subscription and organization policies
  • The earlier GitHub CLI extension was deprecated on October 25, 2025
copilot

Official CLI setup and usage

The current terminal surface is a standalone agent, not the old command-suggestion extension. Launch it in the repository you intend to work on, and review its trust and permission prompts before assigning a task. It can read files and perform multi-step work, which makes the same scoping and review practices important here as in the editor. You can still ask it to explain a command without authorizing that command to run. Use the official setup guide for your platform and approved installation method; this slide is not an instruction to install or execute anything automatically.

Copilot in Slack

  • The GitHub app for Slack provides the Copilot cloud-agent integration
  • Use @GitHub in a thread, or a direct message, to start supported work
  • Public preview: verify plan, cloud-agent policy, and app repository access
  • Starting code changes requires write access; not every participant can initiate a session
  • Shared contexts use the app identity; direct messages use your linked account permissions
  • The full thread can become task context and appear in generated artifacts

Slack integration prerequisites and security considerations

Slack is useful when a discussion already contains the problem and the agreed outcome. The integration lives in the GitHub app and can start a cloud task from that conversation. Before mentioning it, consider who can see the thread and whether its full context is appropriate for the generated artifacts. A direct message can limit the conversation context, but permissions and repository access still matter. Shared-context tasks use a different identity model from direct messages, so do not assume every artifact is created as your personal account. Check the current preview requirements in your tenant before relying on this path.
Part 4

The Copilot Cloud Agent

        graph LR
          Task[Scoped task] --> Cloud[Cloud session]
          Cloud --> Change[Proposed change]
          Change --> Checks[Tests and review]
          Checks --> Human[Human merge decision]
You may know this as Copilot coding agent. Current documentation uses cloud agent for delegated work that runs away from your local editor. The important distinction is the execution environment and review boundary, not the label.

What Is the Cloud Agent?

  • Delegate implementation work without keeping your IDE open
  • Assign an issue to Copilot or start a task from a supported agents entry point
  • The agent works in a cloud environment, makes changes, and can open a PR
  • Supported repository instructions guide its work; they do not guarantee compliance
  • Prefer clear requirements, limited scope, and explicit acceptance checks
  • Draft PRs, workflow approvals, and human merge controls are part of the lifecycle
Instead of staying in an interactive editing loop, you delegate a task and return to inspect its progress. The cloud agent can explore code, implement a change, and run checks in its environment. That does not mean every dependency is automatically available or every test can run. Repository setup, network access, and credentials affect what is possible. Its PR is subject to specific safeguards, including draft status and workflow approval defaults. Keep the task narrow enough that another person can verify the result without reconstructing the entire session.

How the Cloud Agent Works

  • 1. Define: select the repository, task scope, and acceptance criteria
  • 2. Start: assign an issue to Copilot or submit a task in the agents UI
  • 3. Implement: the agent explores files, proposes changes, and runs available checks
  • 4. Monitor: inspect session logs and steer supported running sessions
  • 5. Validate: inspect the draft PR; approve workflow execution according to policy
  • 6. Integrate: review CI evidence, request fixes, and obtain required human approvals
An assigned issue should contain enough detail for a bounded implementation, not just a vague goal. Depending on the entry point, a PR may be created immediately or after you request it. Follow the session while it runs and distinguish checks run inside that environment from repository CI. By default, workflows on cloud-agent changes need an authorized person to approve and run them; configured policies can change that behavior. If CI fails, steer the agent through a supported follow-up rather than assuming an endless automatic repair loop. A human still owns the merge decision and required approvals.

When to Use the Cloud Agent

Good Candidates

  • Bug fixes with clear reproduction steps
  • Adding unit or integration tests
  • Small, well-defined features
  • Refactoring with clear scope
  • Documentation updates
  • Dependency version bumps

Needs More Human Involvement

  • Ambiguous or open-ended requirements
  • Large architectural changes
  • Tasks needing sensitive external credentials
  • Performance-sensitive optimizations
  • Security-critical code paths
  • Tasks needing stakeholder discussion
Knowing when to delegate and when to keep a task close to a human developer is critical. Clear reproduction steps, bounded test coverage, and a small documented change make review practical. On the other hand, ambiguous requirements and major architecture decisions need discussion before implementation. Credentials are not automatically forbidden, but granting them changes the risk and requires explicit configuration and review. For a security-critical path, use specialist expertise and independent validation. A complete issue specification improves the odds of success; it does not guarantee that the agent can finish it.
Part 5

Launching Agents from Issues & PRs

We have seen how a delegated task runs. Now let's separate the ways you start implementation, ask for a change, and request a review. Those are different operations even when they happen on the same pull request.

Issues, Changes, and Reviews

GoalSupported entry pointExpected result
Implement an issueAssign the issue to CopilotCloud-agent task and proposed changes
Change an existing PR@copilot in a PR commentAgent works on the PR branch
Review a PRRequest Copilot as a reviewerReview feedback, not approval
Understand codeCopilot Chat with relevant contextAnswers to verify

Use authorized accounts and supported repository settings. An arbitrary issue comment is not a universal agent API.

If you want implementation, assign the issue or start a task from the agents UI. If a PR already exists, a supported at-mention can ask the cloud agent to change its branch. Asking Copilot to review is a separate request through the reviewer workflow. A review does not satisfy the human approval requirement or guarantee that the code is correct. Keep questions in the appropriate chat experience rather than expecting any issue comment to become a conversational bot thread. Permissions still determine who can trigger work.

Automated Triage with Copilot

  • Repository automations can run cloud-agent tasks when issues are created
  • Current eligibility includes private/internal repositories, supported plans, and enabled policies
  • Choose the prompt, trigger filters, model, and least-privilege tools
  • Agentic Workflows offer a separate Markdown-to-Actions approach, currently in public preview
  • Define reviewable outputs and verify routing; posting a mention is not an orchestration API
        graph LR
          Issue[New issue] --> Trigger[Configured automation]
          Trigger --> Scope[Allowed tools and scope]
          Scope --> Proposal[Triage result]
          Proposal --> Review[Review and routing]

Automations · Agentic Workflows

There are documented ways to automate triage without pretending that a bot comment is an API. Built-in automations can react to an issue event in eligible repositories, using only the tools you permit. Depending on configuration, high-confidence actions may be applied while other results need review, so choose the allowed actions deliberately. Agentic Workflows are a separate preview approach that compiles Markdown into Actions workflows with explicit permissions and safe outputs. Check current availability and your repository's trust model before choosing either. If you want duplicate detection or team routing, define and validate that task rather than treating it as guaranteed behavior.
Part 6

Multi-Agent Workflows

Now we enter the most advanced territory of this session: coordinating multiple agents across surfaces to accomplish complex, end-to-end workflows.

Coordination Patterns

Sequential Pipeline

Finish one bounded task before handing its evidence to the next. Example: implement, validate, request review, then update documentation.

Fan-Out / Fan-In

Run independent tasks in parallel, then reconcile their results. Define file ownership, isolation, and one integration owner.

Event-Driven

Use a supported automation or explicitly configured workflow. Specify triggers, credentials, permissions, and reviewable outputs.

Human-in-the-Loop

Pause at a decision boundary. A person reviews evidence and authorizes integration or the next phase.

These patterns describe control flow, not four built-in agent types. You can combine them: parallel implementation tasks might feed one integration step with a human approval gate. Within a supported session, an agent can also delegate bounded work to subagents. That is different from a workflow coordinating independent cloud tasks across repositories. Decide which layer owns retries, cancellation, and integration. More agents are not automatically better; delegation adds usage and coordination overhead, especially when tasks are tightly dependent.

Track Parallel Work with Agent HQ

  • Start and track cloud tasks from GitHub's supported agents surfaces
  • Inspect task status, proposed changes, and session logs; steer running work where supported
  • In VS Code, start an explicit new session for independent work
  • Separate conversation history does not guarantee separate files or branches
  • Choose a worktree or cloud task when implementation changes need isolation
  • Continue across supported surfaces only when the session type and policy allow it
        graph LR
          Owner[Task owner] --> A[Isolated API task]
          Owner --> B[Isolated test task]
          A --> Evidence[Logs and changes]
          B --> Evidence
          Evidence --> Integrate[Reviewed integration]
Agent HQ is about managing work, not just opening more tabs. Use the task and session views to see what is running, what changed, and where a task needs input. In VS Code, a fresh chat can have its own history while sharing the same session's files. Moving a conversation into an editor tab does not create filesystem isolation. For independent implementation, choose a separate session with the right worktree or a cloud task. Supported continuation between surfaces can help you move from monitoring to detailed inspection, but do not assume every client or harness shares live state.

Managing Parallel Agents

  • Assign clear scope, file ownership, acceptance checks, and an integration owner
  • Use separate worktrees for independent branches; shared history is not a complete sandbox
  • Windows example, run only after review and authorization:
# From the original repository, create a NEW task branch:
git worktree add -b migration-branch ..\migration-work
code -n ..\migration-work

# After task changes are reviewed and committed:
# In the original worktree, on the intended integration branch:
git merge migration-branch

# After integration, remove the clean task worktree:
git worktree remove ..\migration-work
A worktree gives the task a separate checkout and branch, so concurrent edits do not overwrite your active working files. The example creates a new branch explicitly; choose an unused branch name and destination. Before merging, finish and commit the reviewed task changes, return to the original worktree, and confirm the intended integration branch and clean state. Resolve conflicts and run integration checks there. Cleanup should not force-delete unfinished work. Worktrees still share repository metadata and can access other machine resources, so they do not replace tool permissions, secret handling, or sandbox controls.

End-to-End: From Issue to Merge

  • 1. Define: record reproduction steps, scope, owner, and acceptance criteria
  • 2. Triage: a person or configured automation proposes classification and routing
  • 3. Delegate: assign the issue to Copilot; monitor the cloud-agent session
  • 4. Inspect: review proposed changes and request Copilot review separately
  • 5. Validate: approve workflow runs as required; inspect CI and steer fixes
  • 6. Integrate: obtain required human approvals and merge
  • 7. Close the loop: share the PR and validation evidence in the team channel
This workflow connects the patterns without relying on an invisible orchestrator. Triage has an explicit implementation and permission boundary. Assignment starts the cloud task, and session logs show what it actually did. A review request adds another opinion, while CI provides repeatable checks after any required workflow approval. If something fails, an authorized follow-up asks for a scoped repair; failure does not guarantee an automatic retry. A person then confirms the evidence and required approvals. Sharing the merged PR is often a clearer handoff than asking a chat integration to reconstruct the entire incident.
Part 7

MCP & Custom Agents

We need two different kinds of customization: guidance about how to work, and access to tools that can act. MCP integrations and custom agents address different parts of that problem. Keeping them separate makes enterprise permissions easier to reason about.

Tools, Specialization, and Delegation

Building blockPurposeBoundary to check
MCP serverExpose tools and external dataTrust, authentication, and allowed actions
Custom agentSpecialize instructions and tool selectionHost support and permitted tools
SubagentDelegate bounded work in another contextScope, tool access, and overhead
Independent sessionOwn a separate task lifecycleWorkspace or worktree isolation

GitHub App-based Copilot Extensions were retired November 10, 2025. MCP is an architectural replacement, not a drop-in protocol conversion.

A custom agent can describe a reviewer's responsibilities and restrict its tools. An MCP server supplies a callable integration; it does not itself become the manager of the task. A subagent gets bounded work and returns a result, while an independent session has its own lifecycle. Neither a custom role nor a separate context automatically isolates file edits. The retired server-side Copilot Extension model is not a path for new integrations. Client-side VS Code extensions are a different category and were not part of that retirement.

A Governed Tool Integration

  • Select a trusted MCP server and review its configuration before enabling it
  • Limit exposed tools and downstream credentials to the task's needs
  • Review tool results as untrusted context; preserve human integration gates
  • Verify supported authentication and policies in each host, not just one client
        graph LR
          Agent[Agent session] --> Gate[Tool permission gate]
          Gate --> MCP[Trusted MCP server]
          MCP --> System[Authorized internal system]
          System --> Result[Scoped result]
          Result --> Agent
          Agent --> Review[Human reviews changes]

Extension retirement and MCP replacement

This is a conceptual integration flow, not a universal wire protocol or runnable server example. The agent requests a tool action through the host's permission controls. The server then needs appropriate authorization to the downstream system; approving a tool does not grant unlimited access to that system. Review the server's provenance, credentials, network reach, and logging behavior before using it with private code. Tool output can contain mistakes or malicious instructions, so keep it inside the same review discipline as repository content. Detailed server implementation belongs in a dedicated MCP session.

Custom Instructions & Enterprise Governance

With agents running across multiple surfaces, consistent behavior and strong governance become essential. Let's look at how custom instructions and enterprise policies work together.

Custom Instructions Across Surfaces

.github/copilot-instructions.md provides shared repository guidance, not an enforcement boundary.

FeatureRepository-widePath-specificOther guidance
VS Code ChatSupportedSupportedHost-supported agent instructions
GitHub.com ChatSupportedNot listedPersonal and organization instructions
Cloud agentSupportedSupportedSupported agent and organization instructions
GitHub code reviewSupportedSupportedFeature-specific agent instructions

Check the current support matrix. Use CI and repository rules to enforce requirements.

A common repository file helps your team express coding standards and testing expectations once. It does not mean every surface reads every instruction type, follows arbitrary linked documents, or complies perfectly. Path-specific instruction files use applyTo patterns in supported features, while personal and agent guidance differ by host. Check the feature you actually use rather than assuming support transfers from another client. Version-control the guidance, keep it relevant, and validate compliance with tests and repository rules. Prompts, skills, and custom-agent files are additional customization mechanisms, not universal policy enforcement.

Enterprise Permissions and Policies

  • Access: approve agent surfaces, repositories, models, and license assignments
  • Tools & secrets: use least privilege and review MCP/server access
  • Content exclusions: not supported in Edit/Agent modes; not a universal agent boundary
  • Isolation: combine workspace scope, sandbox/network controls, and human gates
  • Budgets: bound usage, retries, and escalation before scaling parallel work
  • IP defense: subject to the applicable agreement, mitigations, and product terms
        graph LR
          Policy[Enterprise policy] --> Access[Approved scope and tools]
          Access --> Agent[Bounded agent task]
          Agent --> Evidence[Logs tests and diff]
          Evidence --> Human[Human approval]
Guidance is not a substitute for permissions. In particular, content exclusions do not protect Edit and Agent mode in the way you might expect from other Copilot experiences, and indirect semantic context is another documented limitation. Keep sensitive data out of unnecessary task scope and review credentials and network access. Set a budget or stop condition so a fleet does not turn repeated failures into unbounded work. Any IP defense depends on your actual agreement, purchase channel, required mitigations, and preview terms. Have your legal and platform owners confirm tenant-specific requirements rather than treating a plan name as a blanket guarantee.

No single report gives us a complete cross-surface account of everything an agent did. Audit events help with traceability, session logs explain execution, and PR history shows the reviewed change. Usage reports answer adoption questions, but detailed breakdowns depend on telemetry and some surfaces are excluded. Verify your export permissions and the data each report actually contains. Splunk, Sentinel, or Datadog might be destinations in your design, but this course does not establish a turnkey connector for any of them. Measure review effort, failures, rework, elapsed time, and cost together rather than using activity as a proxy for quality.
Part 9

Real-World Scenarios

Let's bring everything together with three illustrative scenarios. These are patterns to adapt and measure, not claims that a particular tenant already has the integrations enabled or will achieve a guaranteed time saving.

Scenario: Security Vulnerability Remediation

  • Trigger: Dependabot raises a vulnerable-dependency alert, not an issue by default
  • Triage: a security owner confirms severity and the appropriate remediation path
  • Delegate: use a supported alert-to-agent path if eligible, or a clearly scoped issue
  • Fix: assess existing update PRs; delegate compatibility changes and tests where needed
  • Review: inspect scans, CI, and the diff; a security engineer approves integration
  • Measure: track remediation lead time, regressions, and review effort
Begin with the alert and an accountable security owner. Dependabot does not automatically create a GitHub issue; an issue is a separate handoff if your process needs one. Check whether a security update already addresses the dependency before creating duplicate work. Current alert assignment can delegate to an agent, but it has access and licensing prerequisites, so confirm those first. If you use an issue instead, include the affected version, desired outcome, and acceptance tests. Keep specialist approval and measure the actual result rather than promising a reduction from days to hours.

Scenario: Dependency Updates at Scale

  • Challenge: many repositories need a shared internal-library update
  • Prepare: standardize requirements, compatibility checks, and repository owners
  • Fan-out: use reviewed automation to create and assign bounded repository tasks
  • Batch: respect current service limits, budgets, access, and reviewer capacity
  • Fan-in: collect PR and CI status through an explicitly built tracking process
  • Measure: pilot a small batch; compare completion, rework, and total cost
Parallel work is attractive when repositories are independent, but the rollout still needs management. Give each task a clear target version, known breaking changes, and a verification command. A cloud task works in its selected repository; a central coordinator must manage the collection of tasks rather than assuming one run edits every repository. Start with a batch that your reviewers can absorb. Verify current service limits and policy without assuming a fixed organization concurrency quota. The tracking dashboard is a custom integration unless you have explicitly selected a supported product feature. Expand only after the pilot shows acceptable quality and cost.

Scenario: Documentation Generation

  • Trigger: an API version changes and consumer guidance needs revision
  • VS Code: draft reference updates from the relevant source and specification
  • Cloud tasks: delegate scoped integration-guide changes in consumer repositories
  • Review: technical writers and API owners check examples and compatibility claims
  • Communication: share reviewed docs and PRs; use eligible Slack sessions for follow-up tasks
  • Measure: check example correctness, stale references, and adoption questions
Documentation often crosses repository boundaries, so it is a useful test of handoff quality. Give each consumer task the reviewed API contract rather than assuming it knows what another agent just changed. Generated examples need to be tested, and compatibility language needs an API owner. A Slack thread can supply context for a follow-up task when that integration is enabled, but it is not a guarantee of correct answers or access to every team's documentation. The goal is a reviewable update process that can detect drift, not a claim that generated documentation automatically stays synchronized.
Summary

Wrap-Up & Next Steps

Let's wrap up with the key takeaways from today's session.

Key Takeaways

  • Choose the surface: local collaboration, terminal work, or a cloud task
  • Use supported entry points: issue assignment, PR change requests, review, and configured automation
  • Track the lifecycle: inspect sessions, steer work, and review changes
  • Coordinate deliberately: sequential, fan-out, event-driven, and human-checkpoint patterns
  • Separate concepts: MCP tools, custom agents, subagents, and independent sessions
  • Isolate implementation: separate context does not mean separate files
  • Govern with layers: permissions, budgets, tests, evidence, and human approvals
  • Start small: pilot two surfaces, measure quality and cost, then expand
We have kept the same coordination framework while making the handoffs explicit. A task needs a suitable surface, bounded authority, evidence, and an integration owner. Shared instructions help guide behavior, but they do not enforce requirements or create isolation. Agent HQ session tracking, worktrees, and supported automation can connect the pieces without hiding the review boundary. Start with one workflow and compare the result against your existing process. Expand when the evidence shows value, not just because more agents can run at once.
