Intermediate · 45 Minutes

Review Me, Review Me Not, Review Me

Prepare locally. Delegate deliberately. Validate in the cloud.

We're following a complete delivery loop, not touring a catalog of review products. We'll turn an ambiguous task into a bounded plan, prepare the repository for autonomous work, and delegate from VS Code to Copilot cloud agent. Security findings will give us another source of feedback, but a human still owns the merge decision.
Challenge

Ship Without Losing Control

A teammate left an underspecified issue. Your mission is to turn it into an agent-ready task, delegate it to the cloud, and bring the resulting pull request through security and human review.

Starting State

Ambiguous scope, undocumented commands, incomplete tests, and no explicit security boundary.

Done State

Reproducible setup, bounded handoff, validated pull request, resolved security findings, and human approval.

Getting code from the agent is only part of our challenge. We also need to preserve intent and control as execution moves between our machine and the cloud. Which gap in this starting state would create the most expensive failure in your repository: unclear scope, missing tests, or an undefined security boundary?

What You Will Be Able to Do

  • Choose between local, background, and cloud execution
  • Optimize a repository and task before delegation
  • Transfer a local plan into a cloud agent session
  • Supervise cloud execution without micromanaging it
  • Fix PR findings in place and delegate eligible default-branch alerts
  • Return work to local validation and human-controlled merge
The goal is a repeatable decision model, not memorizing buttons. You'll know what another agent needs before it starts and which evidence you need before accepting its work. We'll distinguish a new finding on our PR from an existing default-branch alert because those findings have different remediation entry points.

The Delivery Loop

graph LR
  A[Choose surface] --> B[Optimize locally]
  B --> C[Hand off]
  C --> D[Supervise cloud]
  D --> E[Security feedback]
  E --> F[Review and gate]
  F --> G[Return or merge]
Here's the loop we'll follow. Review and security can send us back for another iteration rather than simply marking the end of implementation. We might continue with the cloud agent or return to local debugging. Either way, we keep the acceptance criteria and review record connected until the change is ready.
1. Choose

Put the Work in the Right Place

The first optimization is choosing the execution surface. Sending every task to the cloud is not maturity. Matching task shape to agent type is.

One Job, Three Execution Surfaces

A conceptual execution model, not an exhaustive list of VS Code session targets.

SurfaceBest FitContextInteraction
Interactive local workAmbiguous explorationWorkspace and local toolsInteractive
Background local workIsolated implementationLocal machine or worktreeAsynchronous
Cloud agentBounded repository taskGitHub and configured cloud toolsAsynchronous
These rows describe where and how work happens. In current VS Code, a harness controls tools and behavior, while Cloud is an execution target. Both the Copilot and Local harnesses can run on your machine, so the labels aren't interchangeable. Copilot cloud agent runs in an Actions-powered ephemeral environment and cannot see arbitrary local terminal state, unsaved files, or local-only services.

The Delegation Decision

Stay Local

Requirements are changing, decisions require rapid feedback, or the task depends on unavailable local state.

Go to Cloud

Scope is bounded, context is durable, commands are reproducible, and completion can be checked.

Decision rule: delegate execution only after uncertainty has been reduced enough for asynchronous work.

Cloud execution isn't the destination for every task. It's useful when the agent has enough context to check whether the work is done. If you expect to answer a design question every two minutes, staying interactive will probably give you a shorter feedback loop.

Context Has a Border

The cloud boundary is why our handoff artifact matters. A supported conversation handoff carries history, but attaching a saved plan to a new session shares that plan, not the entire conversation. Neither transfers local runtime state. Repository files must be available on the target branch, and external tools need their own cloud configuration.
2. Optimize

Prepare Before You Delegate

Before we delegate, we can remove work the agent would otherwise have to rediscover. A predictable setup and a clear completion check reduce both uncertainty and wasted execution time. Let's make the repository easier to work in, not just make the prompt longer.

Optimize for a Short Feedback Loop

graph LR
  A[Clear scope] --> B[Fast setup]
  B --> C[Deterministic checks]
  C --> D[Small diff]
  D --> E[Useful review]
  • Reduce discovery the agent must repeat
  • Make success observable through commands
  • Keep the change within one repository, branch, and pull request
Optimization is not prompt polishing alone. It is repository engineering. A lockfile, a fast test, and a stable setup command often improve results more than another paragraph of instructions. Smaller tasks can reduce retries and AI credit usage, along with billed runner time when GitHub-hosted runners are used.
Lab Checkpoint

Is This Repository Agent-Ready?

  • Can a fresh environment install dependencies without guessing?
  • Are build, test, and lint commands documented and fast?
  • Do tests prove the acceptance criteria?
  • Are instructions specific and free of conflicts?
  • Are secrets, network destinations, and external tools bounded?
  • Can the task complete within the cloud session limit?
Imagine cloning this repository onto a fresh runner. Which command would fail first, and how would you know? The session maximum is 59 minutes, so setup and validation need to fit inside that window. If a setup step fails, the remaining setup steps are skipped and the agent still starts with the environment it has. We need evidence that preparation actually succeeded.

Make Setup Deterministic

name: Copilot Setup Steps
on:
  workflow_dispatch:
  pull_request:
    paths: [.github/workflows/copilot-setup-steps.yml]

jobs:
  copilot-setup-steps:
    runs-on: ubuntu-latest
    permissions:
      contents: read
    steps:
      - uses: actions/checkout@v7
      - uses: actions/setup-node@v7
        with:
          node-version: "22"
          cache: npm
      - run: npm ci
      - run: npm test
This example belongs in .github/workflows/copilot-setup-steps.yml on the default branch, with a single job named copilot-setup-steps. The read-only contents permission is enough for checkout; the agent receives its own credentials separately. npm ci needs a consistent committed lockfile, and npm test needs a real test script. Caching npm downloads doesn't install dependencies. We would run this workflow through Actions before trusting it in a session, using the runtime and commands our repository actually requires.

Put Guidance at the Right Layer

ArtifactPurposeGood Content
.github/copilot-instructions.mdRepository-wide standardsBuild, test, architecture, security
Path-specific *.instructions.mdScoped conventionsAPI, UI, test, or documentation rules
AGENTS.mdAgent-facing operational contextCommands, boundaries, workflow
Agent skillsReusable specialist workflowScripts, references, repeatable procedures
MCP configurationExternal context and toolsOnly the access required for the task
Each layer has a different job. Our universal rules belong in .github/copilot-instructions.md; scoped rules belong in .github/instructions/NAME.instructions.md with an applyTo pattern. Duplicating the same rule in both places creates a maintenance problem. Skills package reusable procedures, while MCP gives access to external tools. We need to check support and permissions at the destination rather than assume our local configuration travels.

Design the Cloud Boundary

Permit Deliberately

Required package registries, least-privilege Agents secrets and variables, approved MCP tools, and isolated runners.

Assume Nothing

The integrated firewall is not comprehensive, does not cover MCP servers, and does not cover setup-step processes.

  • Never expose production credentials to a learning repository
  • Do not rely on content exclusions as an execution security boundary
  • Use ephemeral, single-use infrastructure for self-hosted runners
The firewall is useful, but it isn't a complete security boundary. GitHub documents that it applies to processes started through the agent's Bash tool inside the Actions appliance, not directly to setup steps or MCP server processes. Configured MCP tools can run without individual approval prompts. We therefore need separate controls for those tools, narrowly scoped Agents credentials, and no production secrets in this learning environment.
Lab Checkpoint

Build the Handoff Packet

# Objective
One observable outcome.

## Relevant context
Files, architecture, and prior decisions.

## Acceptance criteria
- Behavior that must be true
- Tests that must pass

## Validation
Exact build, test, lint, and scan commands.

## Constraints and non-goals
Security boundaries and work explicitly excluded.
Our handoff packet can live in an issue, a committed planning document, or a supported conversation handoff. A file such as docs/handoff.md gives us something durable to review before delegation. If a requirement cannot be checked objectively or resolved from available context, we need to clarify it now rather than leave the cloud agent to guess.
3. Hand Off

Move Intent, Not Just a Prompt

The handoff begins locally because ambiguity is cheaper to resolve while the developer is present. Execution moves only after the plan and verification strategy are explicit.

Plan Locally

sequenceDiagram
  participant D as Developer
  participant P as Plan agent
  participant R as Repository
  D->>P: State objective and constraints
  P->>R: Inspect code and tests
  P-->>D: Propose bounded plan
  D->>P: Resolve ambiguity
  P-->>D: Final plan and checks
We can use the Plan agent to inspect the workspace and surface decisions before implementation. In a Copilot harness session, /plan starts that workflow. A useful plan names the affected files and the commands that will prove success. Before approving it, we can challenge assumptions and resolve anything another agent would otherwise have to guess.
Handoff

Continue in the Cloud

  1. Review the local plan and save durable repository context
  2. Check the active harness and available handoff controls
  3. In a Copilot harness session, use /delegate for a bounded cloud handoff
  4. Confirm repository access, branch context, and available agent/model choices
  5. Let the session run asynchronously

Alternatives: Local Plan's Start Implementation dropdown offers supported Continue in destinations. For a new session, select Session Target → Cloud and attach the saved plan.

The controls depend on our harness and installed VS Code version. Copilot Plan has review and approval actions; the Local harness has a Start Implementation dropdown with available Continue in destinations. A supported handoff carries conversation context, while a new Cloud session with an attached plan receives that artifact rather than the whole conversation. Before starting, we need a GitHub repository, permitted cloud-agent access, durable branch content, and cloud-configured tools. Some entry points create a PR immediately, so supervision starts before we mark anything ready for review.

Supervise Through Evidence

  • Read the proposed plan before accepting implementation direction
  • Watch setup-step output for missing tools or blocked downloads
  • Inspect commits and changed files for scope drift
  • Confirm which build, test, and lint commands actually ran
  • Use follow-up instructions when evidence contradicts the goal
  • Approve workflow runs when required; mark the PR ready only after checking evidence
We can supervise without prescribing every edit by comparing the session's evidence with our handoff packet. By default, workflows on a cloud-agent PR wait for a write-access person to select Approve and run workflows, unless automatic running is configured. A missing check may mean approval is pending, not that tests passed. The agent cannot mark its PR ready for review, approve it, or merge it; those decisions stay with people.

Recover at the Right Layer

FailureBest Response
Dependency cannot installRepair setup steps or firewall access
Agent misunderstood architectureImprove durable repository guidance
Task expanded beyond one outcomeStop and split the work
Implementation needs a small correctionGive a specific follow-up instruction
Approach is fundamentally wrongReturn local, revise the plan, and redelegate
A longer prompt won't repair a broken dependency setup. We get a more durable improvement by fixing each failure where it starts: environment configuration, repository guidance, or task scope. A focused follow-up is enough for a small implementation mistake, but a fundamentally wrong plan is a reason to return local and rethink it.
4. Secure

Turn Findings into Agent Work

Security findings give us a new task, but the alert's location changes the handoff. A finding introduced on our PR needs a fix on that PR. An eligible existing default-branch alert can instead be assigned to agentic autofix for a separate remediation PR. In either case, we need fresh analysis and tests rather than a promise that the fix worked.
Lab Checkpoint

Route the Finding by Branch

graph LR
  A[PR-only alert] --> B[Fix same PR]
  B --> C[Rerun checks]
  C --> D[Human review]
  E[Default-branch alert] --> F[Assign to Copilot]
  F --> G[Best-effort validation]
  G --> H[Draft fix PR]
  H --> D
Here's the important fork. Agentic autofix can receive default-branch alerts, but alerts detected only on a PR or another branch cannot be assigned to it. We fix new PR findings manually or with a bounded cloud-agent follow-up on that same PR, then rerun the checks. We never merge vulnerable code just to make an alert eligible. For an existing default-branch backlog or campaign, we can assign up to 25 eligible alerts together and review the resulting fix PR.

CodeQL Detects. Agents Remediate.

CapabilityRoleOutput
CodeQLDeterministic static analysisAlert and data-flow evidence
Copilot AutofixOne-step suggested correctionProposed fix
Agentic autofixDefault-branch alert remediationDraft PR with best-effort validation
Copilot code reviewContextual pull-request reviewReview comments
GitHub Code QualityQuality, coverage, and debt controlsConfigured findings and merge gates
CodeQL is the analysis engine, not an autonomous agent. By default, cloud agent also attempts its own CodeQL, dependency, and secret checks plus a Copilot review second opinion; those built-in checks don't require separate security licensing and can be configured. They aren't a substitute for repository code-scanning setup or required checks. Agentic autofix is a separate alert-remediation workflow, and its ability to confirm a fix depends on the query and analyzer involved.

What Agentic Autofix Actually Does

  1. Receives up to 25 eligible default-branch alerts as task context
  2. Explores relevant files across the repository
  3. Generates a repository-aware correction
  4. Attempts validation by rerunning CodeQL with its code-scanning query suite
  5. Iterates when the result still fails
  6. Opens a draft pull request recording validation results and limitations

Generally available since October 15, 2026. Check repository eligibility, administrator enablement, and billing before assignment.

Agentic autofix and Copilot Autofix have separate access controls; enabling one is not a universal prerequisite for the other. Current documentation says agentic autofix doesn't require a Copilot license, but repository eligibility, higher-level policy, and a billing method still matter. Organizations that used the preview must enable it again. Usage consumes Code Security AI credits and runner-dependent Actions minutes. Validation is best effort: it cannot confirm fixes for custom CodeQL queries, security-extended, or third-party-tool alerts. Those cases need separate original-tool analysis; a draft PR is not proof of success.

Trust the Evidence, Then Review the Code

  • Rerun the relevant analyzer and confirm the original alert is absent
  • Inspect the complete data flow, not only the reported line
  • Run functional and regression tests
  • Check for behavior changes introduced by sanitization or validation
  • Review dependencies, permissions, and new network access
  • Ask Copilot to iterate when the fix is incomplete or overbroad

Validation is best effort. An unresolved or unverifiable result must remain visible to the reviewer.

A successful rerun tells us that the same analysis no longer detects the original path. It doesn't prove complete application correctness, and dismissing an alert is not the same evidence as fixing it. For an unsupported validation case, we need to run the original tool separately and keep any unconfirmed result visible. Our review still needs to consider alternate paths, regressions, and changes to intended behavior.
5. Gate

Return Control to the Team

The final phase combines machine feedback with accountable human approval. Automation establishes a consistent floor. It does not become the approver of its own work.
Lab Checkpoint

Build a Layered Review Gate

LayerQuestionEnforcement
Tests and lintDoes the change behave as intended?Required checks
Code scanningDid it introduce a known security path?Severity threshold
Code Quality, if enabledDid quality or coverage regress?Configured quality/coverage rules
Copilot reviewWhat contextual concerns remain?Review comments
Human reviewShould this change enter the product?Independent required approval
Required tests and lint are our baseline. Code-scanning rules can then enforce severity thresholds. GitHub Code Quality needs its own licensing and enablement; coverage checks need an uploaded Cobertura XML report, not just a test run. Its PR findings are rules-based, while Copilot review adds contextual comments rather than an approval. The person who requested the agent-created PR cannot approve it, so we need another reviewer. Additional approval can apply to unattributed agent PRs. We check the repository's actual rules instead of bypassing them to finish.

Know When to Return Local

graph LR
  A[Cloud PR] --> B{Evidence complete?}
  B -->|Yes| C[Human approval]
  B -->|Small gap| D[Cloud iteration]
  B -->|Needs local state| E[Checkout branch]
  E --> F[Local debug and test]
  F --> G[Push to same PR]
  G --> B
Returning local isn't a failure. We may need interactive inspection, unavailable hardware, or a private test environment to resolve the remaining gap. Keeping the same PR where possible preserves its review and security history. After pushing a correction, we wait for fresh checks and any required reapproval rather than treating earlier evidence as current.

Operate the Loop Deliberately

  • One cloud session changes one repository and one branch
  • A task can open at most one new PR; it may update an existing PR or open none
  • Sessions have a maximum execution time of 59 minutes
  • Check product-specific AI credit budgets and runner-dependent Actions costs
  • Repository rules must permit agent branch operations without bypassing final approval
  • Measure merged outcomes, review cycles, time to merge, and remediation quality
A bounded task still needs operating discipline. Model choice, retries, setup, and validation all affect cost. GitHub-hosted runner time can be billed, while self-hosted runners don't consume Actions minutes; code review can also fall back without its agentic capabilities. Agentic autofix uses Code Security AI credits, and Code Quality has its own licensing and usage model. We measure merged outcomes and remediation quality rather than counting sessions as success.
Challenge Complete

Delegate Execution, Keep Accountability

Prepare, hand off, inspect, secure, and decide.

We've connected preparation, delegation, security feedback, and human control. New PR findings stay in the PR correction loop; eligible default-branch findings can enter agentic autofix. Neither a generated fix nor a clean scan removes our responsibility to test and review the change. The most useful work often happens before delegation: making intent durable and success observable.
