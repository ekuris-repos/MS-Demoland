Mission Briefing

Plan an inventory-report feature across a React frontend and Express backend. Implementation requires an accessible, approved project; the original sample repository is currently unverified. Discover actual files and commands before making changes.

Deliverables

  • A new GET /api/reports/inventory endpoint that returns current stock levels grouped by category
  • A React inventory-report page using the project's actual component, routing, and data-fetching conventions
  • API and component tests using the installed test runner; use Vitest only if the project uses it

Constraint

Agent-led discovery and implementation. Ask and Plan are allowed. Human source, diff, command, and official-documentation review are always allowed.

Success Criteria

  • The endpoint matches an agreed category/quantity contract and handles empty data
  • The page renders API data, loading, empty, and error states through a working navigation entry
  • Relevant tests, linting, and an integrated browser check pass using verified project commands
Our target route is a proposed feature requirement, not a claim that the unavailable sample already contains it. Before coding, we agree what a category means, which quantity is aggregated, and how empty results are represented. For example, a small test fixture can put two products in one category and check the agreed total. We confirm those fields against the real schema rather than inventing them. Agent-led means the agent does the exploration and coding; it does not mean you stop reading diffs or checking documentation. If project access is unavailable, the implementation and runtime success criteria remain blocked.

Part 2

Agent Mode Deep Dive

Now that we've oriented ourselves in the codebase, let's look at what tools agent mode has available and how approval gates keep you in control. The next two slides cover the built-in tool set and the permission controls you'll use throughout the mission.

Tools Available to Agent Mode

Built-in Tools

  • File operations - Create, edit, read, and delete files
  • Terminal - Run shell commands under the session's permissions and sandbox controls
  • Codebase search - Semantic and text-based search across your workspace
  • Diagnostics - Read compiler errors and lint warnings
  • Fetch - Retrieve content from URLs
  • Browser tools - Use the integrated browser to check a running app; no MCP server required

Extensible via MCP

  • MCP servers - Connect external tools and data sources
  • GitHub, Playwright, databases, custom APIs
  • Browse the Preview gallery with @mcp in Extensions, or use MCP: Add Server
  • Copilot portable workspace configuration: .mcp.json; Local compatibility configuration: .vscode/mcp.json
  • Review trust, authentication, and a first tool call; never commit secrets
Available tools depend on the session's harness and configuration. Start with built-in search, file reading, diagnostics, and browser tools rather than adding servers we do not need. MCP connects an agent to external tools, such as GitHub issues or a remote data source; servers can run locally or remotely. For shared Copilot configuration, the portable workspace file is .mcp.json with a top-level mcpServers object. Local's .vscode/mcp.json uses servers instead. They are not interchangeable formats. Sharing a file does not grant credentials or establish trust. We review the publisher, requested access, and an actual successful tool call before relying on a server. The dedicated MCP courses cover setup in more depth.

Approval Gates and Control

  • Copilot permissions: Manual permissions, Assisted permissions, or Allow all, subject to policy and isolation
  • Common read-only commands can run automatically; risky commands normally require approval
  • Edits are saved to disk. Inspect diffs before integrating; review controls differ by harness.
  • Checkpoints restore affected files and chat history, not external services or completed command effects
  • Copilot Autopilot is a separate mode; in Local it is a permission level. It auto-approves tools.
// Optional settings.json example: false requires approval, not a ban.
// Prefer reviewing commands and granting narrowly scoped session approvals.
{
  "chat.tools.terminal.autoApprove": {
    "npm install": false,
    "rm": false,
    "del": false
  }
}
Manual permissions is our starting point, not Allow all or Autopilot. Assisted permissions uses a model to evaluate calls and can make mistakes; availability depends on policy and the session's isolation. Under normal terminal rules, common read-only commands may proceed while risky ones ask for confirmation. A false rule means ask, not block, and these rules are not a security boundary. Do not copy a catch-all rule approving every npm install or npm run command. Scripts can execute arbitrary code. An enabled sandbox is a separate control and does not cover every tool. Review saved changes through diffs, and remember that a checkpoint cannot reverse a deployment, a database write, or another external action. If the agent drifts, stop or redirect it and inspect what has already happened.
Part 3

The Agent Picker

Now let's talk about how agent mode fits into the broader picture. VS Code's Copilot Chat has three built-in agents, and knowing when to use each one is a key skill. Your mission focuses on the Agent agent, but knowing when to switch to Ask or Plan will save you time during the build.

Three Agents, Three Jobs

Agent roleWhen to use it
AskRead-only research and explanation, without implementing changes
PlanResearch a plan; review scope and checks before implementation
AgentImplement and validate using enabled tools and permissions

Choose separately: harness (Copilot or Local), agent role, reasoning model, and permissions.

Copilot is the current default harness. Local-only customizations do not automatically work there.

Agent, Plan, and Ask describe jobs, not permission levels or models. Our main workflow targets the Copilot harness, the default for new sessions in the current release reviewed on October 27, 2026. Ask uses read-only tools to research without implementing changes. Plan, available through /plan in Copilot, gives us an approach to review before implementation. Agent makes changes and validates them under the selected permissions. Choosing a stronger model does not switch the harness or grant more access. Local is a different harness with different customization support, not a synonym for running on your machine. The optional prompt-file example later requires Local; it cannot be run as a prompt file in the Copilot harness.
Part 4

Preparing the Mission

Before building, we establish the project conventions the agent needs. Preparation can reduce repeated corrections, but it does not guarantee a particular speedup. We start with existing guidance and an observed problem, such as the wrong test command, rather than generating a large set of generic rules. The useful question is which project-specific decision the agent cannot reliably infer.

Instructions Shape Every Response

  • Repo-wide instructions - .github/copilot-instructions.md
  • Scoped instructions - .github/instructions/*.instructions.md with applyTo globs
  • Prompt files (Local only) - .github/prompts/*.prompt.md for reusable tasks
  • Custom agents - .github/agents/*.agent.md for specialized personas
  • Agent skills - packaged multi-step workflows with scripts and resources (see Enterprise Grade Marmalade)

If you've taken "Prompts, Instructions, Skills, and Agents," this should look familiar. Today we put these to work in a real codebase.

Project instructions provide guidance to supported chat and agent requests; they do not apply to inline suggestions or guarantee that generated code follows every rule. Scoped instructions can attach through applyTo file patterns. Custom agents package a role and tool restrictions. Prompt files are reusable tasks for Local sessions, while skills are the reuse path for the Copilot harness. We only add a customization when it solves a real project problem. Until the original sample is accessible, we cannot claim to have generated or verified its conventions.

Instructions for OctoCAT Supply

Generate guidance from accessible source, not assumptions about the unavailable sample.

Analyze this repository and create or update
.github/copilot-instructions.md. Preserve useful existing guidance.
Confirm the architecture, installed dependencies, source locations,
database driver, and build/test/lint commands from actual files.

Record only verified project conventions. Mark unknowns explicitly.
Require API and component tests using the existing test setup.
Use parameterized SQL for values and validate dynamic identifiers.

Summarize the supporting files so I can review the guidance.
This request works without assuming a particular instruction-generation shortcut. In the Copilot harness, we ask in natural language and review the generated file. Local also has /init, but that shortcut is not available in other harnesses. We do not declare specific versions, testing libraries, styling tools, or database drivers as facts until the manifests and source confirm them. If better-sqlite3 is present, its synchronous API is not something to rewrite into an invented asynchronous database interface. Parameterized values are an important SQL practice, but natural-language instructions do not enforce it. We still inspect query construction, validate identifiers, and test the behavior. A short set of verified conventions is more useful than a confident description of an inaccessible project.
Part 5

Building the Feature

Time for the core of the mission. We're going to use agent mode to build a complete feature: a new API endpoint and the React component that consumes it. This is where agent mode really shines: multi-step tasks that span multiple files. Everything we have covered so far prepares you for this moment: delivering the feature that completes your mission.

Writing a Good Agent Prompt

  • State the goal clearly in the first sentence
  • Specify constraints: frameworks, patterns, file locations
  • Define done: what does success look like?
  • Reference existing code: use route and database files found during reconnaissance
// ❌ Vague
"Add a reports feature"

// ✅ Clear
"Inspect the existing routes, schema, and database connection.
Propose GET /api/reports/inventory with a category/quantity contract
based on the actual schema. Agree aggregation and empty-result
behavior before editing. Follow a verified route example.
Add API tests with the installed runner; preserve existing assertions.
Run the relevant checks and report commands, results, and blockers."
A clear prompt reduces guessing, but it does not guarantee correct output. We give the agent a goal, constraints, a definition of done, and a real example to inspect. Here the route is a proposed feature, while the implementation files must come from reconnaissance. We agree the response shape before building the frontend, and a small fixture checks that the aggregation matches the business meaning of stock. Existing tests are evidence to preserve, not obstacles to delete to get a green result. After the run, we compare the code and reported commands with the agreed criteria. If the schema or test setup cannot be verified, that is a blocker to report rather than fill in.

Building the Frontend

  • Step 1 - Ask agent mode to create a React component that calls the new API endpoint
  • Step 2 - Reference a verified component and the agreed API contract
  • Step 3 - Let it add the route and navigation entry
  • Tip - Attach a screenshot of an existing page as context to set visual expectations for the new component
"Find the project's page, data-fetching, routing, and navigation patterns.
Propose locations for an InventoryReport page and component tests.
Use the agreed GET /api/reports/inventory contract.
Render a table plus loading, empty, and failed-request states.
Wire a /reports/inventory route and navigation entry using existing
conventions. Add component tests and run the verified checks.
Do not invent ProductList.tsx, router.tsx, or Sidebar.tsx paths."
Now the frontend consumes the same contract the backend agreed to provide. We discover an existing page and use its real styling and data-fetching patterns. The original sample's component and router paths are unverified, so they are not instructions to create a parallel application structure. Loading, empty, and failed-request states are part of the feature, not optional polish. Component tests check those states, while the browser check later verifies that routing, navigation, and the actual endpoint work together. An attractive table backed by mock data does not satisfy the mission.

Parallelizing Agent Work

  • Parallel work is optional: first agree the API contract and file ownership
  • Use Open in Agents for supported Agent Host sessions; Local sessions remain editor-only
  • Split independent backend and frontend tasks; do not have both edit shared routing or configuration
  • Illustrative new-branch command: git worktree add -b inventory-ui ../inventory-ui
  • Requires a Git repository, an unused branch/path, and reviewed baseline changes
  • Worktrees isolate working files, not ports, databases, external services, or merge conflicts
  • Review each result, integrate deliberately, then rerun the combined checks
Parallel sessions can help when tasks are genuinely independent, but they add coordination and integration work. We keep the single-session build as our default. If we split frontend and backend, both need the agreed response contract and clear ownership of shared files. The Agents window supports Copilot Agent Host sessions, not Local sessions; moving a Local prompt-file workflow there is not a supported handoff. The worktree command shown explicitly creates a new branch, so it requires an unused branch name and directory. Worktrees share repository metadata, and they can still use the same database or port unless we configure isolation. Review and test both changes after integration; separate green test runs do not prove the combined feature works.
Part 6

Quality Assurance

Implementation is only part of the mission. We still need evidence that the feature meets the agreed requirements and preserves existing behavior. Passing tests help, but they are not enough if the tests assert the wrong contract or the browser is still showing mock data. We will inspect both the change and the validation results before calling the feature ready for review.

Testing With Agent Mode

  • Agent mode can write tests, run them, and fix failures in a single loop
  • Point it at existing test files so it matches your team's testing patterns
  • Test aggregation against known fixtures, empty results, and invalid inputs where the contract permits inputs
  • Cover component data, loading, empty, and error states; preserve existing regression assertions
  • Run verified test and lint commands, then check the integrated page with built-in browser tools
"Open the running inventory page. Follow its navigation entry,
compare displayed totals with the API response, and check empty
and failed-request behavior using the project's supported test setup.
Report the exact checks, results, console errors, and anything blocked.
Do not weaken tests or introduce mock production data to pass."
The useful loop is implement, run, inspect, and correct, not change assertions until the output is green. We check that the fixtures and expected totals represent the business requirement. The API and component tests should exercise the agreed contract independently, then an integrated browser check verifies the real route, navigation, and data. Built-in browser tools do not require Playwright MCP. A new agent-opened page has isolated browser state; sharing an existing authenticated tab is a separate access decision. We inspect the exact commands, exit results, and browser observations, including anything skipped. Since the sample is unavailable, none of these runtime checks has been certified for this course.

Iterative Refinement

  • Review the diff after each agent loop completes
  • Provide follow-up prompts for specific corrections: "The error handling should return a 400, not a 500, for invalid input"
  • Use Plan to break down a complex next step before implementing it
  • Use Ask to discuss trade-offs before committing to a direction
Agent mode rarely produces perfect output on the first pass, and that's fine. The real workflow is iterative. The agent builds the initial version, you review the diff, and then you refine. For broad adjustments, stay in Agent: "The error handling should return a 400 for invalid input, not a 500." If you need to rethink the approach before continuing, switch to Plan to create a structured breakdown. For design discussions, switch to Ask: "What are the trade-offs between returning all results versus paginating?" This agent switching is a skill. Over time you'll develop a rhythm: Agent for the initial build, Plan for structural thinking, Ask for design questions. Don't be afraid to switch agents in the middle of a task. Each agent is a different tool in your toolbox.
Part 7

Multi-File Workflows

Real features rarely live in a single file. The report route, response mapping, page, and tests need to agree even when they are implemented in small steps. We will use the shared contract to coordinate those changes, then check the integrated result rather than assuming independent edits fit together.

Cross-Stack Changes

  • Agent mode coordinates changes across backend, frontend, tests, and configuration files
  • A single prompt can touch: API route, database query, React component, router config, test file
  • Agent mode reads the output from each change to inform the next one
// One prompt, multiple files
"Rename the 'stock' field to 'quantity' across the entire codebase.
First identify schema, callers, and compatibility requirements.
Propose a migration and rollback plan before changing persisted data.
After approval, update queries, API mappings, types, components,
and affected tests without removing regression coverage.
Run verified checks and report any callers or data you cannot verify."
A field rename is an illustrative cross-stack change, not a confirmed requirement or schema fact about this sample. Search can help trace queries, response mappings, types, and components, but it does not guarantee every caller was found. Persisted data and external clients add migration and compatibility decisions that a text replacement cannot solve. We review those decisions before allowing changes, preserve regression coverage, and test the integrated result. If we cannot inspect a caller or database, the agent should report that gap rather than claim nothing broke.

When Agent Mode Struggles

  • Ambiguous goals - If you don't know what you want, the agent can't either
  • No reference code - Without examples to follow, output is generic
  • Very large changes - Break big features into smaller, testable increments
  • External dependencies - Authentication, network access, trust, and tool availability can block verification

When in doubt: break the task down, give the agent reference files, and iterate.

Ambiguous goals, missing examples, and large changes make it harder to judge progress. We reduce that uncertainty with a contract, real reference files, and small testable steps. External dependencies introduce another kind of gap: a tool may need authentication, network access, or explicit trust. Do not paste credentials into chat or pretend a mocked test proves the live integration. Mocks can support focused tests, but we label them and separately report the real integration as blocked until it is exercised. The unavailable original repository is exactly this kind of honest boundary.

Mission Debrief: The Solution

A proposed workflow, not an executed solution for the unavailable sample.

PhaseExpected change or evidence
DiscoverAccessible revision, real paths, schema, commands, and existing guidance
PrepareReviewed project instructions and agreed API contract
BackendReport route, registration, query, and API tests
FrontendReport page, component tests, routing, and navigation
ValidateTest/lint results, browser observations, reviewed diff, and explicit blockers

Paths come from reconnaissance. Green tests alone do not prove contract correctness or a working integration.

We compare evidence rather than demand identical filenames. Discovery should identify a real source revision and existing conventions. Preparation should produce concise, reviewed instructions and a contract both sides can use. The implementation needs API tests and component tests, plus the route and navigation wiring. Validation records the commands, results, observed browser behavior, and remaining gaps. Common mistakes are guessing paths, replacing the project stack to match an example, and weakening tests to make a run pass. None of the proposed file changes here is a claim that the original sample was executed successfully. That remains blocked until source access and runtime verification are available.
