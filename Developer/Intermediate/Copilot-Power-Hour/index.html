Part 1 · 5 min

GitHub Copilot Today

Let's start with the landscape. GitHub Copilot is moving fast, and the product people are using today looks very different from what shipped two years ago. This section is five minutes of grounding so we all share the same vocabulary before we go deeper.

Where Copilot Lives Today

IDE

Inline completions across supported editors. Chat, Agent mode, and Next Edit Suggestions vary by IDE; this session uses VS Code.

CLI

A standalone agentic AI in your terminal. Reads files, writes code, runs commands, and connects to GitHub without opening an editor.

github.com

Copilot Chat on github.com, Copilot cloud agent for delegated development tasks, and Copilot code review.

SDK

Build AI-powered applications and workflows outside the editor using the Copilot SDK and agent runtime.

Four surfaces, four different jobs. In VS Code, we can combine completions, Chat, Agent mode, and Next Edit Suggestions. Other editors have different support; Neovim, for example, supports completions but not those chat and agent features. The CLI can read project files, write code, run commands, and work with GitHub from the terminal, subject to permissions. GitHub.com adds Chat, cloud agent tasks that can produce pull requests, and code review. The SDK lets teams embed the agent runtime in their own applications. We will focus on VS Code and CLI, not assume every client behaves identically.

One Product, Many Models

  • Copilot is backed by a catalog of large language models from OpenAI, Anthropic, Google, and more
  • Choose Auto or a supported model in your client's model selector; availability depends on plan and policy
  • Different models have different strengths: speed, reasoning depth, context window, and credit cost
  • Check published per-token rates and measured usage; an agent task is not a fixed-price message
  • Rule of thumb: fast model for simple questions, reasoning model for complex debugging or architecture

Model names and availability change, but the choice we are making is durable. A narrow question often needs a fast, efficient model; architectural decisions may justify deeper reasoning. Auto can route a task to an appropriate available model. Your plan, client, and organization policies determine the choices you see. Actual cost depends on token usage and the model's rates, not a flat price for each message. Choose deliberately at the start of a coherent task, because switching models can lose the benefit of cached context. We will return to that tradeoff in the optimization section.

Part 2 · 15 min

Context Engineering

Context engineering is the skill of deliberately shaping what information Copilot has access to when it responds. Most developers think of Copilot as a chat interface where the quality of the output depends on the quality of the question. That is true, but only a fraction of the picture. The files you have open, the instructions in your repo, the plugins you have connected, the agent you are using: all of these are part of the context that shapes every single response. Mastering context engineering is how you go from "Copilot is pretty good" to "Copilot feels like it actually knows our codebase."

What Is Context Engineering?

  • A model's context window limits how much input and conversation it can work with at once
  • Context engineering is the practice of deliberately filling that window with the right information
  • Context can include selected or retrieved code, chat history, applicable instructions, loaded skills, MCP tool results, and your prompt
  • More relevant context = better output; irrelevant or missing context = vague, generic, or wrong output
  • Attach decisive evidence explicitly. Applicable instructions and agent retrieval can supply additional context.
graph TD
  A["copilot-instructions.md"] --> Z["Context Window"]
  B["Selected or retrieved code"] --> Z
  C["Instruction files (.instructions.md)"] --> Z
  D["Skills (SKILL.md)"] --> Z
  E["MCP tool outputs"] --> Z
  F["Your prompt"] --> Z
  Z --> G["Model response"]
The window is a limit, not a promise that every open file has been attached. Copilot gathers context differently across clients and agent harnesses. We can make the important evidence explicit: attach the function, requirements, or failing test that should drive the answer. Applicable instructions provide standing guidance, while skills load relevant expertise on demand. Discovery metadata can still take space even when a skill's full content is not loaded. The goal is useful signal, not filling the window. Inspect the attached context and tool results rather than assuming an open tab or a file in the repository has been read.

The Five Customization Primitives

Prompts

.prompt.md files capture reusable tasks in VS Code's Local harness. Invoke them from chat and share them in .github/prompts/.

Instructions

Repository guidance in copilot-instructions.md, with targeted .instructions.md files for matching work. Support depends on client and harness.

Skills

SKILL.md folders package instructions, scripts, and resources. Compatible agents load relevant content on demand rather than loading every guide in full.

Hooks

.json configurations run commands at supported lifecycle events. VS Code hooks are Preview; event coverage and formats depend on the harness.

Agents

.agent.md files that define specialized modes combining instructions, skills, and tools. A virtual team member with a specific role and persona.

These are five useful customization concepts, not five universally interchangeable file formats. Check your selected client and agent harness first. Prompt files are a VS Code Local example; skills provide reusable workflows across compatible agents, including CLI. Instructions guide supported chat and agent requests, not inline suggestions. Hooks run commands at supported events without relying on the model to remember, but their schemas vary and the VS Code experience is Preview. Custom agents combine a role with instructions and allowed tools. Plugins can package several customizations together. Start with the smallest mechanism that solves a repeated problem, and remember that instructions or hooks alone are not a security boundary.

MCP: Giving Copilot More to Work With

  • Model Context Protocol (MCP) is an open standard for connecting AI agents to external tools and data sources
  • MCP servers expose tools, resources, and prompts that Copilot can call during a conversation
  • Copilot CLI includes the GitHub MCP server for authorized GitHub interactions
  • Use MCP: Add Server in VS Code or /mcp add in CLI; configuration and authentication depend on the server and client
  • Tools can retrieve live data or change external systems. Review the publisher, access, requested action, and returned evidence.
graph LR
  A[User request] --> B[Copilot agent]
  B -->|Call tool| C[MCP server]
  C -->|Query| D[External system]
  D -->|Return data| C
  C -->|Live context| B
  B --> E[Grounded response]
Instead of pasting a pull request into chat, we can let an authorized GitHub tool retrieve its diff and related issue. That is useful grounding, but a tool response is still evidence to inspect, not an instruction to trust blindly. MCP also supports resources and user-invoked prompts; client support determines what is exposed. In VS Code, start with MCP: Add Server and choose the appropriate configuration destination. CLI includes GitHub MCP and offers /mcp add for other servers, with user configuration in ~/.copilot/mcp-config.json. External integrations need their own server, credentials, and permissions. Review access before enabling them, especially tools that write data or run local commands.

This sample describes one team's TypeScript, React, and testing choices; it is not a claim that other tools or patterns are obsolete. Put shared project guidance in .github/copilot-instructions.md, then use targeted files for rules that apply only to matching work. In VS Code, applyTo can match files the agent creates or modifies; check the selected harness's discovery rules rather than assuming a topic alone activates a file. These instructions guide supported chat and agent requests, not inline suggestions, and they do not enforce compliance. Organization instructions have a narrower GitHub.com scope. Start with a few relevant rules, then verify the resulting diff and tests.

Context Engineering: Decision Framework

Situation Reach for Why
You type the same detailed prompt every morning Prompt file Invoke a saved task in VS Code Local; check client support
Copilot keeps generating code that breaks your team's conventions Instruction file Standing or targeted guidance for supported chat and agent requests
Your deployment procedure is a 20-step wiki nobody reads Skill Compatible agents load relevant workflow content on demand
A validation or policy check must run at a specific lifecycle event Hook Runs a command at a supported event; verify the harness and configuration
You want a security reviewer who uses your specific standards Agent A virtual team member with its own persona, tools, and methodology
Copilot needs live data from an external system MCP server Tool calls fetch real-time information into the context window
The framework starts with the problem, not the file extension. Repeating a task in a client that supports prompt files? Save a prompt. Packaging a workflow for compatible agents? Use a skill. Guiding project conventions? Instructions. Running a command at a supported event? A hook, with its configuration tested in that harness. Need a specialist? A custom agent. Need external data or actions? MCP. These mechanisms can work together, but adding more is not automatically better. We want focused guidance and the fewest tools needed for the task, with tests and permissions doing the enforcement that prose alone cannot provide.
Part 3 · 15 min

Token Optimization

Token optimization is the practice of getting the most value out of every credit you spend. The goal is not to use Copilot less. The goal is to be deliberate. A well-scoped prompt on a well-chosen model with clean context produces a better result than a vague prompt on a premium model with a cluttered context window, and it costs less.

What Drives Credit Spend

  • 1 AI credit = $0.01 USD. Model usage is priced by input, output, cached input, and any applicable cache-write tokens.
  • Token usage is converted to credits at the model's published rate. Premium models cost more per token.
  • Agent work is not one fixed-price message: Chat, CLI, and cloud agent tasks can involve multiple model calls
  • What is not billed from credits: Inline completions and Next Edit Suggestions (included in paid plans)
  • Business and Enterprise seats contribute to a shared, pooled credit balance
graph LR
  A["Input tokens (your context)"] --> C["Credit charge"]
  B["Output tokens (Copilot's response)"] --> C
  D["Model tier"] --> C
One credit is one cent, but input, output, and cached tokens do not all have the same price. Published rates depend on the model and sometimes the context tier. An agent may make several model calls while exploring, editing, and testing, so a short user prompt does not guarantee a small final charge. Context engineering helps by reducing irrelevant input and corrective work. Stable context can also be reused from cache at a different rate. Our goal is not to starve the task of evidence; it is to provide the smallest reliable context that lets the work succeed, then inspect actual usage.

Context Hygiene

  • Inspect attached context. An open tab is not proof its contents were sent; remove irrelevant attachments and attach decisive evidence.
  • Select before you ask. Attach the relevant function or block when a whole file is unnecessary.
  • Start a new chat for unrelated tasks. Chat history accumulates. An old debugging conversation pollutes context for a documentation request.
  • Keep instruction files focused. Targeted applyTo patterns match relevant files in supported clients.
  • Avoid pasting large blobs. In VS Code use file #-mentions, Add Context, or #codebase for a relevant workspace search.
Think of context as a shared whiteboard. Old assumptions and irrelevant attachments make the current problem harder to see. Opening a file does not guarantee its full contents are included, and closing a tab does not prove a specific credit saving. Attach the evidence you need and inspect what the client actually includes. In VS Code, use the context picker or file mentions; #codebase requests a search, not an upload of the entire repository. Start a new chat for unrelated work. If we are continuing the same task, compaction can retain important decisions while reducing old conversation history.

Context Starvation and Context Poisoning

Too little reliable context forces assumptions. Repeated assumptions can become false premises that shape later work.

Context starvation

The agent lacks requirements, constraints, current code, or decisive evidence. It must guess or spend time rediscovering the task.

Context poisoning

A plausible mistake enters the active context, gets repeated in plans and output, and starts to look like an established fact.

Recovery: Supply the missing evidence. If a false premise has taken hold, start a clean session with only the corrected objective, verified facts, and relevant evidence.

These failure modes need different responses. When context is starved, add the smallest authoritative evidence that resolves the uncertainty: the acceptance criteria, applicable instruction, current code, or decisive test result. Context poisoning is more stubborn. It does not mean the conversation retrained the model. It means an early mistake was repeated until later work began treating it as true. Continuing to debate that mistake in the same session can reinforce it with even more references. When an approach is abandoned or AI-generated reasoning itself is faulty, start a clean session and carry forward only verified facts, the corrected objective, and relevant evidence.

Prompt Discipline

Be specific about scope

Tell Copilot exactly what it should and should not touch. "Refactor the error handler in api/routes.ts, do not change the interface" beats "clean up my code."

State your constraints upfront

Tell Copilot what framework, version, or pattern you are using before it makes assumptions. Assumptions generate output tokens that you have to correct.

Request the format you need

Ask for the artifact and explanation you actually need. Output tokens are billed too, often at a higher rate than input; check the model's rates.

One task per prompt

Multi-goal prompts lead to long, diffuse responses. Split complex work into sequential focused prompts. Each one is easier to verify and cheaper to correct if wrong.

Prompt discipline is about reducing avoidable retries, not chasing an unsupported savings percentage. Scope tells the agent what it may change. Constraints prevent an implementation built on the wrong framework or version. Format helps us get a reviewable artifact without pages of unnecessary narration. A focused task also gives us a clear stopping condition. Input and output have different prices, and a concise answer is not useful if it omits evidence we need to review the change. Compare quality, retries, and measured usage on representative tasks instead of promising a fixed percentage improvement.

Model Selection as a Cost Lever

Task type Model tier Rationale
Quick syntax question, code lookup Fast and efficient Optimize for latency and credit efficiency when the task is narrow
Refactoring, feature implementation Balanced coding Strong coding and reasoning for most daily development work
Agentic coding, architecture review, complex debugging Deeper coding and reasoning Use deeper reasoning when multi-step decisions justify additional credits
Large repository or long-document analysis Supported model with extended context Check supported context limits and any long-context pricing before use

Auto can match capability to the task. Availability varies by client, plan, and policy. Check current per-token rates and preserve cached context within a coherent task.

Match capability to the task rather than memorizing model names that may retire. Auto is a useful starting point where supported; manual selection is still useful when we have a specific requirement. Narrow edits usually need less reasoning than architectural decisions or complex debugging. Extended context and higher reasoning levels are model-specific options, not universal defaults. Configure them deliberately before the task. Switching models or changing reasoning and tool configuration mid-session can invalidate cached context, so repeated switching may cost more than it saves. Use the supported-model list, published rates, and actual task results to guide the choice.

Token Anti-Patterns to Avoid

  • Conversational sprawl: Using a single chat thread all day accumulates history that is irrelevant to your current task. Start fresh threads for new tasks.
  • Overkill model selection: Running every request through a premium reasoning model. Match the model to the complexity of the task.
  • Over-loaded instruction files: Long project-wide guidance burdens supported chat and agent requests. Keep the baseline lean and package detailed workflows as skills.
  • Undirected agent mode: Asking an agent to "improve my code" without a defined scope. Agents loop, generating significant token spend without a clear stopping condition.
  • Redundant context: Pasting the same code repeatedly. Attach the relevant file or selection once and let the agent retrieve additional evidence as needed.
A long conversation is not automatically bad, but carrying unrelated work forward can make it harder to find the important facts. In VS Code, use New Chat or Chat: New Chat. In CLI, /new starts a fresh conversation; Ctrl+L only clears the screen. If we need to keep working on the same task, /compact summarizes older conversation instead. Neither action removes saved files or applicable instructions. Keep repository instructions focused on shared fundamentals and skills focused on detailed workflows. Instructions do not affect inline suggestions, and skill discovery metadata is not literally free context even when full instructions load only on demand.

Quick Optimization Checklist

  • Before asking: attach decisive evidence, remove irrelevant context, start a new chat for an unrelated task
  • When writing a prompt: scope it to a specific file and task, state your constraints, specify the output format
  • When choosing a model: try Auto or a suitable capability tier; avoid unnecessary mid-task switching that loses cache reuse
  • For team scale: keep copilot-instructions.md lean; move deep expertise into Skills; use scoped applyTo patterns
  • For agent tasks: define done, review plans and permissions, inspect /usage and /context in CLI
These habits give us something we can test rather than a guaranteed savings claim. Start with a clear task and decisive evidence, choose enough capability, and inspect what the session actually consumed. In CLI, /usage reports credits and token breakdowns, while /context shows context usage. Use /compact when continuing a long task, not as a substitute for preserving the right evidence. Check organization budgets too: a stopping condition is not a financial cap. CLI also offers Preview session soft limits, which can overshoot while a response finishes; they do not replace monthly budgets. The goal is lower rework with results we can still verify.

Q&A

Key Takeaways

  • Copilot is not just an IDE plugin anymore. The CLI, SDK, and github.com surfaces each unlock different workflows; know which one fits your task.
  • Context engineering is the core skill. Instruction files, skills, agents, and MCP servers let you automate the context that previously lived in your head.
  • Precision beats volume. Focused evidence, suitable capability, and clear stopping conditions can reduce retries; measure quality and usage.
  • Parallelize deliberately. Isolate independent write tasks, review and integrate results, and account for aggregate costs.
  • Start small, iterate fast. Create one instruction file this week. Add one prompt file. Try the CLI on one task. Build the habit before adding complexity.
Copilot has several surfaces, but we do not need to adopt all of them at once. Choose one useful task, provide authoritative context, and use the smallest customization that helps. Match capability to the work and inspect actual usage rather than assuming a short prompt is cheap. Parallel work can reduce waiting, but it still consumes credits and needs isolation, integration, and review. Start with one shared instruction file and one reusable workflow supported by your client, then try a bounded CLI session. Judge the result by the diff, tests, and cost, not by how confidently the agent describes it.
