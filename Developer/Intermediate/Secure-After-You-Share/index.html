Secure After You Share

Turn every pull request into a cloud-enforced security checkpoint.

Welcome to Secure After You Share. Our companion course began in the local diff, where developer context is strongest. This course begins when that change reaches GitHub. We will build a cloud security system around the pull request using Actions, CodeQL, secret scanning, dependency controls, Copilot code review, and rulesets. The goal is not to collect more alerts. The goal is to produce trustworthy evidence before merge.
Challenge

Can This Pull Request Safely Merge?

A pull request passes its unit tests, but it changes a workflow, adds a dependency, exposes a credential, and crosses an application trust boundary.

Starting State

Green tests, incomplete security signals, broad workflow permissions, and pressure to merge.

Done State

Independent checks, explained findings, least privilege, protected artifacts, and accountable approval.

Here is our challenge. The tests are green, which tells us the expected behavior still works. It does not tell us whether the workflow can be abused, the new package is trustworthy, the credential is exposed, or the data flow is safe. Our scenario follows a pull request through each cloud security signal and asks whether the platform should permit the merge. A green check is evidence, not a verdict.

What You Will Be Able to Do

  • Threat-model a GitHub Actions workflow and reduce its permissions
  • Use CodeQL, secret scanning, and dependency review as distinct controls
  • Evaluate Copilot code review comments with repository evidence
  • Protect cloud deployments with environments, OIDC, and attestations
  • Combine rulesets and required checks into a defensible merge policy
  • Use security campaigns to coordinate alert remediation at scale
  • Explain why a human still owns the final risk decision
By the end, you will be able to explain what each cloud control contributes and where it stops. Actions gives us repeatable execution, but the workflow itself has a threat model. CodeQL reasons about code paths. Secret scanning looks for credentials. Dependency review evaluates supply-chain changes. Copilot code review adds contextual comments, and security campaigns coordinate remediation across repositories. We will combine those capabilities without pretending that any one of them understands the whole business risk.

The Cloud Security Loop

graph LR
  A[Pull request] --> B[Actions run]
  B --> C[Security signals]
  C --> D[Review findings]
  D --> E[Remediate]
  E --> B
  D --> F{Policy satisfied?}

This loop starts with a pull request event. Actions runs checks in a consistent cloud environment, and specialized controls produce different security signals. We review those findings, remediate the supported risks, and rerun the checks against the new commit. Rulesets evaluate whether policy is satisfied, but they do not replace approval. The final decision belongs to a human who can connect technical evidence to business impact.
1. Secure the Runner

Automation Is Part of the Attack Surface

Before we trust what a workflow reports, we need to trust how it runs. A workflow can read code, receive tokens, publish artifacts, and deploy to cloud environments. That makes the workflow both a security control and a potential attack path. We will begin by treating YAML with the same care we apply to application code.
Workflow Review

Threat-Model the Workflow

SurfaceQuestionSafer Pattern
TriggerCan untrusted code invoke privileged work?Separate trusted and untrusted events
TokenWhat can GITHUB_TOKEN write?Declare minimum permissions
ActionCan referenced code change unexpectedly?Pin to a full commit SHA
InputCan event data reach a shell?Use environment variables and quoting
RunnerWhat persists between jobs?Prefer isolated hosted runners
Start with the trigger because it defines who can cause the workflow to run and which context is trusted. Then follow privilege through the token, third-party actions, event inputs, and runner. Pay special attention to workflows that combine untrusted pull-request code with write permissions or secrets. The important question is not whether the YAML is valid. It is whether an attacker can influence a privileged step.

Make Least Privilege Visible

name: pr-security
on: pull_request

permissions:
  contents: read
  security-events: write

jobs:
  analyze:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@FULL_COMMIT_SHA
      - uses: github/codeql-action/analyze@FULL_COMMIT_SHA

Set workflow permissions to read-only by default, then grant each job only what it needs.

Explicit permissions make the security boundary reviewable. Begin with read-only access and add a write scope only when a job truly needs it. Job-level permissions can narrow the token further when one workflow contains different responsibilities. Pinning an action to a full commit SHA also prevents a mutable tag from silently changing the code that receives this token.

Deploy Without Long-Lived Cloud Secrets

sequenceDiagram
  participant W as GitHub workflow
  participant G as GitHub OIDC
  participant C as Cloud identity
  participant E as Protected environment
  W->>G: Request signed token
  G->>C: Present repository claims
  C-->>W: Issue short-lived credential
  W->>E: Request deployment
  E-->>W: Apply reviewers and policy
OpenID Connect replaces a stored cloud password with a short-lived credential based on signed claims. The cloud provider can restrict trust to a specific organization, repository, branch, tag, or environment. GitHub environments then add deployment reviewers, branch restrictions, and scoped secrets. This reduces credential lifetime and limits where deployment authority can be exercised.
Hardening Pattern

Harden the Automation Boundary

  • Separate pull-request validation from privileged deployment
  • Declare minimum token permissions at workflow and job scope
  • Pin third-party actions and review their source and ownership
  • Keep untrusted event values out of inline shell scripts
  • Use OIDC and protected environments for cloud access
  • Record the threat, control, and residual risk in the pull request
A strong workflow review proposes the smallest complete hardening change. Do not merely remove a permission until the file passes review. Trace what the workflow needs to do, preserve that behavior, and explain why the reduced authority is sufficient. If deployment needs elevated access, move it behind a trusted event and a protected environment instead of granting that access to pull-request code.
2. Build Independent Signals

Different Risks Need Different Detectors

A secure workflow gives us a trustworthy place to run checks. Now we need checks with different ways of seeing risk. One detector cannot reliably cover source code, credentials, dependencies, and generated artifacts. The value comes from independent signals whose blind spots do not completely overlap.

Match the Control to the Question

CapabilityPrimary QuestionEvidence
CodeQLDoes code follow a vulnerable path?Semantic alert and data flow
Secret scanningDoes content contain a credential?Secret type, location, validity
Dependency reviewWhat supply-chain risk enters this PR?Added packages and advisories
DependabotWhich dependencies need remediation?Alerts and update pull requests
Copilot code reviewWhat contextual issue deserves review?Comment tied to the diff
These capabilities are complementary because they answer different questions. CodeQL follows semantic program relationships. Secret scanning recognizes credential patterns and can check validity for supported token types. Dependency review focuses on what a pull request introduces, while Dependabot tracks known vulnerable versions over time. Copilot code review reasons about the diff and repository context, but its comments remain suggestions that require verification.
CodeQL Analysis

Trace CodeQL from Source to Sink

graph LR
  A[Untrusted source] --> B[Propagation]
  B --> C{Control present?}
  C -->|No| D[Sensitive sink]
  D --> E[Code scanning alert]
  C -->|Yes| F[Path interrupted]

Verify the analyzed commit, query, severity, precision, path, and missing control before choosing a remediation.

Read a CodeQL alert as a path, not as a highlighted line. Confirm where untrusted data enters, how it propagates, which control is missing, and where the sensitive operation occurs. Then verify that the check analyzed the current pull-request commit. Autofix may propose a change for a supported alert, but the path gives us the evidence needed to judge whether that change addresses the root cause.

Prevent Secrets Before Detection Becomes Response

  • Push protection blocks supported secrets before they reach the repository
  • Secret scanning monitors repository history and other supported surfaces
  • Validity checks help prioritize supported active credentials
  • Custom patterns extend detection to organization-specific formats
  • Bypasses require a reason and create an auditable decision
  • A committed secret must be revoked and rotated, not merely deleted
Prevention is cheaper than incident response, so push protection is our first preference. If a secret reaches GitHub, deleting the line does not remove it from history or invalidate the credential. We must revoke or rotate it, investigate use, and then remove it safely. Bypass can be necessary for tests or false positives, but the reason should be specific enough for another reviewer to understand and audit.

Review the Supply-Chain Delta

  • Inspect direct and transitive packages added by the pull request
  • Set dependency review policy for severity and license risk
  • Use the dependency graph as the inventory behind alerts
  • Let Dependabot propose bounded version updates
  • Run tests and security checks against every automated update
  • Group updates only when shared validation makes failures diagnosable
Dependency review is strongest at the moment a package enters or changes in the pull request. It can show direct and transitive additions, known advisories, and license information before merge. Dependabot then helps maintain that inventory by raising alerts and update pull requests. Automated updates reduce toil, but they still need the same tests, scanning, and human review as any other code change.
Triage Model

Triage the Signals Without Flattening Them

SignalImmediate QuestionPossible Decision
CodeQL pathIs the source-to-sink flow reachable?Fix, dismiss with evidence
Exposed secretWas the credential valid or used?Revoke, rotate, investigate
Vulnerable packageIs it reachable and fixable?Update, mitigate, accept formally
License changeDoes policy permit distribution?Replace or approve exception
A single severity label does not make these findings interchangeable. A leaked credential creates an incident-response question. A CodeQL result asks us to verify reachability and the missing control. A vulnerable package adds exploitability, exposure, and update availability to the decision. A useful triage record preserves the evidence and owner for each signal instead of collapsing everything into pass or fail.
3. Add Agentic Review

Use AI to Expand Attention, Not Authority

Deterministic checks give us repeatable evidence for known classes of risk. We can now add Copilot code review to look across the diff and repository context for issues that may not map to a scanner query. That broader reasoning is useful, but it also means comments can be incomplete or incorrect. We expand reviewer attention without transferring approval authority.

Give Copilot Review the Right Context

  • Keep the pull request bounded and explain its intended behavior
  • Store repository security expectations in custom instructions
  • Request Copilot review manually or through configured rules
  • Apply suggested changes only after inspecting the complete diff
  • Resolve comments with evidence, tests, or a documented rejection
  • Request a fresh review after material changes
Copilot code review works best when the pull request has a clear purpose and the repository contains explicit conventions. Custom instructions can describe security boundaries, test expectations, and framework patterns that should influence review. Treat every comment as a hypothesis tied to the diff. Confirm it in code, add validation where needed, and explain rejections so the conversation remains useful to human reviewers.
Review Method

Test the Review Comment

graph LR
  A[Copilot comment] --> B[Locate evidence]
  B --> C{Claim supported?}
  C -->|No| D[Reject with reason]
  C -->|Yes| E[Remediate]
  E --> F[Add validation]
  F --> G[Request rereview]
Choose one Copilot review comment and try to falsify it. Follow the relevant call path, inspect existing controls, and determine whether the behavior is reachable. If the claim holds, remediate the root cause and add a test or check that proves the change. If it does not, reject it with the evidence that breaks the claimed path. Either outcome should leave the pull request clearer than before.

Know Which Agent Is Acting

CapabilityPrimary OutputBoundary
Copilot code reviewPull-request commentsDoes not approve or merge
Copilot AutofixSuggested alert remediationPatch still needs validation
Agentic AutofixIterated draft pull requestAvailability and alert support vary
Copilot coding agentChanges in a pull requestRuns within configured repository policy
These capabilities may all produce code or comments, but they begin from different inputs and have different responsibilities. Copilot code review comments on a diff. Autofix starts from a supported security alert. Agentic Autofix can iterate on assigned alerts where available. The coding agent begins from an assigned development task. None should approve its own output, and every generated change remains subject to repository policy and human review.

Carry Trust into the Artifact

graph LR
  A[Protected source] --> B[Trusted workflow]
  B --> C[Test and scan]
  C --> D[Build artifact]
  D --> E[Artifact attestation]
  E --> F[Verify before deploy]

Attestations record where and how an artifact was built. Verification connects deployment back to the trusted workflow.

Merge protection secures source changes, but production consumes an artifact. Artifact attestations create signed provenance that links the artifact to its repository, workflow, and build event. Verification at deployment helps prevent an untrusted build from bypassing the reviewed path. This does not prove the code is vulnerability-free. It proves that the artifact came from the build process we intended to trust.
Policy Design

Turn Signals into Merge Policy

  • Require pull requests and prevent direct changes to protected refs
  • Require current Actions and code-scanning results
  • Block selected dependency risk before merge
  • Require code-owner or designated human approval
  • Dismiss stale approvals after material changes
  • Restrict bypass authority and audit every exception
Rulesets convert team expectations into enforceable repository behavior. Require the checks that represent real risk decisions, and make sure they apply to the current commit. Keep bypass authority narrow because an exception path can quietly become the normal path. Policy should create a dependable security floor while leaving the human reviewer responsible for risks that cannot be encoded as a status check.

Every Signal Needs an Owner

RoleOwnsProduces
DeveloperChange intent and remediationCode, tests, explanations
Platform teamSecure workflow foundationsReusable workflows and runners
Security teamDetection and response policyRules, patterns, triage guidance
ReviewerMerge risk decisionComments and approval
OrganizationExceptions and improvementAudit history and trends
Automation without ownership creates alert queues, not security. Developers own the change and remediation evidence. Platform teams provide secure workflow foundations. Security teams tune detections and define response expectations. Reviewers own the merge decision. The organization watches exceptions and trends to improve the system. Clear ownership keeps a failing check from becoming someone else's problem.
4. Remediate at Scale

Turn Alert Backlogs into Security Campaigns

We have built controls for one pull request and assigned ownership for each signal. Organizations still face a larger problem: hundreds of related alerts spread across many repositories. GitHub security campaigns turn a selected alert cohort into time-bound, visible work. The campaign does not weaken our evidence standards. It gives security teams and developers a shared operating model for applying them repeatedly.

A Campaign Creates Focus and Ownership

Alert Backlog

Many severities, repositories, owners, causes, and remediation paths compete for attention.

Security Campaign

A related alert cohort receives a purpose, due date, managers, contact path, and visible progress.

Use campaigns for coherent work: one vulnerability class, one training goal, one provider, or one business priority.

A campaign is more than a saved filter. It tells developers why this set of alerts matters, when the work is due, and who can answer questions. Closely related alerts also let teams reuse knowledge. Once a developer understands one log-injection path or one exposed token provider, the next alert becomes easier to resolve correctly. Focus creates learning as well as throughput.
Campaign Scope

Choose a Cohort Developers Can Finish

DimensionCode CampaignSecret Campaign
Starting pointCode scanning filters or templateSecret scanning filters or template
Useful focusRule, severity, CWE, languageProvider, secret type, bypass

Keep each campaign at 1,000 alerts or fewer. Secret scanning campaigns are currently in public preview.

Campaign scope determines whether the work feels achievable or arbitrary. Code campaigns can focus on a rule, severity, CWE, language, or repository property. Secret campaigns can focus on a provider, secret type, or push-protection bypass. GitHub limits a campaign to one thousand alerts, but a much smaller, coherent cohort is often more useful. The secret campaign capability is currently preview functionality, so confirm availability and behavior before making it part of a required process.

Publish an Operating Contract

  • Name the risk and explain why this cohort matters now
  • Set a due date that reflects severity and team capacity
  • Assign campaign managers who can answer remediation questions
  • Provide a contact link for support and escalation
  • For code campaigns, optionally create tracking issues by repository
  • Publish only after owners agree on scope and response expectations
Publishing creates an operating contract between security and engineering. The name and description should explain the risk, not merely repeat a query name. Managers need authority and technical context to unblock developers. The due date should reflect both urgency and realistic capacity. For code campaigns, repository tracking issues can connect the organization-wide goal to each team's normal planning workflow.

Route Alerts to the Right Remediation Path

graph LR
  A[Filter alerts] --> B[Publish campaign]
  B --> C{Remediation path}
  C -->|Developer| D[Assign alert]
  C -->|Supported code alert| E[Copilot Autofix]
  E --> F[Copilot cloud agent]
  D --> G[Fix and validate]
  F --> G
  G --> H[Campaign progress]

Generated fixes remain pull requests. Repository checks and human review still decide whether they are safe.

Campaigns coordinate work without forcing every alert through the same remediation path. A developer can own an alert directly. Code campaigns automatically request Copilot Autofix suggestions as capacity allows. When an Autofix is available, supported alerts can also be assigned to Copilot cloud agent to create a pull request. That pull request still travels through tests, scanning, repository policy, and human review. Scale changes the routing, not the standard of proof.
Outcome Review

Measure Risk Reduction, Not Motion

SignalUseful QuestionWeak Proxy
ResolutionWas the root cause removed?Alert count changed
TimeDid high-risk alert age fall?Campaign closed on time
QualityDid fixes pass policy without reopening?Pull requests created
LearningDid the same weakness recur?Training attendance
OwnershipWere exceptions explicit and reviewed?Alerts assigned
A campaign can generate activity without reducing risk. Measure whether root causes were removed, high-risk alert age fell, fixes remained closed, and exceptions received explicit review. Then feed what you learned back into prevention. A recurring CodeQL class may justify secure coding guidance or a reusable framework control. Repeated secret exposure may justify stronger push protection, custom patterns, or credential architecture changes.
Merge Gate

Make the Merge Decision

  • The workflow uses trusted triggers, pinned actions, and minimum permissions
  • CodeQL findings are fixed or dismissed with reviewable evidence
  • Exposed credentials are revoked, rotated, and investigated
  • Dependency and license changes satisfy policy
  • Copilot review comments are verified, resolved, or rejected explicitly
  • Required checks apply to the current commit
  • An authorized human accepts the documented residual risk
This is the decision point. We have secured the workflow, reviewed each specialized signal, tested Copilot's comments, and confirmed that policy applies to the current commit. Any remaining risk should be explicit and owned. If a credential was exposed, a passing secret scan after deletion is not enough; rotation and investigation still matter. When every item has evidence, an authorized human can make a defensible merge decision.

Independent signals, enforceable policy, and human accountability protect every merge.

The local course taught us to arrive at the pull request with a security story. This course taught us to make the cloud challenge that story. Secure the workflow first, run independent controls, verify agentic suggestions, protect the resulting artifact, and encode the minimum acceptable evidence in rulesets. Security campaigns can then coordinate remediation across repositories without lowering the standard of proof. The platform makes protection consistent, but people still define policy, investigate exceptions, and own the final decision.
