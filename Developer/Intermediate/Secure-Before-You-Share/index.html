Secure Before You Share

Review locally. Remediate deliberately. Let the platform verify.

Welcome to Secure Before You Share. Today we are starting where developers actually work: in the local diff, before a pull request exists and before a scanner has a chance to tell us what went wrong. We will use GitHub Copilot to inspect a change, fix what the evidence supports, and then let CodeQL and Copilot Autofix challenge our work on the platform. The goal is not to hand security to a tool. The goal is to build a workflow where developers catch risk early and GitHub makes that protection consistent.
Challenge

Stop the Vulnerability Before the PR

A feature works, but its diff crosses a trust boundary. Your mission is to review it locally, remediate supported findings, and open a pull request that can survive CodeQL and human review.

Starting State

Passing feature tests, unreviewed data flow, and a developer ready to commit.

Done State

Documented local review, verified remediation, clean platform checks, and accountable approval.

Here is the situation: the feature works, the tests pass, and you are one command away from committing it. That is exactly when security issues are easiest to overlook, because everything feels finished. In our challenge, the diff crosses a trust boundary, so we are going to slow down before the pull request and use the context we still have in our heads. You will work in a disposable repository with an intentionally vulnerable branch, which gives us room to investigate and make mistakes safely.

What You Will Be Able to Do

  • Review a local diff with a security-focused Copilot prompt
  • Separate evidence-backed findings from speculation
  • Remediate vulnerabilities without changing intended behavior
  • Use CodeQL results to trace source, flow, and sink
  • Evaluate Copilot Autofix as a proposed patch, not an automatic verdict
  • Explain how rulesets and required checks protect teams at scale
By the end of this session, you will have practiced the whole path from a local diff to a protected pull request. We will use Copilot for contextual review, but we will not accept findings without evidence. We will use CodeQL for repeatable data-flow analysis, and we will treat Autofix as a proposed patch that still needs review. Finally, we will connect those developer actions to rulesets and required checks, because a good habit becomes much more valuable when the platform can reinforce it across every repository.

The Secure Change Loop

graph LR
  A[Inspect diff] --> B[Review locally]
  B --> C[Remediate]
  C --> D[Validate behavior]
  D --> E[Open PR]
  E --> F[CodeQL analyzes]
  F --> G[Autofix proposes]
  G --> H[Human decides]
This is our path for the session. We begin with the diff, review it locally, remediate what we can prove, and validate that the feature still behaves correctly. Only then do we open the pull request. Once the change reaches GitHub, CodeQL gives us an independent analysis, Autofix may offer a remediation, and a human makes the final decision. Notice that this is a loop, not a conveyor belt. New evidence can send us back to the code at any point.
1. Inspect

Start with the Change You Actually Made

Let's begin with the change in front of us. A bounded diff gives us something concrete to reason about, and it keeps the review tied to the work we are about to share. Before we ask Copilot anything, we need three things: a clean baseline, a clear statement of intended behavior, and an honest look at every file that changed.
Lab Checkpoint

Establish a Trustworthy Baseline

  • Confirm the branch and inspect git status --short
  • Run the repository's tests, lint, and build commands
  • Read the full diff, including generated and dependency files
  • State the intended behavior in one sentence
  • Identify inputs, outputs, credentials, and external systems touched
Our first job is to establish what was true before we touch the code again. If the tests were already failing, we need to know that now, because neither Copilot nor CodeQL can read our memory and separate an inherited problem from a new regression. Also, do not limit the diff to files you remember editing. Package managers, generators, and assistants can change files quietly, and those changes are still part of what you are asking the team to review.

Threat-Model the Diff, Not the Entire World

QuestionLook ForEvidence
What enters?User input, files, headers, eventsCall sites and schemas
Where does it travel?Transforms, storage, subprocessesData-flow path
What trusts it?Queries, templates, shells, APIsValidation boundary
What can escape?Secrets, logs, errors, responsesOutput and telemetry
Who can invoke it?Users, roles, services, workflowsAuthorization checks
We are not threat-modeling the entire application in the next five minutes. We are threat-modeling this change. Ask what enters, where it travels, what eventually trusts it, and what could leave the system as a result. That gives us a simple but useful path from an untrusted source toward a sensitive operation. It also gives Copilot something much sharper to inspect than a vague request to find security bugs.

Ask for Findings You Can Verify

Review my uncommitted diff as a security reviewer.

Focus on changed code and its immediate call paths. Trace untrusted
inputs to sensitive sinks. Check authorization, injection, secret
exposure, unsafe deserialization, path handling, and dependency risk.

For each finding, provide:
1. severity and affected file
2. source-to-sink evidence
3. a safe remediation
4. a regression test that would fail before the fix

Do not edit files. Mark uncertain claims as hypotheses.
This prompt does a few important things. It keeps the review close to the changed code, asks Copilot to trace a real path, and requires evidence for every finding. It also tells Copilot not to edit yet. We want to understand and classify the risk before we start changing files. Adjust the categories for your stack, and let repository instructions provide the framework conventions, build commands, and security rules that should apply every time.
Lab Checkpoint

Run the Local Security Review

Copilot Provides

Candidate findings, code-path context, remediation options, and test ideas.

You Provide

Intent, risk tolerance, runtime evidence, validation, and the decision to change code.

Capture the review: record confirmed findings, rejected hypotheses, and validation plans in docs/security-review.md.

Now it is your turn to run the review. Copilot is going to give you candidate findings, not verdicts. Your job is to trace each claim back to the code and decide whether the evidence holds up. We are writing that reasoning into a review record because a chat response should never become an invisible authority. If Copilot makes a weak claim, say why it is weak and record what evidence is missing.

Triage Before You Edit

ClassificationMeaningNext Action
ConfirmedCode path and impact are supportedRemediate and test
Needs evidencePlausible, but runtime or call path is unclearInvestigate before editing
False positiveControl or invariant breaks the claimed pathDocument the control
Out of scopeReal issue outside the current changeCreate tracked follow-up
A strong review is not the one with the most accepted comments. It is the one where every decision has a reason. Some findings will be confirmed, some will need another test or call-path check, and some will be false positives because an existing control breaks the path. If you reject a finding, point to that control. Silent dismissal teaches the team nothing and leaves the next reviewer to repeat the same investigation.
Lab Checkpoint

Remediate Without Hiding the Risk

  • Fix the trust boundary rather than filtering one known payload
  • Prefer safe APIs, parameterization, allowlists, and least privilege
  • Add a regression test that demonstrates the original weakness
  • Run focused tests first, then the full local validation suite
  • Ask Copilot to review the revised diff for bypasses and regressions
  • Update the security review artifact with the evidence
Once we have a confirmed finding, we want the smallest complete fix. That means repairing the trust boundary, not blocking the one payload we happened to demonstrate. Prefer the safe API or established framework pattern, then add a regression test that fails for the vulnerable behavior and passes after the fix. That test tells the next developer why this code matters and makes it harder for the same weakness to return.
2. Transition

Move from Developer Evidence to Platform Evidence

At this point, we have done the work that is easiest to do locally. We understand the intent, we have reviewed the diff, and our tests support the remediation. Now we are ready to commit and let the platform challenge our conclusions. GitHub is not replacing the developer's review here. It is repeating important checks in a consistent environment and adding evidence we may not have had locally.

Each Layer Sees Something Different

LayerStrengthLimitation
DeveloperIntent and local runtime contextManual and inconsistent
Copilot local reviewContextual reasoning across the changeMay miss or overstate findings
Tests and lintRepeatable expected behaviorOnly check encoded assertions
CodeQLDeterministic semantic data flowLimited to configured queries and languages
Human reviewerBusiness risk and accountable judgmentTime and attention are finite
No single layer on this table sees the whole picture. The developer understands why the feature exists. Copilot can reason across the surrounding code, but its answers can vary. Tests are repeatable, but they only prove what we thought to assert. CodeQL follows configured security patterns consistently, but it does not know every business rule. We layer these checks because their blind spots are different, and we keep a human reviewer at the end because someone still has to own the decision.

CodeQL Treats Code as Data

graph LR
  A[Untrusted source] --> B[Program flow]
  B --> C{Sanitizer?}
  C -->|No| D[Sensitive sink]
  C -->|Yes| E[Safe path]
  D --> F[Code scanning alert]

Read an alert as a path: source, propagation, missing control, sink, and impact.

CodeQL looks at code differently than a text search or a chat response. It builds a database representation of the program and runs queries over relationships and data flow. When an alert includes a path, follow it from the untrusted source through each important step to the sensitive sink. The highlighted line may be where the problem becomes visible, but the missing control can be much earlier in the flow.

Treat the Scan as New Evidence

  • Confirm the workflow analyzed the pull-request commit
  • Check the query, severity, precision, and affected language
  • Follow every path step before deciding on a fix
  • Compare the alert with the local review artifact
  • Investigate why local review missed any new finding
  • Dismiss only with a documented, reviewable reason
A clean local review does not promise a clean CodeQL result, and that is useful. If CodeQL finds something we missed, we should ask why. Did our prompt ignore a call path? Were the repository instructions missing an important security rule? Did we need a regression test? Sometimes the answer is simply that CodeQL has a deterministic query designed for this exact pattern. The difference between the two reviews helps us improve the workflow.
Lab Checkpoint

Open a Draft Pull Request

  • Commit only the reviewed change and its regression test
  • Link docs/security-review.md in the pull-request description
  • State the trust boundary, confirmed finding, and remediation
  • Include exact local validation commands and results
  • Wait for CodeQL and required checks before requesting approval
When we open the pull request, we want the next reviewer to inherit our reasoning, not reconstruct it from scratch. The description should explain the trust boundary, the finding, the fix, and the commands we ran locally. Keep the pull request in draft while the platform checks are still running. The local review record now becomes a useful comparison point when CodeQL reports its result.
3. Remediate

Use Autofix as a Proposal, Not Permission

Now we are moving from detection to remediation. Copilot Autofix can shorten the time between a CodeQL alert and a candidate patch, which is valuable when teams are carrying a large security backlog. But faster is only better if the fix is sound. We still need to understand the alert, inspect every changed line, and prove that the application behaves correctly afterward.

Know Which System Is Acting

CapabilityInputOutput
CodeQLCode database and queriesDeterministic alert and path
Copilot AutofixAlert context and relevant codeSuggested code change
Agentic AutofixAssigned alert and repositoryIterated draft pull request
Copilot code reviewPull-request diff and contextReview comments
These names are easy to blur together, so let's separate the jobs. CodeQL produces the alert and the data-flow path. Copilot Autofix uses that alert context to suggest a code change. Agentic Autofix, where it is available, can go further by exploring the repository, making changes, rerunning analysis, and opening a draft pull request. Copilot code review comments on the pull-request diff. Each capability adds evidence or a proposal, but none of them gets to approve its own work.

Review an Autofix Like Production Code

  • Does the patch break the complete source-to-sink path?
  • Does it use the framework's safe API or invent a custom filter?
  • Are alternate paths, encodings, and error branches still exposed?
  • Did authorization, logging, dependencies, or permissions change?
  • Does the regression test fail on the vulnerable code?
  • Do functional tests and CodeQL pass after the patch?
Review this suggestion exactly as you would review production code from a teammate. Does it break the whole unsafe path, or only the example that triggered the alert? Does it use the framework's safe API? Did it quietly change authorization, logging, dependencies, or error handling? An alert disappearing is good evidence, but a patch that breaks the feature or opens another path is not a successful fix.
Lab Checkpoint

Accept, Revise, or Reject the Suggestion

graph LR
  A[Inspect alert] --> B[Read Autofix]
  B --> C{Breaks full path?}
  C -->|No| D[Reject or revise]
  C -->|Yes| E[Run tests]
  E --> F[Run CodeQL]
  F --> G[Human review]
Here is the decision point: accept, revise, or reject. Start with the CodeQL path, then compare it with the proposed change. If the patch breaks the full path and preserves behavior, validate it. If it only handles part of the problem, revise it. If it introduces more risk than it removes, reject it and explain why. In the lab, we use a prepared vulnerable pull request so everyone can evaluate the same alert even if your local fix already prevented it.

The Platform Makes Good Practice Repeatable

  • Default setup or advanced workflows run CodeQL consistently
  • Repository rulesets require code-scanning results before merge
  • Severity thresholds prevent high-risk alerts from being ignored
  • Branch protection requires tests and accountable human approval
  • Security campaigns and alert assignment organize remediation work
  • Audit history preserves decisions, dismissals, and review evidence
So far we have focused on one developer and one change. The platform is what makes this practice repeatable when an organization has hundreds of developers and thousands of pull requests. CodeQL workflows run the same analysis consistently. Rulesets can stop high-risk findings from being ignored. Required checks and human approval keep the merge decision accountable. These controls create a dependable floor, but they work best when developers arrive at the pull request having already done the local review.

Protection Is a Shared System

RolePrimary ResponsibilityEvidence Produced
DeveloperInspect, remediate, test, explainDiff, tests, review record
Repository platformRun consistent checks and gatesCheck runs and alerts
Security teamConfigure queries, policy, and responseRulesets and guidance
ReviewerEvaluate risk and approveComments and decision
OrganizationMeasure and improve the systemTrends and audit history
Secure development is shared work, but shared does not mean vague. The developer owns the change and the evidence behind it. The platform runs consistent checks. The security team maintains policy, queries, and guidance. The reviewer evaluates the complete risk and makes the approval decision. At the organization level, we use trends and audit history to improve the system, not to turn security findings into a blame report.
Final Checkpoint

Prove the Change Is Ready

  • The complete diff matches the stated intent
  • Confirmed local findings have evidence-backed remediation
  • Regression tests fail before the fix and pass after it
  • Required tests, lint, build, and CodeQL checks pass
  • Autofix changes were reviewed, revised, or rejected explicitly
  • No security alert was dismissed without a documented reason
  • An accountable human reviewer makes the merge decision
Before this pull request is ready, we should be able to prove every item on this list. The diff matches the intended feature. The confirmed finding has a real remediation and a regression test. Local and platform checks apply to the current commit. Any Autofix change has been reviewed rather than trusted by default. Passing checks matter, but they do not tell us whether this is the right change for the business. That final judgment still belongs to an accountable human reviewer.

Security Starts Before the PR

Developer context finds risk early. Platform controls make protection consistent.

Let's close with the habit I want you to take back to your next change: security starts before the pull request. Inspect the diff while the intent is still fresh. Use Copilot to challenge your assumptions, but require evidence. Fix the trust boundary and prove it with a regression test. Then let CodeQL and Autofix challenge that work again on the platform. When a pull request arrives with that security story already documented, reviewers can spend their time on the decisions that truly require human judgment.
