Secure Before You Share

Review locally. Remediate deliberately. Let the platform verify.

Welcome to Secure Before You Share. Today we are starting where developers actually work: in the local diff, before a pull request exists and before a scanner has a chance to tell us what went wrong. We will use GitHub Copilot to inspect a change, fix what the evidence supports, and then let configured CodeQL analysis challenge our work on the platform. For a supported alert in an enabled environment, we can also evaluate an Autofix proposal. The goal is not to hand security to a tool. The goal is to build a workflow where developers catch risk early and GitHub makes that protection consistent.
Challenge

Stop the Vulnerability Before the PR

A feature works, but its diff crosses a trust boundary. Your mission is to review it locally, remediate supported findings, and open a pull request that can survive CodeQL and human review.

Starting State

Passing feature tests, unreviewed data flow, and a developer ready to commit.

Done State

Documented local review, verified remediation, clean platform checks, and accountable approval.

Here is the situation: the feature works, the tests pass, and you are one command away from committing it. That is exactly when security issues are easiest to overlook, because everything feels finished. In our challenge, the diff crosses a trust boundary, so we are going to slow down before the pull request and use the context we still have in our heads. You will work in a disposable repository with an intentionally vulnerable branch, which gives us room to investigate and make mistakes safely.

What You Will Be Able to Do

  • Review a local diff with a security-focused Copilot prompt
  • Separate evidence-backed findings from speculation
  • Remediate vulnerabilities without changing intended behavior
  • Use CodeQL results to trace source, flow, and sink
  • Evaluate Copilot Autofix as a proposed patch, not an automatic verdict
  • Explain how rulesets and required checks protect teams at scale
By the end of this session, you will have practiced the whole path from a local diff to a protected pull request. We will use Copilot for contextual review, but we will not accept findings without evidence. We will use CodeQL for repeatable data-flow analysis, and we will treat Autofix as a proposed patch that still needs review. Finally, we will connect those developer actions to rulesets and required checks, because a good habit becomes much more valuable when the platform can reinforce it across every repository.

This is our path for the session. We begin with the diff, review it locally, remediate what we can prove, and validate that the feature still behaves correctly. Only then do we open the pull request. Configured CodeQL analysis adds independent evidence, but an Autofix suggestion is conditional, not a guaranteed next step for every PR alert. For the Autofix demonstration, we need a supported default-branch backlog alert and verified access in the delivery environment, or a captured proposal. A human makes the final decision, and new evidence can send us back to the code at any point.
1. Inspect

Start with the Change You Actually Made

Let's begin with the change in front of us. A bounded diff gives us something concrete to reason about, and it keeps the review tied to the work we are about to share. Before we ask Copilot anything, we need three things: a clean baseline, a clear statement of intended behavior, and an honest look at every file that changed.
Lab Checkpoint

Establish a Trustworthy Baseline

  • Confirm the branch and inspect git status --short
  • Run the repository's tests, lint, and build commands
  • Read the full diff, including generated and dependency files
  • State the intended behavior in one sentence
  • Identify inputs, outputs, credentials, and external systems touched
Our first job is to establish what was true before we touch the code again. If the tests were already failing, we need to know that now, because neither Copilot nor CodeQL can read our memory and separate an inherited problem from a new regression. Also, do not limit the diff to files you remember editing. Package managers, generators, and assistants can change files quietly, and those changes are still part of what you are asking the team to review.

Threat-Model the Diff, Not the Entire World

QuestionLook ForEvidence
What enters?User input, files, headers, eventsCall sites and schemas
Where does it travel?Transforms, storage, subprocessesData-flow path
What trusts it?Queries, templates, shells, APIsValidation boundary
What can escape?Secrets, logs, errors, responsesOutput and telemetry
Who can invoke it?Users, roles, services, workflowsAuthorization checks
We are not threat-modeling the entire application in the next five minutes. We are threat-modeling this change. Ask what enters, where it travels, what eventually trusts it, and what could leave the system as a result. That gives us a simple but useful path from an untrusted source toward a sensitive operation. It also gives Copilot something much sharper to inspect than a vague request to find security bugs.

Ask for Findings You Can Verify

Review my uncommitted diff as a security reviewer.

First list reviewed files and any missing context. Distinguish staged,
unstaged, and newly added files in the supplied review scope.

Focus on changed code and its immediate call paths. Trace untrusted
inputs to sensitive sinks. Check authorization, injection, secret
exposure, unsafe deserialization, path handling, and dependency risk.

For each finding, provide:
1. severity and affected file
2. source-to-sink evidence
3. a safe remediation
4. a regression test that would fail before the fix

Do not edit files. Mark uncertain claims as hypotheses.
Before you send this prompt, explicitly provide the intended diff and relevant call paths through your chat interface. Do not assume that opening a file gives Copilot the full change. Include the staged and unstaged changes you intend to share, plus any newly added files, and check its reviewed-file list against your own inventory. The prompt keeps findings close to that scope and requires evidence before editing. Adjust the categories for your stack, and let supported repository instructions provide framework conventions, build commands, and security rules. Missing context is a reason to investigate, not proof that the change is safe.
Lab Checkpoint

Run the Local Security Review

Copilot Provides

Candidate findings, code-path context, remediation options, and test ideas.

You Provide

Explicit diff context, intent, runtime evidence, validation, and the decision to change code.

Capture the review: record confirmed findings, rejected hypotheses, and validation plans in docs/security-review.md.

Now it is your turn to run the review. First compare the files Copilot says it reviewed with the scope you supplied. Then trace each candidate finding back to the code and decide whether the evidence holds up. We are writing that reasoning into a review record because a chat response should never become an invisible authority. If Copilot makes a weak claim, say why it is weak and record what evidence is missing.

Triage Before You Edit

ClassificationMeaningNext Action
ConfirmedCode path and impact are supportedRemediate and test
Needs evidencePlausible, but runtime or call path is unclearInvestigate before editing
False positiveControl or invariant breaks the claimed pathDocument the control
Out of scopeReal issue outside the current changeCreate tracked follow-up
A strong review is not the one with the most accepted comments. It is the one where every decision has a reason. Some findings will be confirmed, some will need another test or call-path check, and some will be false positives because an existing control breaks the path. If you reject a finding, point to that control. Silent dismissal teaches the team nothing and leaves the next reviewer to repeat the same investigation.
Lab Checkpoint

Remediate Without Hiding the Risk

  • Fix the trust boundary rather than filtering one known payload
  • Prefer safe APIs, parameterization, allowlists, and least privilege
  • Add a regression test that demonstrates the original weakness
  • Run focused tests first, then the full local validation suite
  • Ask Copilot to review the revised diff for bypasses and regressions
  • Update the security review artifact with the evidence
Once we have a confirmed finding, we want the smallest complete fix. That means repairing the trust boundary, not blocking the one payload we happened to demonstrate. Prefer the safe API or established framework pattern, then add a regression test that fails for the vulnerable behavior and passes after the fix. That test tells the next developer why this code matters and makes it harder for the same weakness to return.
2. Transition

Move from Developer Evidence to Platform Evidence

At this point, we have done the work that is easiest to do locally. We understand the intent, we have reviewed the diff, and our tests support the remediation. Now we are ready to commit and let the platform challenge our conclusions. GitHub is not replacing the developer's review here. It is repeating important checks in a consistent environment and adding evidence we may not have had locally.

Each Layer Sees Something Different

LayerStrengthLimitation
DeveloperIntent and local runtime contextManual and inconsistent
Copilot local reviewContextual reasoning across the changeMay miss or overstate findings
Tests and lintRepeatable expected behaviorOnly check encoded assertions
CodeQLDeterministic semantic data flowLimited to configured queries and languages
AI Scan on PRsAdditional language and framework coverageAdvisory findings, not merge gates
Human reviewerBusiness risk and accountable judgmentTime and attention are finite
No single layer on this table sees the whole picture. The developer understands why the feature exists. Copilot can reason across supplied context, but its answers can vary. Tests only prove what we thought to assert. CodeQL follows configured security patterns consistently, but it does not know every business rule. When enabled, AI Scan complements CodeQL for languages and frameworks outside its coverage. Its PR findings have an AI indicator and are advisory: they do not fail the code-scanning check or block merges through rulesets. This is a separate platform scan, not our local Copilot conversation, and it does not use repository custom instructions. We keep a human reviewer because someone still has to own the decision.

CodeQL Treats Code as Data

graph LR
  A[Untrusted source] --> B[Program flow]
  B --> C{Effective modeled control?}
  C -->|No| D[Sensitive sink]
  C -->|Yes| E[Path blocked for query]
  D --> F[Code scanning alert]

For a data-flow alert with a path, trace source, propagation, control, sink, and impact. This is a simplified model, not proof of safety.

CodeQL looks at code differently than a text search or a chat response. It builds a database representation of the program and runs queries over relationships and data flow. Not every query produces a path. When an alert includes one, follow it from the untrusted source to the sensitive sink. A sanitizer name alone does not make that path safe: the control must work for this sink and context, and analysis must model it correctly. This diagram illustrates one query's reasoning, not a guarantee about every possible behavior. The missing control can be much earlier than the highlighted line.

Treat the Scan as New Evidence

  • Confirm the workflow analyzed the pull-request commit
  • Check the query, severity, precision, and affected language
  • Follow every path step when the alert provides a path
  • Compare the alert with the local review artifact
  • Investigate why local review missed any new finding
  • Dismiss only with a documented, reviewable reason
A clean local review does not promise a clean CodeQL result, and that is useful. If CodeQL finds something we missed, did our prompt ignore a call path, or did we need a regression test? Compare the actual evidence. Also check which engine produced the finding. AI Scan results appear only on PRs, not in the alert backlog, and do not run on fork or Dependabot PRs. They depend on effective settings and available Code Security AI Credits. Their advisory status means that a green check can coexist with a finding that still deserves investigation.
Lab Checkpoint

Open a Draft Pull Request

  • Commit only the reviewed change and its regression test
  • Link docs/security-review.md in the pull-request description
  • State the trust boundary, confirmed finding, and remediation
  • Include exact local validation commands and results
  • Wait for CodeQL and required checks before requesting approval

Platform preflight: confirm configured CodeQL analysis, a supported language, and repository access. Private or internal organization repositories need the relevant GitHub Code Security entitlement.

When we open the pull request, we want the next reviewer to inherit our reasoning, not reconstruct it from scratch. Explain the trust boundary, finding, fix, and local validation commands. Before expecting a scan, confirm that CodeQL is enabled for a supported language and that the repository has the required access and entitlement. Default setup and advanced setup are both valid, but neither a PR nor a ruleset enables scanning by itself. GitHub-hosted workflow runs can consume Actions minutes. Keep the PR in draft while configured checks run, then compare the results with the local review record.
3. Remediate

How to Use Copilot Autofix

Preflight a supported default-branch backlog alert and the effective repository settings. Do not assume a PR-only alert offers the same actions.

We are ready to evaluate a proposed fix, but first we need to know which experience this environment supports. Our documented demonstration route starts from a supported default-branch backlog alert. Official pages differ on one-step Autofix availability for CodeQL alerts found only on a PR, so we will not promise that interface without verifying it here. Agentic autofix specifically cannot take alerts found only on PRs or other branches. If the required alert or access is unavailable, a captured candidate diff lets us practice the same review decision without inventing a live result. Neither experience transfers responsibility for the patch.

From a CodeQL Alert to a Candidate Patch

graph LR
  A[Supported backlog alert] --> B[Choose available experience]
  B --> C[Draft PR and diff]
  C --> D[Review and test]
  D --> E[CodeQL evidence]
  E --> F[Human review]
  1. Open Security and quality → Code scanning and inspect a supported default-branch alert.
  2. For one-step Autofix, choose Generate fix, read the proposal, then Create PR with fix: a new branch from the default branch and a draft PR.
  3. If agentic autofix is enabled, Assign to Copilot replaces that action and starts a session that prepares a draft PR.
  4. Inspect the actual PR branch and diff, revise as needed, and run tests and CodeQL before approval.

No Copilot subscription is required. One-step suggestions do not consume AI credits; agentic sessions consume Code Security AI Credits and Actions minutes.

Start from the alert, not a blank chat, and read its path when available. With one-step Autofix, Generate fix gives us a proposal; Create PR with fix puts it on a new branch from the default branch. It does not silently patch your current local branch. If effective policy and settings enable agentic autofix, Assign to Copilot replaces that action. The session explores the codebase and attempts to validate its fix before opening a draft PR. Read the session evidence: validation is best effort, and it cannot confirm fixes for custom queries, security-extended queries, or third-party findings. Agentic sessions consume AI credits and Actions minutes, unlike the free one-step suggestions. Both routes still need our review and tests on the actual proposed branch.

Review an Autofix Like Production Code

  • Does the patch block the unsafe source-to-sink path while preserving behavior?
  • Does it use the framework's safe API or invent a custom filter?
  • Are alternate paths, encodings, and error branches still exposed?
  • Did authorization, logging, dependencies, or permissions change?
  • Does the regression test fail on the vulnerable code?
  • Do functional tests and CodeQL pass after the patch?
Review this suggestion exactly as you would review production code from a teammate. Does it break the whole unsafe path, or only the example that triggered the alert? Does it use the framework's safe API? Did it quietly change authorization, logging, dependencies, or error handling? An alert disappearing is good evidence, but a patch that breaks the feature or opens another path is not a successful fix.
Lab Checkpoint

Accept, Revise, or Reject the Suggestion

graph LR
  A[Inspect alert] --> B[Read Autofix]
  B --> C{Blocks unsafe path?}
  C -->|No| D[Reject or revise]
  C -->|Yes| E[Run tests]
  E --> F[Run CodeQL]
  F --> G[Human review]

Demo prerequisite: use a verified supported default-branch backlog alert in an isolated disposable repository, or a captured proposal. PR-only Autofix availability must be checked in the delivery environment.

Here is the decision point: accept, revise, or reject. Compare the alert evidence with the proposed change. If the patch blocks the unsafe path and preserves intended behavior, validate it. If it handles only part of the problem, revise it. If it introduces more risk than it removes, reject it and explain why. A successful local fix may leave no new alert on your PR, which is good. Our separate demonstration needs a supported default-branch backlog alert with verified settings, or a captured candidate diff. A captured proposal supports patch evaluation, but it is not evidence that a live scan passed or a live action was available.

The Platform Makes Good Practice Repeatable

  • Default setup or advanced workflows run CodeQL consistently
  • Configured rulesets require selected code-scanning results within their supported scope
  • Per-tool severity thresholds block qualifying alerts, not every security risk
  • Required status checks and human approvals are separate configured gates
  • Security campaigns and alert assignment organize remediation work
  • Alert timelines and PR records preserve remediation and review evidence
These controls make one developer's good practice repeatable, but only when configured and effective. Require code scanning results is a ruleset rule with selected tools and alert thresholds; it is separate from required status checks and does not enable scanning. A successful analysis job is not the same as a successful Code scanning results check. Current ruleset limitations include merge queue groups and Dependabot PRs analyzed by default setup; alert applicability also depends on locations in the PR diff. AI Scan findings remain advisory and cannot enforce this gate. Required approvals and bypass permissions need deliberate policy choices too. Alert timelines and PR records preserve evidence, but code-scanning timeline events are not automatically entries in the organization audit log. Passing the applicable gates is useful evidence, not proof that every risk was found.

Protection Is a Shared System

RolePrimary ResponsibilityEvidence Produced
DeveloperInspect, remediate, test, explainDiff, tests, review record

Secure development is shared work, but shared does not mean vague. The developer owns the change and the evidence behind it. The platform runs consistent checks. The security team maintains policy, queries, and guidance. The reviewer evaluates the complete risk and makes the approval decision. At the organization level, we use trends and audit history to improve the system, not to turn security findings into a blame report.
Final Checkpoint

Prove the Change Is Ready

  • The complete diff matches the stated intent
  • Confirmed local findings have evidence-backed remediation
  • Regression tests fail before the fix and pass after it
  • Required tests, lint, build, and code-scanning results cover the current commit
  • Applicable alert thresholds are satisfied; advisory findings were triaged
  • Autofix changes were reviewed, revised, or rejected explicitly
  • No security alert was dismissed without a documented reason
  • An accountable human reviewer makes the merge decision
Before this pull request is ready, the evidence must match the actual change and current commit. Confirm that required checks passed and applicable code-scanning thresholds are satisfied, rather than looking only for a successful analysis job. Triage advisory findings too, including AI Scan findings that cannot block merge. If Autofix produced a proposal, review and validate its actual branch; do not treat a captured example as a live check result. Passing gates still cannot establish that every risk was found or that this is the right business change. That final judgment belongs to an accountable human reviewer.
Challenge Complete

Security Starts Before the PR

Developer context finds risk early. Platform controls make protection consistent.

Let's close with the habit I want you to take back to your next change: security starts before the pull request. Inspect the diff while the intent is still fresh. Use Copilot to challenge your assumptions, but require evidence. Fix the trust boundary and prove it with a regression test. Then compare that work with configured CodeQL results and any advisory findings. If an Autofix proposal is available, review it as production code, not as a verdict. When a pull request arrives with that security story already documented, reviewers can spend their time on the decisions that truly require human judgment.
