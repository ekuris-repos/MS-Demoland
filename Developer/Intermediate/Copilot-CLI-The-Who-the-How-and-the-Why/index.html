Terminal AI - Copilot CLI: The Who, the How, and the Why

Meet GitHub Copilot CLI: an agentic AI that lives in your terminal, reads and writes code, executes commands, and connects to GitHub

Today we are looking at the standalone GitHub Copilot CLI, not the retired gh copilot extension that returned command suggestions and explanations. The current CLI is an agent: it can inspect a repository, edit files, run commands, and work with GitHub.com through tools. That capability is useful precisely because it carries real authority. Our goal is to learn where the CLI fits, then choose controls that match the consequence of the task.

Today's Journey

  • Orient: understand the agent loop and where terminal-native work fits
  • Start: install, authenticate, and establish folder trust
  • Operate: choose an interaction mode and control tool access
  • Automate: design bounded, non-interactive commands
  • Extend: add project context, tools, agents, and policies
  • Apply: choose the right surface and build a safe working pattern
We will follow the decisions you make in a real workflow. First, is the terminal the right place for the task? Next, what should the agent be allowed to do? Only after those choices do we consider automation and extensions. By the end, you should be able to choose an operating pattern before you type the first prompt.

Copilot CLI at a Glance

  • A standalone agentic AI that runs directly in your terminal
  • Installed with npm, WinGet, Homebrew, an install script, or a direct download; launched with copilot
  • Can read, modify, and execute files in your project, not just suggest commands
  • Three interaction modes: standard, plan, and autopilot; plus a programmatic interface (-p)
  • Comes pre-configured with the GitHub MCP server for direct GitHub.com integration
  • Supported on Linux, macOS, and Windows (PowerShell and WSL)
The important change is not the command name. The old extension produced an answer for you to run. The standalone CLI can take a sequence of actions and use the result of one action to decide the next. In the default permission mode, operations that need authority prompt for approval, but preapproved tools and more autonomous modes change that behavior. Control comes from the permission policy you choose, not from assuming every action will pause.

Who Is Copilot CLI For?

  • Terminal-first developers who want AI assistance without leaving the command line
  • DevOps and platform engineers managing infrastructure, CI/CD pipelines, and cloud environments
  • SSH users working on remote machines where an IDE is not available
  • Automation builders who want to integrate AI into shell scripts and pipelines
  • Anyone who wants to avoid context switching between the terminal, browser, and editor
The CLI is a natural fit when the shell already contains the evidence and controls you need. That might be a remote session, a container, a repository-wide Git operation, or a repeatable job. It is a weaker fit when visual comparison, line-level review, or debugger state is central to the decision. Terminal preference matters, but observability and risk should decide the surface.

How Copilot CLI Works

Copilot CLI follows an agentic loop: you describe a task, Copilot selects tools, the permission policy is applied, and results inform the next step.

flowchart LR
  A["You describe a task"] --> B["Copilot analyzes"]
  B --> C{"Tool needed?"}
  C -- Yes --> D{"Already permitted?"}
  D -- No --> E["Request approval"]
  D -- Yes --> F["Execute tool"]
  E -- Approved --> F
  E -- Rejected --> H["Redirect or stop"]
  F --> G["Show result"]
  C -- No --> G
  G --> A
  H --> A
Each turn can contain several model calls and tool calls. When Copilot selects a tool, the CLI checks the current permission rules. It prompts only when the action is neither allowed nor denied already. The result then becomes evidence for the next decision. This is why a narrow permission such as one Git subcommand is more meaningful than a general instruction to be careful.

Prerequisites

  • Node.js 22 or later only when installing through npm
  • An active GitHub Copilot subscription or eligible plan
  • If your organization provides Copilot, the Copilot CLI policy must be enabled in the organization's settings
  • Windows users: PowerShell v6 or higher is required ($PSVersionTable.PSVersion to verify)
  • Network access for GitHub-hosted models, authentication, and GitHub.com operations
The installation route determines the local prerequisites. npm needs Node.js 22 or later; native packages and direct downloads do not. Access also depends on your Copilot entitlement and, for managed accounts, organization or enterprise policy. Most sessions use GitHub-hosted models and therefore need network access. Advanced users can configure another compatible model provider, but authentication and GitHub.com tools still have their own network requirements.

Installing Copilot CLI

# npm (all platforms, requires Node.js 22+)
npm install -g @github/copilot

# WinGet (Windows)
winget install GitHub.Copilot

# Homebrew (macOS and Linux)
brew install --cask copilot-cli

# Verify the installation
copilot --version
  • Multiple install methods: npm, WinGet, Homebrew, install script, or direct download
  • To update later, run the same install command again or use copilot update
Pick one installation route and keep its update path consistent. npm is portable when Node.js is already part of your toolchain. WinGet and the Homebrew cask install the native package without adding a Node.js dependency. Direct downloads are useful for controlled environments. Whichever route you choose, verify with copilot --version and use copilot update when the installed channel supports it.

First Launch and Trust

  • Navigate to your project directory and type copilot to begin
  • On first launch, Copilot asks you to trust the current directory
  • Three options:
    • Yes, proceed: trust for this session only
    • Yes, and remember this folder for future sessions: persist trust until it is removed
    • No, exit (Esc): cancel and exit
  • If you are not authenticated, use the /login slash command and follow the prompts
  • In GitHub Actions, prefer the built-in GITHUB_TOKEN with copilot-requests: write; use a fine-grained token only when another environment requires it
Folder trust is a decision about which repository may influence the session. It is not a security verdict on every file in that tree, and GitHub describes path protection as heuristic rather than airtight isolation. Interactive users can sign in with /login. In GitHub Actions, the built-in token avoids a long-lived personal secret. Grant copilot-requests: write plus only the repository permissions the workflow needs.

The Interactive Interface

  • Type copilot to start a session; Copilot greets you and waits for input
  • Describe tasks in natural language: "refactor the error handler to use async/await"
  • Include specific files with @ followed by a relative path: Explain @src/app.js (Tab completion supported)
  • Copilot responds by reading files, proposing changes, and executing commands
  • You approve or redirect when an action is not already covered by the current permission policy
  • Send follow-up messages while Copilot is thinking to steer the conversation
  • Resume a previous session with /resume or copilot --continue for the most recent
  • Continue until you exit with /exit or Ctrl+D; Ctrl+C cancels the current operation or input
Interactive mode is useful when the task is still changing as you learn. Mention a file with @ when you know the evidence you want Copilot to inspect, and steer the turn when its approach drifts. A rejected permission is also feedback: explain the safer route instead of merely saying no. Sessions are durable, so /resume can reopen a selected session and copilot --continue can reopen the most recent one for the current directory.

Interaction Modes

  • Press Shift+Tab to cycle between three modes: standard, plan, and autopilot
  • Standard (ask/execute): Copilot acts immediately and prompts when a tool is not already allowed or denied
  • Plan mode: Copilot analyzes the request and blocks direct project edits while building a plan; connected external tools need separate controls
  • Autopilot mode: Copilot completes multi-step tasks autonomously without requiring approval at each step (use --autopilot on the command line)
  • Review and approve plans before execution; use --max-autopilot-continues to limit autonomous runs
  • Use plan mode when intent is uncertain; use autopilot only with clear scope, permissions, isolation, and verification
Standard mode is the right baseline while you are exploring because permission decisions remain visible. Plan mode protects project files from clear, direct edits while Copilot researches and drafts a plan, but GitHub describes that protection as a safety net rather than airtight isolation. Autopilot removes the turn-by-turn pause, so confidence in the prompt is not enough. Bound its tools, environment, continuation count, and verification before you delegate the work.

Tool Approval

When Copilot needs a tool that is not already allowed or denied, it requests your approval:

  • Yes: allow this tool once; Copilot asks again next time
  • Yes, and approve TOOL for the rest of the session: blanket approval for this tool type during the current session
  • No, and tell Copilot what to do differently (Esc): reject the action and redirect Copilot

Be cautious with session-wide approvals. Approving rm for the session allows Copilot to delete any file in the trusted directory without further prompts.

Approval is about the permission pattern, not only the command currently displayed. A one-time approval covers one request. A session approval can cover later commands with the same tool pattern and any options the agent chooses. That distinction is easy to miss with commands such as rm or git. Read the scope of the approval, then reject and redirect when the requested authority is broader than the task.

Slash Commands

Command Purpose
/login Authenticate with GitHub
/model Inspect and select models available to your plan and policy
/compact Manually compress conversation context
/context View token usage breakdown
/mcp View and manage connected MCP servers
/sandbox enable Enable experimental local sandboxing where supported
/resume Resume a previous session (or use copilot --continue for the most recent)
/limits Inspect or set a soft AI credit limit
/exit End the session
These commands change the session around the task. /model shows the choices currently available to your account, while /context and /compact expose and manage conversation size. Local sandboxing is experimental and requires platform support, including a Windows Insiders build on Windows. AI credit limits are soft because usage is known only after a model call returns, so a call can cross the threshold before the next one is blocked.

Programmatic Mode

Need Option
One-shot request -p or --prompt
Quiet script output -s and --no-ask-user
Minimal capability --allow-tool='shell(git)'
Soft cost guardrail --max-ai-credits=N 
copilot -p "Summarize this week's commits" -s --no-ask-user \
  --allow-tool='shell(git)' --max-ai-credits=30
Programmatic mode turns one prompt into a command that exits when the response finishes. Here, -s removes usage statistics, --no-ask-user disables the agent's question tool, and the Git permission is supplied explicitly. The credit value is a soft guardrail, not a precise billing cutoff. For automation, pair those controls with deterministic validation and an isolated working environment.
The How

Customization

Permissions define what the agent may do. Customization defines what it knows, which tools it can discover, and which repeatable procedures it can follow. Those are different control surfaces, and we should add each one for a specific reason.

Custom Instructions and Memory

  • Custom instructions give Copilot context about your project: how to build, test, and validate changes
  • All instruction files in your project combine automatically; no priority-based fallback
  • Copilot Memory builds persistent understanding of your repository over time
  • Memories capture coding conventions, patterns, and preferences that Copilot deduces as it works
  • Memory is in public preview and depends on user settings and organization policy
  • Reduces the need to repeat context in every session
Instructions are authored rules; memory is learned context. The CLI combines applicable instruction sources, so overlapping guidance can still conflict even though there is no single fallback file. Memory can store repository facts and personal preferences, but it is a public preview feature governed by user and organization settings. Stored facts are validated against cited code before use, and unused entries expire after 28 days. Keep durable policy in instructions rather than relying on memory to infer it.

MCP Servers

  • Copilot CLI comes with the GitHub MCP server configured for issues, pull requests, Actions, and other GitHub.com operations
  • Connect additional MCP servers to extend Copilot's capabilities
  • Use cases:
    • Integrate domain-specific tools and workflows
    • Add contextual data from your environment
    • Customize automation to fit your team's practices
  • Manage servers with the /mcp slash command during a session
  • Control server access with --allow-tool='MCP_SERVER' and --deny-tool='MCP_SERVER(tool_name)'
MCP servers widen the agent's reach beyond local files and shell commands. The GitHub MCP server is the stable built-in integration; additional servers and tools vary by version and configuration. A server can expose internal systems, so installation is not the same as authorization. MCP tool calls still pass through permission controls, including read-only calls to external services. Review the server source, enabled tools, credentials, and enterprise policy before you connect it.

Agents, Hooks, and Model Selection

  • Custom agents: create specialized versions of Copilot tailored to specific tasks (e.g., a frontend engineer agent that follows your team's guidelines)
  • Hooks: execute custom shell commands at key points during agent execution for validation, logging, or security scanning
  • Skills: enhance Copilot's ability to perform specialized tasks with bundled instructions, scripts, and resources
  • Model selection: use /model or --model to choose from the models currently available to you
  • Use the model picker and /usage to understand current AI credit rates and consumption
These extension points solve different problems. Agents define a role and tool boundary. Hooks add deterministic checks around execution. Skills package repeatable procedures and resources. Model choice changes capability, latency, and cost, so inspect the current picker rather than building a workflow around a default that can change. Add an extension only when it makes the task more predictable or easier to govern.

Local Tasks

These prompts are typed inside an interactive session (after running copilot):

# Modify code directly
Change the background-color of H1 headings to dark blue

# Create an application from scratch
Use create-next-app with Tailwind CSS to build a dashboard

# Improve code quality
Suggest improvements to @content.js

# Git operations
Commit the changes to this repo
Revert the last commit, leaving the changes unstaged

# Environment setup
Set up a Python virtual environment and install requirements.txt
These examples differ in blast radius. Explaining one file may need only read access. Creating an application can write hundreds of files and run package scripts. Git operations may affect history or a remote. Start by naming the evidence and verification you expect, then approve only the tools that support that path. Agentic execution does not remove your responsibility to inspect the result.

GitHub.com Tasks

These prompts are typed inside an interactive session (after running copilot):

# Issue and PR management
Create an issue for adding GitHub Copilot instructions
Create a pull request with the changes we have made
List my open PRs

# Work on an assigned issue
Start working on issue #42 in a new branch

# Review and manage PRs
Check the changes in PR #57 and report any serious errors
Merge all of the open PRs that I've created in org/repo

# Actions and workflows
List any Actions workflows in this repo that add comments to PRs
Create a GitHub Actions workflow that runs eslint on pull requests
The built-in GitHub MCP server can inspect and change GitHub resources, subject to its enabled tool subset, your identity, repository permissions, and CLI approval rules. A request to list pull requests is materially different from a request to merge them. Name the repository and desired state explicitly, then inspect the proposed mutation before authorizing it. Mentioning the GitHub MCP server can help the agent choose the intended tool when several routes are available.
The Why

CLI vs. VS Code Chat

The CLI and VS Code can both perform agentic work, so capability lists do not settle this choice. The practical question is where you can best inspect context, actions, and evidence for the task in front of you.

Key Differences

Copilot CLI

  • Terminal-native experience
  • Works over SSH, in CI, and in containers
  • Agentic: reads and modifies files via tools
  • Pre-configured GitHub MCP server
  • Can connect to VS Code for editor context and visual diffs
  • Programmatic mode for automation

VS Code Copilot Chat

  • Editor-native experience
  • Deep VS Code integration (diff, apply, debug)
  • Visual context from open files, selections, diagnostics, and workspace search
  • Custom agents plus editor and extension tools
  • Rich UI with inline suggestions
  • Built-in code review UX
Both surfaces can perform agentic work, so the useful distinction is where you need to observe and control it. The CLI travels with the shell and works in remote or automated environments. VS Code makes review, navigation, diagnostics, and inline feedback visible. When the CLI runs inside the integrated terminal, it can connect to the editor and use that context, so this is not a hard product boundary. Choose the surface that makes the current risk easiest to inspect.

When to Use Which

  • Use CLI when: you are in the terminal, working over SSH, running automation scripts, or managing GitHub operations from the command line
  • Use VS Code Chat when: you want visual diffs, inline code suggestions, or tight integration with editor features like debugging and testing
  • Use both when: the task begins in the shell but benefits from editor context, visual diffs, diagnostics, or inline review
Start with the work, not a favorite interface. A remote incident, pipeline, or repository-wide shell operation naturally belongs in the CLI. A change that depends on diagnostics, visual comparison, or line-level feedback benefits from VS Code. Inside the integrated terminal, you can keep the command-line workflow and still use the editor connection for context and review. The best surface is the one that exposes the evidence you need before accepting the result.
The Why

Trust & Security

We have already used trust, approvals, and automation limits. Now we can see how those controls fit together, and where their guarantees stop.

Security Considerations

  • Trusted directories: scope expected file access, but are not a hard isolation boundary; do not launch from your home directory
  • Tool approval: mutating operations generally prompt by default; preapproved tools and selected read-only commands may not
  • Least privilege: allow only the tool patterns, paths, and URLs required by the task
  • Local sandbox: use /sandbox enable or --sandbox with experimental features on supported platforms
  • Cost guardrail: set a soft limit with /limits or --max-ai-credits before autonomous work
  • Defense in depth: use a worktree, container, VM, or dedicated runner when the potential impact warrants stronger isolation
No single control is an isolation guarantee. Folder trust and path checks are heuristic. Permission patterns govern approvals, while the experimental local sandbox restricts commands and tools according to an OS-level policy. Built-in file tools enforce that policy in process on a best-effort basis because the CLI itself is not inside the sandbox. For higher-impact work, add a worktree, container, VM, or dedicated runner and verify the result outside the agent's own report.

Aliases & Shell Integration

# Bash/Zsh: predictable output, no implicit permissions
alias cpcli='copilot -p -s --no-ask-user'

# PowerShell equivalent
function cpcli { copilot -p @args -s --no-ask-user }

# Add the minimum permission at the call site
cpcli "Explain each of these scripts and offer improvements"
cpcli "Summarize recent commits" --allow-tool='shell(git)' \
  --max-ai-credits=30
A useful helper can standardize output without silently widening authority. Here, -s suppresses usage statistics and --no-ask-user removes the agent's question tool. Neither option approves a shell command or file write. The caller still supplies the minimum permission and a soft credit guardrail for each task, which keeps convenience separate from authorization.

Write a Complete Task Contract

  • Outcome: state the observable result, not just the activity
  • Evidence: point to relevant files, issues, logs, or commands
  • Boundaries: name what may change and what must remain untouched
  • Constraints: specify compatibility, policy, framework, or performance requirements
  • Verification: define the tests or checks that prove completion
  • Stop condition: say when to pause for input instead of guessing
A strong prompt is a small contract. "Fix the login bug" names an activity, but it does not define success or limit the blast radius. A better request points to the failing behavior and evidence, protects unrelated code, names compatibility constraints, and requires a specific test. The stop condition matters when information is missing: asking Copilot to pause is safer than allowing it to invent a product decision. This structure improves both interactive work and unattended automation.
Summary

From Features to Practice

We have covered the controls individually. Now we will combine them into an operating pattern you can choose before a task begins.

Choose the Operating Pattern

Situation Pattern
Unclear or high-impact change Plan first, review, then execute
Exploratory repository work Interactive session with explicit approvals
Repeatable automation Prompt mode, minimal tools, sandbox, credit limit
Review-intensive code change CLI with the VS Code editor connection
The durable skill is choosing an operating pattern before starting. Uncertainty calls for a reviewed plan. Exploration calls for an interactive session where approvals remain visible. Repetition can justify automation, but only after tools, isolation, verification, and cost are bounded. When visual evidence matters, keep the terminal workflow and use the editor connection. The same CLI can support all four situations; your control model should change with the risk.

Where to Go Next

  • Choose one recurring task: start with a read-only workflow you can verify easily
  • Capture repository context: add build, test, and validation instructions
  • Bound automation: specify tools, sandbox policy, finish criteria, and an AI credit limit
  • Review the evidence: compare output quality, runtime, and cost before expanding scope

  • Documentation: copilot --help or visit the GitHub Docs
  • Feedback: use /feedback in any session to share your experience
Do not begin adoption with the most autonomous task you can imagine. Pick a recurring, read-only job whose answer you already know how to check. Add the repository context it needs, set explicit boundaries, and record whether the result is faster or better than your current method. Expand scope only after the evidence supports it.
