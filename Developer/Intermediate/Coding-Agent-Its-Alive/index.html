Part 1

Meet the Cloud Agent

Let's start with the fundamentals. Where should a task run, and what context will the agent have when it gets there?

What Is Copilot Cloud Agent?

  • An asynchronous agent with its own development environment, powered by GitHub Actions
  • Issue assignment creates a pull request; a prompt can research, plan, or edit a branch before you request a PR
  • Uses code, documentation, instructions, and any explicitly configured tools or context
  • Available with supported paid Copilot plans, subject to organization and repository policies
        graph LR
          A[Bounded task] --> B[Prepare environment]
          B --> C[Plan and implement]
          C --> D[Validate changes]
          D --> E[Human review]
Cloud execution means your laptop does not need to stay on while the task runs. By default, Copilot works in an ephemeral GitHub-hosted development environment; organizations can also configure supported runners. We do not need to assume a particular virtualization implementation. Issue assignment creates a PR workflow, while a task started with a prompt can stay on a branch until you request a PR. Changes are scoped to the task repository, but configured MCP servers can supply additional context or tools. Ephemeral compute does not mean all information disappears: session logs persist, and optional Copilot Memory can retain useful facts under the applicable policies.

Cloud vs. Local VS Code Sessions

Copilot Cloud Agent

  • Uses a separate development environment
  • Start with issue assignment or an agent task prompt
  • Works asynchronously; you can close your laptop
  • Works on a branch or PR, depending on the entry point
  • Does not inherit your local workspace or editor tools

Local VS Code Session

  • Works against your local workspace
  • Triggered by chat prompts
  • Works interactively; you guide it in real time
  • Edits files in your workspace directly
  • Tools, terminal, and MCP access depend on permissions and configuration
The important distinction is the execution environment, not simply which window you use. VS Code can display local and cloud sessions. A local session can use your workspace and permitted local tools, while a cloud session uses the repository and services configured for that task. It cannot reach an unsaved file on your laptop just because the task began in your editor. Current VS Code offers different agent harnesses, so the exact controls and session lifetime vary. Before handing work off, check where it will run and which context will actually be available.

Parallelizing Agent Work

Local: Separate Workspaces

  • Use VS Code's Agents window to organize independent sessions
  • Use separate worktrees when tasks need isolated working directories
  • Review and merge each result deliberately

Cloud: Multiple Issues

  • Assign separate, bounded issues to Copilot
  • Each task has its own branch and development environment
  • Review the PRs independently; merge when ready
  • Account for usage cost and coordination, not just elapsed time
  • You manage the boundaries. Worktrees isolate edits, but overlapping changes can still conflict when merged.
Parallel work helps when tasks are genuinely independent. A documentation update and an isolated test improvement may be good candidates; two changes to the same API contract need more coordination. Worktrees prevent agents from overwriting one shared working directory, but they do not prevent conflicting assumptions or merge conflicts. Use the Agents window to keep sessions organized, budget for their combined usage, and integrate one reviewed result at a time. We will keep local orchestration brief here; the Agent Potato companion course covers that environment in more depth.

How the Cloud Agent Works

  • 1. Assign an issue - Select Copilot as assignee and provide any additional prompt
  • 2. Prepare - The agent uses its development environment and your optional setup workflow
  • 3. Implement - It reads context, changes code, and attempts validation
  • 4. Track the PR - The issue-assignment path creates a PR; a draft can exist while work continues
  • 5. Review and iterate - Inspect evidence, approve workflow runs when appropriate, and direct follow-up to the agent
  • Prompt-based alternative: Research or edit on a branch first, then request a PR when ready
Our main path starts with an assigned issue, not a bare mention in an issue comment. Copilot prepares its environment and works against the task repository. The issue workflow creates a PR, which can remain a draft while implementation continues, so a PR appearing does not prove that the task is finished. We inspect the session and validation evidence before review. A task started with a prompt on GitHub.com is different: it can research, plan, or edit a branch without automatically creating a PR. That lets us agree on an approach before requesting implementation or review.
Part 2

Triggering the Cloud Agent

Now that we know where the work runs, let's give it a task with a clear starting point and a clear definition of done.

Assigning Issues to Copilot

  • Open the issue's Assignees control and select Copilot; an Assign to Copilot shortcut may also appear
  • Add context in the optional prompt; check the target repository and base branch
  • Copilot receives the title, description, and comments that exist at assignment time
  • Later issue comments are not a continuing input channel; use session steering or the PR for follow-up
Treat assignment as a snapshot of the task. Before starting, make sure the issue contains the expected behavior and any important existing discussion. The assignment dialog lets you add a focused prompt and choose the target repository or base branch when those controls are available. The screenshot shows that dialog, not an environment configuration file. Once the task is assigned, do not rely on a new issue comment reaching Copilot. Open the running session to steer it, or direct follow-up to the resulting PR. Start time depends on service and repository conditions, so we do not promise an instant response.

Writing Effective Issue Descriptions

✅ Good Issue

  • Clear, specific title
  • Describes the desired outcome
  • Lists acceptance criteria
  • References relevant files or APIs
  • Scoped to a single, well-defined task

❌ Weak Issue

  • Vague title like "Fix the bug"
  • No context about expected behavior
  • Multiple unrelated tasks in one issue
  • No mention of affected files or modules
  • Assumes knowledge the agent does not have
The quality of the issue description directly determines the quality of the agent's output. Think of the issue as your spec. A good issue has a clear, specific title and describes the desired outcome, not just the problem. It lists acceptance criteria so the agent knows what "done" looks like. It references specific files, functions, or APIs when relevant. And critically, it is scoped to a single task. The agent does much better with focused changes than with sweeping refactors. On the other hand, vague issues like "Fix the bug" or "Update the UI" give the agent almost nothing to work with. Multi-part issues that bundle unrelated tasks together will also produce poor results. The agent works best when it can focus on one coherent piece of work.

Watching the Agent Work

  • Open the Agents panel or repository tab and select the session
  • Inspect the session log, changes, and actual test or build results
  • Steer a running session with a follow-up prompt; it is applied after the current tool call
  • For PR follow-up, mention @copilot with a specific change request
  • A status summary is not proof of success; check what ran and what could not run
We want an evidence trail, not just a reassuring status message. Open the task in the Agents interface and inspect which files changed, which tools ran, and whether validation succeeded. You can steer an active session through its prompt box without expecting it to watch the original issue thread. Once work is in a PR, an explicit @copilot comment gives a concrete follow-up request. If the task is no longer useful, stop the session rather than spend more usage on a stale approach. Session logs remain available to people with repository access, so prompts and tool output deserve the same care as other shared development records.
Part 3

Custom Instructions

Now we get into the core configuration topic: custom instructions. We will separate organization settings from repository files, because putting the right guidance in the wrong place does not configure the intended scope.

Organization-Level Instructions

  • An organization owner opens Organization Settings → Copilot → Custom instructions
  • Enter guidance under Preferences and instructions, then Save changes
  • Requires an organization with Copilot Business or Enterprise
  • Supported on GitHub.com for Copilot Chat, code review, and cloud agent
  • Use for organization-wide conventions; instructions are guidance, not policy enforcement
Organization guidance is configured in settings, not by placing a copilot-instructions.md file in a special organization repository. As an organization owner, open Copilot's Custom instructions page, enter the guidance, and save it. This configuration is available for organizations with Business or Enterprise and is supported by the documented GitHub.com experiences. It does not mean a local IDE automatically receives the same organization settings. Keep universal guidance concise, such as requiring tests for behavior changes and avoiding hardcoded secrets. Use repository checks and review to enforce requirements; a natural-language instruction is not an access control.

Example: Organization Settings Text

Paste into Organization Settings → Copilot → Custom instructions, then save.

# Organization Coding Standards for Copilot

## General Rules
- Follow the repository's declared language and supported versions.
- Use ESLint and Prettier configurations from the repository root.
- Always include unit tests for new functions and methods.

## Security
- Never hardcode secrets, API keys, or credentials.
- Use parameterized queries for all database access.
- Validate all user input at system boundaries.

## Pull Request Standards
- Keep PRs focused on a single concern.
- Include a clear description of what changed and why.
- Reference the originating issue number.
This is example text for the organization settings field, not a file to create in an organization repository. The structure is still useful: short general rules, concrete security expectations, and a focused PR convention. We let each repository declare its language and supported versions instead of forcing an unsuitable stack across the organization. Instructions can improve consistency, but the model may miss or interpret them differently between runs. That is why the tests and required review checks remain part of the workflow.

Repository-Level Instructions

  • Add a .github/copilot-instructions.md file inside your repository
  • These instructions apply only to that repository
  • Use them for: framework-specific patterns, project architecture, naming conventions
  • Add scoped rules in .github/instructions/*.instructions.md with applyTo patterns
  • AGENTS.md can provide agent-oriented guidance within the repository
  • Keep applicable guidance consistent; do not assume a universal precedence order across clients
Now we are working with a real repository file: .github/copilot-instructions.md. Put the architecture, supported framework versions, and exact build and test commands here. A mixed-language repository can put narrower rules in .github/instructions files with applyTo patterns. AGENTS.md is another supported agent-oriented instruction mechanism, and the nearest applicable file matters. Keep those mechanisms distinct from custom agent profiles. Different clients and features handle instruction precedence differently, so we avoid conflicting requirements rather than teach an invented universal override rule.

Example: Repo-Level copilot-instructions.md

# Project-Specific Instructions

## Architecture
- This is a Next.js application using the App Router.
- Use the framework and runtime versions declared by this repository.
- API routes live in `app/api/` and use Route Handlers.
- Database access goes through Prisma; never write raw SQL.

## Testing
- Use Vitest for unit tests and Playwright for E2E tests.
- Place unit tests next to the source file: `foo.ts` → `foo.test.ts`.

## Styling
- Use Tailwind CSS utility classes. Do not create custom CSS files.
- Follow this repository's Tailwind theme and design-token configuration.
This example describes an existing Next.js project, not a recommendation to install a particular stack. In a real repository, record its supported versions and precise commands instead of copying assumptions from an unrelated example. Route Handlers and colocated unit tests are concrete conventions the agent can check. Tailwind configuration varies by version, so point to the project's actual theme location rather than assume a legacy configuration filename. Specific context reduces guesswork, but we still inspect the resulting code and validation evidence.

Layering: Org + Repo Instructions

  • Give each kind of guidance a clear scope:
  1. Organization settings → common conventions for supported GitHub.com experiences
  2. Repository files → .github/copilot-instructions.md, scoped *.instructions.md, and applicable AGENTS.md
  3. Issue description → task-specific context and requirements
  • Support and precedence vary by client and feature; avoid contradictory instructions
  • Enforce requirements with tests, rulesets, permissions, and human review, not prose alone
Organization, repository, and task are useful scopes, not a claim that only three instruction sources exist. Organization settings hold shared conventions. Repository files explain this project's structure and commands, with scoped rules where needed. The issue or prompt explains today's desired outcome. Do not copy a precedence table for one chat surface and assume it applies everywhere. If two instructions disagree, fix the conflict at its source. When a rule must hold regardless of model behavior, enforce it through permissions, checks, rulesets, and review.
Part 4

Environment Setup

Instructions explain how the project works. A setup workflow can prepare dependencies deterministically before the agent begins, so it spends less time rediscovering the development environment.

The copilot-setup-steps.yml File

  • Lives at .github/workflows/copilot-setup-steps.yml
  • A GitHub Actions workflow with a single job named copilot-setup-steps
  • Merge it to the default branch; check out code before repository-dependent commands
  • Preinstall dependencies and tools; keep preparation focused and repeatable
  • Optional, but recommended: without it, the agent can attempt its own setup, which may be slower or unreliable
The full path includes workflows: .github/workflows/copilot-setup-steps.yml. The job must be named copilot-setup-steps, and the file needs to be on the default branch. This is a workflow, not a bare list of steps. If setup commands need package.json or other project files, check out the repository first. Copilot can try to install dependencies and run tests without this file, but that discovery can be slow or fail on private dependencies. A deterministic setup reduces that uncertainty. It does not prove that the agent later ran the right tests, so we still inspect validation results.

Example: copilot-setup-steps.yml

name: Copilot Setup Steps
on: workflow_dispatch
jobs:
  copilot-setup-steps:
    runs-on: ubuntu-latest
    permissions:
      contents: read
    steps:
      - uses: actions/checkout@v6
      - uses: actions/setup-node@v7
        with:
          node-version: "24"
          cache: npm
      - run: npm ci
  • Assumes a Node 24-compatible project and a consistent package-lock.json; otherwise use the repository's supported runtime
  • Document actual validation commands in repository instructions, for example npm run build and a terminating CI-mode npm test
Here is a complete minimal workflow for a Node 24-compatible project. It checks out the source, configures the runtime, and installs locked dependencies with read-only repository permissions for setup. Node 24 is a supported LTS in the verified lifecycle table; Node 20 is EOL and is not our fresh teaching baseline. Match the actual project's supported runtime rather than changing versions blindly. The current action examples use checkout v6 and setup-node v7; self-hosted runners must meet their runtime requirements. The workflow_dispatch trigger lets us test setup manually after merging it to the default branch. npm ci requires a consistent lockfile and fails rather than repairing one. Build and test commands are project scripts, not universal npm behavior: only use npm run build if that script exists, and ensure the test script terminates instead of watching for changes. Record the exact commands in repository instructions and check the session log to see which validation actually ran.
Part 5

Reviewing & Handoff

Delegation changes who prepares the first version, not who owns the result. Let's inspect the output and the review gates, then choose when to continue locally or in the cloud.

Reviewing Cloud Agent Pull Requests

  • Inspect the diff, session log, test evidence, edge cases, and any unvalidated behavior
  • By default, Actions workflows wait: inspect changes before selecting Approve and run workflows
  • Request specific follow-up with @copilot on the PR, or push your own refinements
  • The task initiator's approval does not count toward required PR approvals; arrange another reviewer
  • Copilot cannot approve or merge its PR; humans own readiness and merge
A summary of completed work is a starting point, not validation evidence. Read the diff and the session results, then check whether the tests cover the requested behavior. By default, Actions workflows do not run automatically when Copilot pushes to its PR. Review the proposed code, especially workflow changes, before approving those runs. Repository settings can allow automatic runs, so check the actual policy rather than assume this default. If required PR approvals are enabled, the person who initiated the task needs another reviewer because their own approval does not count. Copilot cannot approve or merge the PR itself. For a useful but incomplete change, mention @copilot with a focused correction or push a refinement yourself. If the approach is fundamentally wrong, stop the work, refine the specification, and decide whether to restart.

Common Patterns in Agent Output

What the Agent Does Well

  • Boilerplate and scaffolding
  • CRUD endpoints and data models
  • Unit tests for existing functions
  • Documentation and README updates
  • Small, well-scoped refactors

Where to Watch Closely

  • Complex business logic with edge cases
  • Performance-sensitive code paths
  • Security-critical authentication flows
  • Cross-service integration points
  • Large-scale architectural changes
Treat these as task-selection heuristics, not guarantees of quality. Boilerplate, documentation, tests, and focused refactors often have clearer acceptance criteria than a broad architectural change. Authentication, performance-sensitive code, and cross-service behavior need especially careful validation because a plausible diff can still violate an important invariant. Ask what evidence would convince you that the change is correct, then make sure the task specification and review obtain that evidence.

Handoff: VS Code → Cloud Agent

  • Explore locally, then define a bounded outcome and acceptance criteria
  • In a supported Copilot harness session, use /delegate to continue a focused task in the cloud
  • For a Local harness session, use Session Target → Cloud when available
  • Durable fallback: write a detailed issue and assign it to Copilot
  • Confirm repository/base branch and available context; unpublished edits and local tools do not automatically become cloud resources
Start locally when you need to investigate the code or try a small idea. Once the outcome is clear, choose a native handoff supported by your VS Code harness, or capture the findings in an issue. Current documentation describes /delegate for Copilot harness sessions and a Cloud target for Local harness handoff. The controls depend on your version, account, and policy. Conversation context can travel with a supported handoff, but that is not permission to assume an unsaved file, unpublished commit, local secret, or local MCP server is available remotely. Confirm the repository and base branch, make required source changes available through your normal approved workflow, and include acceptance criteria that stand on their own.

Handoff: Cloud Agent → VS Code

  • The agent opens a PR; check out the branch locally in VS Code
  • Use VS Code agent mode or Copilot Chat to refine the agent's work
  • Run the app locally to verify behavior beyond what automated tests cover
  • Push your refinements to the same branch; the PR updates automatically
  • This "agent start, human finish" pattern combines speed with precision
The reverse handoff is straightforward: check out the PR branch locally, inspect the changes, and validate the application in the environment you understand. You can use a local agent to refine the work, but keep the same review standards. If a cloud session is still editing the branch, stop it or coordinate before pushing your own changes. Otherwise you can end up reviewing one version while another is being written. Your pushed commits update the same PR, where the normal checks and required reviews still apply.
Part 6

Governance & Best Practices

We have the delegation and review loop. Now let's make sure the costs, persistent records, and access boundaries are as deliberate as the task itself.

Managing Sessions and Capacity

  • Cloud-agent model usage consumes GitHub AI Credits under current usage-based billing; monitor budgets and actual usage
  • Compute is separate: check current Actions/runner charges and the repository's billing owner
  • Break work into bounded tasks; current cloud sessions have a 59-minute execution limit
  • Development environments are ephemeral by default, but session logs persist and optional Memory can retain facts
  • Access depends on organization/repository policy; adoption metrics are not a billing ledger
Budgeting has two distinct questions: what model usage did we consume, and what compute did the development environment use? Current Copilot billing meters model usage in AI credits, and the model, task size, and steering affect consumption. Check Actions and runner billing separately; do not assume a Copilot subscription includes a particular Actions allowance. Some existing annual individual subscriptions can remain on legacy request billing, so confirm the account's actual billing model. Adoption metrics help us understand usage patterns, but they are not the spend ledger. Current cloud sessions have a 59-minute limit, which is another reason to keep tasks bounded. Finally, environment cleanup does not erase the session log. Copilot Memory is an optional preview capability with policy controls, so avoid both promising that it is always on and claiming the agent can never retain knowledge.

Security and Trust

  • Write access is restricted to the task branch; the agent cannot approve or merge its PR
  • Admins can explicitly provide Agents secrets and variables; arbitrary Actions secrets are not automatically inherited
  • A default allowlisted firewall limits agent internet access, but is not a complete security boundary
  • Default security checks and code review help; human validation and workflow approval gates remain
  • Session logs persist; data retention and model-training use are separate policy questions
  • Use current privacy terms for training assurances; do not infer them from ephemeral compute
Least privilege still matters when the contributor is an agent. Its write access is limited to the task branch, and it cannot approve or merge its own PR. Organization and repository administrators can intentionally provide dedicated Agents secrets and variables, including private registry access. Values prefixed COPILOT_MCP_ are reserved for MCP servers; do not assume every tool needs every credential. Current documentation describes an allowlisted firewall, but it does not directly cover setup steps or MCP server processes, and sophisticated attacks may bypass it. Configured runners need their own network controls. Default checks include CodeQL, dependency advisory checks, secret scanning, and a code-review second opinion; these are additional signals, not proof of safety. Required checks and rulesets still apply, and Actions runs wait for human approval by default unless settings change that behavior. Cloud session logs remain available to repository collaborators. We are not making an unverified claim about exact model-training or retention terms; check the current privacy policy for the plan and service being used.

Best Practices for Success

  • Write detailed issues with acceptance criteria, file references, and examples
  • Scope tasks tightly; one issue per focused change, not sweeping refactors
  • Prepare a repeatable environment and document actual build/test commands
  • Use the right instruction scope: organization settings, repository files, and task context
  • Review iteratively; inspect evidence and direct specific follow-up to the session or PR
  • Use handoff workflows; explore locally, then delegate to the agent (and vice versa)
  • Monitor budgets; distinguish AI-credit usage, compute, and adoption metrics
Here is the repeatable pattern: specify a bounded outcome, prepare the environment, inspect the evidence, and keep a human merge decision. Organization settings and repository files make the context easier to reuse, but neither replaces tests or required review. If the agent is going in the wrong direction, steer the session or leave an explicit @copilot request on the PR instead of adding an issue comment it will not see. Choose a local or cloud handoff deliberately, and account for usage budgets as well as turnaround time.

Wrap-Up & Next Steps

Let's bring it all together and talk about where to go from here.

Key Takeaways

  • Copilot cloud agent supports issue-to-PR work and prompt-based research, planning, and branch-first changes
  • Organization settings and repository instruction files are different configuration mechanisms
  • .github/workflows/copilot-setup-steps.yml provides optional, repeatable environment preparation
  • Sessions and PRs are the follow-up channels; later issue comments are not
  • Handoffs require context checks; cloud execution does not inherit arbitrary local resources
  • Humans own validation, approvals, budgets, and merge; ephemeral compute does not erase logs or Memory
If you remember one distinction, make it guidance versus enforcement. Organization settings and repository files help Copilot understand expectations; tests, permissions, rulesets, and human review establish the checks around its work. A setup workflow makes preparation more reliable, but we still verify the actual results. Follow-up belongs in the session or PR, not in a newly added issue comment. Check what context a handoff carries, what usage it incurs, and who must approve the result. Those habits make asynchronous delegation useful without treating it as unattended authority.
