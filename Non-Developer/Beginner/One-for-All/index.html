Part 1

More Than Code

Most people first encounter GitHub as a place where developers store source code. That is true, but it barely scratches the surface. Let's reframe what the platform really is.

GitHub Is a Complete Platform

What People Think

GitHub is where developers store and share code. It is a code hosting service with version control.

What It Actually Is

GitHub is an end-to-end software delivery platform: plan, build, test, secure, deploy, and govern, all in one place.

Discuss: Where does your organization plan, build, approve, and govern work today?

The most common misconception about GitHub is that it is "just a code host." In reality, GitHub has grown into a full software delivery platform that covers the entire lifecycle. Planning can happen in Issues and Projects. Building and testing can happen through Actions. Security tools can provide feedback during pull requests. Deployment pipelines can run directly from the repository. Enterprise controls give administrators visibility and governance across the organization. Feature availability varies by plan, repository visibility, organizational policy, and configuration. Understanding this broader picture, including the choices each organization makes, is the purpose of today's session. Use the discussion question to identify where learners currently switch tools or lose context.

The Platform at a Glance

  • Plan: Issues, Projects, milestones, and Discussions
  • Build: Repositories, pull requests, code review, and Copilot
  • Test & Automate: GitHub Actions with CI/CD workflows
  • Secure: Dependabot, secret scanning, code scanning, and push protection
  • Deploy: Environments, deployment protection rules, and release management
  • Govern: Audit logs, policies, identity integration, and compliance reporting

Part 2

Repositories & Collaboration

Now let's look at the foundational layer: repositories and how teams collaborate within them.

Repositories: The Foundation

  • A repository is a project folder whose committed changes are tracked over time
  • Committed files and changes are recorded in Git history, along with their contributors
  • Teams work in branches: isolated copies where changes can be developed safely
  • Pull requests are proposals to merge a branch back into the main project
  • Code review happens directly inside the pull request before changes are accepted
Think of a repository as a project folder with a built-in time machine for committed changes. You can see who changed what and when, while uncommitted or ignored files remain local until they are added and committed. A contributor can create a branch, work independently, and open a pull request to propose merging those changes. The pull request is where teammates review the code, leave comments, suggest improvements, and approve or request changes. Organizations can use branch rules or rulesets to require this review process before changes reach the main branch.

Pull Requests: Where Collaboration Happens

For Contributors

Describe what you changed, link to the related issue, and request specific reviewers. The pull request becomes a living document of the conversation around the change.

For Reviewers

See exactly what changed, leave inline comments on specific lines, suggest edits, and approve or request revisions. Every decision is documented and searchable.

Pull requests are arguably the most important collaboration feature on GitHub. For the person making the change, the pull request is where they explain their work, link it to a tracked issue, and request feedback from the right people. For reviewers, it provides a clear view of every line that changed, with the ability to comment directly on specific code. Conversations, decisions, and approvals are all captured in the pull request history. This is valuable not just for quality; it also creates an audit trail that compliance and governance teams appreciate. Months later, anyone can look at a pull request and understand why a change was made and who approved it.
Part 3

Issues & Projects

Next, let's look at how teams plan and track their work using Issues and Projects.

GitHub Issues: Capturing Work

  • Issues are lightweight work items: bugs, feature requests, tasks, or questions
  • Each issue has a title, description, labels, assignees, and a full comment thread
  • Issues link directly to pull requests, so you can trace a change back to the reason it was made
  • Templates standardize how teams file issues, reducing back-and-forth
  • Issue fields add consistent priority, effort, date, and custom business data across repositories
  • Sub-issues and task lists break large work items into smaller, trackable pieces
GitHub Issues are the starting point for tracking work. An issue can be a bug report, feature request, compliance task, or question. Labels support categorization, assignees establish ownership, and comments capture discussion. Issue fields add structured business data such as priority, effort, start date, and target date. A pull request can close an issue automatically when it uses a supported closing keyword and merges into the default branch. This traceability connects a change to the business need that drove it. Issue templates standardize the information teams need, reducing confusion and speeding up triage.

GitHub Projects: Planning at Scale

Board View

Kanban-style columns (To Do, In Progress, Done) give teams a visual workflow. Drag issues and pull requests between columns to update status instantly.

Table & Roadmap Views

Switch to a spreadsheet-style table for sorting and filtering, or use the roadmap view to see work plotted on a timeline with start and target dates.

Discuss: Which information must stay current for leaders to trust a project view?

GitHub Projects organizes issues and pull requests into flexible views. A board shows stages of work, a table supports sorting and filtering, and a roadmap plots work on a timeline. Projects pulls data directly from repositories. Some workflows are enabled by default in new projects, while others, such as changing status when a pull request merges, must be configured by the project owner. Automation can reduce manual updates, but teams still need clear ownership for the business data that automation cannot infer. Use the discussion question to surface which fields matter to this audience.
Part 4

GitHub Actions

Now we move into automation. GitHub Actions is the engine that powers CI/CD on the platform.

GitHub Actions: Automation Built In

  • Actions automate tasks that run in response to events in your repository
  • Common uses: build the application, run tests, check for vulnerabilities, and deploy
  • Workflows are defined in YAML files that live in the repository alongside the code
  • A marketplace of thousands of community and verified actions means teams rarely start from scratch
  • Results appear directly on pull requests, so reviewers see pass/fail status immediately
graph LR
  A[Event Trigger] --> B[Workflow]
  B --> C[Job 1]
  B --> D[Job 2]
  C --> E[Steps]
  D --> F[Steps]
  E --> G[Status on PR]
  F --> G
GitHub Actions is the platform's built-in automation system. When something happens in a repository, such as a pull request being opened, code being pushed, or a release being created, Actions can automatically run tasks in response. The most common use case is CI/CD: continuously building, testing, and deploying your application. Workflows are defined in simple YAML files that live right in the repository, so they are versioned and reviewed just like any other code. The GitHub Marketplace offers thousands of community and verified actions for common tasks like deploying to Azure, sending notifications, or running security scans. Teams can assemble sophisticated automation pipelines by combining these building blocks without writing everything from scratch.

Actions in Practice

Continuous Integration

Configured workflows can build and test pull requests. Required checks can prevent failing changes from reaching the main branch.

Continuous Deployment

After a merge, workflows can deploy to staging or production with approval gates and organization-defined rollback procedures.

Discuss: What would you automate first, and which decision should remain human?

Actions often supports two phases. For continuous integration, teams configure workflows to build and test selected pull requests. Results appear on the pull request, and required checks can block a merge when validation fails. For continuous deployment, teams can configure workflows to deploy merged changes to staging, run additional validation, and promote to production. Deployment protection rules can require approval for sensitive environments. Teams can also automate their own rollback procedures, but rollback is not an automatic guarantee. Thoughtfully designed automation replaces many manual, error-prone steps with repeatable, observable workflows.
Part 5

Code Quality

Automation is powerful, but it needs guardrails. Let's look at the code quality features that protect the main branch.

Protecting Quality at Every Step

  • Branch rules can require pull requests and restrict who may push or bypass controls
  • Required reviews can set how many approvals a change needs before merge
  • Required status checks can block merging until selected automated checks pass
  • CODEOWNERS identifies responsible reviewers for specific areas of a repository
  • Rulesets let administrators define and enforce policies across many repositories at once
  • GitHub Code Quality can find reliability, maintainability, and coverage issues before merge
graph LR
  A[Push] --> B[Pull Request]
  B --> C{Reviews?}
  C -->|Approved| D{Checks Pass?}
  D -->|Yes| E[Merge Allowed]
  C -->|Missing| F[Blocked]
  D -->|No| F
Code quality on GitHub can be supported through people, rules, and automated analysis. Branch protection rules and rulesets can require pull requests, reviews, and selected status checks. They can also restrict pushes, although administrators must decide who can bypass those controls. CODEOWNERS identifies the people or groups responsible for reviewing specific areas. GitHub Code Quality is a separate paid product that combines deterministic and AI-assisted analysis to find reliability and maintainability issues, report coverage, suggest fixes, and support quality gates. Availability varies by plan and configuration.

Code Review: More Than a Checkbox

  • Code review shares knowledge: reviewers learn about changes across the codebase
  • It catches bugs, security issues, and design problems before they ship
  • Review comments create a searchable record of decisions and trade-offs
  • Suggested changes let reviewers propose edits that authors can accept with one click
Code review spreads knowledge so that no single person is the only one who understands a given area. It can catch bugs, security issues, and design concerns that automated checks miss. The conversation creates a written record of decisions and trade-offs. Copilot code review can add another source of feedback when requested or configured, but GitHub recommends validating its feedback and supplementing it with human review. Ask learners where judgment, accountability, or business context makes a human reviewer essential.
Part 6

Security

Security does not need to be a separate final phase. GitHub provides capabilities that teams can configure throughout the developer workflow. Some are included broadly, while private and internal repositories may require GitHub Code Security or GitHub Secret Protection.

Security Built Into the Workflow

Dependabot

Monitors supported dependencies for known vulnerabilities and can open update pull requests when enabled and a fix is available.

Secret Scanning

Detects supported credentials in repository content and alerts the team so exposed secrets can be investigated and revoked.

Dependabot alerts monitor supported dependencies for known vulnerabilities. Dependabot security updates can open a pull request when the feature is enabled, the dependency is supported, and a patched version is available. Secret scanning searches repository content for supported secret patterns and alerts the team so a credential can be investigated and revoked. GitHub Secret Protection adds capabilities for private and internal repositories, custom patterns, AI-detected secrets, and stronger bypass governance. Teams still need owners and response processes for the alerts these tools produce.

Proactive Security Controls

Code Scanning

Can analyze configured pull requests and branches for vulnerabilities using CodeQL or compatible third-party tools.

Push Protection

Can block supported secrets during a push, with bypass and approval behavior controlled by organizational policy.

Discuss: Who owns an alert after GitHub identifies a dependency, code, or secret risk?

Code scanning examines code rather than only its dependencies. Teams can configure CodeQL or compatible third-party tools to analyze pull requests and branches. For private and internal repositories, code scanning generally requires GitHub Code Security. Push protection can block supported secret patterns before they enter a repository. Repository-level push protection must be enabled, and bypass behavior depends on policy; GitHub Secret Protection adds delegated bypass controls. These capabilities reduce risk, but they do not replace ownership, triage, remediation, or incident response.
Part 7

GitHub Copilot

Now let's look at how AI fits into the platform. GitHub Copilot is more than an autocomplete tool.

AI Assistance Across the Platform

  • Assist: Code suggestions and Chat help people write, understand, and improve work
  • Work locally: Agent mode plans and performs multi-step tasks in the developer's environment
  • Delegate in the cloud: Copilot cloud agent can research, plan, change a branch, and create a pull request
  • Review: Copilot can summarize pull requests and provide feedback when requested or configured
  • Operate: Copilot CLI can answer questions, edit files, run approved tools, and interact with GitHub
  • Govern: Plans, policies, budgets, and AI Credits determine access and usage

Discuss: Where could AI remove toil, and where must a person remain accountable?

GitHub Copilot works across the platform, not only inside the code editor. Code suggestions and Chat assist people as they work. Agent mode performs multi-step tasks locally in a developer's environment. Copilot cloud agent is distinct: it works asynchronously in a GitHub Actions-powered environment and can research a repository, create a plan, change a branch, and optionally open a pull request. Copilot code review provides feedback when requested, or automatically when configured, and its output still requires human validation. Copilot CLI is a broader terminal agent that can answer questions, edit files, run approved tools, and create pull requests. Access is shaped by plan, administrator policy, budgets, and AI Credits. Focus the discussion on useful delegation, review, and accountability.
Part 8

Enterprise Controls

For organizations that need governance, compliance, and administrative oversight, GitHub Enterprise provides a robust control plane.

Governance and Compliance

  • Audit log records defined enterprise, organization, repository, and user events
  • SAML SSO & SCIM integrate with your identity provider for centralized authentication and provisioning
  • Repository policies enforce naming conventions, visibility rules, and default branch settings
  • IP allow lists restrict supported access paths to protected enterprise resources
  • Usage and license metrics show seat allocation, adoption, usage, and selected Copilot outcomes

Discuss: What evidence would leadership need before expanding GitHub or Copilot?

GitHub Enterprise gives administrators controls for access, policy, monitoring, and compliance. The audit log records defined events such as repository creation, permission changes, and policy updates. It supports search, export, APIs, and streaming, but it does not record every workflow step. SAML single sign-on and SCIM provisioning integrate access with identity providers such as Microsoft Entra ID or Okta. Repository policies and rulesets establish organizational standards. IP allow lists restrict supported authenticated access paths to protected resources, but anonymous access to public resources and some application scenarios are outside their scope. Usage and license reporting can show allocation, adoption, and selected Copilot outcomes.
Part 9

How It All Connects

We have toured each area individually. Now let's connect the dots and see how an idea becomes production-ready software on GitHub.

From Idea to Production

  • 1. Capture: A stakeholder files an Issue and adds structured business context
  • 2. Build: A contributor creates a branch and opens a pull request linked to the Issue
  • 3. Review: People review the change; configured rules require selected approvals and checks
  • 4. Secure: Enabled security tools analyze code, dependencies, and supported secret patterns
  • 5. Deploy: Configured Actions workflows promote the change through protected environments
  • 6. Govern: Defined events are audited; configured links and workflows update planning records

  A[1. Capture] --> B[2. Build]
  B --> C[3. Review]
  C --> D[4. Secure]
  D --> E[5. Deploy]
  E --> F[6. Govern]
This is the "One for All" moment: seeing how the capabilities can work together as a connected system. A stakeholder creates an Issue with the business context needed for prioritization. A contributor opens a linked pull request. Configured rules can require reviewers and checks. Enabled security tools can analyze code, dependencies, and supported secret patterns. After approval and merge, Actions workflows can deploy through protected environments. Supported closing keywords can close the Issue after a merge into the default branch, and configured Project workflows can update planning records. Defined events appear in the audit log. Teams still choose the policies, automation, ownership, and human decisions that make the workflow trustworthy.

Wrap-Up & Next Steps

Key Takeaways

  • GitHub is a unified platform that covers planning, building, testing, securing, deploying, and governing software
  • Issues and Projects connect business needs to the code changes that address them
  • Configured Actions workflows automate repetitive work, reducing human error and increasing delivery speed
  • Enabled security tools bring risk feedback into the development workflow instead of waiting for a final audit
  • Copilot can accelerate work, while people remain responsible for review and outcomes
  • Enterprise controls provide the audit trails, access management, and policy enforcement that organizations require
GitHub is not just code hosting; it is a complete delivery platform. Planning tools can link business goals to the changes that address them. Thoughtfully configured Actions workflows reduce manual steps and risk. Enabled security tools bring feedback into the development workflow. Copilot can assist and take on delegated work, while people remain accountable for review and outcomes. Enterprise governance features help align the platform with organizational requirements. The real power comes from integrating these areas intentionally, not from enabling every feature by default.
