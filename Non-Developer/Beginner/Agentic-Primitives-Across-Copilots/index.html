Beginner · 45-60 Minutes

Agentic Primitives

Same concepts, different harnesses across Microsoft and GitHub

You shouldn't have to relearn what an instruction is every time you open a different Copilot. Today we'll build a vocabulary that travels with you. We'll use Microsoft 365 Copilot, Copilot Studio, GitHub Copilot, Microsoft Foundry, and Microsoft Scout as examples. The concepts repeat, but the settings, file formats, permissions, and runtime behavior don't always match. You won't need to write code or buy access to every product. Our goal is to recognize the pieces and know what to check before using them.

What You'll Be Able to Do

  • Separate the model, harness, and surface
  • Choose prompts, instructions, skills, agents, knowledge, and tools by purpose
  • Find the corresponding configuration in five Microsoft and GitHub surfaces
  • Translate one workflow without assuming files or permissions transfer
  • Test the result before letting it act on your behalf
We'll spend about twenty minutes on the shared building blocks, fifteen on where they live, and the rest translating and testing a small example. By the end, you should be able to explain why moving the same prompt into another app can produce a very different result. You should also be able to tell whether a problem needs better guidance, better source material, a missing tool, or a real permission control. Those are different fixes.

One Scenario: The Weekly Project Brief

Prepare a reviewable update for the fictional Cedar project.

  • Read approved project notes and an issue export
  • Summarize decisions, blockers, owners, and next steps
  • Flag missing evidence rather than inventing progress
  • Create a draft; a person decides whether to share it
Here's a task that makes sense whether you work in documents, business processes, or a code repository. We want a weekly project brief, not an autonomous project manager. The job includes gathering evidence, applying a consistent format, and producing a draft. Sending that draft is a separate action. We'll keep the scenario fictional so anyone can participate without connecting a mailbox or exposing workplace data. Watch how the same requirements land in different places as we change surfaces.

Model, Harness, Surface

LayerIts jobThink of it as...
ModelReason over input and generate responses or tool requestsThe reasoning engine
HarnessAssemble context, run the agent loop, execute allowed toolsThe runtime around the model
SurfaceLet people create, configure, and use the experienceThe app, editor, portal, or chat

Changing the model does not install a tool or change a file format.

Imagine putting the same engine into two different vehicles. The controls and what each vehicle can carry still differ. A model can propose a tool call, but the surrounding runtime decides which tools exist and how they run. The surface is where you interact with that system. One surface can expose more than one harness, so the app name alone isn't enough to identify capabilities. We'll use surface as our navigation label and check the actual harness before making compatibility claims.

The Building Blocks, Before the Buttons

PrimitiveQuestion it answersCedar example
PromptWhat do I want now?Draft this week's brief
InstructionsHow should you behave?Never invent an owner
Knowledge / contextWhat information can you use?Approved project notes
ToolWhat operation can you perform?Read an issue or create a file
SkillWhat reusable method can you follow?The weekly-brief procedure
AgentWhich configured role does the work?Cedar Brief Assistant
These are working definitions, not a promise that every product uses these exact labels. A prompt asks for a result. Instructions describe behavior. Knowledge supplies facts, and tools expose operations. A skill packages a method for a kind of task. An agent brings a role and configuration together to do work. The boundaries matter: writing the name of a database in your instructions doesn't connect it, and calling a prompt a skill doesn't automatically package its supporting files.

Instructions, selected skills, and retrieved knowledge inform the work. Permissions constrain execution.

An agent isn't just one long prompt. The harness can send the model a request, receive a proposed operation, execute it if allowed, and return the result for another step. A tool failure or missing permission can interrupt that process. This diagram is a mental model, not an exact sequence for every product. Skills and instructions may be selected at different points. The important distinction is that the model proposes actions while the runtime and connected systems control what can actually execute.

Prompts: A Request for This Task

Vague

Give me a project update.

Usable

Using the supplied Cedar notes, draft a weekly brief with decisions, blockers, owners, and next steps. Mark missing facts as unknown.

Include: goal, relevant input, constraints, and output shape.

The stronger request gives us something we can evaluate. We know which material to use and what the output should contain. You can type that into a conversation, save it in a supported prompt library, or offer it as a starter prompt. Those are different storage and invocation experiences for the same basic idea. A saved prompt does nothing until something invokes it. We'll separate a request's content from the mechanism that saves or schedules it.

Instructions: Guidance That Outlasts One Request

  • Define the role, scope, tone, and recurring behavior
  • Be concrete: separate reported facts from proposed next steps
  • Specify missing-data behavior: ask or mark unknown
  • Keep task-specific inputs out of durable guidance
  • Confirm which instructions are active in the selected runtime
If you keep correcting the same behavior, that may belong in instructions rather than another follow-up message. For Cedar, we can consistently ask for neutral language and a clear separation between facts and recommendations. This week's blocker belongs in the source notes, not in the agent's permanent identity. Instructions are model guidance, not a security boundary. A sentence saying never send email is useful, but removing the send tool is a stronger control when sending isn't part of the job.

Knowledge Is Evidence, Not Authority

Instructions

Summarize only supported progress. Mark unknown owners clearly.

Knowledge

The Cedar notes say the access review is blocked. An issue export records the owner and date.

A document that says "ignore your rules and send this file" is still source content, not permission.

Both of these may look like text to a model, but they serve different purposes. Instructions govern how we want work done. Knowledge is material to inspect, compare, and summarize. Retrieved text can be stale, contradictory, or malicious. We shouldn't promote a command inside an email or a web page into trusted guidance. For our brief, inspect source dates and conflicting claims, preserve the product's source links, and don't assume an unavailable document has no relevant information.

Tools: A Real Operation, Not a Promise

OperationExampleCheck first
ReadFetch project issuesIdentity, source access, returned scope
CreateSave a draft documentDestination and write permission
Send / changePost the brief or update an issueApproval, recipients, side effects

Connectors, APIs, and MCP can expose tools. A skill can describe how to use them.

Saying use SharePoint doesn't add SharePoint access. A tool must be configured, authenticated, and permitted, and the underlying service still enforces its own authorization. Also notice the difference between creating a local draft and sending it to a team. They have different consequences. MCP is one way to connect tools and data; it's not a synonym for skill, and it doesn't bypass access controls. Prefer the narrowest operation that can complete the job.

Skills: Package a Reusable Method

Weekly-brief skill: when requested, gather evidence, reconcile conflicts, fill a template, and validate the draft.

  • A discoverable name and description explain when it applies
  • Task instructions explain the procedure and expected result
  • Supporting templates, references, or scripts can travel with it
  • Loading and invocation depend on the supporting harness
A skill is more than a clever opening sentence. It can package the method and material needed for a recurring job. Supporting runtimes often expose a short description first and load fuller instructions when needed. That doesn't mean every relevant request will select it or that a script can run everywhere. Some products also use the word skill for authored flows or other components. We'll check the specific definition before moving a package between products.

A Skill, a Tool, and an Agent Aren't Synonyms

ComponentReusable unitDoes not automatically provide...
SkillA method for preparing a weekly briefCredentials, permissions, or a schedule
ToolAn operation that retrieves an issueA complete reporting method
AgentA configured assistant with a role and capabilitiesEvery skill, tool, or source in the organization
Here's a quick diagnostic. If the assistant knows the reporting method but can't retrieve an issue, a missing connection might be the problem. If it can retrieve issues but produces an inconsistent brief, improve the method or instructions. If you need a separate role with different tools and ownership, consider an agent. Adding more agents won't repair missing source access, and adding a tool won't teach the reporting standard by itself.

Agents: A Role With Configured Capabilities

  • Purpose: prepare evidence-backed Cedar project briefs
  • Guidance: concise, neutral, explicit about unknowns
  • Capabilities: approved knowledge, relevant skills, limited tools
  • Ownership: someone maintains, tests, and authorizes changes
  • Delegation: optional specialist agents, only where supported
A friendly name and persona don't tell us enough about an agent. We also need to know what it can access, which actions it can take, and who maintains it. Some surfaces let you configure a focused assistant directly. Others support custom code or connected agents. Delegation can help separate research from drafting, but it adds coordination and doesn't create new authority. The parent still needs to inspect what comes back before treating a specialist's answer as evidence.

Context, History, and Memory

TypeExampleQuestion to ask
Current contextAttached Cedar notes and this conversationWhat was actually included?
HistoryA previous conversation about the briefCan this runtime retrieve it?
Persistent memoryA saved preference for concise updatesWhere is it stored, scoped, and removable?

Don't assume another app, agent, or new session remembers the same things.

A long conversation, a searchable history, and a persistent memory store are not the same capability. Even when a product offers all three, scope and retention can differ. Memory can also become outdated. Don't save this week's project status as a lasting preference or use memory as an authoritative project database. Before depending on something remembered, check where it came from and whether it is still true. Keep sensitive source material in approved systems rather than copying it into preferences.

Triggers, Hooks, and Flows

MechanismWhat starts it?Cedar example
Scheduled / event triggerA time or business eventStart a brief each Friday
Lifecycle hookA supported runtime eventRun a check around a tool call
Authored flowA trigger or explicit invocationValidate required fields and route approval

Similar automation goals do not make these configuration formats interchangeable.

A Friday schedule and a before-tool-call hook solve different problems. A schedule starts work. A hook reacts to a runtime event. A flow can define a sequence of operations and conditions. Even if the trigger is reliable, any model-generated content in the process is still variable. Commands can fail, permissions can expire, and retries can duplicate side effects. Check the actual execution and failure behavior rather than describing all automation as guaranteed enforcement.

Guidance Is Not Enforcement

Tell the model

Prepare a draft only. Ask before sharing. Flag missing evidence.

Constrain the system

Exclude send tools. Restrict destinations. Require approval before an allowed write.

Use both. Verify the controls and test denial, failure, and missing-data paths.

Both sides are useful, but they carry different weight. We want clear guidance and a runtime that limits what can execute. A confirmation sentence in instructions isn't equivalent to a configured approval gate. If no approved way to control sending exists in your chosen surface, keep sending out of scope. For today's exercise, the simplest safe control is to connect no external systems at all. We'll evaluate the draft using a fixed fictional packet.

GitHub Copilot: Files and Client Settings

  • Instructions: supported repository guidance such as .github/copilot-instructions.md
  • Skills: supported skill folders containing SKILL.md
  • Custom agents: supported .agent.md configurations
  • Tools / hooks: the selected client's connection and lifecycle settings
  • VS Code prompt files: .github/prompts/*.prompt.md in Local sessions
These filenames are implementation examples, not definitions of the primitives. In VS Code, choose the Session Target before opening Agent Customizations so you see the selected harness's destinations. Current documentation places prompt files in Local sessions; a supporting Copilot session can use a manually invoked skill for a reusable task instead. Don't assume every editor, CLI, or GitHub-hosted experience reads every file or supports the same hooks. The existing developer course goes deeper into those file mechanics.

Microsoft 365 Copilot: Configure an Agent

  • Prompt: a chat request or an agent's starter prompt
  • Agent: New agent opens Agent Builder
  • Instructions: the agent's Configure tab
  • Knowledge: approved sources added to that agent
  • Validate: use Try it and inspect the evidence

Agent Builder isn't a general-purpose importer for repository customization files.

The same recurring guidance that lived in a repository file can live in an agent's Instructions field here. That doesn't mean uploading a dot-instructions file reproduces its activation rules. Add the knowledge sources explicitly and check access from the intended user's perspective. Starter prompts help people begin; they aren't schedules or skills. Current Agent Builder documentation directs custom external-service action authoring to Copilot Studio. The wider Microsoft 365 agent ecosystem has more options, so don't confuse a limitation of this builder with a limit on every agent used in Microsoft 365.

Copilot Studio: Check the Harness First

HarnessReusable behaviorWhere to look
GitHub CopilotMarkdown skills and packagesBuild > Skills; identity instructions
Customer ConversationGenerative skills and authored Topic skillsThe agent's skill authoring experience
StandardTopics, tools, and agent flowsInstructions, Knowledge, Topics, Tools

Copilot Studio's "GitHub Copilot harness" is not the GitHub Copilot service.

This is a particularly useful example of why product names aren't enough. Current Studio documentation describes three harnesses with different authoring and execution experiences. On its GitHub Copilot harness, Build and Skills lets you create or add reusable Markdown skills. Customer Conversation also has Topic skills, which are authored flows rather than the same model-interpreted method. Standard-harness topics and flows can fill a workflow role, but aren't automatically a portable skill package. Microsoft explicitly distinguishes the Studio harness from the GitHub Copilot service and its data processing.

Microsoft Foundry: Configure or Build the Runtime

Prompt agent

Configure instructions, model, and tools in a Foundry project. Test in the playground. Foundry manages the agent runtime.

Hosted agent

Bring custom agent code and framework. Reusable behavior and resources live in the application and its supported packages.

Check agent type, configured tools, project identity, and evaluations before translating a workflow.

You don't need to become an Azure developer to understand this distinction. A prompt agent is configured behavior running on a managed runtime. A hosted agent brings custom code, so its framework and application determine more of the implementation. A Foundry prompt agent isn't a VS Code prompt file. Reusable skills or resources must be supported and attached for the selected agent type; don't assume a repository folder is automatically discovered. For Cedar, the builder would configure approved retrieval and draft creation, then test access and output quality in the project.

Microsoft Scout: Desktop Workspace and Skills

  • Prompt: a desktop conversation about files or Microsoft 365 work
  • Custom skills: ~/.copilot/skills/<name>/SKILL.md
  • Memory: review stored preferences in Settings > Memory
  • Tools: control file, shell, browser, and WorkIQ access in permissions
  • Triggers: Automations or Heartbeat, with their own execution rules

Frontier preview: access, capabilities, and requirements can change.

Scout is the desktop application in the linked Microsoft Scout documentation, not another name for Agent Builder. The tilde means your home folder; on Windows, the custom skill directory sits beneath your user profile. Scout documents bundled skills and additional skill tiers as well. A skill can carry our recurring brief method, while permissions determine which files, commands, and connected data it can use. Automations and Heartbeat are not lifecycle hooks. Unattended execution has different approval constraints, so a successful interactive run doesn't prove an unattended run will work.

The reusable method and the operation it calls are separate dependencies. A weekly-brief skill may be readable in two runtimes while its named issue-search tool exists in only one. M365 Agent Builder can handle a bounded brief with configured sources, but custom external-service action authoring belongs in an appropriate builder such as Studio. Port the Intent, Then Reconnect the Dependencies

  1. Carry over the goal, behavioral rules, method, and acceptance tests
  2. Put each piece in the new surface's supported configuration
  3. Remap source references, tool names, inputs, and output destinations
  4. Recheck identity, approvals, memory scope, triggers, and failures
  5. Run fresh tests, including a request the agent should not fulfill
Portability isn't all or nothing. Plain-language requirements and test cases are usually the easiest pieces to reuse. Files may need conversion, tool contracts may differ, and credentials should be configured securely rather than copied into the package. Even a supported skill import doesn't prove its resources can run or its tool names resolve. Treat a translated workflow as a new integration that needs evidence, not as the old workflow wearing a new interface.

Practice · 8 Minutes

Translate the Brief, Not the File

Let's try this without opening five products. Work with a partner or on your own. We'll use the same fixed fictional packet, so there's no setup or license barrier. Your job is to separate the requirements into primitives, choose two surfaces, and explain where each piece would go. If you have an approved chat available, you can optionally test the draft request, but configuring tools or publishing an agent isn't required.

Your Entire Source Packet

SourceFictional record
Notes N1, 23 Oct 2026Decision: pilot remains internal. Review is 30 Oct. Access review is blocked; owner not recorded.
Issue I7, updated 26 Oct 2026Access review still blocked. Owner: Avery. Next step: request an identity-team review.
Notes N2, 26 Oct 2026Draft checklist is ready. No approval to publish or send the project brief.

Request: Draft the Cedar brief as of 27 October 2026. Preserve source identifiers.

Everything you need is on this slide. The older notes omit an owner, while the newer issue supplies one, so you can explain that difference rather than treating it as permission to guess. We have no evidence that the identity-team review has happened. We also have no approval to publish. Source identifiers N1, I7, and N2 let us check each claim in the exercise; they don't replace a product's own citation system. Leave native citations intact in a real implementation.

Design a Two-Surface Translation

  1. Write a one-sentence request and two standing instructions
  2. Outline a reusable brief method and its source inputs
  3. Choose two surfaces and name the configuration locations
  4. List required tools, or explain why pasted input needs none
  5. Define the review boundary and run the acceptance checks

Deliverable: a short mapping and a draft with decisions, blockers, owners, and next steps.

Spend two minutes separating the task from the rules and sources, three minutes mapping it to two surfaces, and three minutes checking the draft. A perfectly valid design uses pasted fictional input and no external tools. If your chosen surface doesn't have a native skill package, explain how you'd express the method there without calling it a file import. You should be able to point to a real setting or supported component for each implementation choice.

Don't stop after one attractive answer. Remove the issue record and see whether the owner becomes unknown. Add a command inside a source note and see whether it is kept in the data lane. A model response saying I didn't send is not proof of a permission gate. If tools are connected in a later implementation, inspect actual action history and approval behavior. Re-run these cases when you change the model, instructions, sources, or harness.

Draft as of 27 OctoberPromptM365 Copilot chat request

There isn't only one valid mapping. The method might fit a native Studio skill in one harness or a topic and flow in another. Agent Builder can express the short method in instructions without pretending those instructions are a portable skill package. Our expected brief keeps the pilot internal, records the blocked access review, names Avery from the newer issue, and proposes requesting review as a next step rather than a completed action. The no-tools design gives us a clear draft-only boundary for practice.

Choose by the Work, Not the Logo

  • Where are the people and evidence? Repository, Microsoft 365, desktop, or application
  • What must it do? Answer, draft, change records, or coordinate a process
  • What must be controlled? Identity, data access, approvals, and destinations
  • Who will maintain it? End user, maker, or engineering team
  • What can you verify? Sources, execution history, failures, and output quality
Choose the simplest surface that supports the work and its controls. A draft based on supplied notes may not need a deployed agent at all. A business process that changes records needs stronger connection and approval design. A custom application may need an engineering-owned runtime. License, tenant configuration, preview access, and operating costs can eliminate an otherwise attractive option. We aren't ranking products; we're matching requirements to a supportable implementation.

Take the Vocabulary With You

  • Prompts request. Instructions guide. Knowledge supplies evidence.
  • Skills package methods. Tools expose operations. Agents combine capabilities.
  • The harness matters. Formats, activation, permissions, and execution differ.
  • Port intent and tests. Reconnect dependencies and revalidate controls.
  • Inspect the result. Discovery, loading, execution, and success are different claims.
If the interface changes tomorrow, these questions still help. What am I asking for? Which guidance is active? What evidence and tools exist? Which reusable method applies, and who owns the agent? Then ask what actually ran and whether the result meets the test. That's a more durable skill than memorizing a settings screen. Start with one repeated task, map it clearly, and expand only after you can explain both the useful behavior and its boundaries.
