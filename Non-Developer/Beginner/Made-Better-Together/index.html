Part 1

The Two-Platform Reality

Let's start with the situation many of you are living right now: your organization uses Azure DevOps for work tracking and GitHub for source code, or you are somewhere in the middle of a transition between the two.

Why Organizations Use Both

Azure DevOps

Mature work tracking with Boards, Backlogs, and Sprints. Deep integration with Azure Pipelines and Test Plans. Familiar to enterprise teams that have used TFS or VSTS for years.

GitHub

Industry-standard platform for source code, pull requests, and open-source collaboration. Home of GitHub Copilot, Actions, and the largest developer community in the world.

Most organizations did not choose to run two platforms on purpose. It happened naturally. Azure DevOps (and its predecessors, TFS and VSTS) has been the enterprise standard for work tracking, sprint planning, and test management for over a decade. Meanwhile, GitHub became the default for source code hosting, pull requests, and developer collaboration. When Microsoft acquired GitHub in 2018, these two ecosystems started converging, but many organizations still have significant investment in both. The good news is that Microsoft has built robust integration points between the two platforms, and Copilot adds an AI layer that works across both.

Common Friction Points

  • Context switching: PMs update work items in ADO while developers work in GitHub; neither sees the full picture in one place
  • Manual status syncing: Someone has to remember to update the ADO board when a PR is merged in GitHub
  • Duplicate tooling: Teams maintain Azure Pipelines and GitHub Actions for different parts of the same project
  • Reporting gaps: Stakeholder dashboards in ADO do not automatically reflect activity happening in GitHub
  • Security silos: Vulnerability findings live in one platform while the code and work items live in the other
Access check: Features depend on your Copilot plan, organization policies, permissions, and supported client. Azure DevOps security and code-review services can have separate charges.
Before we talk about solutions, let's name the friction. The number one complaint we hear is context switching. A project manager opens Azure Boards to check sprint progress, but the actual development work is happening in GitHub pull requests. Status updates require manual effort, and things fall through the cracks. Teams sometimes end up maintaining two CI/CD systems because Pipelines are configured in ADO and Actions are configured in GitHub. Reporting becomes fragmented. And security findings from tools like Dependabot or CodeQL may not be visible to the people managing work items in ADO. These are real problems, and the rest of this session is about solving them.
Part 2

GitHub Advanced Security for Azure DevOps

Now let's talk about one of the most important integration points: GitHub Advanced Security for Azure DevOps, commonly known as GHAzDO.

What Is GHAzDO?

  • GitHub Advanced Security features for repositories hosted in Azure Repos
  • Secret scanning: Detects credentials and tokens committed to ADO repositories
  • Dependency scanning: Identifies known vulnerabilities in third-party packages
  • Code scanning: Powered by CodeQL, the same engine used on GitHub.com
  • Security alerts appear directly in the Azure DevOps UI; no need to leave your workflow
  • Available for Azure DevOps Services (cloud) with per-active-committer licensing
GHAzDO brings secret scanning, dependency scanning, and CodeQL code scanning to Azure Repos. That repository location matters. Connecting a GitHub repository to Azure Boards does not move its security alerts into this service. Authorized colleagues can review Azure Repos findings without a GitHub account. Before enabling a pilot, an administrator should check permissions, the linked Azure subscription and the active-committer estimate. Billing counts contributing identities present in pushes within a 90-day window, not simply everyone viewing a report. GitHub-hosted code uses GitHub's own security features and access controls.

Why GHAzDO Matters for You

Visibility Without GitHub

Authorized users can review Azure Repos alerts in the repository security pages and the organization's Security overview.

Remediation Visibility

Filter security findings, share relevant views, and export supported results. Agree with your security owner how these findings become tracked work.

For PMs and team leads, the value is a shared view of findings for enabled Azure Repos repositories. With appropriate access, you can open Organization settings, then Security overview, or inspect a repository's alerts. Those are different destinations from a project dashboard; we are not assuming an installed security widget. Filter by the project or severity that matters, and agree who owns remediation. An alert count is useful evidence, but it does not by itself prove compliance or cover GitHub-hosted repositories. Some newer overview capabilities are preview-only, so confirm what your organization actually exposes.
Part 3

Azure Boards + GitHub Integration

Let's move on to the integration that directly impacts your sprint planning and work tracking: Azure Boards connected to GitHub.

How Azure Boards Connects to GitHub

  • Connect the app: An authorized administrator installs Azure Boards from GitHub Marketplace and connects selected repositories to a project
  • Link only: AB#1234 in a commit message or PR description links work item 1234 without changing its state
  • Link and transition: Fixes AB#1234 in a PR description can transition the item when merged into the repository's default branch; the resulting state depends on the work-item process
  • Link a branch: Use the work item's New GitHub branch action or add the branch link in its Development section
  • Trace the evidence: Inspect linked activity in the work item's Development section and follow work-item links from the PR
We first need an authorized administrator to connect the selected repository and Azure Boards project. Then the wording matters. AB#1234 creates a link, but it does not mark the work complete. Fixes AB#1234 in a PR description can do both when the PR merges into the default branch. The item normally moves to the first Resolved-category state, or a Completed-category state if the process has no Resolved state. That does not always mean a state literally named Resolved. To link a branch, create it from the work item's New GitHub branch action or add its Development link. Merely putting AB# in a branch name is not the documented linking mechanism. We still verify the links and resulting state rather than assuming every board update is handled for us.

Impact on Sprint Planning

Before Integration

  • PM asks developers for status updates in standup
  • Board updates happen hours or days after actual work
  • Sprint burndown charts do not reflect reality
  • End-of-sprint scramble to close items

After Integration

  • Linked PRs provide visible development evidence
  • Qualifying default-branch merges can transition items
  • Team checks states, estimates, and reporting refresh
  • PMs spend standup time on blockers, not status
The practical improvement is better evidence, not a perfectly self-maintaining sprint. A linked PR lets us inspect what happened instead of relying on memory. A qualifying default-branch merge with Fixes AB# can update the work item's state, but a bare link cannot. Opening a PR does not automatically move the item into an In Review state; that would need separately configured automation. We still check iteration assignments, estimates and the state categories our burndown uses, and allow for reporting refresh. That makes standup more useful because we can spend less time reconstructing activity and more time discussing blockers.
Part 4

Copilot with Azure DevOps

Now let's separate two experiences that sound similar: a Copilot assistant connected to Azure DevOps data, and a feature built directly into Azure Repos. Knowing which surface we mean prevents a frustrating search for a button that is not available in your environment.

Choose the Right Copilot Surface

TaskWhere it happensCheck first
Draft acceptance criteria or test cases from work itemsSupported agent-mode assistant with Azure DevOps MCPApproved connection, tool access, and human review
AI-assisted review of Azure Repos PR changesNative Copilot code-review public previewAdministrator enablement and usage charges
Draft a GitHub PR summaryCopilot on GitHub.comFeature access, PR context, and accuracy

Azure DevOps MCP · Azure Repos review preview

These are three different entry points, not three buttons on one Azure DevOps page. For planning assistance, an approved agent-mode assistant can use Azure DevOps MCP tools to retrieve work items and draft criteria or tests. Current Microsoft guidance prefers the hosted remote server where supported; it requires an Entra-backed organization and an appropriate client. Your platform owner can arrange that connection, and you should review proposed text before approving a write. Native Copilot code reviews for Azure Repos entered public preview on August 26, 2026. That is review assistance, not a guarantee of PR-description generation or human approval. On GitHub.com, PR summaries are another supported experience. Availability, permissions and costs differ across these surfaces; we are not claiming a universal native-AI feature bundle or identical models.
Part 5

Copilot in GitHub

Even if Azure DevOps is your primary work tracker, GitHub Copilot offers capabilities that benefit your entire team.

GitHub Copilot for Non-Developer Workflows

  • Browser chat: Ask about accessible repositories, PRs, and issues with the relevant context selected
  • PR summaries: Generate a draft summary in a supported PR description or comment, then review it
  • Issue triage: Analyze issue content with Copilot; configure GitHub Actions separately for labeling or routing. CODEOWNERS requests PR reviews, not issue assignment
  • Documentation drafts: Supply the relevant activity and ask for release notes or documentation updates
  • External context: Use approved MCP servers in a supported client. GitHub App-based Copilot Extensions retired on November 10, 2025
You do not need to read every changed line to start understanding a PR. With the right access, Copilot on GitHub.com can draft a summary, but you still check it against the changes and the team's intended outcome. Issue analysis is different from automatic routing: an Actions workflow needs explicit configuration, and CODEOWNERS concerns PR review requests. For external systems, the supported direction is approved MCP servers, not the retired GitHub App-based Copilot Extensions. That retirement does not include ordinary GitHub Apps or client-side VS Code extensions. Also, a Boards connection does not automatically give browser chat your sprint data. We need to provide the relevant evidence or use an authorized data connection.

Copilot Chat for Stakeholder Communication

For PMs and Leads

  • "Summarize these PR links for owner/repo, October 12-23. Cite each PR."
  • "Summarize this authorized alert export. State its scope and timestamp."
  • "Draft release notes for version 2.4 from this reviewed PR list."
  • "Flag missing evidence or conflicting status in these linked items."

For Stakeholders

  • "Explain this PR in non-technical terms"
  • "List possible risks in this PR and questions for its owner."
  • "Summarize this PR and link the evidence for each claim."
  • "What test files exist for this component?"
Notice how these prompts set boundaries instead of assuming Copilot knows what this sprint means. We name a repository and dates or supply the specific PR list. For security information, we use only an export we are authorized to share and retain its timestamp. A draft can miss items, confuse code completion with delivery, or overstate business impact. Before sharing it, we compare the cited sources with Azure Boards, check omissions with the owner and remove unsupported claims. A list of possible risks is a discussion starter, not a security sign-off. Finding test files also does not prove that tests passed or that the change is safe.
Part 6

Bridging Workflows

Now let's put it all together. How do you create a seamless workflow that spans both platforms?

Connect Evidence, Not Duplicate Trackers

  • Planning owner: Keep the agreed work-item status in Azure Boards and link GitHub development evidence
  • Build owner: Azure Pipelines can build GitHub code directly; running both CI engines is optional
  • Custom automation: Cross-platform triggers require explicit configuration, authentication, and ownership
  • Secret access: Authorized workflows or pipelines can retrieve secrets from Azure Key Vault; a code event does not consume secrets
        graph LR
          A[Azure Boards item] ---|Linked evidence| B[GitHub PR]
          B -->|Configured validation| C[Azure Pipeline]
          C --> D[Build result]
          E[Azure Key Vault] -->|Authorized secret access| C
Here is one possible evidence chain, not a requirement to deploy two automation engines. We keep the planning record in Boards, link a GitHub PR, and let a configured Azure Pipeline validate the code. Someone owns each connection and its permissions. A pipeline may retrieve an authorized secret from Key Vault; a PR or merge event does not read secrets itself. Teams can configure Actions, service hooks or API calls for other needs, but those are separate integration projects. For our planning conversation, the important questions are who owns the status, where the validation result lives and how we follow the evidence.

Shared Dashboards and Reporting

Azure DevOps Views

  • Dashboard burndown and velocity from tracked work items
  • Azure Repos alerts in Security overview
  • Pipeline status and deployment evidence
  • Work-item Development links to connected GitHub activity

GitHub Views

  • Copilot usage dashboard with policy and role requirements
  • PR conversations, reviews, and checks
  • GitHub security views for authorized repositories
  • Actions workflow run results
These are separate reporting destinations, not one universal dashboard. Azure Boards burndown uses tracked work-item data, so links to PRs alone do not guarantee a current chart. Azure Repos security findings have their own Security overview, while GitHub-hosted repositories use GitHub security views. Copilot usage reporting has policy and access requirements, and its data can lag by up to three full UTC days. For combined reporting, a team can build a Power BI model with explicit sources and refresh rules. The simple Azure DevOps Data Connector covers Boards data, not every service; Microsoft recommends OData for broader reporting. The documented GitHub Power Query connector is Preview for Power BI semantic models. We should agree on these limitations before promising a joined executive dashboard.
Part 7

Migration Considerations

A question that comes up in almost every conversation: should we migrate everything to one platform, or keep using both?

When to Stay on Both Platforms

  • Investment in Azure Test Plans: Validate how manual testing, test cases, and acceptance workflows would be preserved before moving
  • Process customization: Compare your existing work item types, states, and rules with the target platform's actual capabilities
  • Regulatory or compliance requirements: Validate audit, retention, identity, and approval controls on either platform against your requirements
  • Large-scale TFVC repositories: If you still use TFVC (Team Foundation Version Control), migration requires careful planning
  • Organizational readiness: Teams that are not ready for change benefit from a gradual, integrated approach
There are legitimate reasons to keep both platforms. If your team depends on Azure Test Plans, identify what happens to manual tests, test cases and acceptance evidence before moving. Compare your custom work-item process with the target platform rather than assuming it can or cannot be reproduced. Both platforms need to be evaluated against your audit, identity, retention and approval requirements; a product name does not prove compliance. Legacy version control also needs its own migration assessment. Coexistence gives us time to test those requirements instead of forcing a big-bang decision.

When Consolidation Makes Sense

  • Reducing tool sprawl: If your organization is paying for and maintaining two platforms with overlapping features, consolidation saves cost and complexity
  • Closer GitHub workflows: GitHub-hosted issues and PRs can simplify context; Copilot access still depends on the feature, plan, and policy
  • Simplifying onboarding: New team members learn one platform instead of two, reducing ramp-up time
  • Open-source alignment: If your organization contributes to or consumes open source, GitHub is the natural home
  • GitHub Projects maturity: GitHub Projects has grown significantly and now supports many enterprise planning scenarios
Consolidation can make sense when its benefits exceed migration and change-management costs. GitHub Projects supports views, custom fields, iterations, automation and roadmaps, so compare those capabilities with what your team actually needs. Keeping issues and PRs together can reduce context gathering, but moving platforms does not automatically unlock every Copilot feature or entitlement. We also need to preserve the controls and testing workflows we just discussed. A small pilot with clear success criteria is more useful than assuming one platform will always be simpler or cheaper.
Part 8

Practical Demo Scenarios

Let's walk through two practical scenarios that show how these integrations work in real life.

Demo: Sprint Planning with Copilot

  • Step 1: Open Azure Boards and review the product backlog for the upcoming sprint
  • Step 2: In an approved agent-mode assistant connected through Azure DevOps MCP, retrieve a selected item and draft acceptance criteria without saving
  • Step 3: Review the draft, approve any write, then assign the item to the sprint and confirm capacity
  • Step 4: Create a linked GitHub branch from the work item; include AB#1234 in the PR description to link it
  • Step 5: When appropriate, use Fixes AB#1234 and merge into the default branch; verify the process-dependent state change
  • Step 6: Supply a reviewed PR list and date range to Copilot, then reconcile its draft summary with Azure Boards before sharing
We start in Azure Boards, where the backlog and iteration live. In the approved connected assistant, we can ask, "Retrieve work item 1234 in our selected project and draft acceptance criteria. Do not update it yet." We review the result with the owner before approving any write. The work item's New GitHub branch action gives us a linked branch. AB#1234 in the PR description links the PR without completing the item. If the change really resolves it, Fixes AB#1234 plus a default-branch merge can transition it according to the process. We check that result in Boards. For reporting, we supply a reviewed list of relevant PRs and explicit dates, then compare the summary with remaining work and blockers. GitHub browser chat does not know our Azure Boards sprint merely because the app is connected.

Demo: Stakeholder Reporting

  • Planning evidence: Open Azure Boards burndown and velocity; check iteration scope, work-item states, and refresh time
  • Copilot PR draft: On an accessible GitHub PR, generate a summary and verify it against the changes
  • Release notes: Supply the reviewed PR list and release boundary; check citations, omissions, and business impact
  • Security evidence: For enabled Azure Repos, use Security overview with the right permissions; use GitHub security views for GitHub-hosted code
  • Share carefully: Export supported Security overview results to CSV, or use a configured Power BI model; label scope, timestamps, and limitations
Imagine a steering committee meeting tomorrow. First we verify the iteration, remaining work and chart freshness in Boards. On an accessible GitHub PR, we can request a Copilot summary from the description or comment field, then review the generated text. For release notes, we supply the PR list and the release boundary instead of asking the model to guess completeness. Security evidence comes from the service that hosts the code: Azure Repos security pages or GitHub security views. With authorized access, Security overview supports CSV exports, but we retain their filters and timestamp. A connected Power BI model can help with recurring reports, although it requires setup. Before the meeting, the work owner confirms that the narrative matches delivery and risk; AI has drafted our report, not approved it.
Summary

Wrap-Up & Next Steps

Let's recap what we covered today and talk about what to do next.

Key Takeaways

  • You do not have to choose one platform. Azure DevOps and GitHub work well together when properly integrated.
  • Match security to repository hosting. GHAzDO protects enabled Azure Repos; GitHub-hosted repositories use GitHub security features.
  • Linking is not completion. Bare AB#1234 links; qualifying default-branch merges with Fixes AB#1234 can transition an item.
  • Name the Copilot surface. Use approved Azure DevOps MCP access for connected planning and GitHub.com for PR drafts; humans validate both.
  • Start with integration, then decide on migration. Get the most out of both platforms today while you evaluate long-term strategy.
We can keep the platforms that serve our needs while making the evidence easier to follow. Remember the boundaries: Azure Repos security is not a mirror of GitHub security, a PR link is not proof of completion, and an AI draft is not an approved status report. When someone says Copilot, ask which surface and data connection they mean. Start with one authorized workflow, confirm its links and state changes, and review the resulting communication with the owner. Those checks let us evaluate coexistence or migration using evidence rather than promises.
