Unified Tooling - Copilot and the Thing

Connect repositories, trackers, and project knowledge, then use Copilot to draft answers you can verify

Welcome to "Copilot and the Thing." Your work may be spread across repositories, issue trackers, documentation, and chat. We will look at how GitHub connects related work and how Copilot can help us understand it. The goal is not to make an assistant responsible for project truth. It is to find useful context, draft an answer, and check the evidence before we share it. This session is designed for project managers, team leads, IT admins, and anyone who coordinates work without necessarily writing code.

Part 1

The Scattered Tools Problem

Let's start with the pain point. Many teams have useful information in several places, but no easy way to connect it. It is worth naming that problem before we talk about any replacement tools.

Too Many Tools, Too Many Tabs

  • Source code lives in one platform; issue tracking lives in another
  • Documentation is split across wikis, SharePoint, Confluence, and Google Docs
  • Project boards sit in Jira, Trello, or an internal spreadsheet
  • Team communication happens in Slack, Teams, and email simultaneously
  • Answering "What is the current status of Project X?" requires several sources
Does this sound familiar? Your developers commit code in GitHub, the project manager tracks work in Jira, and the documentation team writes in Confluence. Stakeholders want an update in a PowerPoint deck. Perhaps one experienced team lead knows where everything lives, but finding the full story becomes harder when that person is away. This is not about any one tool being bad. The problem is reconstructing a decision or a status update across several sources without losing important context.

The Real Cost of Tool Sprawl

Time Lost

Switching platforms and searching for the right source interrupts work. Measure that effort in your own team's pilot.

Knowledge Gaps

When information lives in silos, decisions can miss relevant context. New team members must learn which tool holds each answer.

Every extra search, login, and handoff adds friction. We do not need to assume a fixed number of hours saved to see the opportunity. Think about your last status update: which sources did you need, and which details were difficult to confirm? A pilot can measure that effort before and after a change. Bringing related information closer together may reduce the search burden, but the result still depends on good documentation and clear ownership.
Part 2

GitHub as a Unified Platform

Now that we have outlined the problem, let's look at how GitHub can help. Many people think of GitHub as a place to store code. That is part of the story, but its collaboration features can also connect the planning and explanation around that code.

More Than Source Code

FeatureHow it connects the work
IssuesTrack tasks, bugs, assignees, milestones, and recorded blockers
ProjectsPlan issues and PRs in tables, boards, and roadmaps with custom fields
DiscussionsShare Q&A, announcements, and decisions at repository or organization scope
Wikis and repo docsExplain the project; choose documentation sources explicitly for Copilot
ActionsAutomate CI/CD, repository events, and scheduled tasks
Pull requestsDiscuss and review proposed changes before merging them
These features serve different parts of the same story. An issue records the work, a project organizes it, and a pull request proposes a change. Discussions and documentation capture the reasoning around that change. Actions can automate repeatable checks. They share GitHub sign-in and can link related work, but access and search capabilities depend on the resource and feature. Projects can span repositories at user or organization level. A wiki is a documentation home, but putting a page there does not establish that Copilot will automatically retrieve it. For our examples, we will choose the sources we need.

Why Colocation Matters

Before: Scattered

  • Issue in Jira references a PR in GitHub
  • Design doc in Confluence links to a spreadsheet
  • Slack thread has context that never gets recorded

After: Connected

  • Related issues, PRs, and discussions link to each other
  • Documentation records decisions near the work
  • Selected sources give Copilot useful project context
Colocation means bringing related information closer together. When an issue links to the PR that addresses it and the document that explains the decision, you create a chain of context someone else can follow. That is easier than reconstructing a story from an old chat thread and several disconnected links. Copilot can help explain the sources we provide or retrieve, but moving content does not guarantee that every source will be included in an answer. We still need to check which evidence supports the result.
Part 3

Copilot Ties It Together

GitHub can connect related work, and Copilot can help us navigate that context. The useful question is not whether the assistant knows everything. It is whether we have given it enough reliable information to help with this particular task.

Your AI-Powered Guide to Project Context

  • Ask questions in natural language about a specific project or source
  • Provide repository context, issue or PR links, and relevant documentation
  • Draft summaries of issues, PRs, and discussions you can access
  • Inspect the sources and ask what information is missing
  • Useful to non-developers as well as developers
You do not have to read every line of code to ask a useful project question. A manager can ask which blockers are recorded in a set of issues, or what a particular pull request changes for users. Naming the repository, linking the issue, or attaching a decision document gives Copilot a much better starting point than asking about an unnamed project. It may help discover additional relevant material, but we should not assume that it has searched everything we can access. We will check the sources and make missing context visible.

How Copilot Finds Context

  • Relevant sources - choose a repository, file, issue, PR, or discussion for the question
  • Copilot Spaces - collect project docs and issue/PR references for reusable onboarding context
  • Access still applies - a shared Space does not grant access to restricted sources
  • Coverage is not guaranteed - retrieval selects relevant content, not every file or wiki page

About Copilot Spaces

Think of context as the evidence available for this question. Copilot can retrieve relevant information, but that is not the same as loading an entire organization into memory. For a repeatable onboarding task, a Space can bring together a README, a decision document, and selected issue or PR references. Adding the most useful sources helps make the answer relevant. GitHub-based sources in a Space stay updated, while uploaded or pasted material needs its own freshness check. Sharing the Space does not give someone access to private sources they could not already read. Wiki coverage is not assumed in this workflow; we use explicitly selected, supported sources.
Part 4

Copilot on GitHub.com

Let's get practical with the browser experience. We will start with a question about a selected source, then look at how to turn the answer into a reviewed summary.

Copilot Chat on GitHub.com

  • Sign in with Copilot access and permission to the repository you want to use
  • Open github.com/copilot or use the Copilot entry point on GitHub
  • Start with a repository or a specific issue/PR URL, then ask a focused question
  • Check linked sources, dates, and unresolved questions before using the answer
  • Availability depends on your plan and organizational policies
The screenshot is an example of the Copilot home interface, not a promise that every account will have the same controls. Sign in, check your Copilot access, and confirm you can read the repository you want to discuss. If a feature is missing, your plan or organization policy may explain why. We can start at github.com/copilot and provide the relevant issue or PR link. Ask for the main points and the evidence behind them. Conversation history can help us continue a thread, but it has retention limits, so reviewed project decisions belong in the team's normal documentation rather than only in a chat.

PR Summaries & Issue Summaries

Pull Request Summaries

  • Ask Chat to explain a linked PR for a non-technical stakeholder
  • The editor's Copilot actions → Summary drafts a description or comment
  • Review the result before sharing or posting

Issue Summaries

  • Open the issue in Copilot Chat or supply its URL
  • Ask for decisions, recorded blockers, and unresolved questions
  • Long threads can reduce summary quality; check key comments
There are two different PR workflows here. If you only need to understand a change, give Chat the PR URL and ask for an explanation for your audience. If you are drafting a PR description or comment, the documented Summary action is inside that text editor under Copilot actions. Review that draft before posting it. Our screenshot is a generic pull request example; it does not demonstrate summary generation or establish that its text was written by Copilot. For issues and discussions, ask Chat to summarize the selected thread. There is no special thirty-comment threshold, and very long conversations can reduce answer quality. Check the comments that support important decisions.
Part 5

Copilot in VS Code for Non-Developers

You might be thinking, "VS Code is for developers, why would I use it?" You do not need it for our browser workflow. It is an optional way to explore files and documentation when that is useful to your role, with a few important boundaries.

Exploring Repos Without Writing Code

  • With Git and approved Copilot access set up, clone a trusted repo into VS Code
  • Choose a question-focused workflow; review enabled tools and approval settings
  • Ask: "Explain this README and identify the files that support your answer"
  • Do not enable editing or terminal tools for simple exploration
  • Inspect the referenced files; asking a question is not a read-only guarantee
Opening a repository in VS Code lets you browse its files and ask questions about them. Git is needed for the cloning path, and your Copilot access must be configured. Start with a trusted repository and a narrowly scoped question, such as explaining its README. Current chat and agent experiences can also edit files and run tools, so asking for an explanation does not itself enforce read-only access. Review the selected workflow and available tools; leave edit and terminal capabilities disabled when you only need to explore. Do not approve actions you do not understand. For an unfamiliar repository, use the editor's trust protections rather than assuming it is safe because you only intend to read it.

Practical Tasks in VS Code

Read and Understand

  • "Explain this file in simple terms and point to the evidence"
  • "Which environment variables are documented here?"
  • "Which external APIs can you identify in these selected files?"

Optional Reviewed Edits

  • Draft a README improvement or release-note section
  • Inspect the diff before accepting changes
  • Have config changes validated and reviewed through a PR
Reading and changing a project are separate decisions. For exploration, attach the file you want explained and check the parts Copilot references. A list of dependencies or API calls may be incomplete, so ask which files were considered and what remains uncertain. If you later choose to contribute documentation, review the proposed diff before keeping it. Configuration files can affect deployment or access even though they are not application code. Copilot can help explain YAML, but an explanation is not schema validation or proof that a configuration is safe. Use the project's normal checks and a knowledgeable reviewer before merging a configuration change. Never paste secret values into a prompt to get an explanation.
Part 6

Practical Workflows

Now let's put the pieces together. The same pattern works across these examples: identify the question, supply the relevant context, inspect the evidence, and share a reviewed result.

Workflow: "What's the Status of Project X?"

  • Scope: Select the repository and relevant issue/PR links for checkout-redesign
  • Ask: "Summarize these sources for the past seven days. Link evidence for progress and recorded blockers; list unknowns"
  • Check: Open the sources, confirm dates and blocker relationships, and ask owners about gaps
  • Share: Publish the reviewed draft with source links and an as-of date
Suppose your director asks about checkout-redesign. Rather than assuming Copilot knows which project that means, select the repository and provide the issue or PR links that define the work. Ask for a seven-day summary, evidence links, and unknowns. Then check that the dates and statuses in those sources match the draft. A recorded blocked-by relationship is useful evidence; an inferred blocker needs confirmation. If the real decision is still in Jira or a private chat, it may not be available in this context. Ask an owner or use an approved connection instead of filling the gap with a guess. Only then share the update with an as-of date. The visual is explicitly unfinished until we capture this actual workflow; an empty Projects chart is not evidence of a Copilot summary.

Workflow: "Summarize This PR for a Stakeholder"

  • Open Copilot Chat and provide the pull request URL
  • Ask: "Explain this PR for a non-technical stakeholder. Link the evidence and separate proposed changes from confirmed outcomes"
  • Check the PR description, review discussion, and merge state; confirm business impact with its owner
  • Share a reviewed explanation with the source link, not an unchecked AI answer
A pull request proposes a change; it is not proof that the change has shipped. Give Chat the PR URL and name your audience. It can draft a plain-language explanation, but we should check whether the PR is open, merged, or already released, and confirm any claimed business impact. If the summary says a password reset feature is available to customers, for example, the owner may need to confirm deployment. We can then send a clear, reviewed explanation with a source link. This is separate from using the editor's Summary action to draft a PR description or comment.

Workflow: Onboarding a New Team Member

  • Start from a team-maintained Space with a README, decision document, and relevant issue/PR links
  • Ask: "Using these sources, explain the payments service and link the supporting files"
  • Follow up: "Which ownership information is documented, and what should I confirm with the team?"
  • Check source access and freshness; ask a person when context is missing
  • Keep reviewed decisions in team documentation so future hires can reuse them
A new teammate should not have to guess which repositories describe a service. A team-maintained Space can offer a useful starting set: a README, an architecture decision, and a few representative issue or PR links. Ask Copilot to explain that material and point back to its sources. If the documents do not identify an owner, the honest answer is that ownership needs confirmation. Commit activity alone is not proof of responsibility. Spaces make context reusable, but they do not capture conversations nobody recorded or bypass source permissions. Combine self-service exploration with a team contact who can fill in those gaps.
Part 7

Connecting External Tools

Not every team can or should move everything to GitHub. Let's separate linking work across tools from actually making external data available to an assistant.

Integrations: Meeting Teams Where They Are

  • Jira & Azure Boards - link GitHub development activity to work items; full issue synchronization needs a separately configured solution
  • Slack & Teams - approved GitHub apps support notifications and issue collaboration; capabilities depend on the app and version
  • MCP - approved servers can expose tools or data to supported Copilot surfaces, with appropriate access and policy
  • Check the boundary - a link or notification does not automatically make external content available to Copilot
  • Keep a clear system of record and connect only the access your workflow needs

MCP surfaces and controls · GitHub in Teams

Linking and synchronization are not the same thing. Jira and Azure Boards connections can link GitHub development activity to work items without copying every issue between systems. Slack and Teams apps can bring notifications and issue collaboration into chat, but the exact capabilities depend on the app, its version, and permissions. Do not assume a generic workflow-trigger command exists in every connector. For Teams, ask your administrator which current GitHub app is approved rather than installing a legacy one. MCP can expose tools or data to a supported Copilot experience, but setup differs by surface and requires appropriate authorization and organizational policy. Ordinary GitHub.com Chat tools are distinct from repository MCP settings for delegated agents. Server-side GitHub App-based Copilot Extensions were retired in November 2025, so they are not an integration option here. That retirement does not apply to ordinary GitHub Apps or client-side VS Code extensions.
Part 8

Getting Started

We have seen how the pieces connect and where the boundaries are. The next step is a small pilot that tests one useful question, not an immediate commitment to migrate every tool.

What to Consolidate First

  • Step 1: Choose one pilot team and one status or onboarding question
  • Step 2: Confirm Copilot access, source permissions, organizational policy, and a system of record
  • Step 3: Connect relevant issues and repo docs; collect useful context in a Space
  • Step 4: Use approved integrations for information that must stay elsewhere; check actual retrieval coverage
  • Step 5: Measure search effort, answer accuracy, onboarding support, and review time
Start with a question people already ask, such as a weekly update or an explanation of one service. Before changing tools, confirm that the pilot team can access Copilot and the required sources under your organization's policies. Choose where the authoritative status will live. If moving some issues or documentation into GitHub helps, do it gradually. For the Copilot example, use selected repository documentation and linked issues, perhaps collected in a Space. A wiki can remain a useful documentation home, but do not assume that moving a page there proves it is included in Copilot's answer. Compare the draft with the real sources and measure both time saved and review effort before expanding.

Migration Tips

Do

  • Start with one team and a clear system of record
  • Migrate gradually; use approved integrations as a bridge
  • Write useful README files and maintain selected Space sources
  • Label issues consistently and record blockers explicitly

Avoid

  • Trying to migrate everything at once
  • Abandoning tools before replacements are ready
  • Assuming a connector provides complete synchronization or AI context
  • Sharing a generated report without checking its evidence
A pilot gives you feedback without disrupting the entire organization. Native Jira and Azure Boards connections can provide development links while teams keep their current planning system. If you need issue-object synchronization, third-party products such as Unito or Exalate are examples to evaluate, not automatic recommendations. Check the supported fields, access, cost, and conflict-handling rules with your administrators. Good README files and clear issue relationships make project context easier for both people and Copilot to understand. They do not guarantee a complete answer. Keep an owner for documentation and review any uploaded or pasted Space material when the project changes.
Summary

Wrap-Up & Next Steps

Let's bring it back to the practical habit we want to keep: connect the relevant work, ask a scoped question, and verify the answer before someone makes a decision from it.

Key Takeaways

  • Connecting related work can reduce searching and knowledge gaps
  • GitHub combines planning, documentation, review, and automation features
  • Copilot answers depend on relevant context and permitted access, not automatic coverage of everything
  • Spaces can make selected project context reusable for the team
  • Summaries help draft updates; people check sources and own the final message
  • VS Code exploration is optional; tool permissions and review still matter
  • Use approved integrations, pilot one workflow, and measure actual results
The biggest change is not replacing every tool or trusting every answer. It is making useful context easier to find and using Copilot to help explain it. GitHub can connect planning and implementation, while a Space can collect sources for a repeatable question. Our responsibility is to check the evidence, make missing information visible, and share only a reviewed result. You can start in the browser without writing code. Try one team and one question, measure the results, and expand only when the workflow is genuinely helping.
