Multi-Agent Research - The AI is Mightier than the Sword

Compose specialized AI agents to investigate complex questions, challenge assumptions, and prepare evidence for human decisions

Welcome to "The AI is Mightier than the Sword." Over the next hour, we will explore multi-agent research: dividing a substantial question among focused agents and reviewing their combined evidence. This session is designed for enterprise leaders, researchers, analysts, and decision-makers. You do not need to write application code; we will use natural-language instructions and a small configuration file. You still own the scope, access decisions, and final judgment.

Part 1

Beyond Single-Agent

Let's begin with a practical question: when does splitting the research help enough to justify the extra work?

The Single-Agent Ceiling

  • A single capable agent can compare viewpoints, retrieve evidence, and revise its answer
  • Complex enterprise questions can span legal, technical, financial, and operational domains
  • Finite context and attention can make a very broad investigation harder to manage
  • Separate specialists can explore bounded, independent questions in parallel
  • Start with one agent; add specialists when the research breadth warrants coordination
Think about a vendor decision involving security, cost, integration, and operational risk. One well-equipped assistant may handle a narrow version of that question perfectly well. It can retrieve documents and compare conflicting claims; those abilities are not exclusive to teams. Splitting the work becomes useful when the question has substantial, separable investigations or more evidence than one conversation can comfortably manage. The same model and sources can still produce the same blind spots across specialists. We are creating focused investigations, not manufacturing independent expertise merely by changing role names.

Multiple Perspectives: Tradeoffs

Single Agent

A simpler starting point for focused questions. Can compare multiple sources without handoff overhead, but must manage the whole investigation in one conversation.

Multi-Agent Team

Separate scopes and context can support parallel investigation. More model usage, repeated work, and synthesis overhead require a clear benefit.

A research team is a design choice, not a quality guarantee. A security specialist and a cost specialist can investigate different evidence at the same time, which may help us cover a broad vendor evaluation. But someone must reconcile their assumptions and resolve duplicated or contradictory work. Compare the result against a single-agent baseline on a representative question. Did we gain better source coverage or identify a material risk we previously missed? Set a time and usage budget before expanding the team, rather than measuring success by the number of agents involved.
Part 2

Multi-Agent Patterns

Now that we understand the tradeoff, let's explore a few useful ways to divide the work. The pattern should match the question, not the other way around.

The Four Core Patterns

  • Debate: Opposing analyses help a reviewer compare evidence and tradeoffs
  • Consensus: Compare independently gathered evidence; agreement alone is not proof
  • Specialization: Each agent investigates a bounded domain with appropriate sources
  • Orchestration: A human or enabled coordinator delegates sub-questions and assembles results
        graph TD
          Patterns[Multi-Agent Patterns] --> Debate[Debate]
          Patterns --> Consensus[Consensus]
          Patterns --> Specialized[Specialization]
          Patterns --> Orchestrated[Orchestration]
These four patterns give us different ways to structure an investigation. Debate makes competing assumptions explicit. Consensus is useful only when we examine why the answers agree: three agents repeating the same press release are not three independent confirmations. Specialization gives each investigation a clear scope and suitable sources. Orchestration connects the work. You can coordinate it manually, or an agent with supported subagent tools can delegate bounded tasks. Availability depends on the selected harness, configuration, and organizational policy. We will use a human-led workflow first so that the evidence handoffs remain visible.

Debate Pattern in Practice

  • Scenario: "Should we migrate from monolith to microservices?"
  • Agent A (Advocate): Examines scalability, team autonomy, and independent deployment
  • Agent B (Critic): Examines operational complexity, latency, and data consistency
  • Judge Agent: Compares both analyses, checks support, and preserves unresolved questions
  • The value is the evidence and tradeoffs, not a declared winner
        graph TD
          A[User Question] --> B[Advocate Agent]
          A --> C[Critic Agent]
          B --> D[Judge Agent]
          C --> D
          D --> E[Balanced Recommendation]
Imagine your CTO asks whether the company should migrate from a monolith to microservices. We give both specialists the same business constraints, but different questions to investigate. The advocate looks for conditions that favor migration; the critic looks for risks and cases where staying put is reasonable. Both must include counterevidence rather than defend a position at any cost. In our manual workflow, you pass their cited findings to a judge agent. That agent compares the assumptions and identifies missing evidence. If both agents agree, we still inspect the supporting sources. A human decision-maker owns the recommendation, including any unresolved uncertainty.

Orchestration Pattern in Practice

  • The user defines the question, approved sources, and operating limits
  • Decompose it into 3-5 bounded sub-questions with clear expected outputs
  • Invoke specialists manually, or use enabled subagents for suitable independent tasks
  • Collect evidence, expose contradictions, and preserve gaps in the synthesis
  • A human reviewer validates material findings before a decision
        graph TD
          A[User] --> B[Decompose Question]
          B --> C[Specialist 1]
          B --> D[Specialist 2]
          B --> E[Specialist 3]
          C --> F[Synthesize Results]
          D --> F
          E --> F
          F --> G[Human Validates]
Take the question "Evaluate vendor X for our data platform." We can divide it into security posture, pricing, integration requirements, and operational support. Each assignment needs the goal, relevant context, approved actions, and a return format. A specialist does not necessarily inherit the coordinator's conversation, so make the brief self-contained. VS Code supports delegation through subagents when the appropriate tools and configuration are available. For this introduction, you can invoke specialists yourself and pass only the necessary findings between them. Either way, stop when the agreed scope or budget is reached, and make unresolved contradictions visible rather than asking agents to debate indefinitely.
Part 3

Custom Agents in VS Code

Let's get practical. How do you actually create these specialized agents? The answer starts with a simple Markdown file.

What Is an .agent.md File?

  • A Markdown file defining a reusable Copilot role
  • Contains the agent's name, description, instructions, and tool access
  • Repository agents live in .github/agents/
  • Save the file, then select the agent from the Agent dropdown in chat
  • No application code required; role instructions do not replace tool permissions
A custom agent file combines YAML configuration with natural-language instructions. Place a repository agent in .github/agents/ and select it from the Agent dropdown in chat. This is different from typing an @mention for a chat participant. If the agent does not appear, check its supported location and visibility settings for your selected harness. The image is an illustrative code-review agent file, not a screenshot of our research starter or the current picker. We will use a smaller research example next. Its role description shapes behavior, but actual tool selection and underlying permissions determine what it can access. The current workflow is documented at https://code.visualstudio.com/docs/agent-customization/custom-agents.

Anatomy of a Research Agent

---
name: compliance-researcher
description: Review supplied compliance evidence
tools: ['read', 'search']
---
Review approved workspace documents without editing files.
For each claim, return its source, date, and supporting passage.
Separate requirements, observations, and missing evidence.
Flag uncertainty for qualified human review.
Do not declare compliance without supporting evidence.
Save this as .github/agents/compliance-researcher.agent.md. The opening and closing lines of three hyphens enclose YAML fields, so the line breaks are part of the example, not decoration. The read and search tool sets follow the VS Code documentation's read-only planning example. This starter reviews approved workspace documents; it does not promise live web access or connect to a regulator by itself. Tool names and support depend on the selected harness. Use its tool configuration UI to inspect the available tools, and add only an approved retrieval tool when you need external evidence. Test a harmless read and inspect the returned tool output before relying on it. If access fails, the finding stays unverified. Our definition follows https://code.visualstudio.com/docs/agents/reference/custom-agent-file-reference.

Agent Composition: Building Your Research Team

Specialist Agents

  • Security auditor - Investigates approved security evidence
  • Cost analyst - Evaluates financial impact and TCO assumptions
  • Architecture reviewer - Assesses design and scalability evidence

Coordination Agents

  • Research lead - Decomposes questions into bounded tasks
  • Fact-checker - Checks supplied claims against original sources
  • Report writer - Synthesizes evidence and unresolved gaps
These are example roles you define, not built-in agents or @mention commands. Select a saved custom agent from the picker for a manual workflow. Where enabled, a coordinator can also invoke eligible custom agents as subagents. The research lead needs a clear delegation boundary, while a fact-checker needs access to original evidence rather than only another agent's summary. Start with two or three roles. Adding a specialist makes sense when it introduces a useful scope or source, not merely a different persona. A role called security auditor does not authorize penetration testing, and a compliance role is not a substitute for a qualified reviewer.
Part 4

Research Workflows

Now let's look at how these agents work together in real research scenarios.

A Multi-Agent Research Workflow

  • Step 1: Define the question, approved evidence, budget, and stop conditions
  • Step 2: Assign independent scopes with explicit read-only boundaries
  • Step 3: Return each claim with source URL or file, source date, support, and uncertainty
  • Step 4: Synthesize findings while retaining contradictions and evidence gaps
  • Step 5: A human verifies decision-critical evidence and records the decision
        graph LR
          A[1. Define Scope] --> B[2. Assign Agents]
          B --> C[3. Gather Evidence]
          C --> D[4. Synthesize]
          D --> E[5. Human Review]
Imagine evaluating an acquisition target's technology stack, security practices, and regulatory exposure. We first specify which documents and public sources are allowed, what must remain confidential, and how much time or model usage the investigation may consume. Each specialist returns traceable findings, not just a polished narrative. For example, a security claim includes the original report URL, its publication date, the supporting passage, and any uncertainty about applicability. A missing date stays unknown rather than being invented. In synthesis, distinguish an observed fact from a vendor assertion or a recommendation. When material evidence is unavailable, stop and escalate the gap to a human instead of filling it with plausible text.

Parallel Context Windows for Research

  • Explicitly start a new chat or session for an independent investigation
  • Select the intended custom agent and give it a self-contained research brief
  • Moving a conversation to an editor tab does not itself create a fresh history
  • Separate histories may still share workspace files and permissions; keep this workflow read-only
  • Use enabled subagents as an alternative for bounded delegation
  • Merge cited results for human review; monitor duplication, usage, and elapsed time
Separate conversations can let a security investigation and a pricing investigation progress independently. Create a fresh chat or session explicitly rather than assuming that reopening the panel resets the conversation. The exact controls depend on your VS Code version, surface, and selected harness. Each new investigation needs its own scope and context. A separate conversation history is not a separate filesystem: multiple chats may share the same workspace and worktree. Keep these tasks read-only and avoid granting write tools merely to do research. If subagents are available, the coordinator can collect bounded results without requiring a tab for every specialist. Parallel work may reduce waiting, but it also increases usage and synthesis overhead; measure the benefit rather than promising a fixed speedup. Current guidance is at https://code.visualstudio.com/docs/agents/run/sessions/manage-sessions and https://code.visualstudio.com/docs/agents/run/subagents.

Use Case: Competitive Landscape Analysis

  • Assign each competitor the same evaluation criteria: features, pricing, and positioning
  • A market trends agent checks broader industry shifts and emerging alternatives
  • A comparison agent aligns findings and marks missing evidence
  • Use authorized documentation, public APIs, press releases, and licensed reports
  • Final output: a dated briefing distinguishing verified facts from marketing claims
Competitive analysis is a useful candidate for parallel research because each vendor can be investigated against the same criteria. Keep the comparison fair: record the plan, region, pricing date, and assumptions behind each finding. A press release is evidence of what a vendor announced, not necessarily proof that a capability meets your requirements. Licensed analyst reports also have access and redistribution restrictions. The comparison agent should show unknowns instead of ranking vendors with missing information as though the data were complete. This can accelerate information gathering, but the analyst still interprets the evidence and decides which claims need direct validation.
Part 5

MCP & Approved Sources

Agents are only as useful as the evidence they can access. Let's connect those sources without treating connectivity as permission to use everything.

Approved Research Integrations

  • GitHub App-based Copilot Extensions were sunset on November 10, 2025
  • Client-side VS Code extensions and ordinary GitHub Apps are not covered by that retirement
  • Discover approved MCP servers through the registry, VS Code gallery, or your internal catalog
  • Review the publisher, endpoint or launch command, identity, and requested permissions
  • Use least-privilege, read-only access; confirm data classification and tool approvals
Older guidance may tell you to install a GitHub App-based Copilot Extension from the GitHub Marketplace. That pathway was retired on November 10, 2025. The notice explicitly excludes client-side VS Code extensions and ordinary GitHub Apps, so we should not say that all extensions disappeared. For new research connections, start with an approved MCP server or existing built-in tools that already meet the need. A registry listing is a discovery mechanism, not your organization's approval. Review the publisher, endpoint, permissions, and where confidential information will travel. Public acquisition research and internal due diligence may need very different access boundaries. Keep approvals scoped and retain a human checkpoint for consequential actions. The official retirement notice is https://github.blog/changelog/2025-09-24-deprecate-github-copilot-extensions-github-apps/.

MCP Servers: Your Research Infrastructure

  • Model Context Protocol (MCP) connects AI applications to external tools and data
  • Tools perform calls; resources supply context; prompts provide templates
  • Connect only the authorized knowledge bases, APIs, or document repositories you need
  • Use MCP: Add Server; VS Code workspace configuration uses .vscode/mcp.json
  • Inspect a low-impact tool call and its returned evidence before relying on the connection
MCP is an open protocol, not an automatic grant of access. The host manages connections and permissions. Tools, resources, and prompts are different primitives, so a resource or prompt is not simply another model-invoked tool. In VS Code, the guided MCP: Add Server command helps configure a connection. The VS Code workspace format uses .vscode/mcp.json with a servers object. Current documentation also describes a portable .mcp.json format with an mcpServers object; choose the destination supported by your harness rather than copying one schema into another. Authentication, runtime prerequisites, and organization policy still apply. Keep credentials out of chat and source control. A plausible answer does not prove a connection worked: inspect the actual tool output. The setup and configuration references are https://code.visualstudio.com/docs/agent-customization/mcp-servers and https://code.visualstudio.com/docs/agents/reference/mcp-configuration.

Connecting It All Together

Agent Layer

  • Custom .agent.md files define roles and output contracts
  • Selected tools constrain each investigation
  • A human coordinates, or enables bounded subagent delegation
  • Human review remains the decision checkpoint

Data Layer

  • Approved MCP servers connect authorized sources
  • Workspace files supply curated local evidence
  • Identity and organization policy govern access
  • Retrieved content is evidence, not instructions
The agent layer decides how to investigate; the data layer supplies evidence within real access boundaries. A role instruction saying "read-only" is useful, but we also select appropriate tools and use an identity with only the required permissions. Treat retrieved documents and web pages as untrusted content. A page that tells an agent to ignore its instructions or upload internal files is not authorized to redirect our workflow. Do not copy confidential findings into another agent or external tool unless that destination is approved for the data. A synthesis agent should receive the minimum context needed to compare claims, with source references preserved. These safeguards apply whether you coordinate manually or use subagents. Current VS Code trust and approval guidance is at https://code.visualstudio.com/docs/agents/run/security.
Part 6

Evaluating Agent Output

Multi-agent research produces rich output, but output is not the same as truth. Let's talk about evaluation and trust.

Trust But Verify

  • Agents can be confident and wrong. Confidence labels are not calibrated accuracy scores
  • Require citations, source dates, and the passage supporting each material claim
  • Agreement is not independent confirmation when agents share models or sources
  • Check source authority, recency, relevance, and whether it actually supports the claim
  • Treat agent output as draft research; humans verify decision-critical findings
This is the most important distinction in the session: confidence is not evidence. Three agents may confidently repeat the same outdated vendor claim because they found the same source, or because their models have similar blind spots. Open the original citation and check the passage, publication date, and applicability to your situation. Two different URLs can still repeat one underlying announcement. Preserve disagreements until evidence resolves them, and keep unavailable evidence explicitly unverified. For a low-stakes briefing, sampling can help calibrate the workflow. For a consequential acquisition or compliance decision, every material claim needs appropriate independent verification and a qualified human owner.

Practical Verification Strategies

Requested Agent Checks

  • Claim + source URL/file + source date
  • Supporting passage + uncertainty
  • Separate facts, assertions, and recommendations
  • List contradictions and missing evidence

Human Oversight

  • Open citations and verify material claims
  • Check for shared or circular sources
  • Stop at the scope, time, or usage limit
  • Record decisions and unresolved gaps
These are checks we request and verify, not automatic platform guarantees. A fact-checker agent can help, but it needs access to original evidence and can still make mistakes. Suppose a vendor claims a capability is generally available. We want the official release statement, its date, the passage supporting availability, and any region or plan restriction. A synthesis should not silently turn a preview announcement into a production commitment. Define stop conditions before the investigation: the important questions are answered, a required source is inaccessible, or the agreed time or usage budget is exhausted. Preserve the evidence references and reviewer decision in an approved audit location. That gives the next reviewer a way to challenge the conclusion without rerunning the whole investigation.
Part 7

Enterprise Use Cases

Let's look at five enterprise scenarios where these patterns may help, provided we have suitable sources, permissions, and a human decision owner.

High-Impact Enterprise Scenarios

  • Due Diligence: Investigate technology, security, and compliance using authorized evidence
  • Compliance Research: Map requirements to documented practices and flag gaps for qualified review
  • Architecture Decisions: Compare scalability, cost, security, experience, and operational tradeoffs
  • Vendor Evaluation: Compare pricing, SLA, integration complexity, and references on consistent criteria
  • Incident Post-Mortem: Separate technical, process, and communication evidence without inventing causality
These scenarios share a useful property: the broad question can contain several substantial investigations. Due diligence needs strict confidentiality boundaries. Compliance research needs dated, applicable requirements and qualified interpretation, not a declaration of compliance from an agent persona. Architecture and vendor decisions benefit from explicit assumptions so that specialists compare the same workload and business constraints. In an incident review, separate observed events from hypotheses and avoid treating missing logs as evidence of a particular cause. In every case, judge the workflow by the quality and traceability of its evidence, not by whether it produces an impressive executive summary.

Getting Started: Your First Multi-Agent Workflow

  • Start small: Compare one-agent research with two bounded specialist investigations
  • Define the contract: Role, allowed actions, sources, output format, budget, and stop rule
  • Connect only what is needed: Use approved workspace evidence or one approved read-only MCP source
  • Verify and iterate: Inspect tool output, check citations, and review unresolved gaps
  • Share the approach: Record reusable guidance in .github/copilot-instructions.md, not secrets
Pick one real but low-risk research question. First try a single-agent investigation so that you have a baseline. Then split two useful scopes and compare evidence coverage, effort, and usage. Save clear custom-agent definitions, select them in the picker, and start with approved workspace documents if external access is not ready. An MCP server is optional, not a prerequisite for good research. If you add one, verify the publisher, access scope, and a low-impact tool result before trusting it. Capture the reusable workflow in .github/copilot-instructions.md for the team, but keep credentials and sensitive research findings in approved storage. If a tool or source is unavailable, say so and preserve the gap rather than presenting an unsupported answer.
Summary

Wrap-Up & Next Steps

Let's bring it all together and talk about where to go from here.

Key Takeaways

  • Use multiple agents when separable research scopes justify the overhead
  • Four useful patterns: debate, consensus, specialization, and orchestration
  • Define .agent.md files and select them in the Agent dropdown; enabled subagents can delegate
  • Use approved MCP sources and curated files with least-privilege access
  • Source agreement is not proof; agent output is draft research for human verification
  • Start small, preserve provenance, set operating limits, and measure the benefit
The core decision is whether splitting the question improves the evidence enough to justify the extra work. We have four patterns to choose from, and custom agents let us make roles and output expectations reusable. You can coordinate manually or use supported subagent tools where your environment permits them. MCP and curated workspace documents supply evidence within approved boundaries; neither an agent role nor a server connection replaces authorization. Keep source references, dates, and uncertainty through every handoff. Agreement between agents is a prompt to inspect their evidence, not a vote that establishes truth. Start with a small comparison, set limits, and let a human own the final decision.
